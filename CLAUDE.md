# Scraping Factory — Developer Documentation

## Project Overview

A browser extension that lets users without programming knowledge visually configure web scrapers. The result is a standalone, readable **Python script** (v1). The architecture is designed to support additional target languages later on.

The MVP (v1.0.0) was reached a while ago — the current release is v1.10.0. The project is therefore no longer in MVP buildout but in normal, ongoing feature development beyond it, including well beyond the feature set originally planned for v1. Foundational decisions made during the prototyping phase (IR schema, extension↔companion communication) are considered settled and are evolved during ongoing development rather than re-litigated — see "Architecture Decisions" below.

**Principle:** Scraping Factory is meant to remain a free plugin (no cost, no dependency on paid third-party services). This specifically rules out commercial stealth-browser/anti-bot SDKs with a session or license model (see "Feature Scope").

Full architecture concept: `architekturkonzept.md` (in the repo root, not checked in / kept separately).

For the structural map of the codebase — system diagrams, a feature-to-file index,
and the cross-boundary class/wire-format relationship model between the extension
and the companion — see `docs/ARCHITECTURE.md`. That document is the *where*; this
file remains the *why* (behavioral detail, edge cases, the reasoning behind design
decisions).

## Language

Code comments, commit messages, pull requests, issue descriptions, and all documentation (this file, `README.md`, `.claude/skills/**`) are written in **English**, regardless of what language a task request came in — conversations with the assistant (and the underlying issues/requests) are frequently in German, and that's fine; German task descriptions do not need to be pre-translated before work starts. When a PR/issue names a specific UI element, name it by its English UI string (the `en.json` value, e.g. "Export configuration", not "Konfiguration exportieren") even if the conversation that produced it was in German — English is the one label guaranteed to be stable across the extension's UI languages (see below), unlike any one specific translation.

The extension's own end-user-facing UI (button labels, screen text) is the one place actual runtime *language choice* exists: `extension/i18n/{de,en,es}.json` hold three parallel dictionaries (loaded by `extension/i18n/i18n.js`), picked via an in-popup language selector and persisted like any other setting (`chrome.storage.local`) — adding or changing a user-facing string means updating all three files, not just one, to keep them in sync. Error messages returned by the companion (`/generate`'s `400`/`422` response bodies, thrown exceptions) and the generated scripts' own runtime console output (hardening/proxy/login warnings, etc.) are plain English like the rest of the codebase — neither is part of the extension's i18n system, and unlike the popup UI, neither has a per-language variant.

## Components

### Browser Extension
- Manifest V3, no Node.js access in the service worker
- Contains **no** scraping or code-generation logic
- Communicates with the companion app via a local HTTP server, `http://localhost:5000` by default — configurable on the companion side (see below) and, independently, overridable per-browser-profile from the extension's own `COMPANION_ERROR` screen if the default address isn't reachable (`extension/shared/companion-config.js`: `getCompanionUrl`/`setCompanionUrlOverride`, backed by `chrome.storage.local` so a manually entered address survives a browser restart, the same pattern `i18n/i18n.js` already uses for the language preference)
- **Side panel fills the available height** (Issue #138): `popup/popup.html`'s `<body>`/`.screen` used to have no height layout at all (`width`/`max-width`/`min-width` only, a leftover from when this was a classic dropdown popup that sizes to content), leaving dead whitespace below any screen shorter than the panel. `html, body { height: 100%; }` plus `body`/`.screen` as flex columns (`flex: 1; min-height: 0;` on `.screen`, since only one is ever unhidden at a time, see `render()`) let the active screen stretch to whatever height the side panel actually has. `#screen-idle` (the longest screen) wraps everything except its bottom Export/Generate button row in a new `.screen-idle-scroll` div (`flex: 1; overflow-y: auto;`) so those buttons stay pinned at the bottom of the panel while the field/settings content scrolls independently above them, instead of the whole document scrolling past them. `#screen-api-config`'s own previously hardcoded `max-height: 480px` is gone for the same reason — it now grows via the shared `.screen` rule and scrolls internally within whatever height that ends up being. `body`'s `max-width` was relaxed from `380px` (also a dropdown-popup leftover) to `640px`, since the side panel is user-resizable — the cap now only guards against absurdly long text lines on a genuinely wide panel instead of capping the common case.
- **Visual design refresh: design tokens, icons, interaction consistency** (Issue #139): a purely visual pass over `popup/popup.html`'s CSS — no information-architecture/flow change. A `:root` block of CSS custom properties (`--color-*`, `--radius-*`, `--shadow-*`/`--overlay-*`, `--focus-ring`, `--transition-fast`) replaces ~90 one-off hex/rgba/border-radius literals that had been scattered through the file with no shared source of truth, migrated value-for-value (verified pixel-identical via before/after screenshots) with one deliberate exception: the success-icon's `#22c55e` and the pre-existing `#16a34a` (already used for robots-allowed/toast-info) are two near-identical greens with no reason to differ, so they now share one `--color-success` token. This is also the direct prerequisite for a future dark-mode pass — a `[data-theme="dark"]` block would only need to redefine these tokens, not every rule using them. The two literal Unicode status glyphs (`⚠`/`✓`) are now small hand-drawn inline SVGs (no icon font/CDN, per the "free plugin" principle), sized/colored via the token set. The three independent tree-toggle implementations (`container-tree-ui.js`'s group tree, `api-config-ui.js`'s API tree, `popup.js`'s DOM tree view) — each of which swapped between two different Unicode glyphs (`▸`/`▾`) via `textContent` on every click — now each insert one static chevron SVG per row and toggle a `.collapsed` class instead, with the actual rotation (`transform: rotate(-90deg)`) handled once in shared CSS rather than duplicated per-file click-handler logic; the DOM tree view keeps its "starts collapsed" default (unlike the group/api trees, which start expanded) by applying `.collapsed` at build time. Finally, hover/active/transition treatment is unified: the shared `button{}` base rule now transitions multiple properties via `--transition-fast` (was: `background .1s` only) and every button gets a uniform `:active` press feedback (`translateY(1px)`) — `.mode-btn`/`.btn-toggle` inherit both for free since they're plain `<button>`s; inactive `.mode-btn` tabs and the three tree-row types (`.group-tree-row`/`.api-tree-row`/`.body-tree-row`, previously with zero interactive feedback) gained a hover state; text inputs/textareas/selects share one focus-transition rule. Deliberately out of scope: turning "Remove"/"+ Add"-style text-label buttons into icon+label, which would be a much larger pass and risks breaking existing `.textContent` assertions in `popup.test.js`.
- **Dark mode + visual modernization pass** (Issue #140): builds directly on #139's token groundwork — every color/overlay/shadow token now lives in a light/dark pair instead of one fixed set. `:root` carries the light defaults; `@media (prefers-color-scheme: dark) { :root:not([data-theme]) { ... } }` redefines them automatically when the OS prefers dark and the user hasn't made an explicit choice; an explicit `html[data-theme="light"|"dark"]` override (see `shared/theme.js` below) always wins over both, and needs no rule of its own for "light" specifically since the media query already stays out of its way when the attribute is present. `color-scheme: light dark` on `:root` (narrowed to a single value by the two explicit-override rules) gives native form controls — checkbox/select-popup chrome, and any `input`/`textarea` with no explicit background of its own, like `#input-additional-urls` — a correct dark rendering for free. **Contrast audit** (called for by the issue): every status color already read from #139's token set, so brightening them for dark backgrounds was enough — no per-rule changes needed for `.robots-txt-allowed`/`.preview-summary.warn`/toast variants/etc. One real bug the audit *did* catch: several "white text on a colored background" rules (`.btn-primary`, `.toast`, picked chips) used `var(--color-surface)` for that text color — correct by coincidence in light mode (surface happens to be white) but flips to near-black in dark mode. A new theme-agnostic `--color-on-accent` token (always a light color regardless of theme, since the accent backgrounds themselves stay readable with light text in both) replaces `--color-surface` at every one of those call sites. **Manual toggle**: a new `extension/shared/theme.js` mirrors `i18n.js`'s `getStoredLanguage`/`setLanguage` pattern exactly (`chrome.storage.local`), with one difference — "follow the OS" is a real third state, represented as `null` (not a storable `'system'` string) throughout the module. `#theme-toggle` next to the language selector cycles system → light → dark → system on click (`SFTheme.cycleTheme`), a single compact icon button chosen over a dropdown for lack of panel-width room next to the existing language `<select>`. **Modernization** (requested alongside the issue, not part of its own scope): the radius scale is nudged up again (6/8/10/14, from #139's 4/6/8/10) for a softer feel; `--transition-fast` switches from a plain linear ease to the "standard" `cubic-bezier(0.4, 0, 0.2, 1)` easing curve; a new `--glow-primary` gives `.btn-primary:hover` a soft colored glow instead of a flat color swap; the old flat `--shadow-sm`/`--shadow-md` pair is replaced by a graded `--elevation-1/2/3` scale (layered shadow pairs) for more "floating" depth on the mode-toggle active pill and modal; the `.mode-toggle`/`.mode-btn` segmented controls (mode/engine/notify-method — three markup instances) gain an animated sliding `.mode-toggle-thumb` behind the active button instead of each button just recoloring itself in place, positioned via `popup.js`'s `syncModeToggleThumbs()` (JS, not CSS-only, since it depends on the active button's actual rendered offset/width) — called at the end of every `render()` and on a rAF-throttled `window.resize` listener, since the side panel is user-resizable; `.engine-section`/`.output-settings` get an outlined "card" (border only, no fill, since their own children already use `--color-surface-subtle`) to break up the idle screen's otherwise undifferentiated list of settings — the mode-specific sections are deliberately left unboxed since they're the primary content being edited and already carry their own row-level visual treatment; every scrollable container from #138/#122 gets a slim `::-webkit-scrollbar` (Chromium-only, matching the extension's own supported browser range). Deliberately out of scope, same reasoning as #139: turning text-label buttons into icon+label.
- The popup/side panel (`extension/popup/popup.js`) supports three strictly separate modes: "Fields (flat)" (the original mode), "Containers (nested)" and "API" — switching modes clears the configuration of the other two modes (`switchMode`/`MODE_SWITCH_CLEARS`). The container tree is rendered as an editable tree following the same visual pattern as the DOM tree view (`renderGroupTree`/`buildGroupTreeNodeEl` in `popup/container-tree-ui.js`, mirroring `renderDomTree`/`buildTreeNodeEl` in `popup.js`); creating a container asks for name/type **before** the click-based element selection (`modal-container-new`), while creating a data field asks (as in flat mode) **after** the click-based selection (`modal-field-extended`, with a field-type dropdown: Text/Attribute/Exists?/OwnText — see Issue #169 below)
- Content script (`extension/content/content-script.js`): `buildSelector`/`startSelection` accept an optional scope root (`scopeSelector` on the `START_SELECTION` message) — when adding a nested container/data field, click-based selection is restricted to descendants of the parent group, and the resulting selector is valid relative to whichever instance was actually clicked instead of to `document.body`. `startSelection` resolves `scopeSelector` against *every* matching instance (`document.querySelectorAll`, not just the first), and `onClick`/`isInScope` accept a click inside any of them — the selector is then built relative to the specific instance the click landed in (`scopeRootFor`), not a single instance fixed in advance (Issue #167 fix: previously only `document.querySelector`'s implicit first match was ever scoped, so a sub-element absent from that particular instance — e.g. an optional "vegan" badge only some menu items carry — could never be selected at all, even though the resulting selector would already have matched it correctly wherever it does appear; the extraction runtime's own per-instance handling of a non-matching selector was already null-safe, see `extract_group` below). A click outside every instance is still rejected and now also sends `SELECTION_CLICK_OUT_OF_SCOPE`, shown as a brief non-blocking toast hint instead of being silent
- "Export configuration" (`btn-export-config`, `buildConfigExport`/`downloadConfigExport` in `popup.js`) downloads the current Fields/Groups/Api configuration as JSON — the `config` field inside is byte-for-byte the request body `/generate` would receive (reuses `buildScrapingConfig`), plus `exportedAt`/`extensionVersion`. Intended to be attached to selector/bug reports, independent of the existing "Report bug" log export
- "Check robots.txt" (`btn-check-robots` next to the URL display) shows whether the currently inspected page is allowed or disallowed according to the target site's robots.txt. The actual `robots.txt` fetch runs in the content script (`checkRobotsTxt`/`evaluateRobotsTxt`/`parseRobotsTxt` in `content-script.js`), not in the popup — a fetch from there is same-origin relative to the inspected page and therefore needs no extra `host_permissions`, unlike a fetch from the popup (its own `chrome-extension://` origin) to an arbitrary third-party domain. Popup → service worker → content script uses the same `CHECK_ROBOTS_TXT` request/response pattern as `GET_LOGS`. Only the generic `User-agent: *` group is ever evaluated (per the usual robots.txt rules: "longest matching pattern wins, ties go to Allow") — deliberately not matched against a specific named group even though the static engine's generated scripts do now send an identifying `User-Agent` (see below): the check runs from the content script, at a different time and via a different HTTP client than the eventual generated script's own request, so there's no guarantee the two would ever resolve to the same named group regardless. A missing `robots.txt` (404) is treated as fully allowed; any other error status/network failure is shown as an inconclusive result instead of being guessed at
- **API mode** (Issue #53): automatically finds the matching JSON API request for a clicked data point, instead of scraping HTML. Network recording (`extension/content/api-capture.js`, injected into the MAIN world, `document_start`) patches `fetch`/`XMLHttpRequest.prototype.open`/`send` and buffers request/response pairs while a recording is running; communication to the isolated-world `content-script.js` goes via `window.postMessage`, then on to the popup via `chrome.runtime.sendMessage` (`API_CAPTURE_START`/`_STOP`/`_ENTRY`, `FORWARD_TO_TAB` in the service worker)
- Click-based selection in API mode searches (instead of building a CSS selector) for the clicked value recursively inside the recorded JSON responses (`findApiCandidates` in `content-script.js`) and returns candidates (request + JSON path to the match); for a match inside an array element, the object's sibling keys are offered as one-click suggestions for additional fields. A "select all"/"deselect all" toggle button sits alongside the chips (`.api-sibling-select-all` in `renderApiCandidates`/`popup/api-config-ui.js`) for records with many keys — picking most of them is then "select all, then click off the few not needed" instead of clicking each wanted one individually; picked state itself stays DOM-only (a `.picked` class, never round-tripped through `_state`) the same way individual chip clicks already worked, so the button's own label is flipped directly in the click handler rather than via a `render()` pass
- A confirmed API candidate is turned into a parameterized `ApiConfig` on the `API_CONFIG` screen (`buildApiConfig` in `popup/api-config.js`, `confirmApiConfig` in `popup/api-config-ui.js`): the URL is decomposed into path segments/query parameters, each part individually toggleable between "fixed" and "variable"; each variable part gets a value source — a value list, a second discovery endpoint found via recording-and-correlating, or a locally computable range (ISO week/number/date). For range sources, the date/week format is auto-detected from the recorded raw value of the URL part (presets like "ISO standard"/"year-week without separator" plus "custom format…", `detectRangeFormat`/`RANGE_FORMAT_PRESETS` in `popup/api-config.js`) — necessary because target sites encode weeks/dates inconsistently (e.g. `2026-W35` vs. `2026-35`). Captured request headers are shown and can optionally be adopted per header, either as a literal or via an environment variable (mirroring the credentials pattern used by `FillStep`)
- Every field's name — the primary field (typed once at "Use" time) and every sibling field (originally fixed to its own JSON key) alike — stays editable on the `API_CONFIG` screen itself (`setApiTreeNodeName` in `popup/api-config-ui.js`, `updateApiTreeNode` in `popup/api-config.js`, a committed `change`-event text input per tree row, same pattern as the URL-part-name inputs on the same screen), rather than only ever being nameable once at candidate-confirm time. A blank field name (only reachable through this input — impossible before it existed) blocks "Apply" the same way a blank variable-part name already does (`apiConfigDraftHasAllSourcesChosen`)
- **API mode: nested JSON responses** (Issue #54): the `API_CONFIG` screen's field list is a full tree editor (`renderApiTree`/`buildApiTreeNodeEl` in `popup/api-config-ui.js`, mirroring container mode's own `renderGroupTree`/`buildGroupTreeNodeEl` in `popup/container-tree-ui.js`), not just a flat list — a JSON response with more than one repetition level (e.g. `categories[*].subcategories[*].products[*]`) is represented as nested `ApiGroup` nodes, each scoping its children to whatever its own JSON path resolves to, with `ApiField` as the leaf. A single top-level match still renders as a one-node-deep tree, so the tree UI fully subsumes the original flat shape — the popup only ever builds/sends the tree shape going forward, though the wire format still accepts the legacy flat `ItemsPath`/`Fields` shape too (see the Compiler section below). `content-script.js`'s `deriveApiTreeSkeleton` (generalizing the original single-level `deriveItemsAndValuePath`) splits a clicked value's JSON path at *every* array boundary instead of just the last, and is pre-computed onto each candidate as `treeSkeleton` — `popup.js` runs in a separate execution context and can't call content-script functions directly, the same reason `itemsPath`/`valuePath` were already pre-derived there. Extending an already-confirmed tree has two flows: "+ Data field" on any group row starts a second, JSON-scoped search (`resolveApiGroupScopePath`, the JSON-path analogue of container mode's `scopeSelector` — using the same "first instance is the template" assumption) and inserts the result via `insertApiTreeNode`; "+ Group" opens a small modal collecting a name **and** a JSON path directly, with no click at all — unlike a field, an empty group has no single clicked value to derive one from without implying a leaf field nobody asked for. A dedicated "+ New group (top level)" button adds an entirely independent second root group (a second, unrelated top-level array in the same response body) via an unscoped search
- The full recorded request pool (not just the click-correlated matches above) is reachable two ways, both via a pull-based `GET_API_CAPTURE_ENTRIES` request/response (same pattern as `GET_LOGS`/`CHECK_ROBOTS_TXT`; content script returns its locally buffered `capturedApiEntries`, `isTopFrame`-gated like the others) rather than accumulating the live `API_CAPTURE_ENTRY` stream, which is dropped silently whenever the popup is closed: (1) an inline "Show recorded requests" panel on the idle screen (`toggleApiEntriesPanel`/`renderApiEntriesList` in `popup/api-config-ui.js`) lists every recorded request (method/status/URL/content-type) for whoever wants to inspect the raw pool; (2) once a variable URL part's value source is set to a value list, the pool is searched for *other* recorded requests matching the same URL template — same origin, same path-segment count, every other *fixed* segment/query value equal, other *variable* parts left free — and their differing value at that part is auto-inserted into the value list (`findUrlTemplateMatches` in `popup/api-config.js`, `fillStaticListFromPool` in `popup/api-config-ui.js`), running once automatically when "Value list" is picked and again on demand via a "Fill from recording" button (e.g. after scrolling the inspected page further to trigger more lazy-loaded requests). Newly-derived values are only ever appended, never used to replace the existing list (`mergeValueListValues`), so a value the user has since deleted isn't silently resurrected by a later refresh
- The "output settings" fields ("Script name"/"Output file name", shared across all three modes, at the bottom of the output-settings block in `screen-idle`, see the layout follow-up below) let the user name the downloaded `.py` file and the data file the generated script writes (`output.csv`/`output.xml` by default) — the shown extension (`.csv`/`.xml`/`.json`) tracks the current mode/shape and the "Output as JSON" toggle described below. The downloaded script's filename is decided purely client-side (`triggerDownload`, `sanitizeFileNameBase`) and never round-trips through the companion; `scriptFileName`/`outputFileName` are still sent to `/generate` as free text so the companion can bake the *same* sanitized script name into the generated script's own "# Run: python X.py" comment. `sanitizeFileNameBase` in `popup.js` is a hand-kept mirror of the companion's `FileNameSanitizer` (same pattern as `RangeFormat`'s client-side mirror) — both must independently reach the same sanitized name for the same raw input, since the companion never reports back what it actually used
- **Layout follow-up to Issue #138**: `#additional-urls-row` (Issue #83) sits directly under the URL row it complements instead of down in the output-settings block; within output-settings itself, the script/output filename rows now come *last* — after every toggle (Json output, data preview, change detection, proxy) and their conditional config panels — as a final naming step right before the Export/Generate buttons, instead of being the first thing in the block. The `DONE` screen also gained a "Back" button (`#btn-back-to-config`) alongside "New"/"Download": unlike `btn-new-scraper`, which resets `fields`/`groups`/`apiConfig`/`url`/`scriptText`, it calls `setState(STATES.IDLE)` with no patch — the same "return to IDLE, keep everything" pattern `generate()`'s own 400/422/network-error branches already use — so a data preview that isn't quite right can be fixed (tweak a selector/transform, adjust output settings) and regenerated without starting the whole scraper configuration over
- **Multiple start URLs** (Issue #83): an optional "Additional start URLs" textarea (one URL per line, `#input-additional-urls`, `_state.additionalStartUrls`) directly under the URL row it complements (see the layout follow-up below) — mode-independent like engine/browser-actions (persisted across popup close/reopen, unlike the per-generate opt-in toggles below), but hidden for API mode, since Api builds its own request URL from `apiConfig.urlTemplate` and the companion rejects the combination outright rather than silently ignoring it (see the Compiler section below). `parseAdditionalUrls` splits on newlines and drops blank lines (a pasted list's formatting artifact, not a URL the user meant to add) before threading the result through `buildScrapingConfig`/`buildConfigExport` as `additionalUrls` — omitted from the request entirely when empty, same convention as `browserActions`.
- **Json output format** (Issue #86): a mode-independent "Output as JSON (instead of CSV/XML)" checkbox (`#toggle-output-json`, `_state.useJsonOutput`, not persisted across popup reopen — same per-generate-opt-in treatment as `includeDataPreview`) within the output-settings block. `buildScrapingConfig` adds `outputFormat: 'Json'` to the request when checked — replacing flat mode's always-explicit `'Csv'` literal, or adding the key outright for container/API mode, which otherwise send no `outputFormat` at all and let the companion force its own per-shape default (see the Compiler section below). `renderDataPreview` (Issue #122's trial-run preview, on the `DONE` screen) branches on which sample field a `ScriptPreviewData` actually populates (`xmlSample`/`jsonSample` vs. `columns`/`rows`) rather than solely on `outputFormat === 'Xml'`, so a Json tree-shape preview reuses the existing read-only text block (`#data-preview-text`, renamed from `#data-preview-xml`) and a Json flat-shape preview reuses the existing table renderer unchanged
- **API mode: POST/GraphQL request bodies** (Issue #55): `extension/content/api-capture.js`'s network recorder captures the outgoing request body alongside the response for `fetch`/`XMLHttpRequest` calls (`requestBody`/`requestBodyTruncated`/`requestBodySkipped`, reusing the existing `MAX_BODY_CHARS`/`truncateBody` convention) — only a string body (a `JSON.stringify`'d object) is capturable; `FormData`/`Blob`/`ArrayBuffer`/`URLSearchParams` are flagged via `requestBodySkipped` instead of read, since form-encoded/multipart bodies are out of scope. The recorded-requests panel (`renderApiEntriesList`) shows a captured body inline, or a "not captured" note when skipped. Once a POST candidate is confirmed as the primary field, its own captured body is looked up in the recorded pool and turned into an all-literal draft tree (`jsonValueToBodyDraft`, run as a fire-and-forget follow-up — `loadInitialBodyTreeForCandidate` — so a bodyless POST doesn't block the `API_CONFIG` screen transition on an unnecessary round trip). A new body-tree editor (`renderBodyTree`/`buildBodyTreeNodeEl`, visually mirroring the response tree) shows this shape read-only — the body's own structure is never edited, only a leaf's fixed/variable state (see "Architecture Decisions"): a literal leaf's "→ Variable" action opens a picker listing every already-declared parameter plus a "+ New parameter…" option (a small name-only modal), routing the choice into the *same* parameter-source cards a URL variable part already uses (`allParameterParts` unions URL-derived and body-only parameters) rather than a second, body-specific source picker. Reverting a leaf's only reference to a body-only parameter back to fixed drops that now-orphaned parameter (mirrors the existing "no stale `parameterSources` entry" pattern for URL parts); a URL-derived parameter is left untouched either way, since it's still a real URL segment/query part regardless of whether the body also referenced it. GraphQL needs no dedicated handling anywhere in this UI — a GraphQL body is just an ordinary nested object with a fixed `query` string and a `variables` object, edited with the same generic mechanism
- **Trial-run data preview** (Issue #122): an opt-in checkbox within the output-settings block on `screen-idle` (`#toggle-include-data-preview`, default off, not persisted across popup reopen — same "sticky-within-a-session-only" treatment as `previewActive`/`apiCaptureActive`) threads `includePreview` through `buildScrapingConfig`/`buildConfigExport` the same "only send the key when true" way `engine`/`browserActions` already do. `generate()` branches on whether a preview was requested to parse `/generate`'s response as JSON (`{ script, preview }`) or plain text — the client already knows which one it asked for, no Content-Type sniffing needed — and stores the result in `_state.dataPreview`. `renderDataPreview` shows it on the `DONE` screen: a `<table>` for a Csv sample (built via `document.createElement`/`textContent`, never `innerHTML`, so a scraped value that happens to look like markup is never interpreted) or a read-only, scrollable `<pre>` block for an Xml sample, plus a "showing N of M" (Csv) or generic (Xml) note when the companion's sample was capped. Deliberately named `dataPreview`/`renderDataPreview` throughout, **not** `preview` — that name already belongs to the unrelated, pre-existing DOM-highlight feature (`previewActive`/`togglePreview`/`#btn-preview`, `PREVIEW_START`/`PREVIEW_RESULT` messages), which highlights matched elements on the live page and has nothing to do with the generated script's actual trial-run output.
- **Live selector match-count preview** (Issue #85): existence/quantity feedback the instant a selector is picked, instead of only surfacing via a full `/generate` round-trip (which runs the trial script and only fails much later on zero rows). `content-script.js`'s `onClick` computes `countSelectorMatches(selector, scopeRootEl)` — `document.querySelectorAll(selector).length`, scoped to the container instance exactly like `buildSelector` itself already is — and includes it as `matchCount` on the same `ELEMENT_SELECTED` message, purely client-side, no companion involvement. `service-worker.js`'s existing session-storage fallback (for when the side panel isn't open at click time) carries `pendingMatchCount` alongside `pendingSelector`/`pendingFramePath` unchanged. A flat field (`modal-field-name`) or container field (`modal-field-extended`) pick shows a small "N element(s) found" hint next to the name input (`renderMatchCountHint`, amber-styled via `.match-count-hint.warn` when the count is 0 — the exact case this feature exists to catch early) — mirrors the existing `previewSummary`/`.preview-summary.warn` styling, just scoped to the single in-flight pick instead of every configured field/group at once. Container-group creation has no confirmation modal of its own (name/type are collected *before* the click, see below, and the node is inserted straight away) — its match count is instead shown as a short info/warn toast (`showMatchCountToast`, a new non-error `variant` argument on the existing `showToast`/`#error-toast`, green for a real match, amber for zero) right after insertion, which itself is unaffected. `pendingMatchCount` is threaded through every place `pendingSelector`/`pendingFramePath` already are (the live handler, the popup-reopen recovery path in `init()`, every confirm/cancel flow) so a popup reopened mid-selection still shows the right count.
- **Per-field data transformations** (Issue #84): an optional, ordered chain of post-processing steps (trim/regex-extract/find-replace/to-number) applied to a field's raw extracted value before it's written to the output row — e.g. turning `"Preis: 12,99 €"` into `"12.99"` without the user hand-editing the generated script. New `extension/popup/field-transforms.js` (pure data helpers — `createDefaultTransform`/`addTransform`/`removeTransform`/`updateTransform`/`changeTransformKind`/`moveTransform`/`transformsAreValid`; each transform object's shape already matches the wire format 1:1, so there's no separate serialize step) and `field-transforms-ui.js` (DOM rendering + delegated event wiring, same split as `container-tree.js`/`container-tree-ui.js`). `_state.pendingTransforms` holds the in-progress chain while `modal-field-name`/`modal-field-extended` is open — deliberately **not** persisted across a popup close/reopen (same "form input, not underlying-selection state" treatment the field-name input itself already gets, unlike `pendingSelector`/`pendingMatchCount`/`pendingFramePath`). Flat mode had **zero** per-field configuration UI before this (`modal-field-name` was name-only); container mode's editor is hidden for "Exists?" mode (a boolean-ish presence check, not a string pipeline). `render()`'s modal-open block tracks `lastFieldModalSelector` to tell a genuine closed→open transition apart from a re-render triggered by editing a transform row — the reset-to-defaults/focus logic must only run on the former, or every transform edit (which goes through `patchState`, a full re-render, the same as any other state change) would silently wipe the name/mode the user already typed.
- **Per-field data transformations: live preview** (Issue #143): while `modal-field-name`/`modal-field-extended` is open, a hint below the transform list shows what the chain actually produces against the picked element's real raw value — e.g. `"Preis: 12,99 €"` → after trim+regexExtract+toNumber → `"12.99"` — updating as steps are added/edited/reordered/removed, entirely client-side (no `/generate` round trip). `content-script.js`'s `onClick` now also collects the clicked element's trimmed text and full attribute map (`collectElementAttributes`) and sends both as `rawText`/`attributes` on the same `ELEMENT_SELECTED` message the selector/matchCount already travel on; `service-worker.js`'s session-storage fallback persists them alongside `pendingMatchCount` (`pendingRawText`/`pendingElementAttributes` in `_state`) — underlying-selection state, not user-typed form input, so unlike `pendingTransforms` itself it survives a popup close/reopen mid-selection. `field-transforms.js`'s `applyTransformsPreview`/`toNumberPreview` are a hand-kept JS mirror of the Python runtime's own `_apply_transforms`/`_to_number` (same "both sides must independently reach the same result" relationship `sanitizeFileNameBase` already has to `FileNameSanitizer`) — `regexExtract` runs through JS's own `RegExp`/`exec` rather than Python's `re.search`, the same "not 100% syntax-identical" known risk already documented on `RegexExtractTransform`/`FieldTransformValidator`; a pattern that fails to compile as a JS `RegExp` makes the preview return `null` (rendered as "preview unavailable", distinct from a valid empty-string result) instead of throwing. Flat mode's raw value is always the picked element's trimmed text (flat fields have no attribute mode); container mode reads the *live* `select-field-mode`/`input-field-attribute` DOM values directly (not `_state`, mirroring how the attribute-row visibility toggle already works) — attribute mode's preview stays hidden until an attribute name is actually typed, and "Exists?" mode never shows one (its transforms section is already hidden, see above).
- **Per-field data transformations: API mode** (Issue #84 follow-up): the same editor also reaches API mode now, via a "Transform" button rendered next to every leaf `ApiField` row on the `API_CONFIG` tree screen (`buildApiTreeNodeEl` in `popup/api-config-ui.js`) — never for a group node, since only a leaf actually extracts a value (`ApiGroup` has no `Transforms` property on the companion side either). Backend support (`ApiField.Transforms`, `PythonApiConfigLiteral`, both API templates' `_apply_transforms`) already existed unchanged from the original Issue #84 work — this was purely wiring up the extension side: `buildApiFieldDraft`/`serializeApiTree` in `api-config.js` gained the same optional `transforms` field/wire-omit-when-empty convention `container-tree.js`'s `buildFieldNode`/`serializeGroupTree` already established, and a new `modal-api-field-transforms` reuses the exact same `field-transforms.js`/`field-transforms-ui.js` editor and `_state.pendingTransforms` slot the flat/container modals already use (the `API_CONFIG` screen and those two modals are never open at the same time, so there's no conflict).
- **Per-field data transformations: API mode live preview** (Issue #147): unlike a DOM pick, an API tree field node has no raw value to preview against once inserted — the only value ever available is the one matched at candidate-confirm time. `buildApiFieldDraft` (`api-config.js`) therefore gained an optional `sampleValue` (the raw JSON scalar the field/sibling resolved to, e.g. `candidate.value` for the primary field or the matching entry's own `.value` in `candidate.siblings` for a picked sibling — see `content-script.js`'s `siblingFields`) — popup-internal only, `serializeApiTree` never sends it to the companion. `openApiFieldTransformsModal` (`api-config-ui.js`) converts it into `pendingRawText` the same way the Python runtime resolves a value before applying transforms (`"" if value is None else str(value)`, see `scraper_api.py.j2`'s `_resolve_field` call site) — `undefined` (no sample ever captured) maps to `null` instead, so `renderTransformPreview` hides the hint rather than showing a misleading result — and reuses the exact same `renderTransformPreview` call flat mode's own modal already makes, no new preview logic needed.
- **Per-field data transformations, companion side**: new polymorphic `IR/FieldTransform.cs` (`TrimTransform`/`RegexExtractTransform`/`ReplaceTransform`/`ToNumberTransform`, discriminated via an explicit `"kind"` tag like `ApiParameterSource` — these four kinds have no natural structural tell apart) with a `Transforms` property added independently to `ScrapingField`, `ExtractStep`, `DataFieldNode`, and `ApiField` (no shared leaf type to add it to once, see `ScrapingPlanBuilder`'s own doc comment on why flat mode's translation is a pure passthrough while container/API mode's leaves flow unchanged). `Backends/Python/FieldTransformValidator` mirrors `RangeFormat.ValidateFormat`'s pattern (a static helper returning `string?`, null = valid) — compiles `RegexExtractTransform.Pattern` via .NET `Regex` to catch outright syntax errors before the real script run, called from `ScrapingPlanValidator` at all four per-field-shape sites. **Known risk, same class as `RangeFormat`'s own doc comment:** .NET's `Regex` (validation) and Python's `re` module (runtime) aren't 100% syntax-identical, so a pattern that compiles here could still behave subtly differently, or fail, once the generated script actually runs it — this is a best-effort structural check, not a full guarantee. New `Backends/Python/PythonFieldTransformLiteral` (`Render(...)`, a Python list-of-dicts literal or `"[]"`) is the one canonical serialization used by `PythonGroupTreeLiteral.RenderField`, `PythonApiConfigLiteral` (flat + tree), and a new per-field `transforms_literal` in `PythonCodeGenerator`/`PythonPlaywrightCodeGenerator`'s flat-mode `TRANSFORMS` dict — mirroring exactly how `attribute`/`framePath` are already serialized per field today.
- **Change detection + notification** (Issue #87): an "Enable change detection" toggle within the output-settings block (`#toggle-change-detection`, `_state.changeDetection`, persisted like `additionalStartUrls` — real scrape-target configuration, not a per-generate opt-in toggle) lets the generated script compare each run's output against the previous run's and notify (email or webhook) only when something actually changed. Every credential/target field (SMTP host/port/username/password/from/to, or the webhook URL) is the *name* of an environment variable the user types, never a literal value — mirrors `FillAction.EnvironmentVariableName`'s own input exactly, not a fixed/conventional name the companion would dictate. `buildChangeDetectionConfig` converts the draft into the wire `ChangeDetectionConfig` and returns `null` (silently treated the same as the toggle being off) whenever a *required* field (SMTP host/from/to, or the webhook URL) is still blank — optional fields (port/username/password) are simply omitted from the request when blank rather than blocking it.
- **Proxy support** (Issue #88): a "Use a proxy" toggle right below the change-detection block (`#toggle-proxy`, `_state.proxy`, persisted the same way) lets the generated script route its outbound requests through the user's own proxies instead of connecting directly. There's exactly one input — the *name* of an environment variable holding a comma-separated list of proxy URLs (e.g. `http://user:pass@host:port`) — never a literal address, same `environmentVariableName` pattern as change detection/`FillAction` above. `buildProxyConfig` converts the draft into the wire `ProxyConfig`, returning `null` (toggle-off-equivalent) whenever the env-var-name field is still blank.
- **Script hardening** (Issue #129): a "Hardening" section right below the Proxy block (`#hardening-config`) — this issue's own check, "no result", is a checkbox (`#toggle-hardening-no-result`, `_state.hardening.noResult.enabled`) plus a Warning/Error segmented toggle (`#hardening-no-result-severity`, reusing the `.mode-toggle` pattern from #139/#140 — the sliding thumb comes for free since `syncModeToggleThumbs()` already picks up every `.mode-toggle` on the page), persisted the same way as change detection/Proxy above (real scrape-target configuration, not a per-generate toggle). `_state.hardening` is nested one level per check (`noResult`, plus `nullRate` since Issue #130) so the three still-planned checks (see "Planned for Future Releases") can each add their own key without restructuring `buildHardeningConfig` or the UI section. `buildHardeningConfig` converts the state into the wire `Hardening` array — a list even with a single check, since the wire format is inherently a list (see the Compiler section below) — using the same camelCase `kind` discriminator convention `FieldTransform`'s own kind values already establish (`'trim'`/`'toNumber'`/...), distinct from `severity`, a plain enum value needing no translation.
- **Script hardening: per-field null-rate check** (Issue #130): catches the case #129's own "no result" check can't — a field whose selector silently starts matching the wrong thing (row/element count stays healthy, but the value is always empty). A second subsection within `#hardening-config` (below the "no result" toggle) holds a dynamic list of rows (`_state.hardening.nullRate`, an *array* — unlike `noResult`, more than one is expected, one per monitored field), each a field `<select>`, a threshold `%` number input, and its own Warning/Error `.mode-toggle`; rendered by `renderHardeningNullRateList` (mirrors `renderBrowserActions`' add/remove/update/delegated-event shape, see `addNullRateCheck`/`removeNullRateCheck`/`updateNullRateCheck`). The field `<select>`'s options come from `collectFieldNames(mode, fields, groups, apiConfig)` — reuses whatever field list the current mode/shape already has (flat's `fields` array; container's live `GroupNode`/`DataFieldNode` draft tree, walked via its `kind: 'group'|'field'` discriminator; API mode's already-*serialized* `apiConfig`, walked structurally via `children` presence instead, the same way `countApiConfigFields` already reads it — Issue #54's tree shape or the older flat `itemsPath`/`fields` shape) rather than a free-text field name input that could drift out of sync with a renamed/removed field; a row's own already-chosen field name is kept selectable even if it's since dropped out of that list, instead of silently switching to a different field. `buildHardeningConfig` skips a row with no field chosen (same "incomplete draft, not blocking generation" convention as an unfinished Fill/Proxy env-var name) and converts the UI's friendlier 0-100 percent threshold into the wire format's 0.0-1.0 fraction, clamping/defaulting an invalid number input to 50%.
- **Script hardening: baseline-drop check** (Issue #131): a third subsection within `#hardening-config` (below the null-rate list) — a checkbox (`#toggle-hardening-baseline`, `_state.hardening.baseline.enabled`), a Warning/Error `.mode-toggle`, and a `%` number input (`#input-hardening-baseline-threshold`, `dropThresholdPercent`), the same single-object shape `noResult` already uses rather than `nullRate`'s dynamic list — only one baseline check ever makes sense, since there's only one "the" result count to track. `buildHardeningConfig` converts the percent into the wire format's 0.0-1.0 fraction the same way `nullRate`'s own threshold already does; unlike a `nullRate` row, an invalid/out-of-range percent is clamped/defaulted (to 20%) rather than skipping the check entirely, since there's no "which field" completeness gate the way `nullRate` has. The extension never sees or stores the actual baseline count itself — that lives only in the generated script's own sidecar file (see the Compiler/Python Templates sections below).
- **Script hardening: blocking-detection check** (Issue #132): a fourth subsection within `#hardening-config` (below the baseline block) — a checkbox (`#toggle-hardening-blocking`, `_state.hardening.blocking.enabled`), a Warning/Error `.mode-toggle`, an optional `#input-hardening-blocking-min-body-length` number input (blank = signal disabled — unlike `nullRate`/`baseline`'s thresholds, there's no sensible default to clamp/fall back to here), and a `#input-hardening-blocking-phrases` textarea (one block phrase per line, e.g. "Access Denied"/"Please verify you are human" — mirrors the API mode `StaticListSource` value-list textarea pattern the issue itself calls out, except split on newlines only, not commas, since a phrase could plausibly contain one of its own). A third signal — the final response's host differing from the requested URL's host — needs no UI at all, since it's always active whenever the check is on. `buildHardeningConfig` sends `minBodyLength: null`/`blockPhrases: []` (not "check omitted") when both are left blank — a `BlockingCheck` with only the always-on redirect signal is still a meaningful, valid configuration, unlike `nullRate`'s "no field chosen yet" incomplete-draft case.
- **Script hardening: required-fields check** (Issue #133): a fifth subsection within `#hardening-config` (below the blocking block) — a checkbox (`#toggle-hardening-required-fields`, `_state.hardening.requiredFields.enabled`), a Warning/Error `.mode-toggle`, and a dynamic list of already-chosen field names, reusing `collectFieldNames` — the exact same field-name source `nullRate`'s own per-row picker already draws from — rather than a free-text input. Unlike `nullRate`'s rows (each its own unfinished draft object with a field/threshold/severity), a required field is a complete, chosen name the moment it exists in the list, so there's no per-row field `<select>`; picking a *new* one to add uses one shared `#select-hardening-required-field`/`#btn-add-required-field` pair instead, filtered to exclude names already added. The whole section (`#hardening-required-fields-section`) is hidden for container mode and Api-mode's tree shape — this check has no unambiguous "row" to drop there — mirroring how `#additional-urls-row` is already hidden for API mode. `buildHardeningConfig` omits the check entirely (not an empty `fieldNames: []`) when enabled but nothing's been added yet, the same "incomplete draft, not sent" convention `nullRate`'s own rows already follow.

### Companion App (`companion/ScrapingFactory.Companion`)
- .NET 10 console application
- Starts a local HTTP server for the extension
- `/generate` generates the script, then runs it as a trial via the language module's verifier (`Backends/Python/PythonScriptVerifier`) in a temporary directory and only returns it on success (exit code 0, at least one data row, or — for container mode — one XML element) — on failure, returns `422` with an error message instead of the script
- **Trial-run data preview** (Issue #122): `ScrapingConfig.IncludePreview` (nullable bool, additive/wire-compatible — absent/false is byte-for-byte today's response) lets the caller opt into seeing a capped sample of what the trial run actually scraped, instead of it being discarded once verification's pass/fail check is done. When `true`, a successful `/generate` returns JSON (`{ script, preview }`) instead of the plain script text; `preview` is `Backends/ScriptPreviewData` (`outputFormat`, `totalCount`, `truncated`, plus `columns`/`rows` for Csv or a pretty-printed, capped `xmlSample` for Xml — a structured tree view for Xml, mirroring the container/API config tree UI, is deliberately out of scope for now, see `PLAN-trial-run-data-preview.md`, kept locally/uncommitted like `architekturkonzept.md`). `PythonScriptVerifier.VerifyAsync`'s new `includePreview` parameter builds this from the *same* CSV lines/XML document it already reads for the row/element-count check — no new I/O — capped at 50 rows/top-level elements (`PreviewSampleCap`) regardless of how much the script actually scraped. CSV field-level parsing (needed here, unlike the row-count check, which only counts lines) mirrors Python's `csv.DictWriter` default dialect via a small `ParseCsvLine` helper (quoted fields, `""` escaped quotes) — the row-count check itself is untouched.
- **Runtime requirement:** `python3` (or `python`) including `requests` + `beautifulsoup4` must be available on the PATH of the machine running the companion app — not just for the end user who later runs the downloaded script. For the browser engine (`Engine: "Browser"`), `playwright` (`pip install playwright`) plus an installed Chromium (`playwright install chromium`) is additionally required
- **Configuration** (`appsettings.json`'s `Companion` section, standard ASP.NET Core precedence — so also overridable via e.g. `Companion__Port=5050` env var or a CLI arg, with no extra wiring): `Host`/`Port` (default `localhost`/`5000`, read by `CompanionHostOptions.BuildListenUrl` and passed to `builder.WebHost.UseUrls`) let the app bind somewhere other than the default when that port is already taken or the companion runs on a different machine than the extension expects — the extension-side counterpart is `shared/companion-config.js` above. `PythonExecutable`/`VerifierTimeoutSeconds` (both unset/null by default, keeping today's `python3`/`python` auto-probe and 45s timeout) reach `PythonScriptVerifier`'s own already-optional constructor parameters via `CompanionBackendOverrides.Build` and `LanguageModuleRegistry`'s generic `ctorOverrides` (a `Dictionary<string, object?>` matched against a reflectively-discovered backend's constructor parameter names) — useful for a machine with a non-standard Python install path, or one slow enough that the default trial-run timeout needs raising. All four are the same kind of hosting-machine-specific value; `ctorOverrides` is deliberately generic (name-matched, no compile-time reference to `PythonScriptVerifier`) so a future non-Python language module could expose its own optional constructor parameters through the same mechanism without touching the registry again
- Builds the IR and hands it off to `ScrapingFactory.Compiler`

### Compiler (`companion/ScrapingFactory.Compiler`)
- Contains the IR types: the wire format `ScrapingFactory.Compiler.IR.ScrapingConfig` (a Fields list, as sent by the extension) is translated by `ScrapingPlanBuilder` into the canonical `ScrapingPlan` (a step sequence of `NavigateStep`/`ExtractStep`) — the code generator and verifier only ever see `ScrapingPlan`
- **Multiple start URLs** (Issue #83): `ScrapingConfig.AdditionalUrls` (`List<string>?`, additive/wire-compatible — absent/empty is today's exact single-URL behavior) lets the caller run the same Fields/Groups extraction config against more than one page, combining the results into one output file. `ScrapingPlanBuilder` combines `Url` (still the required "primary" URL) with each trimmed, non-blank `AdditionalUrls` entry into `NavigateStep.Urls` (`List<string>`, always at least one entry) — the one breaking change to the canonical `ScrapingPlan`, confined to `PythonCodeGenerator`/`PythonPlaywrightCodeGenerator`, which now loop over the list instead of reading a single `Url`. `ScrapingPlanValidator` validates every entry is an absolute http/https URI, identifying which one failed by index (`"Invalid start URL #N"`) instead of only ever checking one. Mutually exclusive with `Api` (`422`/`400` in `/generate`, same style as the existing Fields/Groups/Api guards) — `PythonApiCodeGenerator` builds its request URL entirely from `ApiConfig.UrlTemplate`/`Parameters` and never reads `NavigateStep`/the start URL at all, so silently accepting `AdditionalUrls` there would do nothing rather than express what the caller intended.
- **Container mode** (groups/containers, Issue #21): as an alternative to `Fields`, `ScrapingConfig` carries a `Groups` field (`List<GroupNode>`, see `IR/ContainerNode.cs` — `GroupNode`/`DataFieldNode`, recursively nestable). The two are mutually exclusive (`422`/`400` in `/generate`, before `ScrapingPlanBuilder`). `ScrapingPlanBuilder` translates `Groups` into a single `ExtractGroupStep` instead of the flat `ExtractStep` list, and forces `OutputFormat.Xml` regardless of what the extension sends — analogous to how a login flow forces `Engine=Browser` — unless the extension explicitly requested `Json` instead (Issue #86, see below). Container mode is **engine-independent** (works equally with Static and Browser), unlike login. Since `List<ContainerNode>` is polymorphic (`GroupNode`/`DataFieldNode`), de-/serialization needs `IR/ContainerNodeJsonConverter` — System.Text.Json can neither deserialize into an abstract type nor serialize elements of a `List<ContainerNode>` by their runtime type
- **Container mode: "own text" extraction** (Issue #169): a fourth `DataFieldNode.Mode` value, `ExtractMode.OwnText` (`IR/ContainerNode.cs`), alongside `Text`/`Attribute`/`Exists` — extracts only an element's direct text-node children, excluding text contributed by any nested element (e.g. a "vegan" badge `<span>` nested directly inside a dish-name `<h3>`, no separating whitespace in the markup, no longer gets pulled into the name the way plain Text mode's `get_text()`/`text_content()` unavoidably would, since those walk every descendant). `Backends/Python/PythonGroupTreeLiteral.RenderField` serializes it to the `"ownText"` mode string like the other three; `scraper_grouped.py.j2`'s `extract_group()` implements it via `found.contents` filtered by `isinstance(c, str)` (`NavigableString` is itself a `str` subclass, so no separate import is needed), `playwright_scraper_grouped.py.j2`'s via a small `ElementHandle.evaluate()` call over `childNodes` filtered to `nodeType === 3` (Playwright's `ElementHandle` has no built-in "own text" accessor). No validator changes needed — like Text/Exists, only a non-empty `Selector` is required (unlike Attribute mode's extra `Attribute` requirement), and `FieldTransformValidator`/the transform pipeline already apply mode-agnostically. Extension-side: `modal-field-extended`'s `select-field-mode` dropdown gains a fourth option; the click-time raw-value collection (`content-script.js`'s `collectOwnText`, alongside the existing `rawText`/`attributes` collection for Issue #143's live preview) is a JS-side mirror of the same `found.contents`-filtering logic, threaded through `service-worker.js`'s session-storage fallback and `popup.js`'s state (`pendingOwnText`) with full parity to `pendingRawText`/`pendingElementAttributes` at every existing call site
- Contains the language modules: `Backends/Python/PythonCodeGenerator` (engine `Static`, requests+BeautifulSoup) and `Backends/Python/PythonPlaywrightCodeGenerator` (engine `Browser`, Playwright), both implementing `ICodeGenerator`; `Backends/Python/PythonScriptVerifier` implements `IScriptVerifier` and runs both script kinds the same way (for container mode, against `output.xml`/`output.json` instead of `output.csv`, see the `OutputFormat` parameter of `VerifyAsync`). `LanguageModuleRegistry` resolves code generators by `(LanguageId, Engine)` tuple, and verifiers by `LanguageId` — callers never see the concrete types
- **API mode** (Issue #53): a third alternative, exclusive with `Fields`/`Groups` — `ScrapingConfig.Api` (`IR/ApiConfig.cs`: `ApiConfig` with `UrlTemplate`, optional `Headers`, `Parameters`, and either the flat `ItemsPath`/`Fields` shape or the recursive `Groups` tree shape below). `ScrapingPlanBuilder` translates `Api` into a single `ApiCallStep` and forces a third `ScrapingEngine.Api` value regardless of what the extension sends — analogous to container mode/login above — plus an `OutputFormat` that now depends on which response shape is set: `Csv` for the flat shape, `Xml` for the tree shape (see "Architecture Decisions"), unless the extension explicitly requested `Json` instead (Issue #86, see below). `Engine.Api` is a deliberate compromise, reusing `LanguageModuleRegistry`'s existing `(LanguageId, Engine)` mechanism even though "engine" is really meant to describe rendering behavior (see "Architecture Decisions"). `ApiParameter.Source` (three variants: `StaticListSource`/`DiscoverySource`/`RangeSource`) is polymorphic, discriminated via System.Text.Json's `[JsonPolymorphic]`/`[JsonDerivedType]` with an explicit `"kind"` field — unlike `ContainerNode`, which is recognized structurally, there's no natural distinguishing feature here
- **API mode: nested JSON responses** (Issue #54): `ApiConfig.Groups` (`List<ApiGroup>`) is the recursive alternative to the flat `ItemsPath`/`Fields` shape, mirroring container mode's own `Groups`/`ContainerNode` split. `ApiNode` (`ApiGroup`/`ApiField`, `IR/ApiConfig.cs`) is the JSON-path counterpart to `ContainerNode`'s CSS-selector tree: an `ApiGroup` scopes its children to whatever its own `Path` resolves to relative to the parent scope (the whole parsed response body for a root group), an `ApiField` is the leaf. Unlike `GroupNode.Repeating`, `ApiGroup` has no explicit repeating flag — whether resolving `Path` yields a JSON array (N instances) or an object/scalar (one instance) is a structural, stable property of the API's own schema, not a transient runtime fact the way a CSS selector's match count is, so it's simply inferred at runtime instead of chosen by the user (see "Architecture Decisions"). `List<ApiNode>` is polymorphic like `List<ContainerNode>`, so `IR/ApiNodeJsonConverter` discriminates structurally (presence of a `"children"` key) rather than via an explicit tag — the same reasoning `ContainerNodeJsonConverter` already uses, and unlike `ApiParameterSource` above, which has no natural structural tell between its three variants. `Backends/Python/PythonApiCodeGenerator` picks `scraper_api_grouped.py.j2` over `scraper_api.py.j2` whenever `Groups` is set, and `Backends/Python/PythonApiConfigLiteral.RenderGroups` serializes the tree into the same kind of Python dict/list literal `PythonGroupTreeLiteral` already builds for container mode
- **API mode: POST/GraphQL request bodies** (Issue #55): `ApiConfig.Method` may now be `"GET"` or `"POST"` (was GET-only) — `DiscoverySource`'s own `Method` stays GET-only, unchanged, since discovery endpoints are out of scope here. `ApiConfig.Body` (`IR/ApiBodyNode.cs`) is the write-side mirror of the `ApiGroup`/`ApiField` response-extraction tree: `ApiBodyObject`/`ApiBodyArray` recurse, `ApiBodyLiteral` (`Kind` + one of `StringValue`/`NumberValue`/`BoolValue`, whichever `Kind` says is set) is a fixed value, `ApiBodyVariable` (`ParameterName` + optional `CoerceTo`) references an `ApiConfig.Parameters` entry by name — reusing the existing `ApiParameter`/`ApiParameterSource` machinery rather than a second, body-specific value-source (see "Architecture Decisions"). `IR/ApiBodyNodeJsonConverter` discriminates the outer object/array/variable/literal split structurally (presence of `properties`/`items`/`parameterName`, else literal), the same style as `ContainerNodeJsonConverter`/`ApiNodeJsonConverter`; `ApiBodyLiteral` keeps its own explicit `Kind` tag internally, since structural sniffing can't tell "no value" from a literal `null`, or reliably tell a number from a numeric-looking string. `ScrapingPlanValidator` rejects `Body` set without `Method == "POST"` (a bodyless POST stays valid); a new recursive `ValidateApiBodyNode` walks the tree (Object/Array recursion, `Variable.ParameterName` must reference a declared parameter, a `Literal`'s `Kind` must match whichever value field is actually set); the existing "declared parameter must be used somewhere" check now also counts a parameter referenced only from the body, not just `UrlTemplate`. `Body` (request-side) and `Groups`/tree-vs-flat (response-side, Issue #54) are fully orthogonal — all four GET/POST × flat/tree combinations validate independently
- `Backends/Python/PythonApiConfigLiteral.RenderBody` serializes `ApiConfig.Body` into the same kind of runtime-readable dict-of-dicts literal `RenderGroups` already builds for the response tree; both `scraper_api.py.j2` and `scraper_api_grouped.py.j2` gain `METHOD`/`BODY` constants and a runtime `_render_body`/`_coerce_body_value` pair (the write-side mirror of `_extract_api_group`) that resolves the body fresh for each cartesian-product parameter combination — `scrape()` sends `requests.post(url, headers=headers, json=body, timeout=10)` when `METHOD == "POST"`, `requests.get(...)` otherwise. `_coerce_body_value` is best-effort: every `ApiParameterSource` value is string-typed end to end, so a body variable bound to a `Number`/`Boolean` parameter needs converting to fit a strictly-typed body (e.g. a GraphQL server rejecting a stringified number); an unparsable value falls back to the raw string rather than raising
- `RangeSource` (ISO week/number/date) carries an optional `Format` (`Backends/Python/RangeFormat`, a mini-template made of `{yyyy}`/`{ww}`/`{mm}`/`{dd}` placeholders), because target sites encode weeks/dates inconsistently (e.g. `2026-W35` vs. `2026-35`) — if `Format` is absent, ISO 8601 is the default. `RangeFormat` compiles the format into a regex and is used by `ScrapingPlanValidator` to validate `From`/`To` against it before the actual script run, instead of letting a format mismatch surface only as a raw Python traceback
- `Backends/Python/PythonApiCodeGenerator` (`LanguageId="python"`, `Engine=ScrapingEngine.Api`) generates plain `requests`+`itertools.product` Python (no BeautifulSoup/Playwright needed), automatically discovered by `LanguageModuleRegistry`'s reflection scan. `PythonScriptVerifier` runs it for real like any other script, against `output.csv`. The generated script tries the full cartesian product of all parameter value lists (no way to express dependencies between parameters, a deliberate limitation, see Issue #53); a single `404` response for one combination is treated as "this combination doesn't exist" and skipped instead of aborting the whole run — any other error status still aborts immediately, and the existing "at least one data row" success check remains the safety net against configurations that fail consistently
- **Configurable script/output filenames**: `ScrapingConfig.ScriptFileName`/`OutputFileName` (both nullable base names, no extension) let the extension name the downloaded script and the data file it writes. `ScrapingPlanBuilder` sanitizes both via `IR/FileNameSanitizer` (strips everything but letters/digits/`_`/`-`, defaults to `"scraper"`/`"output"` for empty/fully-invalid input — the same "don't reject, just default" pattern `OutputFormat`/`Engine` already use) and carries the sanitized result on `ScrapingPlan.ScriptFileName`/`OutputFileBaseName`, which every code generator renders into its template (the `"# Run: python X.py"` comment and the `open(...)`/`tree.write(...)` call) and which `PythonScriptVerifier.VerifyAsync`'s `outputFileBaseName` parameter uses to look for the *same* file the script was actually told to write — a mismatch here would make verification fail even for an otherwise-correct script
- **Json output format** (Issue #86): `OutputFormat.Json` is a third alternative to `Csv`/`Xml`, available in every mode/shape — a flat list-of-records dump for `Fields`/API-flat (the `Csv` analog), or a nested object mirroring the group/API tree for `Groups`/API-tree (the `Xml` analog). `ScrapingPlanBuilder`'s three forced-default spots (container `Xml`, API-flat `Csv`, API-tree `Xml`) each yield to an explicit `config.OutputFormat == OutputFormat.Json` instead of forcing their own default; flat `Fields` mode already passed `OutputFormat` straight through unmodified, so it gets `Json` for free. `PythonScriptVerifier.VerifyJsonOutput` tells the two Json shapes apart *structurally*, by parsing `output.json` via `System.Text.Json.Nodes.JsonNode` and checking whether the root is a `JsonArray` (flat, success iff non-empty, `RowCount` = array length, preview reuses the Csv preview's `Columns`/`Rows` table shape) or a `JsonObject` (tree, success iff a recursive property/array-item count is non-zero — not numerically equivalent to `Xml`'s `Descendants().Count()`, since a JSON leaf field folds into its parent's dict instead of being its own element; preview is a capped, pretty-printed `ScriptPreviewData.JsonSample`, the Json analog of `XmlSample`) — no second parameter is needed the way `OutputFormat` itself already distinguishes `Csv` from `Xml`, because Json's own two shapes self-describe via their JSON root type
- **Change detection + notification** (Issue #87): `ScrapingConfig.ChangeDetection` (`IR/ChangeDetectionConfig.cs`, optional/additive) is mode-independent — applies identically to Fields/Groups/Api. `Notify` is `"Email"` or `"Webhook"`; `EmailNotificationConfig`/`WebhookNotificationConfig` carry only environment-variable *names* (`SmtpHostEnvVar`/`FromEnvVar`/`ToEnvVar` required, `SmtpPortEnvVar`/`SmtpUsernameEnvVar`/`SmtpPasswordEnvVar`/`UrlEnvVar` as applicable), never literal credentials/targets — same pattern as `FillAction.EnvironmentVariableName`. `ScrapingPlanBuilder` carries it through to `ScrapingPlan.ChangeDetection` unchanged in all three shape branches (no forcing/translation needed, unlike `OutputFormat`/`Engine`); `ScrapingPlanValidator` checks the notify method, that exactly the matching sub-config is set, and every configured env-var name against the existing `EnvironmentVariableNamePattern`. `Backends/Python/PythonChangeDetectionLiteral.BuildContext` builds the one Scriban context object (`change_detection.*`) every one of the six templates renders from, always emitting all seven possible env-var-name fields (a Python string literal or `"None"`) regardless of which method is active, so template logic never has to branch on which shape of object it got. No companion-side diffing/notification logic exists at all — that all happens at runtime inside the generated script (see the Python Templates section below); the companion's only job is validating the config and rendering the right literals into it
- **Proxy support** (Issue #88): `ScrapingConfig.Proxy` (`IR/ProxyConfig.cs`, optional/additive) is mode-independent, carrying a single required `EnvironmentVariableName` — the wire format never sees a literal proxy address, only its env-var name, same as `ChangeDetectionConfig` above. `ScrapingPlanBuilder` carries it through to `ScrapingPlan.Proxy` unchanged in all three shape branches; `ScrapingPlanValidator` checks the env-var name against `EnvironmentVariableNamePattern`. `Backends/Python/PythonProxyLiteral.BuildContext` builds the one Scriban context object (`proxy.*`, an `enabled` flag plus `env_var_literal`) every one of the six templates renders from, mirroring `PythonChangeDetectionLiteral` exactly. All three code generators extend their existing `needs_os_import`/`NeedsOsImport` checks with `plan.Proxy is not null`, since the generated script reads the proxy list via `os.environ.get(...)` at runtime too. `Backends/Python/PythonScriptVerifier` treats a generated script's dedicated `EXIT_MISSING_ENV_VAR` (78) exit code as compatible with success — unlike any other nonzero code, which fails verification immediately — falling through to the same "did it actually produce data" check every other exit code goes through; only when that code is combined with no output file at all (the FillStep case, which can't produce anything) does it short-circuit, surfacing the script's own clean stderr message as the error instead of the generic "script did not produce X" (Issue #88 follow-up — see below and the Python Templates section).
- **Script hardening** (Issue #129): `ScrapingConfig.Hardening` (`IR/HardeningCheck.cs`, `List<HardeningCheck>?`, optional/additive) is mode-independent, carrying a polymorphic list of checks the *generated script itself* runs on its own result after scraping — independent of #87's change detection, which notifies on data *changing*, not on the scrape *breaking*. Each check is independently configured to `Warning` severity (printed by the script, still exits `0`) or `Error` severity (printed, script exits a dedicated `EXIT_HARDENING_FAILED` code). Discriminated via `[JsonPolymorphic]`/`[JsonDerivedType]` with an explicit `"kind"` tag, exactly like `ApiParameterSource`/`FieldTransform` (no natural structural tell between kinds) — camelCase discriminator values (`"noResult"`), not the PascalCase the issue's own prose informally used. `NoResultCheck` (zero data rows/elements after scraping — the classic "site redesign broke a selector, scheduled job silently produces nothing" case) was the first of five related checks the issue itself calls out (see "Planned for Future Releases"); `NullRateCheck` (Issue #130, see below) is the second. `ScrapingPlanBuilder` carries it through to `ScrapingPlan.Hardening` unchanged in all three shape branches; `ScrapingPlanValidator` rejects a duplicate check kind (the only structural rule needed for `NoResultCheck`, since it has no parameters of its own and `Severity` is already covered by deserialization). `Backends/Python/PythonHardeningLiteral.BuildContext` builds the one Scriban context object (`hardening.*`, an `enabled` flag plus a `checks_literal` Python list-of-dicts) every one of the six templates renders from, mirroring `PythonProxyLiteral` exactly. `Backends/Python/PythonScriptVerifier` treats the generated script's dedicated `EXIT_HARDENING_FAILED` (2) exit code as compatible with success the same way it already does `EXIT_MISSING_ENV_VAR` (78) — unlike Proxy's own case, hardening's check always runs *after* the output file is written, so there's no "nothing to verify yet" short-circuit needed on top of that.
- **Script hardening: per-field null-rate check** (Issue #130): `NullRateCheck : HardeningCheck` (`"kind": "nullRate"`) adds `FieldName` and `Threshold` (a fraction, 0.0-1.0, *not* a 0-100 percentage — the extension's own UI collects a percentage and divides by 100 before sending it, see the Browser Extension section above) — catches a field whose selector quietly starts matching the wrong thing (still returns a value, always empty) even though the overall row/element count `NoResultCheck` watches stays healthy. Unlike `NoResultCheck`, more than one `NullRateCheck` is expected (one per monitored field), so `ScrapingPlanValidator`'s "duplicate kind" rule is relaxed to a "duplicate `FieldName`" rule for this kind specifically, plus its own `FieldName`-non-blank and `Threshold`-in-`[0,1]` checks. `FieldName` is matched at runtime **globally by name**, not scoped to whichever parent group/container instance it's nested under — a deliberate simplification resolving the issue's own "open design question" about container/API-tree mode (where a field can repeat arbitrarily deep): a flat row's dict key for flat/API-flat shapes, or every element sharing that tag name anywhere in the built output tree for container/API-tree shapes (`root.iter(field)`), rather than a rate computed separately per parent group. `Backends/Python/PythonHardeningLiteral.RenderCheck` renders the extra `"field"`/`"threshold"` keys (via the existing `PythonLiteral.Num` for the threshold, same shortest-round-trippable-form rendering `ApiBodyLiteral.NumberValue` already uses).
- **Script hardening: baseline-drop check** (Issue #131): `BaselineCheck : HardeningCheck` (`"kind": "baseline"`) adds only `DropThreshold` (a fraction, same 0.0-1.0 convention as `NullRateCheck.Threshold`) — catches a gradual drop in result volume (e.g. a broken "load more"/pagination selector quietly losing entries) that neither `NoResultCheck` (only fires at exactly zero) nor `NullRateCheck` (only watches one field) would ever trip. Unlike `NullRateCheck`, only one `BaselineCheck` ever makes sense, so `ScrapingPlanValidator`'s existing duplicate-kind rule applies unchanged (no exemption needed), plus its own `DropThreshold`-in-`[0,1]` check. The *previous run's own result count* is deliberately **not** part of this wire type at all — it's runtime-only state the generated script tracks for itself in a small sidecar JSON file next to its own output (see the Python Templates section below), not something the companion needs to know about or persist; this was a deliberate choice over reusing `ChangeDetectionConfig`'s (Issue #87) own "compare against the previous output" mechanism, since that one unconditionally diffs the *entire* output file's content on every run, whereas Baseline only ever needs one integer and — critically — must only update after a run that didn't itself hard-fail, so a bad run's own low count never becomes the new normal for the next comparison (a materially different update rule). `PythonHardeningLiteral.BuildContext` gains a `has_baseline` flag (`list.Any(check => check is BaselineCheck)`) alongside the existing `enabled`/`checks_literal`, since this is the first hardening check needing its own on-disk state between runs — the templates use it to gate their sidecar-file helpers and `import json`.
- **Script hardening: blocking-detection check** (Issue #132): `BlockingCheck : HardeningCheck` (`"kind": "blocking"`) adds two optional parameters, `MinBodyLength` (an `int?` byte-length threshold; `null` disables the signal) and `BlockPhrases` (a `List<string>?` of case-insensitive substrings; `null`/empty disables the signal) — catches a site that starts blocking the script (rate-limiting, IP ban, CAPTCHA wall, redirect to a login page) while still responding with a normal-looking HTTP 200, which neither `NoResultCheck` nor `NullRateCheck` would necessarily catch if the blocked response still contains enough markup to produce a non-empty result. A third signal — the final response's host differing from the requested URL's host, i.e. a cross-origin redirect — needs no parameter at all and is always evaluated; this is the concrete, deterministic resolution of the issue's own vaguer "doesn't match the requested URL's origin/path shape" phrasing (deliberately *not* a hardcoded path-pattern list like `/login`/`/blocked` — too fragile/false-positive-prone across arbitrary sites, and not something the issue asked to be configurable). Unlike `NullRateCheck`, only one `BlockingCheck` ever makes sense, so `ScrapingPlanValidator`'s existing duplicate-kind rule applies unchanged; `MinBodyLength` must be positive when set, and every `BlockPhrases` entry must be non-blank — there's no "at least one signal configured" requirement, since a `BlockingCheck` with both fields unset still meaningfully checks the always-on redirect signal. Unlike `BaselineCheck`, this evaluates the *raw* response (final URL, body length, body text) captured at request time, not the already-extracted data/output tree — see the Python Templates section below for how each engine captures that snapshot from whatever "response" concept it actually has.
- **Script hardening: required-fields check** (Issue #133): `RequiredFieldsCheck : HardeningCheck` (`"kind": "requiredFields"`) adds `FieldNames` (`List<string>`, required, non-empty) — structurally different from its four siblings, which are all post-hoc aggregate checks evaluated once *after* scraping and never change what gets written: this one is a per-row *filter* that runs *before* the output file is finalized, dropping any row missing a non-empty value for any of `FieldNames` entirely (rather than writing it with a blank cell), serving the issue's own "safe for DB import" motivation (e.g. a `NOT NULL` database column that would otherwise silently break on import). The filtering itself always happens regardless of `Severity` — only whether the *run* is flagged as failed afterward depends on it, so an all-`Warning` configuration still guarantees the output file never contains a row missing a required value, without necessarily failing the whole run. Flat-shaped output only (`Fields`/flat mode, Api-mode's flat `ItemsPath`/`Fields` shape) — container mode and Api-mode's tree shape (`Groups`) have no unambiguous "row" to drop, so `ScrapingPlanValidator` rejects the combination outright at the `ExtractGroupStep`/`ApiCallStep`(tree) branches in `Validate()` (before shape is known, `ValidateHardening` itself can't do this check) rather than inventing an unrequested tree-dropping semantic the issue itself declined to resolve. Only one `RequiredFieldsCheck` ever makes sense, so the existing duplicate-kind rule applies unchanged; `FieldNames` must be non-empty with no blank or duplicate entries.

### Python Templates (`language-modules/python/templates/`)
- Scriban templates (the `.j2` file extension is a historical artifact — the syntax is Scriban, not Jinja2)
- `scraper.py.j2`: a monolith for the static engine (`PythonCodeGenerator`) — a declarative dict approach (SELECTORS/ATTRIBUTES), no step-by-step composition needed
- `playwright_scraper.py.j2` + `playwright_navigate_step.py.j2` + `playwright_wait_step.py.j2` + `playwright_fill_step.py.j2` + `playwright_click_step.py.j2`: for the browser engine (`PythonPlaywrightCodeGenerator`) — Navigate/WaitFor/Fill/Click steps are each rendered as their own fragment per step type and inserted into the shell in order, because (unlike Extract) each corresponds to one concrete action at a fixed point in the flow. `FillStep` values are never written into the script as a literal — they're always read at runtime via the shared `_require_env(name)` helper (`import os` is only added when a `FillStep` is actually present). A missing (not just empty) credential env var no longer surfaces as a raw, unhandled `KeyError` traceback — `_require_env` prints a clean English error naming the missing variable and exits via the same `EXIT_MISSING_ENV_VAR` (78) sentinel Proxy uses below, instead of the default `1` from an uncaught exception (Issue #88 follow-up, prompted by exactly this confusing traceback surfacing through `/generate`'s error response). Unlike Proxy, this is still a hard stop — a login flow genuinely can't continue without its credential — but `PythonScriptVerifier` surfaces the clean stderr message as the error instead of the generic "script did not produce output.csv" it would otherwise fall back to
- `scraper_grouped.py.j2` (static) + `playwright_scraper_grouped.py.j2` (browser): for container mode. The group tree is not reproduced as Scriban recursion (Scriban has no cross-template recursion) — instead, `Backends/Python/PythonGroupTreeLiteral` builds it as a nested Python dict/list literal (`GROUPS = [...]`) and inserts it into the template verbatim; a generic `extract_group()` function in the template walks the tree at runtime — identical between the two templates except for the two DOM-access calls (`select`/`select_one` vs. `query_selector_all`/`query_selector`). Output is `output.xml` (`xml.etree.ElementTree`; multiple root groups are combined under an `<Ergebnis>` wrapper)
- `scraper_api.py.j2` (API mode, `PythonApiCodeGenerator`): no BeautifulSoup needed, just `requests` + `itertools.product` + a minimal JSON-path DSL (dot notation for object keys, `[*]`/`[n]` for arrays) for per-record field extraction. Discovery sources resolve their values via an extra request; range sources (ISO week/number/date) are parsed/rendered against the `Format` mini-template (`_parse_range_value`/`_render_range_value`, mirroring `RangeFormat` on the companion side). A `404` response for a single parameter combination is skipped instead of aborting the run. Auth headers configured via `EnvironmentVariableName` are, like `FillStep`, never written as a literal — they're read via `os.environ[...]`. Output is `output.csv`, with parameter values as extra columns. `METHOD`/`BODY` (Issue #55) control whether `scrape()` sends a `requests.post(..., json=body)` with a rendered request body (`_render_body`/`_coerce_body_value`) instead of a plain `requests.get(...)` — see the Compiler section above
- `scraper_api_grouped.py.j2` (API mode, nested responses, Issue #54): the tree-shaped counterpart to `scraper_api.py.j2`, picked instead of it whenever `ApiConfig.Groups` is set. Reuses `scraper_api.py.j2`'s existing `_resolve_items()`/`_resolve_field()` JSON-path helpers unchanged — `_resolve_items()`'s "N instances if the resolved value is a list, else at most one" semantics already match `ApiGroup`'s own inferred repeating-ness — and adds a generic `_extract_api_group()` walker, exactly mirroring `scraper_grouped.py.j2`'s `extract_group()` for container mode's CSS-selector tree. Output is `output.xml` instead of `output.csv`; multiple root groups (and results accumulated across every parameter combination) are combined under the same `<Ergebnis>` wrapper container mode already uses. Also gains `METHOD`/`BODY` support (Issue #55), identical to `scraper_api.py.j2`'s own — response shape (flat/tree) and request method/body are fully orthogonal
- **Multiple start URLs** (Issue #83): `scraper.py.j2`/`playwright_scraper.py.j2` and `scraper_grouped.py.j2`/`playwright_scraper_grouped.py.j2` each gain a `URLS` list constant (from `NavigateStep.Urls`) instead of a single `URL` string. The two flat templates' `main()` loops over it, combining every URL's rows into one `data` list before writing the output file; the two grouped templates' `main()` wraps a single combined `<Ergebnis>` root and appends every URL's own `scrape(url)` children into it — reusing the exact sibling-merging pattern already used for multiple root groups from one URL. `scraper_api.py.j2`/`scraper_api_grouped.py.j2` are untouched — API mode builds its request URL from `URL_TEMPLATE` and never had a `URL`/`URLS` constant to begin with. Fixes a latent bug surfaced by this change: `playwright_navigate_step.py.j2` used to bake the target URL in as a literal (`page.goto("...")`), ignoring `scrape(url)`'s own parameter entirely — it now emits `page.goto(url, ...)`, which is what makes per-URL looping possible for the Browser engine at all (the Static engine's `scrape(url)` already used its parameter correctly)
- **Per-field data transformations** (Issue #84): all six templates above (`scraper.py.j2`, `playwright_scraper.py.j2`, `scraper_grouped.py.j2`, `playwright_scraper_grouped.py.j2`, `scraper_api.py.j2`, `scraper_api_grouped.py.j2`) carry the identical, hand-duplicated `_apply_transforms(value, transforms)`/`_to_number(value)` runtime helper pair, wrapped around each template's existing raw-value assignment — the same intentional duplication convention `scraper_grouped.py.j2`/`playwright_scraper_grouped.py.j2`'s own `extract_group()` already established (Scriban has no cross-template includes/recursion). `_to_number` auto-detects the decimal separator (handles both `"12,99"` and `"12.99"`) and strips thousands separators/currency symbols; when both `.` and `,` appear, the rightmost is the decimal point, and a single separator appearing more than once is treated as a thousands separator and stripped — a genuinely ambiguous single-occurrence case like `"1.234"` is always read as `1.234`, never `1234` (documented heuristic limitation, not a bug; chain a `regexExtract` transform first if that's not what's wanted)
- **Json output format** (Issue #86): the same six templates listed above gain an `output_is_json` flag from their code generator. The two flat templates (`scraper.py.j2`, `playwright_scraper.py.j2`) and the flat API template (`scraper_api.py.j2`) swap `import csv`/`csv.DictWriter` for `import json`/`json.dump(data, ...)` and write `output.json` instead of `output.csv` — `data` is already a list of dicts, so this is a straight serialization swap, no extraction-side change. The three tree templates (`scraper_grouped.py.j2`, `playwright_scraper_grouped.py.j2`, `scraper_api_grouped.py.j2`) instead gain a small `_xml_to_dict(element)` helper that converts the already-built `ET.Element` tree (built by `extract_group()`/`_extract_api_group()` regardless of output format) into nested dicts/lists, reusing the same extraction walk instead of a second, JSON-specific one — a tag occurring more than once among one element's children (several matches of a repeating group, or same-named sibling fields/groups, which Container-Mode explicitly allows) becomes a JSON list, a tag occurring exactly once stays a plain nested value
- **Default `User-Agent` header (bug fix)**: `scraper.py.j2`/`scraper_grouped.py.j2` (static engine) send a fixed `HEADERS = {"User-Agent": "Mozilla/5.0 (compatible; ScrapingFactory/1.0; +https://github.com/Aventinis/Scraping-Factory)"}` on every `requests.get(...)` call, and `scraper_api.py.j2`/`scraper_api_grouped.py.j2`'s own `_build_headers()` sets the same value as the first entry before folding in the user's own configured `ApiConfig.Headers` — many sites (Wikipedia among them) reject the bare `python-requests/x.y` default with `403 Forbidden`, and an honest, identifying UA (not a spoofed browser) is enough to pass that check on most sites. Setting it first in `_build_headers()` lets a user-configured `"User-Agent"` header (any casing) still override it: Python dict assignment order plus `requests`' own case-insensitive header handling means whichever entry was written later always wins. The Playwright/Browser engine templates are unaffected — a real Chromium browser already sends its own legitimate UA
- **Change detection + notification** (Issue #87): all six templates gain an `OUTPUT_PATH` constant (replacing the previously duplicated output-filename literal in each write/print call) and, when `change_detection.enabled`, a `_read_previous_output`/`_notify_email`/`_notify_webhook`/`_notify_change` helper set (hand-duplicated per template, same convention as `_apply_transforms`/`extract_group`) wrapped around the existing, unchanged write logic: the previous run's output is read *before* the new one is written, then the two are compared via `difflib.unified_diff` *after* — a notification only fires when they differ, and never on the first run (no previous file yet simply establishes the baseline instead), which also means this code path never executes during `/generate`'s trial-run verification (the temp directory is always fresh). Email delivery uses `smtplib` with *opportunistic* STARTTLS — `server.ehlo()` then `server.starttls()` only if `server.has_extn("starttls")` says the server actually advertised it — so the same generated script works against both a real provider and an unauthenticated local/internal relay without needing to know in advance which kind it's talking to. Webhook delivery uses `urllib.request`, kept stdlib-only like `smtplib` — no new pip dependency for either path, matching the issue's own "dependency-free" requirement. A notification failure (unreachable SMTP host, webhook down, ...) is caught and printed as a warning, never re-raised — by the time notification is even attempted, the current run's own output has already been written successfully, so a delivery hiccup must not turn a genuinely successful scrape into a failed run
- **Proxy support** (Issue #88): all six templates gain, when `proxy.enabled`, a `PROXY_ENV_VAR` constant plus a small duplicated runtime helper set (same "no cross-template includes" convention as `_apply_transforms`/`extract_group`): `PROXY_ENV_VAR`'s value is split on commas into a proxy list, cycled round-robin (`itertools.cycle`) so a fresh proxy is picked per request/browser-launch. The static and API engines (`requests`) wire a `_proxies_for_requests()` helper (returning `{"http": p, "https": p}`) into every `requests.get`/`requests.post` call site, including the API templates' discovery-source request — the browser engine (Playwright) instead parses the picked proxy URL via `urllib.parse.urlsplit` into Playwright's `{"server", "username", "password"}` shape (`_next_playwright_proxy()`) and passes it to `p.chromium.launch(proxy=...)`. A missing `PROXY_ENV_VAR` no longer raises a raw `KeyError` (Issue #88 follow-up — the original hard-fail-if-unset behavior mirroring `FillStep` made it impossible to verify a proxy-enabled config via `/generate` unless the companion host's own OS environment already had the var set, unlike `FillStep`, which has `VerificationValues` for exactly this): it's now read via `os.environ.get(...)`, and a missing var prints an English warning to stderr and is treated the same as an empty/blank value — "no proxies configured", direct connection, no crash. The run is still flagged, though: a shared `EXIT_MISSING_ENV_VAR = 78` sentinel (also used by `FillStep`'s `_require_env` helper in the two Playwright templates, see the paragraph above — the four static/API templates have no FillStep and so define just the constant, inline in the proxy block) is emitted whenever Proxy is enabled; once `main()` has otherwise completed successfully, the script exits with that code instead of `0` if the proxy var was missing — `PythonScriptVerifier` treats it as compatible with success (see the Compiler section above), so this alone no longer blocks `/generate`, while a real cron/scheduled run can still detect the degraded connection by checking for exit code 78 specifically instead of just "nonzero".
- **Script hardening** (Issue #129): all six templates gain, when `hardening.enabled`, an `EXIT_HARDENING_FAILED = 2` constant, the `HARDENING` list-of-dicts literal, and a small duplicated `_run_hardening_checks(...)` runtime helper (same "no cross-template includes" convention as `_apply_transforms`/`extract_group`/Proxy's own helpers) that iterates `HARDENING`, dispatches on each entry's `"kind"` (`"noResult"`: `result_count == 0`), and prints an English warning/error line to stderr per entry's `"severity"`, returning whether any `Error`-severity check failed. Called in `main()` right after scraping is otherwise done; `sys`'s existing conditional import (previously Proxy-only, or `needs_exit_helper` for the two Playwright templates) is broadened to also fire when only hardening is enabled; `EXIT_MISSING_ENV_VAR`'s own gate stays untouched, since that block is specifically about `FillStep`/Proxy's missing-credential handling, not something hardening piggybacks onto.
- **Script hardening: per-field null-rate check** (Issue #130): since a `"nullRate"` check needs more than a bare count to evaluate (it needs to inspect one specific field's actual values), `_run_hardening_checks` now takes the real scraped data instead of a pre-computed count, computing `result_count` internally so the `"noResult"` branch is unaffected: the two flat templates and `scraper_api.py.j2` now take `data` (the list of row dicts, `result_count = len(data)`), looking a field up via `row.get(field, "")` per row; the three tree templates (`scraper_grouped.py.j2`, `playwright_scraper_grouped.py.j2`, `scraper_api_grouped.py.j2`) now take `root` (the built `ET.Element` tree, `result_count = len(root.findall(".//*"))`), matching a field **globally by tag name across the whole tree** via `root.iter(field)` — not scoped to whichever parent group it's nested under, per `NullRateCheck`'s own "open design question" resolution (see the Compiler section above). A field name with zero matches is skipped rather than dividing by zero. Covered by real end-to-end tests (`HardeningNullRateEndToEndTests.cs`) that run the generated script as a subprocess and inspect its exit code/stderr directly — unlike `NoResultCheck`, a high null rate still produces a non-empty output file, so `PythonScriptVerifier`'s own black-box success/failure result can't distinguish a triggered check from an untriggered one.
- **Script hardening: baseline-drop check** (Issue #131): all six templates gain, when `hardening.has_baseline`, `import json` (needed for the sidecar file regardless of the script's own `OUTPUT_PATH` format), a `BASELINE_PATH = OUTPUT_PATH + ".hardening-baseline.json"` constant, and a `_read_baseline()`/`_write_baseline(count)` helper pair (missing/corrupt sidecar — first run ever, or the file got deleted — is treated as "no baseline yet", not an error). `_run_hardening_checks` gains a `"baseline"` branch comparing `result_count` against `_read_baseline()`'s value; a triggered check's message ("Result count dropped from X to Y…") follows the same Warning/Error print convention as the other two kinds. `main()`'s hardening call site now captures `hardening_failed = _run_hardening_checks(...)` explicitly (previously inlined straight into the `sys.exit` `if`) so it can separately gate `_write_baseline(...)`: the baseline only advances when `hardening_failed` is `False`, i.e. no *Error*-severity check fired (including this one comparing against the old baseline) — a Warning-severity trigger still advances it, since severity never changes anything else about how a run is treated anywhere else in this mechanism. Covered by real *two-run* end-to-end tests (`HardeningBaselineEndToEndTests.cs`) that run the generated script as a subprocess twice and inspect the sidecar file's own content in between — the one hardening check whose correctness inherently depends on state persisting between separate runs, something `PythonScriptVerifier`'s single always-fresh-temp-directory trial can never exercise at all.
- **Script hardening: blocking-detection check** (Issue #132): all six templates gain, when `hardening.enabled`, `from urllib.parse import urlsplit` (or, for the two Playwright templates, `import urllib.parse` folded into the same conditional that already covers Proxy's own need for it) and a module-level `_BLOCKING_RESPONSES = []` list, populated by `scrape()` right when each engine's own "response" concept is freshest: the four `requests`-based templates append `{"url", "final_url": response.url, "length": len(response.content), "text": response.text}` right after a successful (non-404) response; the two Playwright templates append `{"url", "final_url": page.url, "length", "text": page.content()}` right after `{{ actions }}` completes — i.e. the page actually about to be scraped, not an intermediate redirect a login flow's own Fill/Click steps legitimately pass through on the way there. Populated unconditionally whenever hardening is enabled at all (not gated behind a separate `has_blocking`-style flag the way `has_baseline` gates the sidecar helpers) — appending an already-in-memory string is cheap enough that a dedicated flag purely to skip it for the other three check kinds wasn't worth the extra generated-code branching. `_run_hardening_checks` gains a `"blocking"` branch iterating `_BLOCKING_RESPONSES` and evaluating all three signals per captured response (`urlsplit(...).netloc` mismatch, `length < minBodyLength`, a case-insensitive substring hit against `blockPhrases`), printing one combined message per affected response listing every signal that tripped. Playwright has no single raw response body to measure after JS execution, so its `length` approximates true network bytes as the rendered page's own UTF-8-encoded size (`len(page.content().encode("utf-8"))`) — a documented, deliberate per-engine simplification, consistent with the issue's own "open design question" about the Browser engine having no raw response to inspect the same way. Covered by real end-to-end tests (`HardeningBlockingEndToEndTests.cs`, static engine) for all three signals plus a same-host-redirect false-positive guard, and by `/generate` round-trip tests (`CompanionEndpointTests.cs`) proving the Scriban syntax also renders and runs cleanly for the API and Browser engines.
- **Script hardening: required-fields check** (Issue #133): only the three flat-shaped templates (`scraper.py.j2`, `playwright_scraper.py.j2`, `scraper_api.py.j2`) gain anything at all — the three tree-shaped templates need zero runtime changes, since `ScrapingPlanValidator` rejects `RequiredFieldsCheck` for their shape before codegen ever runs (`PythonHardeningLiteral`'s serialization switch still needs a case for it regardless, since `checks_literal` is built once and shared by every template). A new `_filter_required_fields(data)` helper, deliberately kept separate from `_run_hardening_checks` (see that function's own history: this check changes what gets *written*, not just what gets *reported* about what was already written) — looks up the `"requiredFields"` entry in `HARDENING` (no-ops if absent), filters `data` by requiring every row's value for each of `fieldNames` to be non-blank after `.strip()`, and prints one `WARNING:`/`ERROR:` line with the drop count if anything was dropped. Called from `main()` right after `data` is built (`data.extend(scrape(url))`/`data = scrape()`) and *before* the output file is written — ahead of `change_detection`'s own post-write "new content" read, so a filtered run's change-detection comparison naturally sees the filtered output as the truth, with no special-casing needed between the two features. `hardening_failed = _run_hardening_checks(data) or required_fields_failed` folds its own pass/fail into the same `EXIT_HARDENING_FAILED` decision the other four checks already drive. Covered by real end-to-end tests (`HardeningRequiredFieldsEndToEndTests.cs`, static engine) proving rows are actually dropped (and survivors kept) at both severities, and that a row missing *any* of several required fields is dropped — one of these tests caught a real, previously-latent quirk of flat mode's own extraction: each field's selector is matched independently, page-wide, then zipped by *index*, not scoped per repeating container, so a fixture that *omits* an element for a "missing value" case shifts every later field's index out of alignment instead of producing an empty value at that row (fixed by using an empty element instead of an omitted one in the test fixture, not a code change).
- Generated code should be idiomatic, commented, and readable for end users

It wasn't reproducible in Opera on the same setup (possibly different Ozone/XWayland defaults; not confirmed), which makes Opera a working alternative for affected users that needs no extra setup beyond loading the same unpacked extension.

## Architecture Decisions

Made during the prototyping phase and actively in use (no longer open questions — changes to them are normal ongoing development, not foundational decisions anymore):

1. **IR schema** — the wire format remains `ScrapingFactory.Compiler.IR.ScrapingConfig` (a fields list, selector as a CSS string, optional attribute, `OutputFormat`; camelCase/string enums, see `CompanionEndpointTests`). Internally, `ScrapingPlanBuilder` translates this into the canonical `ScrapingPlan` (a step sequence of `NavigateStep`/`ExtractStep`), which the code generator and verifier consume — the foundation for future step types (login, waiting, clicks) without breaking the wire format
2. **Extension ↔ companion communication** — a local HTTP server (`http://localhost:5000` by default, configurable — see the Companion App and Browser Extension sections above), no native messaging

A known, ongoing limitation (not an open decision, but a property of the chosen approach):

3. **Selector compatibility** — CSS selectors that don't map 1:1 onto BeautifulSoup/soupsieve (`:contains()`, shadow DOM, dynamic classes). This surfaces during script verification in `/generate` (a selector that returns no data → `422`), and is not validated separately.
4. **`ScrapingEngine.Api` as a third engine value** — conceptually, "engine" (how the page is rendered) doesn't quite fit a plain JSON call, but it's the cheapest way to hook into the existing `LanguageModuleRegistry` mechanism. A deliberate compromise, not a hard requirement — a dedicated axis later would be cleaner, but would require significantly more rework for little additional benefit at the current scale (see Issue #53).
5. **API mode: no dependencies between parameters** — the full cartesian product of all parameter value lists is always tried, exactly like the original manual approach (e.g. "week X only exists for category Y" can't be expressed). A `404` response per combination is therefore treated as expected and skipped, not as an error.
6. **`ApiGroup`'s repeating-ness is inferred, never an explicit flag** (Issue #54) — unlike `GroupNode.Repeating`, which exists because a CSS selector's match count is a transient runtime fact that could vary page to page (chosen explicitly by the user, never inferred from match count), whether resolving a JSON path yields an array or an object/scalar is a structural, stable property of the API's own schema — so `ApiGroup` simply has no `Repeating` property; at runtime, N matches means N instances, anything else means at most one instance.
7. **`ApiNode` uses a structural discriminator, not a tag** (Issue #54) — `ApiGroup` vs. `ApiField` has the same structural asymmetry as `GroupNode` vs. `DataFieldNode` (a branch has `Children`, a leaf doesn't), which is exactly the reason `ApiParameterSource`'s three variants instead needed an explicit `"kind"` tag (no natural structural tell between them) — that reason simply doesn't apply here, so `IR/ApiNodeJsonConverter` sniffs for a `"children"` property, exactly like `ContainerNodeJsonConverter` already does.
8. **API mode's `OutputFormat` follows response shape, not "being API mode" itself** — flat data (one repetition level, `ItemsPath`/`Fields`) still forces `Csv`; tree data (`Groups`, Issue #54) forces `Xml`, since a tree doesn't fit CSV's column model any more than container mode's own tree does. The rule was really always "flat data → CSV, tree data → XML" — API mode just didn't have a tree-shaped response option until Issue #54. `Json` (Issue #86) fits *either* shape, so it isn't part of this rule — it's a caller-chosen override that yields nothing about mode/shape detection, and both forced defaults above (as well as container mode's own `Xml` default) still apply exactly as before whenever `Json` isn't explicitly requested.
9. **A request-body "variable" is just another `ApiParameter`, referenced by name** (Issue #55) — rather than inventing a second, body-specific value-source concept, `ApiBodyVariable.ParameterName` points into the exact same `ApiConfig.Parameters`/`ApiParameterSource` list a `UrlTemplate` placeholder already resolves against. The only genuinely new concept `ApiConfig.Body` introduces is *where else* a parameter can be referenced from — not a new way to *supply* a value.
10. **The request body is a typed tree (`ApiBodyNode`), not a flat string template like `UrlTemplate`** (Issue #55) — a text-splicing approach would force every substituted value to be a JSON string, which is wrong for GraphQL's `variables` object: GraphQL variables are genuinely typed JSON (numbers, booleans, arrays, objects), so a numeric/boolean parameter needs to reach the body as a real JSON value, not a quoted string (see `ApiBodyVariable.CoerceTo`). A typed tree also composes naturally with a tree-shaped editor UI (Phase B4), reusing the same pattern Issue #54's response tree already established — the "overlap, not identity" between #54 and #55 the original issues themselves flagged.
11. **GraphQL gets no dedicated UI/wire concept anywhere** (Issue #55) — a GraphQL request is, structurally, just an ordinary POST body whose top-level JSON happens to have a `query` key (an ordinary fixed-literal leaf) and a `variables` key (an ordinary nested object subtree, marked up with the same generic fixed/variable-value UI as any other nested POST body). Baking in GraphQL-specific handling would duplicate machinery the generic body tree already provides for free; the only place GraphQL is even mentioned is descriptive documentation/UI hints, never a distinct code path.

## Feature Scope (as of v1.5.0)

Originally tracked as "v1 scope (MVP)" — the MVP has been reached since v1.0.0; this section is kept up to date with the overall current scope (most recently extended with, among other things, container-based scraping and API mode). Individual items move here from "Planned for Future Releases" once they ship.

- The default engine is still static rendering (`requests` + `BeautifulSoup`, no JS). An optional browser engine (Playwright + Chromium, `Engine: "Browser"`, plain Playwright + stock Chromium — **no commercial stealth-browser/anti-bot services with a license or session model**, e.g. CloakBrowser was evaluated and rejected, see git history) for dynamically rendered pages is fully wired into the extension UI (Issues #41/#42, Phases 5/6): an Engine toggle plus a generic, ordered browser-actions list (`WaitFor`/`Fill`/`Click`/`Scroll`, each with FramePath support for iframe-scoped actions), not a dedicated wizard per action kind. Verified through actual execution just like the static engine (the consistency rule is unchanged)
- Logging in within a single script run is possible (fill out a form → submit → wait → extract, credentials only via environment variables, never in the script) — assembled from the generic browser-actions list above as a Fill+Fill+Click+WaitFor sequence, no dedicated login-specific UI (Issue #43). The popup also lets the user type one-time test values per `Fill` action, sent to the companion only with that `/generate` request (`ScrapingConfig.VerificationValues`, keyed by environment-variable name, filtered server-side against the actually-declared `Fill` actions — see `IR/FillVerificationValues.cs`) and used only for that request's trial-run subprocess (`PythonScriptVerifier`'s `extraEnvironmentVariables`) — never persisted (not even across a popup close/reopen, see `fillTestValues` in `popup.js`), never logged, never written into the generated script — so a login flow can be verified without the credentials already needing to be set as OS environment variables on the machine running the companion app. No persistent session handling across multiple script runs (no saving/reusing cookie/storage state)
- **No CAPTCHA solving/bypassing** — a deliberate boundary, not an open item: CAPTCHAs are a targeted anti-automation measure by the target site; a generic bypass feature would be evasion tooling regardless of intent in any specific case, and would typically require paid third-party solving services (violating the principle above). If a CAPTCHA blocks the flow, the script simply fails honestly (e.g. a `WaitForStep` after the login click doesn't find the expected element → timeout) — there is no special handling
- **Container-based scraping** (groups/containers, Issue #21): fully implemented, including extension UI (mode selection, tree editor, click-based selection scoped to whichever repeating instance is actually clicked, Issue #167). Four field-extraction modes: Text, Attribute, Exists, and OwnText (Issue #169 — an element's direct text only, excluding nested elements like a badge/tag sharing the same container)
- **API-based extraction** (API mode, Issue #53): fully implemented, including extension UI — network recording, click correlation against recorded JSON responses, parameter configuration with a value list/discovery endpoint/range as value sources (including automatic format detection for ISO week/date). GET and POST requests (Issue #55, see below); no dependencies between parameters (see "Architecture Decisions")
- **API mode: nested JSON responses** (Issue #54): fully implemented, including extension UI — a response with more than one repetition level (e.g. `categories[*].subcategories[*].products[*]`) is represented as a full tree editor on the `API_CONFIG` screen instead of a flat record list, output as XML instead of CSV. Multi-level, JSON-scoped click-based search for extending an already-confirmed tree (adding a sibling field at any group's own scope, or an entirely independent second root group) — see the extension section above
- **API mode: POST/GraphQL request bodies** (Issue #55): fully implemented, including extension UI — the recorder captures the outgoing request body alongside the response; a confirmed POST candidate's own captured body becomes an editable draft tree where any value can be marked fixed or variable, the latter bound to a new or already-declared `ApiConfig` parameter (reusing the exact same parameter-source configuration cards a URL variable part already uses). GraphQL needs no dedicated support of its own — its `query`/`variables` shape is just an ordinary nested POST body, handled by the same generic mechanism (see "Architecture Decisions"). Request-body construction has the same "no dependencies between parameters" limitation as URL parameters (see above); discovery-endpoint sources remain GET-only
- **Trial-run data preview** (Issue #122): fully implemented — an opt-in checkbox lets the user see a capped sample (up to 50 rows/top-level elements) of what `/generate`'s trial run actually scraped, right in the popup, before downloading/using the script. Flat/API-mode-flat output shows as a table; container/API-mode-tree output shows as a read-only, pretty-printed Xml (or, since Issue #86, Json) text sample (a structured tree view for the latter, mirroring the config-tree editors, is explicitly out of scope for now)
- **Live selector match-count preview** (Issue #85): fully implemented, extension-only (no companion/IR/code-generator changes) — a flat/container field pick shows a live "N elements found" hint the instant the selector is built, and a container-group pick shows the same count as a toast right after insertion; both purely client-side (`document.querySelectorAll(selector).length` in the content script), no `/generate` round-trip needed. Existence/quantity feedback only — a full extracted-values preview remains the separate, existing "Show preview" DOM-highlight feature and Issue #122's trial-run data preview above
- **Per-field data transformations** (Issue #84): fully implemented — an optional, ordered chain of trim/regex-extract/find-replace/to-number steps, configurable in flat mode (`modal-field-name`, which had no per-field configuration UI at all before this), container mode (`modal-field-extended`, hidden for "Exists?" mode), and API mode (a "Transform" button per leaf field on the `API_CONFIG` tree screen, Issue #84 follow-up). Applies identically across every code generator (static/browser × flat/container, API flat/tree). **Live preview** (Issue #143, and its API-mode follow-up Issue #147): fully implemented across all three modes — the modal shows what the chain actually produces against the picked element's own raw value (flat/container) or the field's own captured sample value from candidate-confirm time (API mode), live, purely client-side
- **Json output format** (Issue #86): fully implemented — a mode-independent "Output as JSON" checkbox lets the user opt into `output.json` instead of the mode's default `output.csv`/`output.xml`, for every mode/shape (flat, container, API flat, API tree). Trial-run data preview (Issue #122 above) supports it too, reusing the Csv table renderer for Json's flat shape and the Xml text-sample renderer for Json's tree shape
- **Multiple start URLs** (Issue #83): fully implemented for flat and container mode — an optional "Additional start URLs" textarea lets the user run the same Fields/Groups extraction config against a static, user-supplied list of pages in one run, combining the results into a single output file (CSV/XML/Json alike). Not applicable to API mode, which already builds its own request URL from `urlTemplate`/parameters and rejects the combination outright rather than silently ignoring it. Out of scope, deliberately: crawling/following links matching a pattern, and pagination (see below)
- **Change detection + notification** (Issue #87): fully implemented, mode-independent (Fields/Groups/Api alike) — an opt-in toggle lets the generated script compare each run's output against the previous run's (a whole-file text diff via `difflib`, not a granular per-record diff) and notify by email (`smtplib`, opportunistic STARTTLS) or webhook (`urllib.request`) only when something actually changed, both stdlib-only with no new pip dependency. Every credential/target is an environment-variable name the user chooses, never a literal value baked into the script. Single-script, single-machine only, as scoped by the issue itself — no hosted/cloud scheduling and no multi-recipient alerting system; the user is responsible for actually running the script on a recurring basis (their own cron/Task Scheduler entry)
- **Proxy support** (Issue #88): fully implemented, mode-independent (Fields/Groups/Api alike) — an opt-in toggle lets the generated script route its outbound requests through proxies the user already has access to, instead of connecting directly. The extension never sees the proxy addresses themselves, only the name of an environment variable holding a comma-separated list; the generated script reads that list at runtime and, if more than one proxy is present, rotates through them round-robin per request. Wired into every engine's own HTTP layer: `requests`' `proxies` parameter for the static/API engines, Playwright's `proxy` launch option for the browser engine. Pass-through only, as scoped by the issue itself — no proxy acquisition, rotation service, or IP-pool management
- **Script hardening** (Issue #129): the first of five planned checks (see "Planned for Future Releases") sharing one mechanism — an opt-in "no result" check lets the generated script re-validate, on every run (not just the companion's own `/generate` trial run), that it actually scraped at least one row/element, independently configurable to print a warning (script still exits `0`) or fail the run (script exits a dedicated non-zero code, distinguishable from an unhandled crash) so a scheduled re-run weeks later doesn't silently produce nothing without anyone noticing. Mode-independent (Fields/Groups/Api alike).
- **Script hardening: per-field null-rate check** (Issue #130): fully implemented, the second of the five planned checks — catches the narrower case "no result" can't: a row/element count that stays healthy while one specific field's selector quietly starts matching the wrong thing and returns empty every time. Independently configurable per monitored field (any number of fields, each its own threshold and Warning/Error severity), reusing the exact field list already built in the current mode instead of a free-text field-name input. In container/API-tree mode, the rate is computed **globally per field name** across the whole result, not scoped to whichever parent group the field is nested under (a deliberate scoping decision — see the Compiler section above).
- **Script hardening: baseline-drop check** (Issue #131): fully implemented, the third of the five planned checks — catches a gradual volume drop (e.g. a broken "load more"/pagination selector) that neither "no result" nor per-field null-rate would ever trip, by comparing this run's own result count against the last run's, tracked entirely by the generated script itself in a small sidecar file next to its own output (never sent to or known by the companion). The sidecar only ever updates after a run that itself didn't hard-fail, so a bad run's own low count can never become the new baseline for the next comparison. Mode-independent (Fields/Groups/Api alike).
- **Script hardening: blocking-detection check** (Issue #132): fully implemented, the fourth of the five planned checks — catches a site that starts blocking the script (rate-limiting, IP ban, CAPTCHA wall, redirect to a login page) while still responding with a normal-looking HTTP 200, evaluated against the *raw* response (final URL, body length, body text) rather than the already-extracted data. Three signals: a redirect to a different host (always active, no configuration needed), a response shorter than an optional configured byte threshold, and an optional list of case-insensitive block phrases. Mode/engine-independent (Fields/Groups/Api × Static/Browser alike), though each engine's own "response" concept differs — see the Compiler/Python Templates sections above. Detection-and-reporting only, consistent with the "No CAPTCHA solving/bypassing" boundary below — it never attempts to bypass or work around whatever it detects.
- **Script hardening: required-fields check** (Issue #133): fully implemented, the fifth and last of the originally planned checks — unlike the other four (aggregate checks that only ever *report* on already-final data), this one *filters* the output before it's written: a row missing a non-empty value for any of a configured set of fields is dropped from the output entirely, serving a "safe for database import" use case (e.g. a `NOT NULL` column that would otherwise silently break on import). Filtering happens unconditionally regardless of severity — only whether the run itself is flagged as failed depends on it, so an all-Warning configuration still guarantees the output file never contains an incomplete row. Flat-shaped output only (Fields/flat mode, API mode's flat response shape) — container mode and API-mode's tree shape have no unambiguous "row" to drop, so the companion rejects the combination with a clear error rather than silently doing nothing.
- **Dark mode** (Issue #140): fully implemented, extension-only (no companion/IR changes) — follows the OS/browser `prefers-color-scheme` by default, with a manual system/light/dark toggle next to the language selector that persists the same way the language preference does (`chrome.storage.local`). See the extension section above for the token/theme-module mechanics
- No pagination
- Python only as a target language
- Backend of the generated script: `requests` + `BeautifulSoup` (static), Playwright (browser), or just `requests` (API mode); output as CSV (flat mode, and API mode's flat response shape), XML (container mode, and API mode's tree response shape, Issue #54), or Json instead of either (Issue #86)

## Consistency Rule

The companion app doesn't just verify at the same rendering stage as the generated script anymore — before delivery, it runs the exact generated script once as a trial (`Backends/Python/PythonScriptVerifier`: write the script to a temporary directory, run it via a `python3`/`python` subprocess, check the exit code and `output.csv`). This rules out any discrepancy between verification and the generated script (encoding, selector compatibility, network errors, runtime errors), and is why a separate Playwright- or AngleSharp-based verification path was rejected: it could only ever have approximated real script behavior.

Before this real execution, `/generate` also runs `IR/ScrapingPlanValidator` as a fast, purely structural pre-check of the `ScrapingPlan` (broken URL, duplicate/empty field names) — this doesn't replace real verification, it just saves the subprocess startup cost for configurations that are always wrong regardless of script behavior. CSS selector syntax/compatibility is deliberately still not checked separately (see point 3 above) — it remains solely the concern of the actual script execution.
