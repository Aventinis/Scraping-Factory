# Scraping Factory — Developer Documentation

## Project Overview

A browser extension that lets users without programming knowledge visually configure web scrapers. The result is a standalone, readable **Python script** (v1). The architecture is designed to support additional target languages later on.

The MVP (v1.0.0) was reached a while ago — the current release is v1.5.0. The project is therefore no longer in MVP buildout but in normal, ongoing feature development beyond it, including well beyond the feature set originally planned for v1. Foundational decisions made during the prototyping phase (IR schema, extension↔companion communication) are considered settled and are evolved during ongoing development rather than re-litigated — see "Architecture Decisions" below.

**Principle:** Scraping Factory is meant to remain a free plugin (no cost, no dependency on paid third-party services). This specifically rules out commercial stealth-browser/anti-bot SDKs with a session or license model (see "Feature Scope").

Full architecture concept: `architekturkonzept.md` (in the repo root, not checked in / kept separately).

## Language

Code comments, commit messages, pull requests, and all documentation (this file, `README.md`, `.claude/skills/**`) are written in **English**, regardless of what language a task request came in — conversations with the assistant (and the underlying issues/requests) are frequently in German, and that's fine; German task descriptions do not need to be pre-translated before work starts. The one deliberate exception is the extension's own end-user-facing UI (button labels, screen text in `extension/popup/popup.html`/`popup.js`) and any user-facing strings in generated scripts, which stay in German for now, since that's a product/UX decision independent of this policy — untranslated on purpose, not an oversight.

## Components

### Browser Extension
- Manifest V3, no Node.js access in the service worker
- Contains **no** scraping or code-generation logic
- Communicates with the companion app via a local HTTP server (`http://localhost:5000`)
- The popup/side panel (`extension/popup/popup.js`) supports three strictly separate modes: "Felder (flach)" ("Fields (flat)", the original mode), "Container (verschachtelt)" ("Container (nested)") and "API" — switching modes clears the configuration of the other two modes (`switchMode`/`MODE_SWITCH_CLEARS`). The container tree is rendered as an editable tree following the same visual pattern as the DOM tree view (`renderGroupTree`/`buildGroupTreeNodeEl`, mirroring `renderDomTree`/`buildTreeNodeEl`); creating a container asks for name/type **before** the click-based element selection (`modal-container-new`), while creating a data field asks (as in flat mode) **after** the click-based selection (`modal-field-extended`, with a field-type dropdown: Text/Attribute/Exists?)
- Content script (`extension/content/content-script.js`): `buildSelector`/`startSelection` accept an optional scope root (`scopeSelector` on the `START_SELECTION` message) — when adding a nested container/data field, click-based selection is restricted to descendants of the first instance of the parent group, and the resulting selector is valid relative to that instance instead of to `document.body`
- "Konfiguration exportieren" ("Export configuration", `btn-export-config`, `buildConfigExport`/`downloadConfigExport` in `popup.js`) downloads the current Fields/Groups/Api configuration as JSON — the `config` field inside is byte-for-byte the request body `/generate` would receive (reuses `buildScrapingConfig`), plus `exportedAt`/`extensionVersion`. Intended to be attached to selector/bug reports, independent of the existing "Fehler melden" ("Report bug") log export
- "robots.txt prüfen" ("Check robots.txt", `btn-check-robots` next to the URL display) shows whether the currently inspected page is allowed or disallowed according to the target site's robots.txt. The actual `robots.txt` fetch runs in the content script (`checkRobotsTxt`/`evaluateRobotsTxt`/`parseRobotsTxt` in `content-script.js`), not in the popup — a fetch from there is same-origin relative to the inspected page and therefore needs no extra `host_permissions`, unlike a fetch from the popup (its own `chrome-extension://` origin) to an arbitrary third-party domain. Popup → service worker → content script uses the same `CHECK_ROBOTS_TXT` request/response pattern as `GET_LOGS`. Only the generic `User-agent: *` group is ever evaluated (per the usual robots.txt rules: "longest matching pattern wins, ties go to Allow"), since the scripts this tool generates (the default `requests` user agent, or plain Playwright/Chromium) don't carry a product token a robots.txt could specifically name. A missing `robots.txt` (404) is treated as fully allowed; any other error status/network failure is shown as an inconclusive result instead of being guessed at
- **API mode** (Issue #53): automatically finds the matching JSON API request for a clicked data point, instead of scraping HTML. Network recording (`extension/content/api-capture.js`, injected into the MAIN world, `document_start`) patches `fetch`/`XMLHttpRequest.prototype.open`/`send` and buffers request/response pairs while a recording is running; communication to the isolated-world `content-script.js` goes via `window.postMessage`, then on to the popup via `chrome.runtime.sendMessage` (`API_CAPTURE_START`/`_STOP`/`_ENTRY`, `FORWARD_TO_TAB` in the service worker)
- Click-based selection in API mode searches (instead of building a CSS selector) for the clicked value recursively inside the recorded JSON responses (`findApiCandidates` in `content-script.js`) and returns candidates (request + JSON path to the match); for a match inside an array element, the object's sibling keys are offered as one-click suggestions for additional fields. A "select all"/"deselect all" toggle button sits alongside the chips (`.api-sibling-select-all` in `renderApiCandidates`/`popup.js`) for records with many keys — picking most of them is then "select all, then click off the few not needed" instead of clicking each wanted one individually; picked state itself stays DOM-only (a `.picked` class, never round-tripped through `_state`) the same way individual chip clicks already worked, so the button's own label is flipped directly in the click handler rather than via a `render()` pass
- A confirmed API candidate is turned into a parameterized `ApiConfig` on the `API_CONFIG` screen (`buildApiConfig`/`confirmApiConfig` in `popup.js`): the URL is decomposed into path segments/query parameters, each part individually toggleable between "fixed" and "variable"; each variable part gets a value source — a value list, a second discovery endpoint found via recording-and-correlating, or a locally computable range (ISO week/number/date). For range sources, the date/week format is auto-detected from the recorded raw value of the URL part (presets like "ISO standard"/"year-week without separator" plus "custom format…", `detectRangeFormat`/`RANGE_FORMAT_PRESETS` in `popup.js`) — necessary because target sites encode weeks/dates inconsistently (e.g. `2026-W35` vs. `2026-35`). Captured request headers are shown and can optionally be adopted per header, either as a literal or via an environment variable (mirroring the credentials pattern used by `FillStep`)
- Every field's name — the primary field (typed once at "Use" time) and every sibling field (originally fixed to its own JSON key) alike — stays editable on the `API_CONFIG` screen itself (`renderApiConfigFieldsList`/`setApiConfigFieldName` in `popup.js`, a committed `change`-event text input per row, same pattern as the URL-part-name inputs on the same screen), rather than only ever being nameable once at candidate-confirm time. A blank field name (only reachable through this input — impossible before it existed) blocks "Übernehmen" the same way a blank variable-part name already does (`apiConfigDraftHasAllSourcesChosen`)
- The full recorded request pool (not just the click-correlated matches above) is reachable two ways, both via a pull-based `GET_API_CAPTURE_ENTRIES` request/response (same pattern as `GET_LOGS`/`CHECK_ROBOTS_TXT`; content script returns its locally buffered `capturedApiEntries`, `isTopFrame`-gated like the others) rather than accumulating the live `API_CAPTURE_ENTRY` stream, which is dropped silently whenever the popup is closed: (1) an inline "Aufgezeichnete Anfragen anzeigen" panel on the idle screen (`toggleApiEntriesPanel`/`renderApiEntriesList` in `popup.js`) lists every recorded request (method/status/URL/content-type) for whoever wants to inspect the raw pool; (2) once a variable URL part's value source is set to a value list, the pool is searched for *other* recorded requests matching the same URL template — same origin, same path-segment count, every other *fixed* segment/query value equal, other *variable* parts left free — and their differing value at that part is auto-inserted into the value list (`findUrlTemplateMatches`/`fillStaticListFromPool` in `popup.js`), running once automatically when "Werteliste" is picked and again on demand via a "Aus Aufzeichnung übernehmen" button (e.g. after scrolling the inspected page further to trigger more lazy-loaded requests). Newly-derived values are only ever appended, never used to replace the existing list (`mergeValueListValues`), so a value the user has since deleted isn't silently resurrected by a later refresh
- The "output settings" fields ("Skriptname"/"Name der Ausgabedatei", shared across all three modes, at the bottom of `screen-idle` in `popup.html`) let the user name the downloaded `.py` file and the data file the generated script writes (`output.csv`/`output.xml` by default) — the shown extension (`.csv`/`.xml`) tracks the current mode, since container mode always writes XML. The downloaded script's filename is decided purely client-side (`triggerDownload`, `sanitizeFileNameBase`) and never round-trips through the companion; `scriptFileName`/`outputFileName` are still sent to `/generate` as free text so the companion can bake the *same* sanitized script name into the generated script's own "# Run: python X.py" comment. `sanitizeFileNameBase` in `popup.js` is a hand-kept mirror of the companion's `FileNameSanitizer` (same pattern as `RangeFormat`'s client-side mirror) — both must independently reach the same sanitized name for the same raw input, since the companion never reports back what it actually used

### Companion App (`companion/ScrapingFactory.Companion`)
- .NET 9 console application
- Starts a local HTTP server for the extension
- `/generate` generates the script, then runs it as a trial via the language module's verifier (`Backends/Python/PythonScriptVerifier`) in a temporary directory and only returns it on success (exit code 0, at least one data row, or — for container mode — one XML element) — on failure, returns `422` with an error message instead of the script
- **Runtime requirement:** `python3` (or `python`) including `requests` + `beautifulsoup4` must be available on the PATH of the machine running the companion app — not just for the end user who later runs the downloaded script. For the browser engine (`Engine: "Browser"`), `playwright` (`pip install playwright`) plus an installed Chromium (`playwright install chromium`) is additionally required
- Builds the IR and hands it off to `ScrapingFactory.Compiler`

### Compiler (`companion/ScrapingFactory.Compiler`)
- Contains the IR types: the wire format `ScrapingFactory.Compiler.IR.ScrapingConfig` (a Fields list, as sent by the extension) is translated by `ScrapingPlanBuilder` into the canonical `ScrapingPlan` (a step sequence of `NavigateStep`/`ExtractStep`) — the code generator and verifier only ever see `ScrapingPlan`
- **Container mode** (groups/containers, Issue #21): as an alternative to `Fields`, `ScrapingConfig` carries a `Groups` field (`List<GroupNode>`, see `IR/ContainerNode.cs` — `GroupNode`/`DataFieldNode`, recursively nestable). The two are mutually exclusive (`422`/`400` in `/generate`, before `ScrapingPlanBuilder`). `ScrapingPlanBuilder` translates `Groups` into a single `ExtractGroupStep` instead of the flat `ExtractStep` list, and forces `OutputFormat.Xml` regardless of what the extension sends — analogous to how a login flow forces `Engine=Browser`. Container mode is **engine-independent** (works equally with Static and Browser), unlike login. Since `List<ContainerNode>` is polymorphic (`GroupNode`/`DataFieldNode`), de-/serialization needs `IR/ContainerNodeJsonConverter` — System.Text.Json can neither deserialize into an abstract type nor serialize elements of a `List<ContainerNode>` by their runtime type
- Contains the language modules: `Backends/Python/PythonCodeGenerator` (engine `Static`, requests+BeautifulSoup) and `Backends/Python/PythonPlaywrightCodeGenerator` (engine `Browser`, Playwright), both implementing `ICodeGenerator`; `Backends/Python/PythonScriptVerifier` implements `IScriptVerifier` and runs both script kinds the same way (for container mode, against `output.xml` instead of `output.csv`, see the `OutputFormat` parameter of `VerifyAsync`). `LanguageModuleRegistry` resolves code generators by `(LanguageId, Engine)` tuple, and verifiers by `LanguageId` — callers never see the concrete types
- **API mode** (Issue #53): a third alternative, exclusive with `Fields`/`Groups` — `ScrapingConfig.Api` (`IR/ApiConfig.cs`: `ApiConfig` with `UrlTemplate`, optional `Headers`, `Parameters`, `ItemsPath`, `Fields`). `ScrapingPlanBuilder` translates `Api` into a single `ApiCallStep` and forces `OutputFormat.Csv` plus a third `ScrapingEngine.Api` value, regardless of what the extension sends — analogous to container mode/login above. `Engine.Api` is a deliberate compromise, reusing `LanguageModuleRegistry`'s existing `(LanguageId, Engine)` mechanism even though "engine" is really meant to describe rendering behavior (see "Architecture Decisions"). `ApiParameter.Source` (three variants: `StaticListSource`/`DiscoverySource`/`RangeSource`) is polymorphic, discriminated via System.Text.Json's `[JsonPolymorphic]`/`[JsonDerivedType]` with an explicit `"kind"` field — unlike `ContainerNode`, which is recognized structurally, there's no natural distinguishing feature here
- `RangeSource` (ISO week/number/date) carries an optional `Format` (`Backends/Python/RangeFormat`, a mini-template made of `{yyyy}`/`{ww}`/`{mm}`/`{dd}` placeholders), because target sites encode weeks/dates inconsistently (e.g. `2026-W35` vs. `2026-35`) — if `Format` is absent, ISO 8601 is the default. `RangeFormat` compiles the format into a regex and is used by `ScrapingPlanValidator` to validate `From`/`To` against it before the actual script run, instead of letting a format mismatch surface only as a raw Python traceback
- `Backends/Python/PythonApiCodeGenerator` (`LanguageId="python"`, `Engine=ScrapingEngine.Api`) generates plain `requests`+`itertools.product` Python (no BeautifulSoup/Playwright needed), automatically discovered by `LanguageModuleRegistry`'s reflection scan. `PythonScriptVerifier` runs it for real like any other script, against `output.csv`. The generated script tries the full cartesian product of all parameter value lists (no way to express dependencies between parameters, a deliberate limitation, see Issue #53); a single `404` response for one combination is treated as "this combination doesn't exist" and skipped instead of aborting the whole run — any other error status still aborts immediately, and the existing "at least one data row" success check remains the safety net against configurations that fail consistently
- **Configurable script/output filenames**: `ScrapingConfig.ScriptFileName`/`OutputFileName` (both nullable base names, no extension) let the extension name the downloaded script and the data file it writes. `ScrapingPlanBuilder` sanitizes both via `IR/FileNameSanitizer` (strips everything but letters/digits/`_`/`-`, defaults to `"scraper"`/`"output"` for empty/fully-invalid input — the same "don't reject, just default" pattern `OutputFormat`/`Engine` already use) and carries the sanitized result on `ScrapingPlan.ScriptFileName`/`OutputFileBaseName`, which every code generator renders into its template (the `"# Run: python X.py"` comment and the `open(...)`/`tree.write(...)` call) and which `PythonScriptVerifier.VerifyAsync`'s `outputFileBaseName` parameter uses to look for the *same* file the script was actually told to write — a mismatch here would make verification fail even for an otherwise-correct script

### Python Templates (`language-modules/python/templates/`)
- Scriban templates (the `.j2` file extension is a historical artifact — the syntax is Scriban, not Jinja2)
- `scraper.py.j2`: a monolith for the static engine (`PythonCodeGenerator`) — a declarative dict approach (SELECTORS/ATTRIBUTES), no step-by-step composition needed
- `playwright_scraper.py.j2` + `playwright_navigate_step.py.j2` + `playwright_wait_step.py.j2` + `playwright_fill_step.py.j2` + `playwright_click_step.py.j2`: for the browser engine (`PythonPlaywrightCodeGenerator`) — Navigate/WaitFor/Fill/Click steps are each rendered as their own fragment per step type and inserted into the shell in order, because (unlike Extract) each corresponds to one concrete action at a fixed point in the flow. `FillStep` values are never written into the script as a literal — they're always read at runtime via `os.environ[...]` (`import os` is only added when a `FillStep` is actually present)
- `scraper_grouped.py.j2` (static) + `playwright_scraper_grouped.py.j2` (browser): for container mode. The group tree is not reproduced as Scriban recursion (Scriban has no cross-template recursion) — instead, `Backends/Python/PythonGroupTreeLiteral` builds it as a nested Python dict/list literal (`GROUPS = [...]`) and inserts it into the template verbatim; a generic `extract_group()` function in the template walks the tree at runtime — identical between the two templates except for the two DOM-access calls (`select`/`select_one` vs. `query_selector_all`/`query_selector`). Output is `output.xml` (`xml.etree.ElementTree`; multiple root groups are combined under an `<Ergebnis>` wrapper)
- `scraper_api.py.j2` (API mode, `PythonApiCodeGenerator`): no BeautifulSoup needed, just `requests` + `itertools.product` + a minimal JSON-path DSL (dot notation for object keys, `[*]`/`[n]` for arrays) for per-record field extraction. Discovery sources resolve their values via an extra request; range sources (ISO week/number/date) are parsed/rendered against the `Format` mini-template (`_parse_range_value`/`_render_range_value`, mirroring `RangeFormat` on the companion side). A `404` response for a single parameter combination is skipped instead of aborting the run. Auth headers configured via `EnvironmentVariableName` are, like `FillStep`, never written as a literal — they're read via `os.environ[...]`. Output is `output.csv`, with parameter values as extra columns
- Generated code should be idiomatic, commented, and readable for end users

## Architecture Decisions

Made during the prototyping phase and actively in use (no longer open questions — changes to them are normal ongoing development, not foundational decisions anymore):

1. **IR schema** — the wire format remains `ScrapingFactory.Compiler.IR.ScrapingConfig` (a fields list, selector as a CSS string, optional attribute, `OutputFormat`; camelCase/string enums, see `CompanionEndpointTests`). Internally, `ScrapingPlanBuilder` translates this into the canonical `ScrapingPlan` (a step sequence of `NavigateStep`/`ExtractStep`), which the code generator and verifier consume — the foundation for future step types (login, waiting, clicks) without breaking the wire format
2. **Extension ↔ companion communication** — a local HTTP server (`http://localhost:5000`), no native messaging

A known, ongoing limitation (not an open decision, but a property of the chosen approach):

3. **Selector compatibility** — CSS selectors that don't map 1:1 onto BeautifulSoup/soupsieve (`:contains()`, shadow DOM, dynamic classes). This surfaces during script verification in `/generate` (a selector that returns no data → `422`), and is not validated separately.
4. **`ScrapingEngine.Api` as a third engine value** — conceptually, "engine" (how the page is rendered) doesn't quite fit a plain JSON call, but it's the cheapest way to hook into the existing `LanguageModuleRegistry` mechanism. A deliberate compromise, not a hard requirement — a dedicated axis later would be cleaner, but would require significantly more rework for little additional benefit at the current scale (see Issue #53).
5. **API mode: no dependencies between parameters** — the full cartesian product of all parameter value lists is always tried, exactly like the original manual approach (e.g. "week X only exists for category Y" can't be expressed). A `404` response per combination is therefore treated as expected and skipped, not as an error.

## Feature Scope (as of v1.5.0)

Originally tracked as "v1 scope (MVP)" — the MVP has been reached since v1.0.0; this section is kept up to date with the overall current scope (most recently extended with, among other things, container-based scraping and API mode). Individual items move here from "Planned for Future Releases" once they ship.

- The default engine is still static rendering (`requests` + `BeautifulSoup`, no JS). An optional browser engine (Playwright + Chromium, `Engine: "Browser"`, plain Playwright + stock Chromium — **no commercial stealth-browser/anti-bot services with a license or session model**, e.g. CloakBrowser was evaluated and rejected, see git history) for dynamically rendered pages is fully wired into the extension UI (Issues #41/#42, Phases 5/6): an Engine toggle plus a generic, ordered browser-actions list (`WaitFor`/`Fill`/`Click`/`Scroll`, each with FramePath support for iframe-scoped actions), not a dedicated wizard per action kind. Verified through actual execution just like the static engine (the consistency rule is unchanged)
- Logging in within a single script run is possible (fill out a form → submit → wait → extract, credentials only via environment variables, never in the script) — assembled from the generic browser-actions list above as a Fill+Fill+Click+WaitFor sequence, no dedicated login-specific UI (Issue #43). The popup also lets the user type one-time test values per `Fill` action, sent to the companion only with that `/generate` request (`ScrapingConfig.VerificationValues`, keyed by environment-variable name, filtered server-side against the actually-declared `Fill` actions — see `IR/FillVerificationValues.cs`) and used only for that request's trial-run subprocess (`PythonScriptVerifier`'s `extraEnvironmentVariables`) — never persisted (not even across a popup close/reopen, see `fillTestValues` in `popup.js`), never logged, never written into the generated script — so a login flow can be verified without the credentials already needing to be set as OS environment variables on the machine running the companion app. No persistent session handling across multiple script runs (no saving/reusing cookie/storage state)
- **No CAPTCHA solving/bypassing** — a deliberate boundary, not an open item: CAPTCHAs are a targeted anti-automation measure by the target site; a generic bypass feature would be evasion tooling regardless of intent in any specific case, and would typically require paid third-party solving services (violating the principle above). If a CAPTCHA blocks the flow, the script simply fails honestly (e.g. a `WaitForStep` after the login click doesn't find the expected element → timeout) — there is no special handling
- **Container-based scraping** (groups/containers, Issue #21): fully implemented, including extension UI (mode selection, tree editor, scoping click-based selection to one container instance)
- **API-based extraction** (API mode, Issue #53): fully implemented, including extension UI — network recording, click correlation against recorded JSON responses, parameter configuration with a value list/discovery endpoint/range as value sources (including automatic format detection for ISO week/date). GET requests only, no request body; only one repetition level per response (a flat record list, not a nested tree like in container mode); no dependencies between parameters (see "Architecture Decisions")
- No pagination
- Python only as a target language
- Backend of the generated script: `requests` + `BeautifulSoup` (static), Playwright (browser), or just `requests` (API mode); output as CSV (flat mode, API mode) or XML (container mode)

## Planned for Future Releases

- **Persistent session/cookie handling** — no saving/reusing cookie/storage state across multiple script runs; each run starts fresh (see "Feature Scope" for what's already possible — engine/action configuration, login flows, and one-time verification values — within a single run). CAPTCHA solving is not a goal (see "Feature Scope")
- **Pagination**
- **Additional target languages** besides Python (the architecture is already designed for this, see "Project Overview")
- **API mode: POST/GraphQL requests and nested JSON responses** — Issue #53 only covers GET without a request body and flat record lists; request-body support (follow-up issue "POST requests / request body support") and a recursive tree like in container mode (follow-up issue "nested JSON responses") are deliberately deferred

## Consistency Rule

The companion app doesn't just verify at the same rendering stage as the generated script anymore — before delivery, it runs the exact generated script once as a trial (`Backends/Python/PythonScriptVerifier`: write the script to a temporary directory, run it via a `python3`/`python` subprocess, check the exit code and `output.csv`). This rules out any discrepancy between verification and the generated script (encoding, selector compatibility, network errors, runtime errors), and is why a separate Playwright- or AngleSharp-based verification path was rejected: it could only ever have approximated real script behavior.

Before this real execution, `/generate` also runs `IR/ScrapingPlanValidator` as a fast, purely structural pre-check of the `ScrapingPlan` (broken URL, duplicate/empty field names) — this doesn't replace real verification, it just saves the subprocess startup cost for configurations that are always wrong regardless of script behavior. CSS selector syntax/compatibility is deliberately still not checked separately (see point 3 above) — it remains solely the concern of the actual script execution.
