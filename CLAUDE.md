# Scraping Factory — Developer Documentation

## Project Overview

A browser extension that lets users without programming knowledge visually configure web scrapers. The result is a standalone, readable **Python script** (v1). The architecture is designed to support additional target languages later on.

The MVP (v1.0.0) was reached a while ago — the current release is v1.14.0. The project is therefore no longer in MVP buildout but in normal, ongoing feature development beyond it, including well beyond the feature set originally planned for v1. Foundational decisions made during the prototyping phase (IR schema, extension↔companion communication) are considered settled and are evolved during ongoing development rather than re-litigated — see "Architecture Decisions" below.

**Principle:** Scraping Factory is meant to remain a free plugin (no cost, no dependency on paid third-party services). This specifically rules out commercial stealth-browser/anti-bot SDKs with a session or license model (see "Feature Scope").

Full architecture concept: `architekturkonzept.md` (in the repo root, not checked in / kept separately).

For the structural map of the codebase — system diagrams, a feature-to-file index,
and the cross-boundary class/wire-format relationship model between the extension
and the companion — see `docs/ARCHITECTURE.md`. That document is the *where*; this
file remains the *why* (behavioral detail, edge cases, the reasoning behind design
decisions).

## Language

Code comments, commit messages, pull requests, issue descriptions, and all documentation (this file, `README.md`, `.claude/skills/**`) are written in **English**, regardless of what language a task request came in — conversations with the assistant (and the underlying issues/requests) are frequently in German, and that's fine; German task descriptions do not need to be pre-translated before work starts. When a PR/issue names a specific UI element, name it by its English UI string (the `en.json` value, e.g. "Export configuration", not "Konfiguration exportieren") even if the conversation that produced it was in German — English is the one label guaranteed to be stable across the extension's UI languages (see below), unlike any one specific translation.

The extension's own end-user-facing UI (button labels, screen text) is the one place actual runtime *language choice* exists: `extension/i18n/{de,en,es}.json` hold three parallel dictionaries (loaded by `extension/i18n/i18n.js`), picked via an in-popup language selector and persisted like any other setting (`chrome.storage.local`) — adding or changing a user-facing string means updating all three files, not just one, to keep them in sync. Error messages returned by the companion (`/generate`'s `400`/`422` response bodies, thrown exceptions) and the generated scripts' own runtime console output (hardening/proxy/login warnings, etc.) are plain English like the rest of the codebase — neither is part of the extension's i18n system, and unlike the popup UI, neither has a per-language variant.

## Components

### Browser Extension
- Manifest V3, no Node.js access in the service worker
- Contains **no** scraping or code-generation logic
- **Popup module boundaries**: `popup/popup.js` had grown to over 4000 lines by the time Issue #178 shipped — every feature since roughly Issue #83 had simply been appended to it instead of extracted, the one part of the popup that never got the same logic/`-ui` split its own newer features (container mode, API mode, field transforms) already used. It was split into focused modules, each following the pre-existing `<feature>.js` (pure data/logic, no DOM) + `<feature>-ui.js` (DOM rendering + event wiring) convention `container-tree.js`/`container-tree-ui.js`, `api-config.js`/`api-config-ui.js`, and `field-transforms.js`/`field-transforms-ui.js` already established: `toast.js` (toast notifications + last-reported-error tracking), `bug-report.js` (log collection, GitHub issue prefill), `scraping-config-builder.js` (every pure `build*`/`add*`/`remove*`/`update*` wire-format helper — `buildScrapingConfig`, `buildConfigExport`, `buildChangeDetectionConfig`, `buildProxyConfig`, `buildPaginationConfig`, `buildHardeningConfig`, etc.), `dom-tree-ui.js` (the DOM inspector tree), `preview.js` (the DOM-highlight "Vorschau" feature), `companion-client.js` (every `fetch` call to the companion's `/health`/`/generate` endpoints, including the resolved `companionUrl` itself via `getResolvedCompanionUrl()`), `download-helpers.js` (Blob-download plumbing), `saved-configs-ui.js` (Issue #141/#202's `/configs`/`/configs/{id}/outputs` endpoints and the "Saved configurations" panel), and `settings-panel-ui.js` (the Monitoring/Settings sections' render + wiring: change detection, proxy, pagination, all five hardening checks). `popup.js` itself is now the thin orchestrator: `_state`, `setState`/`patchState`/`persistState`, `render()`/`wireEvents()` as dispatchers, `init()`, and the handful of screen-specific bits (flat/container/API mode switching, modal confirm flows) that don't cleanly belong to any single extracted feature. Since none of these modules can import `_state` directly (it stays module-private to `popup.js`), every function that needs to read/mutate state takes a `bridge` object as its first parameter — `{ getState, setState, patchState, stopPreviewIfActive, requestDomTree, showToast, fetchSavedConfigs }`, constructed once at module scope in `popup.js` (not just inside `wireEvents()`, so `popup.js`'s own top-level functions can use it too) — the exact convention `api-config-ui.js`/`container-tree-ui.js` already used for the same reason; a module needing no state access at all (`toast.js`, `download-helpers.js`'s `downloadFile`) just takes plain parameters instead. Test coverage was split the same way: each new module with genuine pure-function unit tests got its own `<feature>.test.js` (`scraping-config-builder.test.js`, `dom-tree-ui.test.js`, `bug-report.test.js`), while integration-style tests that exercise the full wired-up popup (`require('./popup')`, simulated `chrome.runtime.onMessage` dispatch, real DOM clicks) were relocated — not rewritten — into their own file per feature (`companion-client.test.js`, `saved-configs-ui.test.js`, `download-helpers.test.js`, `preview.test.js`, `settings-panel-ui.test.js`), shrinking `popup.test.js` from over 9000 lines without changing what any single test actually verifies. See Architecture Decision #12 below for the rule this establishes going forward.
- **Popup module boundaries, flat mode's turn** (follow-up to the above): flat mode was the *original* mode and, unlike container mode (`container-tree.js`/`container-tree-ui.js`) and API mode (`api-config.js`/`api-config-ui.js`), had never gotten its own module — its render/wire code was still sitting directly in `popup.js` even after every other feature had been extracted. `popup/flat-mode-ui.js` closes that last gap: the flat fields list (`renderFields`), the "+ Datenfeld" pick flow and `modal-field-name` (`renderFlatFieldModal`/`confirmField`), and that modal's own match-count hint/transform-chain editor (`renderMatchCountHint`/`refreshFlatTransformPreview`), all wired via one `wireFlatModeEvents(bridge)` called once from `popup.js`'s `wireEvents()` — the same `bridge`-parameter convention every other extracted module already uses. `renderMatchCountHint` is intentionally duplicated verbatim in `container-tree-ui.js` (whose own extended-field modal needs the identical hint) rather than shared, consistent with this codebase's existing "no cross-module includes for small DOM helpers" convention. `container-tree-ui.js` itself gained the matching `renderContainerFieldModal`/`wireContainerModeEvents` pair in the same pass, so `popup.js`'s `render()`/`wireEvents()` now dispatch to `renderFlatFieldModal`/`renderContainerFieldModal` and `wireFlatModeEvents`/`wireContainerModeEvents` symmetrically for both modes instead of inlining container mode's wiring while flat mode's stayed in `popup.js` proper. - **Test-flush robustness fix, prompted by the above**: every `flushMicrotasks()` helper across the popup's test files (~31 near-identical copies) used to loop a fixed count of `await Promise.resolve()` calls (10, one at 15) — enough to drain `init()`'s async chain as it stood, but not future-proof against that chain growing by even one more real `await` (which `loadScreenPartials()` did). - The popup/side panel (`extension/popup/popup.js`) supports three strictly separate modes: "Fields (flat)" (the original mode), "Containers (nested)" and "API" — switching modes clears the configuration of the other two modes (`switchMode`/`MODE_SWITCH_CLEARS`). The container tree is rendered as an editable tree following the same visual pattern as the DOM tree view (`renderGroupTree`/`buildGroupTreeNodeEl` in `popup/container-tree-ui.js`, mirroring `renderDomTree`/`buildTreeNodeEl` in `popup.js`); creating a container asks for name/type **before** the click-based element selection (`modal-container-new`), while creating a data field asks (as in flat mode) **after** the click-based selection (`modal-field-extended`, with a field-type dropdown: Text/Attribute/Exists?/OwnText — see Issue #169 below)
- **Container mode: rename and reorder tree nodes after creation** (Issue #177): every tree row's name is editable in place — a plain `<input class="group-tree-name">` (the same shape API mode's own tree rows already use for their `ApiGroup`/`ApiField` names, `setApiTreeNodeName`/`updateApiTreeNode` in `api-config.js`/`api-config-ui.js`) committed on `change`, replacing the previous read-only label; `formatGroupNodeLabel` is unchanged (still returns the full "name + suffix" string, still what the tests assert on) but is now built from a new `groupNodeSuffix(node)` helper, letting the tree-row editor render the name and the "(wiederholend)"/"— Text"-style suffix as two separate elements. A blank name reverts the input to the node's last name instead of saving an empty one — Container mode already allows duplicate sibling names by design (see the Json-output section below), so no other validation is needed. Each row also gets `↑`/`↓` move buttons (`btn-group-move-up`/`btn-group-move-down`, disabled at the top/bottom of their own sibling list) swapping the node with its adjacent sibling via `moveGroupTreeNode(groups, path, direction)` — the same swap-and-disable-at-the-boundary shape `field-transforms.js`'s own `moveTransform` already established for reordering a field's transform chain. Both rename and reorder apply uniformly to groups and fields alike (not fields-only, despite the issue's own "datafield" wording) — the two node kinds are freely intermixed as siblings in the same `children` array, so restricting either capability to one kind would leave the other unable to move past it or fix a typo'd name. Purely an extension-side change — the wire format's `Groups` array already accepts `children` in whatever order the extension sends, and the companion serializes them in that order, so reordering needs no companion/IR changes at all.
- Content script (`extension/content/content-script.js`): `buildSelector`/`startSelection` accept an optional scope root (`scopeSelector` on the `START_SELECTION` message) — when adding a nested container/data field, click-based selection is restricted to descendants of the parent group, and the resulting selector is valid relative to whichever instance was actually clicked instead of to `document.body`. `startSelection` resolves `scopeSelector` against *every* matching instance (`document.querySelectorAll`, not just the first), and `onClick`/`isInScope` accept a click inside any of them — the selector is then built relative to the specific instance the click landed in (`scopeRootFor`), not a single instance fixed in advance (Issue #167 fix: previously only `document.querySelector`'s implicit first match was ever scoped, so a sub-element absent from that particular instance — e.g. an optional "vegan" badge only some menu items carry — could never be selected at all, even though the resulting selector would already have matched it correctly wherever it does appear; the extraction runtime's own per-instance handling of a non-matching selector was already null-safe, see `extract_group` below). A click outside every instance is still rejected and now also sends `SELECTION_CLICK_OUT_OF_SCOPE`, shown as a brief non-blocking toast hint instead of being silent. A `scopeSelector` miss on the very first lookup now retries for a short window (`retryScopeSelector`, every 180ms up to 1.8s total) before finally sending `SELECTION_UNAVAILABLE`, instead of failing immediately (Issue #137 fix: reported against `penny.de/angebote/`, which server-renders skeleton/placeholder tiles first and swaps them for the real, differently-classed tiles once client-side JS hydrates — a parent container's own selector, confirmed valid the moment it was picked, could transiently stop matching an instant later purely because the page's own rendering caught up in between, permanently blocking every attempt to add a nested container/field inside it. Only ever kicks in on a miss — the common case, where the element is already present, stays perfectly synchronous with zero added delay. Doesn't attempt to solve arbitrary virtual scrolling, where an element is fundamentally never in the DOM until scrolled into view; only closes the gap between "the container was just confirmed" and "the very next click a moment later." At least 2 blocks are required before "Generate" enables, mirroring Combined mode's own `>= 2` gate.
  Shared/outer-level for Blocks mode, unlike Combined: `Url`/`AdditionalUrls`, `Engine`/`BrowserActions`, `Proxy`, `Pagination`, `PersistentSession` — one navigation, one browser session, N extraction+write phases against it (see the Companion App section below for why). `buildScrapingConfig`'s new `blocks` branch (`scraping-config-builder.js`) sends each block as `{name, outputFileName, fields|groups}` verbatim alongside those shared fields; per-block `ChangeDetection`/`Hardening`/`OutputFormat` overrides are supported by the wire format (see the Compiler section below) but have **no UI yet** in this v1 — the same kind of deliberately deferred gap Combined mode's own `VerificationValues` UI has — so `_state.blocks` entries never carry them, and the Monitoring/Settings section's toggles are left visible-but-inert for Blocks mode exactly like Combined mode's own toggles already are. There's also no per-block trial-run preview table yet: `companion-client.js`'s `generate()` recognizes Blocks mode's own `{ script, blocks: [{name, preview, outputFile}] }` response envelope (structurally, via `Array.isArray(data.blocks)`, distinct from every other mode's singular `{script, preview, outputFile}`) and the `DONE` screen's `#blocks-output-panel` renders one row per block with a "Download" button (`downloadFile`) — reading the per-block `preview` samples into a table/text view the way `renderDataPreview` already does for the single-shape case is left as a follow-up.
- **Output Blueprints: reusable output field-name/order mapping** (Issue #191): a persisted, site-independent "Output Blueprint" — just a name plus an ordered list of target field names — lets the user always download the same fixed column set/order/names (e.g. for feeding a downstream import pipeline) regardless of which scrape produced the data. Reachable only for flat-shaped output (flat mode, or API mode's own flat `ItemsPath`/`Fields` shape) via `#output-blueprint-toggle-row` in the Settings section's own picker — hidden entirely for container mode/API's tree shape/Combined/Blocks, the same "ship the simpler shape first" exclusion `ExternalConfig` (Issue #178) already established, mirrored on the companion side by an outright `400` rejection rather than a silent no-op (see below). New `extension/popup/output-blueprints.js` (pure helpers — editing a blueprint's own ordered field-name list in the create/edit modal, and building/validating the per-scrape source-field mapping draft) and `output-blueprints-ui.js` (CRUD against the companion's `/blueprints` endpoints, the management modal, the create/edit modal, and the mapping picker itself), the same pure-logic/DOM-rendering module split every other popup feature uses (Architecture Decision #12). The blueprint list itself is unscoped/reusable across any site or configuration — fetched once on companion connect (`checkCompanion`), like `allSavedConfigs`. Picking a blueprint resolves its own ordered target-field list via `GET /blueprints/{id}` and renders one mapping row per target field, each a `<select>` of the current mode's own available source field names (`collectFieldNames`, the same field-name source the hardening null-rate/required-fields pickers already draw from); switching mode clears any picked mapping (`OUTPUT_BLUEPRINT_RESET`), since a mapping's source-field names only mean something relative to the mode that built it. A blueprint picked but not yet fully mapped blocks "Generate" specifically (mirrors the per-field null-rate hardening check's own rows) without blocking Export/Save/Preview. `buildScrapingConfig`/`buildConfigExport` add the resulting `OutputBlueprintMapping` as `outputBlueprint` only once `buildOutputBlueprintMapping` confirms the mapping is actually complete — the same "incomplete draft → omitted, not sent" convention `buildProxyConfig`/`buildChangeDetectionConfig` already establish; `config-import.js`'s `applyOutputBlueprintConfig` is the reverse, restoring `_state` from a loaded/exported config's own wire mapping without a round trip back to the companion (the wire mapping's own `fields` array already carries every target field in blueprint order).
- **Output Blueprints: container/API-tree mode support** (Issue #192): `idle-screen-ui.js`'s own visibility/completeness gate (previously flat mode/Api's flat shape only) now also covers container mode and Api's tree shape, since both flatten into denormalized rows on the companion side (see the Compiler section below) instead of being rejected outright — only Combined/Blocks stay excluded, neither having a single field/tree config of its own at the outer level to map. No change needed to the picker itself: `collectFieldNames` already walked container mode's tree (leaf `DataFieldNode` names only) and Api mode's tree structurally, so the mapping's own source-field dropdown already offered the right options for every mode before this issue even started. `scraping-config-builder.js`'s `buildScrapingConfig` no longer strips `outputBlueprint` out of the container branch or gates it on `apiConfig.groups` being absent in the Api branch. A blueprint mapping applied to a tree behaves differently from flat mode's own rename/reorder/drop, by design (see the Compiler section's `OutputBlueprintFlattening` entry): the popup surfaces whatever the companion returns (a `400` at generate time for an ambiguous container-mode mapping, or a `422` verification failure for Api-tree's — necessarily runtime-only — equivalent) through the exact same generation-error toast path every other `/generate` failure already uses, needing no Api-tree-specific handling of its own.
- **Output Blueprints: nested/"containered" target schema** (Issue #244): a second, tree-shaped target schema alongside #191's flat, ordered field-name list — a blueprint now carries a `schemaKind` (`'Flat'`/`'Tree'`, one entity/table rather than two, chosen once at creation but editable later), and a Tree-schema blueprint's own target shape mirrors the container/API tree editors (nested target `group`/`field` nodes, no selector/mode/repeating-flag of its own — see the Compiler section's `OutputBlueprintTreeSchema` entry for why no explicit repeating flag is needed here either). This is what lets a mapping cover exactly the case #192's flat mapping rejects: two independent/sibling source repeating groups, each mapped into a *different branch* of one nested target tree instead of needing one shared row scope — the target tree's own nesting is the disambiguation, resolving the open question #244 was filed to answer. New `extension/popup/output-blueprints.js` additions: tree-schema editing helpers for the create/edit modal (`buildBlueprintSchemaGroup`/`buildBlueprintSchemaField`/`parseBlueprintSchemaTree`/`serializeBlueprintSchemaTree`/`blueprintTreeSchemaIsValid`) — the tree's own structural editing (add/remove/rename/reorder/nest a node) deliberately reuses `container-tree.js`'s generic path-based helpers (`insertContainerNode`/`removeGroupTreeNode`/`updateGroupTreeNode`/`moveGroupTreeNode`) directly rather than reimplementing them, since none of those functions read anything group/field-specific (selector, repeating, mode) — only `.children`/array shape, per Architecture Decision #12's "or an existing one it clearly extends" rule; and the per-scrape tree mapping draft (`createTreeMappingDraft`/`updateTreeMappingSource`/`treeMappingIsComplete`), keyed by each leaf's own dot-joined child-index path (e.g. `"0.1.0"`) rather than by name, since two leaves may share a name in different branches (mirrors container mode's own tree already allowing duplicate sibling names). `output-blueprints-ui.js`'s create/edit modal gains a Flat/Tree `.mode-toggle` (`schemaKind` on `blueprintEditDraft`, both drafts always kept populated so toggling back and forth mid-edit never loses either shape's own work) switching between the original flat field-name-list editor and a new tree editor (`renderBlueprintSchemaTree`/`buildBlueprintSchemaNodeEl`, visually mirroring `container-tree-ui.js`'s own group-tree editor). The mapping picker (`renderOutputBlueprintMappingSection`) filters Tree-schema blueprints out of the `<select>` entirely (`currentShapeSupportsTreeBlueprint`) unless the current mode/shape actually has a tree source to map against (container mode, or Api mode's own tree shape — symmetric with #192's own source scope) — there would be nothing for a target group's row scope to resolve against otherwise; once a Tree-schema blueprint is picked, `renderOutputBlueprintTreeMapping` renders a read-only structural view of the fetched target tree (a target group is just a label — there's nothing to pick for it, its own row scope is inferred entirely from its mapped leaf fields, never chosen directly) with a source-field `<select>` per leaf, offering the full current-mode field list at every position rather than scoping it further to "reachable from this tree position" (a deliberate first-version simplification — the generate-time/runtime ambiguity check still catches a genuinely wrong pick either way). `buildScrapingConfig`/`buildConfigExport` thread three new trailing parameters (`outputBlueprintSchemaKind`/`outputBlueprintTree`/`outputBlueprintTreeMapping`) through to `buildOutputBlueprintMapping`, which now dispatches on schema kind to build either the flat `fields` array or the nested wire tree; `config-import.js`'s `applyOutputBlueprintConfig` reverses either shape back into popup state without a round trip to the companion, walking the loaded wire tree and the (structurally identical) draft in lockstep.

### Companion App (`companion/ScrapingFactory.Companion`)
- .NET 10 console application
- Starts a local HTTP server for the extension
- `/generate` generates the script, then runs it as a trial via the language module's verifier (`Backends/Python/PythonScriptVerifier`) in a temporary directory and only returns it on success (exit code 0, at least one data row, or — for container mode — one XML element) — on failure, returns `422` with an error message instead of the script
- **Trial-run data preview** (Issue #122): `ScrapingConfig.IncludePreview` (nullable bool, additive/wire-compatible — absent/false is byte-for-byte today's response) lets the caller opt into seeing a capped sample of what the trial run actually scraped, instead of it being discarded once verification's pass/fail check is done. When `true`, a successful `/generate` returns JSON (`{ script, preview }`) instead of the plain script text; `preview` is `Backends/ScriptPreviewData` (`outputFormat`, `totalCount`, `truncated`, plus `columns`/`rows` for Csv or a pretty-printed, capped `xmlSample` for Xml — a structured tree view for Xml, mirroring the container/API config tree UI, is deliberately out of scope for now, see `PLAN-trial-run-data-preview.md`, kept locally/uncommitted like `architekturkonzept.md`). `PythonScriptVerifier.VerifyAsync`'s new `includePreview` parameter builds this from the *same* CSV lines/XML document it already reads for the row/element-count check — no new I/O — capped at 50 rows/top-level elements (`PreviewSampleCap`) regardless of how much the script actually scraped. CSV field-level parsing (needed here, unlike the row-count check, which only counts lines) mirrors Python's `csv.DictWriter` default dialect via a small `ParseCsvLine` helper (quoted fields, `""` escaped quotes) — the row-count check itself is untouched.
- **Download the full trial-run output** (Issue #161): `ScrapingConfig.IncludeOutputFile` (nullable bool, additive/wire-compatible, independent of `IncludePreview` — either, both, or neither may be requested in the same call) lets the caller keep the trial run's *complete*, uncapped output file instead of it being discarded. `IScriptVerifier.VerifyAsync`/`PythonScriptVerifier`'s new `includeOutputFile` parameter reads the raw file text (`File.ReadAllText`, **not** re-derived from `ScriptPreviewData`'s parsed/capped sample) at each of the three success paths (Csv's inline branch, `VerifyXmlOutput`, `VerifyJsonOutput`) and attaches it to `ScriptVerificationResult.OutputFileContent`/`OutputFileName` — reading the raw bytes rather than reconstructing them from already-parsed lines/nodes is what keeps the eventual download byte-identical to what the script actually wrote. `Program.cs`'s `/generate` handler's JSON-envelope condition (previously "`IncludePreview == true`") is now "`IncludePreview == true || IncludeOutputFile == true`", adding an `outputFile: { fileName, content }` key (or `null`) alongside `script`/`preview` — a request with neither flag set still gets byte-for-byte the same plain-text response as before either feature existed.
- **Runtime requirement:** `python3` (or `python`) including `requests` + `beautifulsoup4` must be available on the PATH of the machine running the companion app — not just for the end user who later runs the downloaded script. For the browser engine (`Engine: "Browser"`), `playwright` (`pip install playwright`) plus an installed Chromium (`playwright install chromium`) is additionally required
- **Configuration** (`appsettings.json`'s `Companion` section, standard ASP.NET Core precedence — so also overridable via e.g. `Companion__Port=5050` env var or a CLI arg, with no extra wiring): `Host`/`Port` (default `localhost`/`5000`, read by `CompanionHostOptions.BuildListenUrl` and passed to `builder.WebHost.UseUrls`) let the app bind somewhere other than the default when that port is already taken or the companion runs on a different machine than the extension expects — the extension-side counterpart is `shared/companion-config.js` above. `PythonExecutable`/`VerifierTimeoutSeconds` (both unset/null by default, keeping today's `python3`/`python` auto-probe and 45s timeout) reach `PythonScriptVerifier`'s own already-optional constructor parameters via `CompanionBackendOverrides.Build` and `LanguageModuleRegistry`'s generic `ctorOverrides` (a `Dictionary<string, object?>` matched against a reflectively-discovered backend's constructor parameter names) — useful for a machine with a non-standard Python install path, or one slow enough that the default trial-run timeout needs raising. All four are the same kind of hosting-machine-specific value; `ctorOverrides` is deliberately generic (name-matched, no compile-time reference to `PythonScriptVerifier`) so a future non-Python language module could expose its own optional constructor parameters through the same mechanism without touching the registry again
- **Local saved-configuration history** (Issue #141): a small local SQLite database (`Microsoft.Data.Sqlite`, no EF Core — a handful of simple queries don't need it), one table (`SavedConfigStore.cs`: `Id`, `Url`, a `Host` column derived once at save time via `Uri.TryCreate(url, ...).Host` — falling back to the raw string if unparseable — so lookups scope by hostname rather than requiring the exact saved page, `Name`, `SavedAt`, `ConfigJson`). Stored in a per-user app-data directory (`Environment.SpecialFolder.ApplicationData`/XDG-equivalent, resolved by `SavedConfigStore.ResolveDbPath` — overridable via `Companion:SavedConfigsDbPath`/`Companion__SavedConfigsDbPath`, same configuration-precedence pattern as `Host`/`Port`/`PythonExecutable` above, used by the test suite to point at an isolated temp file), never the working directory the companion happens to be launched from. `ConfigJson` is stored and returned **opaquely** — bound as a raw `JsonElement` in `POST /configs` and never deserialized into `ScrapingConfig` — so this endpoint doesn't need to track the wire format's own ongoing evolution, only round-trip whatever JSON object the extension handed it. Registered as `AddSingleton<SavedConfigStore>()` (a type, not a pre-built instance like `LanguageModuleRegistry`) so DI only constructs it — and only then creates the SQLite file — on the first actual `/configs` request; `/health`/`/generate` never touch it. Four endpoints alongside `/health`/`/generate`, same local-HTTP-server pattern (Architecture Decision #2): `POST /configs` (`{ url, name, config }` → `201` `{ id, url, name, savedAt }`), `GET /configs?url=...` (→ `200` with every saved entry for that URL's hostname, newest first, summary-only — no `config` blob), `GET /configs/{id}` (→ `200` with the full record including `config`, or `404`), `DELETE /configs/{id}` (→ `204`/`404`). Purely local/additive — no data ever leaves the user's machine, same trust boundary as the rest of the companion↔extension communication
- **Persist and browse run outputs** (Issue #202): a second table in the same SQLite database, `SavedOutputs` (`SavedConfigStore.cs`: `Id`, `SavedConfigId` — a foreign key to `SavedConfigs(Id)` with `ON DELETE CASCADE`, so deleting a saved config also removes its own saved outputs instead of leaving them orphaned — `Name`, `FileName`, `SavedAt`, `Content`). `Content` gets the exact same opaque, stored-and-returned-verbatim treatment `ConfigJson` already gets — it's the same string Issue #161's `outputFile.content` already carries, never parsed/reinterpreted here. The cascade only actually fires because every connection now goes through one `OpenConnection()` helper that sets `PRAGMA foreign_keys = ON` first — SQLite defaults that to *off* per connection, which would otherwise silently skip the `ON DELETE CASCADE` declaration entirely. Four more endpoints, nested under `/configs/{configId}/outputs` (same local-HTTP-server pattern, additive to Issue #141's four): `POST /configs/{configId}/outputs` (`{ name, fileName, content }` → `201` with the summary, or `404` if `configId` doesn't exist, mirroring `/configs`' own required-fields `400`), `GET /configs/{configId}/outputs` (→ `200` with every saved output for that config, newest first, summary-only — no `content`), `GET /configs/{configId}/outputs/{id}` (→ `200` with the full record including `content`, or `404` if either id doesn't exist or `id` belongs to a *different* `configId` than the one in the path), `DELETE /configs/{configId}/outputs/{id}` (→ `204`/`404`, same mismatch check). Deliberately storage/browse/download only — it does **not** evaluate hardening checks against a saved output; that's its own issue (#207), since hardening today only ever runs live, inside the generated script itself, and any cross-configuration comparison mode depends on Output Blueprints (#191) existing first.
- **Combined mode: `GET /configs` lists across every host** (Issue #239): the `url` query parameter on `GET /configs` (Issue #141) is now optional — present, it's byte-for-byte the existing hostname-scoped `SavedConfigStore.ListByUrl` behavior; absent, it calls the new unscoped `SavedConfigStore.ListAll()` (the same query minus the `WHERE Host = @host` clause), returning every saved configuration regardless of host. Purely additive/backward-compatible — needed by the extension's Combined-mode component picker, since a component can come from any previously-scraped site, not just the one the popup currently has open.
- **Combined mode: `/generate` orchestration** (Issue #239): `Program.cs`'s `/generate` handler gained a `Combined` branch, checked before the existing Fields/Groups/Api mutual-exclusion logic (itself extracted into two reusable local functions — `ValidateModeExclusivity(ScrapingConfig)` and `GenerateScript(ScrapingConfig, LanguageModuleRegistry, transformPlan?)`, covering the existing "check exclusivity" and "build→validate→resolve-generator→render" sequences respectively — so both the ordinary single-mode path and, per component, the Combined path share the exact same logic instead of duplicating it). The `Combined` branch rejects: `Combined` set alongside `Fields`/`Groups`/`Api`; `AdditionalUrls`/`Pagination`/`BrowserActions`/`ChangeDetection`/`Proxy`/`Hardening`/`PersistentSession`/`ExternalConfig` set on the *outer* request (all component-level-only for v1 — each component's own nested `ScrapingConfig` carries its own); fewer than 2 components; a component whose own `Config.Combined` is set (no nesting); and duplicate component names (the JSON merge key each component's output is written under, defaulting blank names to `component_{index}`, 1-based). Each component is then generated through `GenerateScript` exactly like a normal request, with a `transformPlan` callback forcing `OutputFormat.Json` and a fixed `OutputFileBaseName` (`"output"`) via the new `ScrapingPlan.With(...)` helper (a plain object-initializer copy — `ScrapingPlan`/`ScrapingConfig` are `sealed class`, not records, so C#'s `with` expression doesn't apply — applied *after* `ScrapingPlanBuilder.Build`/`ScrapingPlanValidator.Validate` have already run the component's own real requested shape/engine, so e.g. container mode's Xml-forcing or a component's own explicit Json request are honored upstream exactly as they would standalone; only the *final* artifact format is then overridden for combination). Every component's own `VerificationValues` (`CombinedComponentConfig.VerificationValues` — one-time `FillStep` login test values scoped to that component, filtered through the existing `FillVerificationValues.Filter` against that component's own `BrowserActions`) are merged into one flat dictionary and passed as the single outer `PythonScriptVerifier.VerifyAsync` call's `extraEnvironmentVariables` — this needs no further plumbing at all, because a subprocess a script spawns inherits its parent's environment by default, so env vars the verifier injects into the *combined* script's own process are automatically visible to every inner per-component subprocess the combined script spawns in turn (see the Python Templates section below). The resulting combined script is verified through the **existing, unmodified** `IScriptVerifier.VerifyAsync(_, OutputFormat.Json, _, ...)` — confirmed against `PythonScriptVerifier.VerifyJsonOutput` that a JSON-*object* root (the merged `{"componentName": [...], ...}` result) is already handled fully generically (a recursive non-zero-content check with no assumption about what produced it), so no verifier changes were needed at all.
- **Blocks mode: `/generate` orchestration** (Issue #182): `Program.cs`'s `/generate` handler gained a `Blocks` branch, checked alongside (not through) `ValidateModeExclusivity`/the ordinary single-mode path — but unlike the `Combined` branch above, it still goes through the *ordinary* `GenerateScript` (one `ScrapingPlanBuilder.Build`/`ScrapingPlanValidator.Validate`/`ICodeGenerator.Generate` call, one `ScrapingPlan`, one script), since Blocks mode is one script sharing one navigation rather than N independent ones. The branch rejects: `Blocks` set alongside `Fields`/`Groups`/`Api`/`Combined`; `ChangeDetection`/`Hardening` set on the *outer* request (per-block-only, unlike Combined mode's much longer outer-field rejection list — `AdditionalUrls`/`Proxy`/`Pagination`/`BrowserActions`/`PersistentSession` all stay valid/shared for Blocks, since they describe the one shared navigation/session every block extracts from); `ExternalConfig` set at all (not designed for more than one block's own output yet); and a block with neither/both of `Fields`/`Groups` set (checked per-block before the plan is even built, since the builder needs to already know each block's shape). The `>= 2 blocks`/duplicate-name/duplicate-output-filename checks live in `ScrapingPlanValidator` instead (see the Compiler section below) rather than here, since — unlike Combined's component list, which never becomes a `ScrapingPlan` at the outer level — a Blocks plan's block list is a normal, already-resolved part of the one plan `ScrapingPlanBuilder`/`ScrapingPlanValidator` already process. Verification uses the new `IScriptVerifier.VerifyBlocksAsync` (see below) instead of `VerifyAsync`, and a successful preview/output-file request returns `{ script, blocks: [{ name, preview, outputFile }] }` instead of the singular `{ script, preview, outputFile }` envelope every other mode uses.
- **Blocks mode: multi-output script verification** (Issue #182): `IScriptVerifier` gains `VerifyBlocksAsync(script, IReadOnlyList<BlockOutputSpec> blocks, ...)` (`BlockOutputSpec(string Name, OutputFormat OutputFormat, string OutputFileBaseName)`, `Backends/BlockVerification.cs`) — runs the script exactly once (the same subprocess-spawn/timeout/exit-code handling `VerifyAsync` already does, factored into a shared private `RunScriptAsync` helper both methods now call) but then checks one output file per block instead of one for the whole plan, reusing the exact same per-format `VerifyCsvOutput`/`VerifyXmlOutput`/`VerifyJsonOutput` helpers `VerifyAsync` itself calls (the CSV branch was factored out of `VerifyAsync`'s own inline logic into its own `VerifyCsvOutput` method for this, mirroring the other two, which were already separate methods). A single empty/failing block fails the *whole* `VerifyBlocksAsync` call, prefixed with which block it was (`Block 'name': ...`) — there's no "partially successful" outcome to represent, the same "did it actually work" bar `VerifyAsync` already holds a single-shape script to, just applied once per block. On success, `ScriptVerificationResult.Blocks` (a new, `VerifyBlocksAsync`-only property) carries one `BlockVerificationResult` (`Name`/`RowCount`/`Preview`/`OutputFileContent`/`OutputFileName`) per block, in the same order the caller's own block list was given in — `RowCount`/`Preview`/`OutputFileContent`/`OutputFileName` on the *outer* `ScriptVerificationResult` stay unset in this case, since those only ever describe a single-shape run's one file.
- **Output Blueprints: `OutputBlueprintStore` and `/blueprints` endpoints** (Issue #191): a small local SQLite database, `OutputBlueprintStore.cs` (own file/db, `output-blueprints.db`, `Companion:OutputBlueprintsDbPath` override — mirrors `SavedConfigStore`'s own configuration-precedence pattern, but no FK/cascade, since a blueprint isn't tied to any saved configuration), one table (`OutputBlueprints`: `Id`, `Name`, `SavedAt`, `FieldNamesJson`). (`Groups`/`Api.Groups` were rejected the same way originally too — see Issue #192 below for why that's no longer the case.)
- **Output Blueprints: container/API-tree mode support** (Issue #192): extends the mapping above to container mode and Api mode's tree shape by *flattening* the source tree into denormalized rows instead of rejecting the combination outright — see the Compiler section's own `OutputBlueprintFlattening` entry for the row-scope/broadcast mechanics. `Program.cs`'s previous `OutputBlueprint`-vs-`Groups`/`Api.Groups` rejection is gone; `Combined`/`Blocks` still reject it, since neither has a single field/tree config of its own at the outer level to flatten.
- **Output Blueprints: nested/"containered" target schema, store/endpoint side** (Issue #244): `OutputBlueprintStore`'s `OutputBlueprints` table gains two columns, added via an idempotent `ALTER TABLE ... ADD COLUMN` migration (checked via `pragma_table_info`) rather than baked into the original `CREATE TABLE IF NOT EXISTS` — so an `output-blueprints.db` created before this feature keeps working without the user deleting/recreating it: `SchemaKind` (`TEXT NOT NULL DEFAULT 'Flat'` — every pre-existing row defaults to the only schema kind that existed before this issue) and `TreeJson` (`TEXT NULL`, populated only for a Tree-schema blueprint, storing its own `List<OutputBlueprintTreeSchemaNode>`; stays `NULL` for a Flat one, whose `FieldNamesJson` keeps its exact pre-#244 meaning). `SchemaKind` is deliberately a plain string, not the Compiler project's `OutputBlueprintSchemaKind` enum type — but still PascalCase (`"Flat"`/`"Tree"`), matching that enum's own `JsonStringEnumConverter` wire serialization exactly, so the extension never needs to translate between two different casings for what both endpoints/wire types call the same concept. `Save`/`Update` take an additional `schemaKind`/`tree` pair (the existing `fieldNames` parameter simply goes unused for a Tree-schema call, and vice versa); `OutputBlueprintSummary.FieldCount`/`ListAll`/`Get` report the total *leaf* count for a tree, recursively, so the extension's picker shows one consistent "N fields" hint regardless of schema kind. `Program.cs`'s `/blueprints` `POST`/`PUT` share one `ValidateBlueprintRequest` local function: a missing/blank `schemaKind` in the request defaults to `"Flat"` (so a pre-#244 extension build's request, which never sends this field at all, keeps working byte-for-byte); a `"Tree"` request's own `tree` is validated via the new `OutputBlueprintTreeSchemaValidator.Validate` (non-blank node names, recursive, a group needs at least one child) instead of duplicating that structural check inline; an unrecognized `schemaKind` value is rejected with a `400`.

### Compiler (`companion/ScrapingFactory.Compiler`)
- Contains the IR types: the wire format `ScrapingFactory.Compiler.IR.ScrapingConfig` (a Fields list, as sent by the extension) is translated by `ScrapingPlanBuilder` into the canonical `ScrapingPlan` (a step sequence of `NavigateStep`/`ExtractStep`) — the code generator and verifier only ever see `ScrapingPlan`
- **Multiple start URLs** (Issue #83): `ScrapingConfig.AdditionalUrls` (`List<string>?`, additive/wire-compatible — absent/empty is today's exact single-URL behavior) lets the caller run the same Fields/Groups extraction config against more than one page, combining the results into one output file. `ScrapingPlanBuilder` combines `Url` (still the required "primary" URL) with each trimmed, non-blank `AdditionalUrls` entry into `NavigateStep.Urls` (`List<string>`, always at least one entry) — the one breaking change to the canonical `ScrapingPlan`, confined to `PythonCodeGenerator`/`PythonPlaywrightCodeGenerator`, which now loop over the list instead of reading a single `Url`. `ScrapingPlanValidator` validates every entry is an absolute http/https URI, identifying which one failed by index (`"Invalid start URL #N"`) instead of only ever checking one. Mutually exclusive with `Api` (`422`/`400` in `/generate`, same style as the existing Fields/Groups/Api guards) — `PythonApiCodeGenerator` builds its request URL entirely from `ApiConfig.UrlTemplate`/`Parameters` and never reads `NavigateStep`/the start URL at all, so silently accepting `AdditionalUrls` there would do nothing rather than express what the caller intended.
- **Pagination** (Issue #174): `ScrapingConfig.Pagination` (`IR/PaginationConfig.cs`, optional) is mode-independent (Fields/Groups alike) — polymorphic (`[JsonPolymorphic]`, `"kind"` tag, same convention as `ApiParameterSource`/`FieldTransform`/`HardeningCheck`, since there's no natural structural tell between the two kinds): `NextLinkPagination { NextLinkSelector }` follows a "next page" link's `href`; `PageNumberPagination { UrlTemplate }` substitutes `{url}` (the start URL, unchanged) and `{page}` (2, 3, …) into a template — both carry a `MaxPages` safety cap (default 50), always active regardless of kind. `ScrapingPlanBuilder` carries it through to `ScrapingPlan.Pagination` unchanged, for the Fields/Groups branches only — not the Api branch, mirroring `AdditionalUrls`' own mutual exclusivity (rejected in `Program.cs`'s `/generate` handler: Api never reads the page-scraping start URL at all, so this would silently do nothing there). `ScrapingPlanValidator` checks `MaxPages > 0`, a non-blank `NextLinkSelector`, or (reusing the same `UrlTemplatePlaceholderPattern` API mode's own `UrlTemplate` validation already uses) that `PageNumberPagination.UrlTemplate` references both `{url}` and `{page}`. `Backends/Python/PythonPaginationLiteral.BuildContext` builds the one Scriban context object (`pagination.*`) every one of the four non-API templates renders from, mirroring `PythonProxyLiteral`/`PythonChangeDetectionLiteral` exactly — always emits every field regardless of kind, so the template layer only ever branches on `enabled`/`kind`. Composes with `AdditionalUrls`: each start URL paginates onward independently, entirely inside the generated script's own `scrape()` function, with no change needed to `main()`'s existing multi-URL loop.
- **Container mode** (groups/containers, Issue #21): as an alternative to `Fields`, `ScrapingConfig` carries a `Groups` field (`List<GroupNode>`, see `IR/ContainerNode.cs` — `GroupNode`/`DataFieldNode`, recursively nestable). The two are mutually exclusive (`422`/`400` in `/generate`, before `ScrapingPlanBuilder`). `ScrapingPlanBuilder` translates `Groups` into a single `ExtractGroupStep` instead of the flat `ExtractStep` list, and forces `OutputFormat.Xml` regardless of what the extension sends — analogous to how a login flow forces `Engine=Browser` — unless the extension explicitly requested `Json` instead (Issue #86, see below). Container mode is **engine-independent** (works equally with Static and Browser), unlike login. Since `List<ContainerNode>` is polymorphic (`GroupNode`/`DataFieldNode`), de-/serialization needs `IR/ContainerNodeJsonConverter` — System.Text.Json can neither deserialize into an abstract type nor serialize elements of a `List<ContainerNode>` by their runtime type
- **Container mode: "own text" extraction** (Issue #169): a fourth `DataFieldNode.Mode` value, `ExtractMode.OwnText` (`IR/ContainerNode.cs`), alongside `Text`/`Attribute`/`Exists` — extracts only an element's direct text-node children, excluding text contributed by any nested element (e.g. a "vegan" badge `<span>` nested directly inside a dish-name `<h3>`, no separating whitespace in the markup, no longer gets pulled into the name the way plain Text mode's `get_text()`/`text_content()` unavoidably would, since those walk every descendant). `Backends/Python/PythonGroupTreeLiteral.RenderField` serializes it to the `"ownText"` mode string like the other three; `scraper_grouped.py.j2`'s `extract_group()` implements it via `found.contents` filtered by `isinstance(c, str)` (`NavigableString` is itself a `str` subclass, so no separate import is needed), `playwright_scraper_grouped.py.j2`'s via a small `ElementHandle.evaluate()` call over `childNodes` filtered to `nodeType === 3` (Playwright's `ElementHandle` has no built-in "own text" accessor). No validator changes needed — like Text/Exists, only a non-empty `Selector` is required (unlike Attribute mode's extra `Attribute` requirement), and `FieldTransformValidator`/the transform pipeline already apply mode-agnostically. Extension-side: `modal-field-extended`'s `select-field-mode` dropdown gains a fourth option; the click-time raw-value collection (`content-script.js`'s `collectOwnText`, alongside the existing `rawText`/`attributes` collection for Issue #143's live preview) is a JS-side mirror of the same `found.contents`-filtering logic, threaded through `service-worker.js`'s session-storage fallback and `popup.js`'s state (`pendingOwnText`) with full parity to `pendingRawText`/`pendingElementAttributes` at every existing call site
- Contains the language modules: `Backends/Python/PythonCodeGenerator` (engine `Static`, requests+BeautifulSoup) and `Backends/Python/PythonPlaywrightCodeGenerator` (engine `Browser`, Playwright), both implementing `ICodeGenerator`; `Backends/Python/PythonScriptVerifier` implements `IScriptVerifier` and runs both script kinds the same way (for container mode, against `output.xml`/`output.json` instead of `output.csv`, see the `OutputFormat` parameter of `VerifyAsync`). `LanguageModuleRegistry` resolves code generators by `(LanguageId, Engine)` tuple, and verifiers by `LanguageId` — callers never see the concrete types
- **API mode** (Issue #53): a third alternative, exclusive with `Fields`/`Groups` — `ScrapingConfig.Api` (`IR/ApiConfig.cs`: `ApiConfig` with `UrlTemplate`, optional `Headers`, `Parameters`, and either the flat `ItemsPath`/`Fields` shape or the recursive `Groups` tree shape below). `ScrapingPlanBuilder` translates `Api` into a single `ApiCallStep` and forces a third `ScrapingEngine.Api` value regardless of what the extension sends — analogous to container mode/login above — plus an `OutputFormat` that now depends on which response shape is set: `Csv` for the flat shape, `Xml` for the tree shape (see "Architecture Decisions"), unless the extension explicitly requested `Json` instead (Issue #86, see below). `Engine.Api` is a deliberate compromise, reusing `LanguageModuleRegistry`'s existing `(LanguageId, Engine)` mechanism even though "engine" is really meant to describe rendering behavior (see "Architecture Decisions"). `ApiParameter.Source` (three variants: `StaticListSource`/`DiscoverySource`/`RangeSource`) is polymorphic, discriminated via System.Text.Json's `[JsonPolymorphic]`/`[JsonDerivedType]` with an explicit `"kind"` field — unlike `ContainerNode`, which is recognized structurally, there's no natural distinguishing feature here
- **API mode: nested JSON responses** (Issue #54): `ApiConfig.Groups` (`List<ApiGroup>`) is the recursive alternative to the flat `ItemsPath`/`Fields` shape, mirroring container mode's own `Groups`/`ContainerNode` split. `ApiNode` (`ApiGroup`/`ApiField`, `IR/ApiConfig.cs`) is the JSON-path counterpart to `ContainerNode`'s CSS-selector tree: an `ApiGroup` scopes its children to whatever its own `Path` resolves to relative to the parent scope (the whole parsed response body for a root group), an `ApiField` is the leaf. Unlike `GroupNode.Repeating`, `ApiGroup` has no explicit repeating flag — whether resolving `Path` yields a JSON array (N instances) or an object/scalar (one instance) is a structural, stable property of the API's own schema, not a transient runtime fact the way a CSS selector's match count is, so it's simply inferred at runtime instead of chosen by the user (see "Architecture Decisions"). `List<ApiNode>` is polymorphic like `List<ContainerNode>`, so `IR/ApiNodeJsonConverter` discriminates structurally (presence of a `"children"` key) rather than via an explicit tag — the same reasoning `ContainerNodeJsonConverter` already uses, and unlike `ApiParameterSource` above, which has no natural structural tell between its three variants. `Backends/Python/PythonApiCodeGenerator` picks `scraper_api_grouped.py.j2` over `scraper_api.py.j2` whenever `Groups` is set, and `Backends/Python/PythonApiConfigLiteral.RenderGroups` serializes the tree into the same kind of Python dict/list literal `PythonGroupTreeLiteral` already builds for container mode
- **API mode: POST/GraphQL request bodies** (Issue #55): `ApiConfig.Method` may now be `"GET"` or `"POST"` (was GET-only) — `DiscoverySource`'s own `Method` stays GET-only, unchanged, since discovery endpoints are out of scope here. `ApiConfig.Body` (`IR/ApiBodyNode.cs`) is the write-side mirror of the `ApiGroup`/`ApiField` response-extraction tree: `ApiBodyObject`/`ApiBodyArray` recurse, `ApiBodyLiteral` (`Kind` + one of `StringValue`/`NumberValue`/`BoolValue`, whichever `Kind` says is set) is a fixed value, `ApiBodyVariable` (`ParameterName` + optional `CoerceTo`) references an `ApiConfig.Parameters` entry by name — reusing the existing `ApiParameter`/`ApiParameterSource` machinery rather than a second, body-specific value-source (see "Architecture Decisions"). `IR/ApiBodyNodeJsonConverter` discriminates the outer object/array/variable/literal split structurally (presence of `properties`/`items`/`parameterName`, else literal), the same style as `ContainerNodeJsonConverter`/`ApiNodeJsonConverter`; `ApiBodyLiteral` keeps its own explicit `Kind` tag internally, since structural sniffing can't tell "no value" from a literal `null`, or reliably tell a number from a numeric-looking string. `ScrapingPlanValidator` rejects `Body` set without `Method == "POST"` (a bodyless POST stays valid); a new recursive `ValidateApiBodyNode` walks the tree (Object/Array recursion, `Variable.ParameterName` must reference a declared parameter, a `Literal`'s `Kind` must match whichever value field is actually set); the existing "declared parameter must be used somewhere" check now also counts a parameter referenced only from the body, not just `UrlTemplate`. `Body` (request-side) and `Groups`/tree-vs-flat (response-side, Issue #54) are fully orthogonal — all four GET/POST × flat/tree combinations validate independently
- `Backends/Python/PythonApiConfigLiteral.RenderBody` serializes `ApiConfig.Body` into the same kind of runtime-readable dict-of-dicts literal `RenderGroups` already builds for the response tree; both `scraper_api.py.j2` and `scraper_api_grouped.py.j2` gain `METHOD`/`BODY` constants and a runtime `_render_body`/`_coerce_body_value` pair (the write-side mirror of `_extract_api_group`) that resolves the body fresh for each cartesian-product parameter combination — `scrape()` sends `requests.post(url, headers=headers, json=body, timeout=10)` when `METHOD == "POST"`, `requests.get(...)` otherwise. `_coerce_body_value` is best-effort: every `ApiParameterSource` value is string-typed end to end, so a body variable bound to a `Number`/`Boolean` parameter needs converting to fit a strictly-typed body (e.g. a GraphQL server rejecting a stringified number); an unparsable value falls back to the raw string rather than raising
- **API mode: embedded JSON source** (Issue #136): `ApiConfig.EmbeddedJsonSource` (`IR/ApiConfig.cs`, optional) is an alternative to a live JSON API call — `UrlTemplate`/`Parameters`/`Headers` still describe an ordinary (optionally parameterized) GET request, but the "response body" `ItemsPath`/`Fields`/`Groups` run against is the text content of one `<script>` tag within the fetched page's HTML (identified by `EmbeddedJsonSource.ScriptSelector`, a CSS selector resolved via BeautifulSoup's `select_one` at runtime — subject to the same selector-compatibility caveat as any other selector in this project, see "Architecture Decisions" point 3), not the HTTP response body itself. A plain optional object, not part of any polymorphic list — unlike `ApiParameterSource`'s three variants, there's nothing to discriminate between, so no `"kind"` tag/converter is needed (the "structural tell vs. explicit tag" choice this codebase otherwise makes for `ApiNode`/`ApiParameterSource` simply doesn't apply to a single optional property). `ScrapingPlanValidator` requires a non-blank `ScriptSelector` and `Method == "GET"` — the latter check alone transitively also rejects `Body`, since `Body` already requires `Method == "POST"` elsewhere in the same validator, so no separate "Body vs. EmbeddedJsonSource" check exists. Orthogonal to the flat-vs-tree response shape (Issue #54) and to `Parameters`/`DiscoverySource`, which stay fully reusable — a parameterized page URL (e.g. scraping N pages, each with its own embedded blob) is supported like any other API-mode request. `Backends/Python/PythonApiConfigLiteral.RenderEmbeddedJsonSource` serializes it into an `EMBEDDED_JSON_SOURCE` Python dict literal (or `"None"` when absent); `PythonApiCodeGenerator` passes it into both `scraper_api.py.j2` and `scraper_api_grouped.py.j2`, which conditionally import BeautifulSoup and gain an `_extract_embedded_json(response)` helper (`BeautifulSoup(response.text, "html.parser").select_one(...)` → `json.loads(tag.string)`, raising a clear `RuntimeError` if the tag is missing/unparseable — a hard failure, unlike a 404 combination, since there's no "this combination doesn't exist" fallback for a page missing the data it was expected to have) used in place of `response.json()` at the one call site each template has. Everything downstream (JSON-path resolution, transforms, hardening, change detection, output writers) needs zero changes — they already operate on "whatever JSON we ended up with", the whole reason `ItemsPath`/`Fields`/`Groups` were kept fetch-mechanism-agnostic in the first place.
- `RangeSource` (ISO week/number/date) carries an optional `Format` (`Backends/Python/RangeFormat`, a mini-template made of `{yyyy}`/`{ww}`/`{mm}`/`{dd}` placeholders), because target sites encode weeks/dates inconsistently (e.g. `2026-W35` vs. `2026-35`) — if `Format` is absent, ISO 8601 is the default. `RangeFormat` compiles the format into a regex and is used by `ScrapingPlanValidator` to validate `From`/`To` against it before the actual script run, instead of letting a format mismatch surface only as a raw Python traceback
- `Backends/Python/PythonApiCodeGenerator` (`LanguageId="python"`, `Engine=ScrapingEngine.Api`) generates plain `requests`+`itertools.product` Python (no BeautifulSoup/Playwright needed), automatically discovered by `LanguageModuleRegistry`'s reflection scan. `PythonScriptVerifier` runs it for real like any other script, against `output.csv`. The generated script tries the full cartesian product of all parameter value lists (no way to express dependencies between parameters, a deliberate limitation, see Issue #53); a single `404` response for one combination is treated as "this combination doesn't exist" and skipped instead of aborting the whole run — any other error status still aborts immediately, and the existing "at least one data row" success check remains the safety net against configurations that fail consistently
- **Configurable script/output filenames**: `ScrapingConfig.ScriptFileName`/`OutputFileName` (both nullable base names, no extension) let the extension name the downloaded script and the data file it writes. `ScrapingPlanBuilder` sanitizes both via `IR/FileNameSanitizer` (strips everything but letters/digits/`_`/`-`, defaults to `"scraper"`/`"output"` for empty/fully-invalid input — the same "don't reject, just default" pattern `OutputFormat`/`Engine` already use) and carries the sanitized result on `ScrapingPlan.ScriptFileName`/`OutputFileBaseName`, which every code generator renders into its template (the `"# Run: python X.py"` comment and the `open(...)`/`tree.write(...)` call) and which `PythonScriptVerifier.VerifyAsync`'s `outputFileBaseName` parameter uses to look for the *same* file the script was actually told to write — a mismatch here would make verification fail even for an otherwise-correct script
- **Json output format** (Issue #86): `OutputFormat.Json` is a third alternative to `Csv`/`Xml`, available in every mode/shape — a flat list-of-records dump for `Fields`/API-flat (the `Csv` analog), or a nested object mirroring the group/API tree for `Groups`/API-tree (the `Xml` analog). `ScrapingPlanBuilder`'s three forced-default spots (container `Xml`, API-flat `Csv`, API-tree `Xml`) each yield to an explicit `config.OutputFormat == OutputFormat.Json` instead of forcing their own default; flat `Fields` mode already passed `OutputFormat` straight through unmodified, so it gets `Json` for free. `PythonScriptVerifier.VerifyJsonOutput` tells the two Json shapes apart *structurally*, by parsing `output.json` via `System.Text.Json.Nodes.JsonNode` and checking whether the root is a `JsonArray` (flat, success iff non-empty, `RowCount` = array length, preview reuses the Csv preview's `Columns`/`Rows` table shape) or a `JsonObject` (tree, success iff a recursive property/array-item count is non-zero — not numerically equivalent to `Xml`'s `Descendants().Count()`, since a JSON leaf field folds into its parent's dict instead of being its own element; preview is a capped, pretty-printed `ScriptPreviewData.JsonSample`, the Json analog of `XmlSample`) — no second parameter is needed the way `OutputFormat` itself already distinguishes `Csv` from `Xml`, because Json's own two shapes self-describe via their JSON root type
- **Change detection + notification** (Issue #87): `ScrapingConfig.ChangeDetection` (`IR/ChangeDetectionConfig.cs`, optional/additive) is mode-independent — applies identically to Fields/Groups/Api. `Notify` is `"Email"` or `"Webhook"`; `EmailNotificationConfig`/`WebhookNotificationConfig` carry only environment-variable *names* (`SmtpHostEnvVar`/`FromEnvVar`/`ToEnvVar` required, `SmtpPortEnvVar`/`SmtpUsernameEnvVar`/`SmtpPasswordEnvVar`/`UrlEnvVar` as applicable), never literal credentials/targets — same pattern as `FillAction.EnvironmentVariableName`. `ScrapingPlanBuilder` carries it through to `ScrapingPlan.ChangeDetection` unchanged in all three shape branches (no forcing/translation needed, unlike `OutputFormat`/`Engine`); `ScrapingPlanValidator` checks the notify method, that exactly the matching sub-config is set, and every configured env-var name against the existing `EnvironmentVariableNamePattern`. `Backends/Python/PythonChangeDetectionLiteral.BuildContext` builds the one Scriban context object (`change_detection.*`) every one of the six templates renders from, always emitting all seven possible env-var-name fields (a Python string literal or `"None"`) regardless of which method is active, so template logic never has to branch on which shape of object it got. No companion-side diffing/notification logic exists at all — that all happens at runtime inside the generated script (see the Python Templates section below); the companion's only job is validating the config and rendering the right literals into it
- **Proxy support** (Issue #88): `ScrapingConfig.Proxy` (`IR/ProxyConfig.cs`, optional/additive) is mode-independent, carrying a single required `EnvironmentVariableName` — the wire format never sees a literal proxy address, only its env-var name, same as `ChangeDetectionConfig` above. `ScrapingPlanBuilder` carries it through to `ScrapingPlan.Proxy` unchanged in all three shape branches; `ScrapingPlanValidator` checks the env-var name against `EnvironmentVariableNamePattern`. `Backends/Python/PythonProxyLiteral.BuildContext` builds the one Scriban context object (`proxy.*`, an `enabled` flag plus `env_var_literal`) every one of the six templates renders from, mirroring `PythonChangeDetectionLiteral` exactly. All three code generators extend their existing `needs_os_import`/`NeedsOsImport` checks with `plan.Proxy is not null`, since the generated script reads the proxy list via `os.environ.get(...)` at runtime too. `Backends/Python/PythonScriptVerifier` treats a generated script's dedicated `EXIT_MISSING_ENV_VAR` (78) exit code as compatible with success — unlike any other nonzero code, which fails verification immediately — falling through to the same "did it actually produce data" check every other exit code goes through; only when that code is combined with no output file at all (the FillStep case, which can't produce anything) does it short-circuit, surfacing the script's own clean stderr message as the error instead of the generic "script did not produce X" (Issue #88 follow-up — see below and the Python Templates section).
- **Script hardening** (Issue #129): `ScrapingConfig.Hardening` (`IR/HardeningCheck.cs`, `List<HardeningCheck>?`, optional/additive) is mode-independent, carrying a polymorphic list of checks the *generated script itself* runs on its own result after scraping — independent of #87's change detection, which notifies on data *changing*, not on the scrape *breaking*. Each check is independently configured to `Warning` severity (printed by the script, still exits `0`) or `Error` severity (printed, script exits a dedicated `EXIT_HARDENING_FAILED` code). Discriminated via `[JsonPolymorphic]`/`[JsonDerivedType]` with an explicit `"kind"` tag, exactly like `ApiParameterSource`/`FieldTransform` (no natural structural tell between kinds) — camelCase discriminator values (`"noResult"`), not the PascalCase the issue's own prose informally used. `NoResultCheck` (zero data rows/elements after scraping — the classic "site redesign broke a selector, scheduled job silently produces nothing" case) was the first of five related checks the issue itself calls out (see "Planned for Future Releases"); `NullRateCheck` (Issue #130, see below) is the second. `ScrapingPlanBuilder` carries it through to `ScrapingPlan.Hardening` unchanged in all three shape branches; `ScrapingPlanValidator` rejects a duplicate check kind (the only structural rule needed for `NoResultCheck`, since it has no parameters of its own and `Severity` is already covered by deserialization). `Backends/Python/PythonHardeningLiteral.BuildContext` builds the one Scriban context object (`hardening.*`, an `enabled` flag plus a `checks_literal` Python list-of-dicts) every one of the six templates renders from, mirroring `PythonProxyLiteral` exactly. `Backends/Python/PythonScriptVerifier` treats the generated script's dedicated `EXIT_HARDENING_FAILED` (2) exit code as compatible with success the same way it already does `EXIT_MISSING_ENV_VAR` (78) — unlike Proxy's own case, hardening's check always runs *after* the output file is written, so there's no "nothing to verify yet" short-circuit needed on top of that.
- **Script hardening: per-field null-rate check** (Issue #130): `NullRateCheck : HardeningCheck` (`"kind": "nullRate"`) adds `FieldName` and `Threshold` (a fraction, 0.0-1.0, *not* a 0-100 percentage — the extension's own UI collects a percentage and divides by 100 before sending it, see the Browser Extension section above) — catches a field whose selector quietly starts matching the wrong thing (still returns a value, always empty) even though the overall row/element count `NoResultCheck` watches stays healthy. Unlike `NoResultCheck`, more than one `NullRateCheck` is expected (one per monitored field), so `ScrapingPlanValidator`'s "duplicate kind" rule is relaxed to a "duplicate `FieldName`" rule for this kind specifically, plus its own `FieldName`-non-blank and `Threshold`-in-`[0,1]` checks. `FieldName` is matched at runtime **globally by name**, not scoped to whichever parent group/container instance it's nested under — a deliberate simplification resolving the issue's own "open design question" about container/API-tree mode (where a field can repeat arbitrarily deep): a flat row's dict key for flat/API-flat shapes, or every element sharing that tag name anywhere in the built output tree for container/API-tree shapes (`root.iter(field)`), rather than a rate computed separately per parent group. `Backends/Python/PythonHardeningLiteral.RenderCheck` renders the extra `"field"`/`"threshold"` keys (via the existing `PythonLiteral.Num` for the threshold, same shortest-round-trippable-form rendering `ApiBodyLiteral.NumberValue` already uses).
- **Script hardening: baseline-drop check** (Issue #131): `BaselineCheck : HardeningCheck` (`"kind": "baseline"`) adds only `DropThreshold` (a fraction, same 0.0-1.0 convention as `NullRateCheck.Threshold`) — catches a gradual drop in result volume (e.g. a broken "load more"/pagination selector quietly losing entries) that neither `NoResultCheck` (only fires at exactly zero) nor `NullRateCheck` (only watches one field) would ever trip. Unlike `NullRateCheck`, only one `BaselineCheck` ever makes sense, so `ScrapingPlanValidator`'s existing duplicate-kind rule applies unchanged (no exemption needed), plus its own `DropThreshold`-in-`[0,1]` check. The *previous run's own result count* is deliberately **not** part of this wire type at all — it's runtime-only state the generated script tracks for itself in a small sidecar JSON file next to its own output (see the Python Templates section below), not something the companion needs to know about or persist; this was a deliberate choice over reusing `ChangeDetectionConfig`'s (Issue #87) own "compare against the previous output" mechanism, since that one unconditionally diffs the *entire* output file's content on every run, whereas Baseline only ever needs one integer and — critically — must only update after a run that didn't itself hard-fail, so a bad run's own low count never becomes the new normal for the next comparison (a materially different update rule). `PythonHardeningLiteral.BuildContext` gains a `has_baseline` flag (`list.Any(check => check is BaselineCheck)`) alongside the existing `enabled`/`checks_literal`, since this is the first hardening check needing its own on-disk state between runs — the templates use it to gate their sidecar-file helpers and `import json`.
- **Script hardening: blocking-detection check** (Issue #132): `BlockingCheck : HardeningCheck` (`"kind": "blocking"`) adds two optional parameters, `MinBodyLength` (an `int?` byte-length threshold; `null` disables the signal) and `BlockPhrases` (a `List<string>?` of case-insensitive substrings; `null`/empty disables the signal) — catches a site that starts blocking the script (rate-limiting, IP ban, CAPTCHA wall, redirect to a login page) while still responding with a normal-looking HTTP 200, which neither `NoResultCheck` nor `NullRateCheck` would necessarily catch if the blocked response still contains enough markup to produce a non-empty result. A third signal — the final response's host differing from the requested URL's host, i.e. a cross-origin redirect — needs no parameter at all and is always evaluated; this is the concrete, deterministic resolution of the issue's own vaguer "doesn't match the requested URL's origin/path shape" phrasing (deliberately *not* a hardcoded path-pattern list like `/login`/`/blocked` — too fragile/false-positive-prone across arbitrary sites, and not something the issue asked to be configurable). Unlike `NullRateCheck`, only one `BlockingCheck` ever makes sense, so `ScrapingPlanValidator`'s existing duplicate-kind rule applies unchanged; `MinBodyLength` must be positive when set, and every `BlockPhrases` entry must be non-blank — there's no "at least one signal configured" requirement, since a `BlockingCheck` with both fields unset still meaningfully checks the always-on redirect signal. Unlike `BaselineCheck`, this evaluates the *raw* response (final URL, body length, body text) captured at request time, not the already-extracted data/output tree — see the Python Templates section below for how each engine captures that snapshot from whatever "response" concept it actually has.
- **Script hardening: required-fields check** (Issue #133): `RequiredFieldsCheck : HardeningCheck` (`"kind": "requiredFields"`) adds `FieldNames` (`List<string>`, required, non-empty) — structurally different from its four siblings, which are all post-hoc aggregate checks evaluated once *after* scraping and never change what gets written: this one is a per-row *filter* that runs *before* the output file is finalized, dropping any row missing a non-empty value for any of `FieldNames` entirely (rather than writing it with a blank cell), serving the issue's own "safe for DB import" motivation (e.g. a `NOT NULL` database column that would otherwise silently break on import). The filtering itself always happens regardless of `Severity` — only whether the *run* is flagged as failed afterward depends on it, so an all-`Warning` configuration still guarantees the output file never contains a row missing a required value, without necessarily failing the whole run. Supported for flat-shaped output (`Fields`/flat mode, Api-mode's flat `ItemsPath`/`Fields` shape), container mode, and — since Issue #204 — Api-mode's tree shape (`Groups`) too; `ScrapingPlanValidator` no longer rejects any mode/shape combination for this check (see container mode's own resolution of the "no flat row" ambiguity below, and Api-mode's follow-up applying the identical mechanism). Only one `RequiredFieldsCheck` ever makes sense, so the existing duplicate-kind rule applies unchanged; `FieldNames` must be non-empty with no blank or duplicate entries.
- **Script hardening: required-fields check, container mode** (Issue #133 follow-up): container mode has no flat "row" the way flat mode does, so `FieldNames` is matched *globally by tag name anywhere in the built output tree* instead — the same simplification `NullRateCheck` already established for this exact ambiguity (see its own doc comment). What actually gets dropped when a match is empty is the *nearest enclosing repeating group instance*: the runtime's `extract_group()` walker (`scraper_grouped.py.j2`/`playwright_scraper_grouped.py.j2`) already builds each repeating instance bottom-up before deciding whether to append it to its parent, so checking "does this instance's own subtree contain an empty required field" at exactly that point naturally drops whichever nesting level actually contains the problem — an inner repeating group's own bad instance is dropped without disturbing its outer container or any sibling instance — with no need to track "nearest repeating ancestor" as separate schema metadata. A required field with no repeating ancestor above it (or only non-repeating ancestors) has no "instance" to drop, so it's simply left as an empty element — a deliberate, documented limitation, not a bug. Api-mode's tree shape got the identical treatment in a later follow-up — see Issue #204 below.
- **Script hardening: required-fields check, Api-mode tree shape** (Issue #204): applies the exact same "nearest enclosing repeating group instance" mechanism to `ApiGroup`/`ApiField` (the JSON-path tree, Issue #54) that the container-mode follow-up above already established for `ContainerNode`/`DataFieldNode` (the CSS-selector tree) — `ScrapingPlanValidator` no longer rejects `RequiredFieldsCheck` combined with `ApiConfig.Groups`. Unlike `GroupNode.Repeating`, `ApiGroup` has no explicit repeating flag at all (see Architecture Decision #6) — whether a given group instance is actually droppable is re-derived at runtime in `scraper_api_grouped.py.j2`'s `_extract_api_group()` (`_is_repeating_instance`, computed via the same "did `Path` resolve to a JSON array" check `_resolve_items` itself already uses internally) rather than read off a stored flag, so an object-rooted (non-array) group's own single, structurally-expected instance is left in place with an empty field, exactly like container mode's own non-repeating-ancestor case — never dropped just because *some* required field inside it happens to be empty. `PythonHardeningLiteral`'s serialization needed no change (`checks_literal` was already built once and shared by every template regardless of shape). Covered by real end-to-end tests analogous to the container-mode ones above, including a two-levels-deep nested-groups case and a dedicated case proving a non-repeating group's instance is *not* dropped.

- **Persistent session/cookie handling** (Issue #175): `ScrapingConfig.PersistentSession` (`bool?`, optional/additive) is Browser-engine only — unlike Proxy/ChangeDetection/Hardening, it has no sub-fields of its own (a plain on/off switch, not a wrapper object), so it needs no dedicated `IR/*Config.cs` type. `ScrapingPlanBuilder` carries it through to `ScrapingPlan.PersistentSession` (a plain non-nullable `bool`, `config.PersistentSession ?? false`) unchanged in all three shape branches; `ScrapingPlanValidator` rejects `PersistentSession == true` combined with any engine other than `Browser`, the same placement/style as the existing `WaitForStep`/`FillStep`/`ClickStep`/`ScrollStep` `browserOnlySteps` gate (this is a plan-level flag rather than a step type, so it can't literally join that gate, but the reasoning and error style match). `Backends/Python/PythonPlaywrightCodeGenerator` is the only code generator affected (Static/API codegen and templates are completely untouched by this feature) — it now separately renders the Navigate step's own fragment (`navigate_action`) from the rest of the action sequence (`login_actions`: WaitFor/Fill/Click/Scroll, minus Navigate, re-indented one level deeper via a small `IndentLines` helper) alongside the existing combined `actions` string (used unchanged when the feature is disabled, so a disabled config's generated script stays byte-for-byte what it was before this existed). Both `playwright_scraper.py.j2` and `playwright_scraper_grouped.py.j2` (Browser-engine flat/container shells) gain, when enabled: a `SESSION_STATE_PATH = OUTPUT_PATH + ".session-state.json"` sidecar-file constant (the same `OUTPUT_PATH + "..."` naming convention `BaselineCheck`'s own sidecar already established) with a code comment warning it contains live session cookies; in `scrape(url)`, `browser.new_context(storage_state=SESSION_STATE_PATH if _session_exists else None)` + `context.new_page()` in place of the always-fresh `browser.new_page()`; the rendered `login_actions` wrapped in `if not _session_exists:` (only emitted at all when there's at least one login-only action to guard — an empty `if` body would be a Python `SyntaxError`, so a `has_login_actions` flag gates the whole block, not just its condition); and `context.storage_state(path=SESSION_STATE_PATH)` saved right before `browser.close()`, refreshing the file after every run regardless of whether it already existed. `/generate`'s own trial-run verification (`PythonScriptVerifier`) needs zero special-casing: its temp directory is always fresh, so a persistent-session-enabled config's trial run naturally takes the same "no saved session yet, run the full login flow" path a login-only config already takes today — the Consistency Rule holds without any extra plumbing.
- **External XML config file for re-editable script parameters** (Issue #178): `ScrapingConfig.ExternalConfig` (`bool?`, optional/additive) is mode-independent — like `PersistentSession`, a plain on/off switch with no sub-fields, needing no dedicated `IR/*Config.cs` type, since which values are editable is a structural property of the current mode/shape rather than something the caller configures. `ScrapingPlanBuilder` carries it through to `ScrapingPlan.ExternalConfig` (`config.ExternalConfig ?? false`) unchanged in all three shape branches; no `ScrapingPlanValidator` rule is needed (a bare bool has no invalid state). `Backends/Python/PythonExternalConfigLiteral.BuildContext(bool)` builds the one Scriban context object (`external_config.enabled`) every one of the six templates renders from — unlike `PythonProxyLiteral`/`PythonChangeDetectionLiteral`, this is the only field it carries, since everything else (the XML schema, self-bootstrapping, validation) lives entirely in the runtime template code below rather than being server-computed. **Scope, resolving the issue's own open questions**: the sidecar *overrides only what's actually present* in the file (partial config, never a wholesale replacement) — the start URL(s)/`AdditionalUrls` and the output filename for Fields/Groups mode (not Api, which builds its own request URL and never reads a start URL to begin with, the same exclusion `AdditionalUrls`/`Pagination` already established), plus flat mode's own field names (rename the output column, not the underlying selector) and Api-mode's `StaticListSource.Values` lists, referenced by parameter name. Container-mode's own group/field names and Api-mode's tree shape (`Groups`) are **not** editable this way (yet) — mapping a nested tree onto a flat-ish XML structure was flagged as a genuinely open design question in the issue itself, so it's deliberately left for a future follow-up rather than guessed at here, the same "ship the simpler shape first" pattern `RequiredFieldsCheck` (Issue #133) already used for container mode. A missing sidecar file is not an error — see the Python Templates section below for the self-bootstrap/validation mechanics that make this true at the script level, not the companion's.

- **Combined mode: wire format and code generation** (Issue #239, follow-up to #181's discovery process — see that issue's own note that #239 doesn't match any of its three listed candidate approaches): `ScrapingConfig.Combined` (`List<CombinedComponentConfig>?`) is a fourth, mutually-exclusive alternative to `Fields`/`Groups`/`Api` — each `CombinedComponentConfig` (`IR/CombinedComponentConfig.cs`) carries an optional `Name` (the merge key, blank defaults to `component_{index}`), a `required ScrapingConfig Config` (a fully independent, standalone config — its own `Url`/mode/engine/browser actions/proxy/hardening/etc., completely untouched), an optional per-component `VerificationValues` (mirroring the outer, single-mode `ScrapingConfig.VerificationValues` field exactly, but scoped to this one component's own `FillStep`s, since `BrowserActions` — and therefore which env var names are even meaningful — lives on each component's own `Config`, not on the outer `Combined` request), and an optional `SavedConfigId`, carried through purely for the extension's own round-tripping (Issue #141's "Load" for a saved Combined configuration) and never read during generation. Nesting (`Config.Combined` set on a component) is rejected — see `Program.cs`'s `/generate` handler in the Companion App section above for the full validation/orchestration story.
  `ScrapingPlan.With(OutputFormat, string outputFileBaseName)` is a small new method (`IR/ScrapingPlan.cs`) used to force each component's *already-built, already-validated* plan to `Json`/a fixed output name — a plain object-initializer copy rather than a C# `with` expression, since `ScrapingPlan` (like `ScrapingConfig`) is a `sealed class`, not a record.
  `Backends/Python/PythonCombinedScriptGenerator` is the actual code generator for the wrapper script — deliberately **not** registered via `LanguageModuleRegistry`/`ICodeGenerator` the way every other backend in `Backends/Python` is, since it needs to *consume* other generators' already-rendered output (one already-complete script per component) rather than being discovered alongside them; giving it a `LanguageModuleRegistry` reference through the registry's own reflective, zero-args-constructor discovery would be circular (the registry would need to fully construct itself before it exists to hand out). `Program.cs` instead resolves and generates each component's own script through the registry directly — exactly like an ordinary single-mode request would — and only hands the finished `(name, script)` pairs to `PythonCombinedScriptGenerator.Generate(...)`, which renders the new `scraper_combined.py.j2` template (see the Python Templates section below for the runtime side).
  **Why embed-and-subprocess whole component scripts, rather than inlining each component's own extraction logic into one Scriban-rendered file the way container mode's group tree or API mode's response tree are inlined**: Scriban has no cross-template includes/recursion (a constraint repeated throughout this file — see e.g. `scraper_grouped.py.j2`'s own doc comment), and unlike a single, structurally-uniform tree walk, a Combined component's own logic can be radically different in *kind* per component (`requests`+`BeautifulSoup` vs. Playwright vs. a plain JSON API call, each with entirely different imports/control flow, not just different selector configuration run through one shared function) — reusing each component's own already-existing, already-tested single-mode template output via a subprocess call, rather than re-implementing all of static/browser/API extraction inline a second time, keeps this feature's own template surface small and avoids duplicating logic that already exists and is already covered by every other issue's own tests.

- **Blocks mode: wire format, `ScrapingPlan`, and code generation** (Issue #182): `ScrapingConfig.Blocks` (`List<ExtractionBlockConfig>?`, `IR/ExtractionBlockConfig.cs`) is a fourth, mutually-exclusive alternative to `Fields`/`Groups`/`Api`/`Combined` — solves a different problem than Combined mode (distinct output *shapes* from *one* page, not merging *already-separate* configurations/sites): each block carries an optional `Name` (blank defaults to `block_{index}`), exactly one of `Fields`/`Groups` (validated per-block in `Program.cs`, since `ScrapingPlanBuilder` needs to already know each block's shape before it can build anything), an optional `OutputFileName` (blank falls back to the sanitized block name) and `OutputFormat` (null = shape default, same Csv-for-flat/Xml-for-Groups rule the single-shape case follows, but honored as an *explicit* override here even for Csv/Xml — not just Json — since every block is independent, unlike the single outer `OutputFormat` the single-shape case compares against), and its own `ChangeDetection`/`Hardening` (per-block, since each block produces its own independent result set — unlike `Pagination`, which stays outer-level because it governs the *shared* page-fetching loop every block extracts from, not any one block's own cadence). Unlike Combined mode, Blocks mode is still just **one** `ScrapingPlan`/one script: `ScrapingPlanBuilder.Build` gains an `ExtractionBlockStep` branch (a new `IR/ScrapingStep.cs` step type, mutually exclusive with `ExtractGroupStep`/`ApiCallStep`/flat `ExtractStep`s, carrying `List<PlanExtractionBlock>` — the plan-level, already-resolved counterpart to `ExtractionBlockConfig`, with `Name`/`OutputFileBaseName`/`OutputFormat` already computed) that resolves each block's shape/name/output filename the same way the whole plan does for the single-shape case, just once per block; `ScrapingPlanValidator` gains a matching `ExtractionBlockStep` branch validating the block list itself (`>= 2` blocks, unique `Name`/`OutputFileBaseName` — two blocks silently overwriting each other's output would defeat the point) and reuses the *existing* per-shape/per-cross-cutting-config validators (`ValidateContainerNodes`, `ValidateChangeDetection`, `ValidateHardening`) looped per block, rather than duplicating their logic.
  `Backends/Python/PythonExtractionBlockLiteral` serializes the resolved block list into one Python list-of-dicts literal, `BLOCKS` — each block embeds its own shape (flat `selectors`/`attributes`/`transforms`/`frame_paths` dicts built inline, mirroring how `PythonCodeGenerator`'s own `fields` context feeds `scraper.py.j2`'s Scriban loop, just pre-rendered to Python source instead; or a `PythonGroupTreeLiteral`-built group tree, exactly like single-shape Container-Mode's own `GROUPS`) plus its own output path/format and its own `hardening`/`change_detection` dicts, reusing `PythonHardeningLiteral`/`PythonChangeDetectionLiteral`'s existing `BuildContext` `*_literal` fragments verbatim via `dynamic` (their `BuildContext` methods return an anonymous type, internal to the assembly but accessible via the DLR from another class in the same assembly) rather than re-deriving them a second time. `PythonCodeGenerator`/`PythonPlaywrightCodeGenerator` each gain an `ExtractionBlockStep`-presence branch (checked alongside the existing `ExtractGroupStep` branch) picking a new, dedicated template — `scraper_blocks.py.j2`/`playwright_scraper_blocks.py.j2` — over the single-shape ones, passing `blocks_literal` plus a handful of `any_*`/`hardening_any`/`change_detection_any` aggregate flags (computed by `.Any()`-scanning the block list) that gate imports/helper-function definitions the same way `hardening.enabled`/`change_detection.enabled` already do for the single-shape templates, just OR'd across every block instead of reading one shared flag.
- **Output Blueprints: wire format and application** (Issue #191): `IR/OutputBlueprintMapping.cs` — `OutputBlueprintMapping` (`BlueprintId` — carried purely for the extension's own round-tripping, mirroring `CombinedComponentConfig.SavedConfigId`; `/generate` never itself queries the blueprint store — plus a `List<OutputBlueprintFieldMapping>`), `OutputBlueprintFieldMapping` (`TargetField`/`SourceField`). Added to `ScrapingConfig`/`ScrapingPlan`, carried through by `ScrapingPlanBuilder` unchanged only in the flat-`Fields` and Api-flat branches (`null` elsewhere, mirroring how `AdditionalUrls`/`Pagination` are similarly excluded from the Api branch). `ScrapingPlanValidator`'s `ValidateOutputBlueprint` requires at least one field mapping, a non-empty target/source per entry, every `SourceField` to reference a real available field name (flat: `ExtractStep.Name`; Api-flat: `ApiField.Name` — parameters are deliberately not mappable, the same exclusion the hardening null-rate/required-fields field pickers already apply), and no duplicate target or source field. `Backends/Python/PythonOutputBlueprintLiteral` renders it into a `[{"target": ..., "source": ...}, ...]` Python list-of-dicts literal, mirroring `PythonFieldTransformLiteral`.
- **Output Blueprints: container/API-tree mode flattening** (Issue #192): a mapping applied to a tree (container mode's `GroupNode`/`DataFieldNode`, or Api mode's `ApiGroup`/`ApiField`) doesn't rename tags in place — it *flattens* the tree into denormalized rows: one row per instance of the single repeating group every mapped field's own ancestor chain shares, with any higher-level mapped field (outside that repeating group, e.g. a category name next to a repeating list of items) copied into every row generated beneath it, so it's never written only once. Mapped fields spanning more than one independent repeating branch (no single row layout could include both without either a cross-product or dropping data) is rejected rather than guessed at. New `IR/OutputBlueprintFlattening.cs` (`ResolveContainerRowScope`) resolves this — or rejects it — for Container-Mode specifically, since `GroupNode.Repeating` is an explicit, config-time-known flag there; `ScrapingPlanValidator`'s `ExtractGroupStep` branch calls it and rejects an ambiguous mapping with a `400` before any script is generated, the same generate-time-safety-net role it already plays for a blank/duplicate field name. `ScrapingPlanBuilder` forces the flat output formats (`Csv`, or `Json`'s flat array) instead of `Xml`/tree-`Json` whenever a blueprint mapping is active for either tree shape — the same "explicit override wins" pattern Issue #86's own `Json` request already established over the tree-forcing default. Api mode's tree shape has no static equivalent of `OutputBlueprintFlattening` at all: `ApiGroup` has no `Repeating` flag (Architecture Decision #6), so the identical ambiguity check is re-derived dynamically instead, inside the generated script itself (`scraper_api_grouped.py.j2`, see the Python Templates section below) — it surfaces as an ordinary `422` trial-run verification failure rather than a `400` here. `CollectContainerFieldNames`/`CollectApiFieldNames` (new private helpers in `ScrapingPlanValidator`) extend the existing `ValidateOutputBlueprint`'s "must reference a real field" check to both tree shapes — leaf field names only (`DataFieldNode`/`ApiField`), the same leaf-only scope the extension's own `collectFieldNames` picker already offers for these modes.
- **Output Blueprints: nested/"containered" target schema** (Issue #244): a second, tree-shaped Output Blueprint target schema alongside #191/#192's flat one — new `IR/OutputBlueprintTreeSchema.cs` (`OutputBlueprintTreeSchemaGroup`/`OutputBlueprintTreeSchemaField`, a structural-discriminator `List<ContainerNode>`-style converter, `OutputBlueprintTreeSchemaValidator`) is the *persisted*, site-independent target shape — deliberately its own small node type rather than reusing `ContainerNode`/`ApiNode`: a blueprint's target schema has no CSS selector/JSON path/engine concept at all, just a name and nesting. Deliberately **no explicit `Repeating` flag** on a target group either, the same "inferred, not chosen" reasoning Architecture Decision #6 already established for `ApiGroup` — a user designing a reusable, site-independent target schema has no source tree in front of them yet to decide repeating-ness against; whether a target group ends up producing one or many instances is entirely derived later, at mapping-resolution time, from what its own mapped fields' common source ancestor turns out to be. `OutputBlueprintMapping` (the *per-scrape*, `/generate`-time wire type) gains `SchemaKind` (`OutputBlueprintSchemaKind`: `Flat`/`Tree`, defaulting to `Flat` for wire-compatibility with a pre-#244 request) and a `Tree` payload (`OutputBlueprintTreeMappingNode`: `OutputBlueprintTreeMappingGroup`/`...Field`, mirroring the persisted schema node-for-node with one addition — each leaf carries the `SourceField` it resolves to for this particular scrape, exactly like `OutputBlueprintFieldMapping.SourceField` does for the flat shape); `Fields` was relaxed from `required` to nullable to make room for this second, mutually-exclusive payload. Which SOURCE GROUP a given target group's own instances are drawn from is deliberately **not** part of this wire shape at all — it's re-derived purely from the leaf `SourceField` mappings, the same "inferred from the mapped fields, never chosen directly" reasoning #192's own row-scope resolution already established.
  `OutputBlueprintFlattening.ResolveContainerTreeRowScopes` generalizes `ResolveContainerRowScope` (unchanged, still used for the Flat schema) to resolve **one row scope per target GROUP node, recursively**, instead of one shared row scope for the whole mapping: for a given target group, it collects the source chains of only the LEAF fields mapped *directly* beneath it (not through a nested target group, which gets its own independent resolution) and resolves them via the exact same `ResolveChain` helper the flat case already uses — reused as-is, just invoked per target-group-subtree instead of once for the whole tree. A child target group's own resolution additionally has to agree with its parent's: every direct leaf's own chain must either be empty (a "broadcast" field with no repeating source ancestor at all, exactly like the flat case's own broadcast fields) or have the parent's own resolved chain as a literal prefix — a chain that diverges before reaching that depth means the field is nested under the wrong target group entirely, and is rejected with a `400` (`ScrapingPlanValidator`'s `ExtractGroupStep` branch, calling the new method instead of the old one whenever `OutputBlueprintMapping.SchemaKind == Tree`). This is the mechanism that actually resolves #244's own reason for existing: two independent/sibling source repeating groups, each placed under a *different* target branch, now resolve independently and cleanly instead of hitting the flat mapping's "spans more than one independent repeating group" rejection — the target tree's own nesting is the disambiguation. Api mode's tree shape still has no static equivalent (`ApiGroup` has no `Repeating` flag, Architecture Decision #6) for the same reason the Flat schema's own ambiguity check doesn't either — the per-target-group version of that same runtime mirror lives in `scraper_api_grouped.py.j2` instead (see the Python Templates section below), surfacing as an ordinary `422` rather than a `400`.
  `ScrapingPlanBuilder`'s existing "an active blueprint mapping forces the flat output formats" override (Container-Mode/Api-tree, from #192) now only fires for a **Flat**-schema mapping — a **Tree**-schema mapping produces a real nested structure of its own, so it keeps the ordinary tree-shape formats (`Xml`, or tree-`Json`) exactly as an unmapped tree response already would; `ScrapingPlanValidator`'s per-shape `ValidateOutputBlueprint` (Flat) vs. the new tree-node-walking validator (leaf `SourceField` existence + non-blank names, recursively) is chosen by `SchemaKind`, and a `Tree`-schema mapping is rejected outright (`400`) against flat-shaped output (plain `Fields`, or Api's flat `ItemsPath`/`Fields` shape) — there's nothing for a tree target to nest against there. `Backends/Python/PythonOutputBlueprintLiteral.RenderTree` is the tree-shaped counterpart to the existing flat `Render`, mirroring `PythonGroupTreeLiteral`'s own nested list-of-dicts layout (group: `{"name", "children"}`, leaf: `{"name", "source"}`) — all three tree-shape code generators now emit both `blueprint_mapping_literal` (Flat) and the new `blueprint_tree_mapping_literal` (Tree), gated on `SchemaKind` so exactly one is ever non-empty for a given plan.

### Python Templates (`language-modules/python/templates/`)
- Scriban templates (the `.j2` file extension is a historical artifact — the syntax is Scriban, not Jinja2)
- `scraper.py.j2`: a monolith for the static engine (`PythonCodeGenerator`) — a declarative dict approach (SELECTORS/ATTRIBUTES), no step-by-step composition needed
- `playwright_scraper.py.j2` + `playwright_navigate_step.py.j2` + `playwright_wait_step.py.j2` + `playwright_fill_step.py.j2` + `playwright_click_step.py.j2`: for the browser engine (`PythonPlaywrightCodeGenerator`) — Navigate/WaitFor/Fill/Click steps are each rendered as their own fragment per step type and inserted into the shell in order, because (unlike Extract) each corresponds to one concrete action at a fixed point in the flow. `FillStep` values are never written into the script as a literal — they're always read at runtime via the shared `_require_env(name)` helper (`import os` is only added when a `FillStep` is actually present). A missing (not just empty) credential env var no longer surfaces as a raw, unhandled `KeyError` traceback — `_require_env` prints a clean English error naming the missing variable and exits via the same `EXIT_MISSING_ENV_VAR` (78) sentinel Proxy uses below, instead of the default `1` from an uncaught exception (Issue #88 follow-up, prompted by exactly this confusing traceback surfacing through `/generate`'s error response). Unlike Proxy, this is still a hard stop — a login flow genuinely can't continue without its credential — but `PythonScriptVerifier` surfaces the clean stderr message as the error instead of the generic "script did not produce output.csv" it would otherwise fall back to
- `scraper_grouped.py.j2` (static) + `playwright_scraper_grouped.py.j2` (browser): for container mode. The group tree is not reproduced as Scriban recursion (Scriban has no cross-template recursion) — instead, `Backends/Python/PythonGroupTreeLiteral` builds it as a nested Python dict/list literal (`GROUPS = [...]`) and inserts it into the template verbatim; a generic `extract_group()` function in the template walks the tree at runtime — identical between the two templates except for the two DOM-access calls (`select`/`select_one` vs. `query_selector_all`/`query_selector`). Output is `output.xml` (`xml.etree.ElementTree`; multiple root groups are combined under an `<Ergebnis>` wrapper)
- `scraper_api.py.j2` (API mode, `PythonApiCodeGenerator`): no BeautifulSoup needed for an ordinary live API call (just `requests` + `itertools.product`, conditionally imported alongside `json`/`bs4` only when `EmbeddedJsonSource` is set — see Issue #136 below), plus a minimal JSON-path DSL (dot notation for object keys, `[*]`/`[n]` for arrays) for per-record field extraction. Discovery sources resolve their values via an extra request; range sources (ISO week/number/date) are parsed/rendered against the `Format` mini-template (`_parse_range_value`/`_render_range_value`, mirroring `RangeFormat` on the companion side). A `404` response for a single parameter combination is skipped instead of aborting the run. Auth headers configured via `EnvironmentVariableName` are, like `FillStep`, never written as a literal — they're read via `os.environ[...]`. Output is `output.csv`, with parameter values as extra columns. `METHOD`/`BODY` (Issue #55) control whether `scrape()` sends a `requests.post(..., json=body)` with a rendered request body (`_render_body`/`_coerce_body_value`) instead of a plain `requests.get(...)` — see the Compiler section above
- `scraper_api_grouped.py.j2` (API mode, nested responses, Issue #54): the tree-shaped counterpart to `scraper_api.py.j2`, picked instead of it whenever `ApiConfig.Groups` is set. Reuses `scraper_api.py.j2`'s existing `_resolve_items()`/`_resolve_field()` JSON-path helpers unchanged — `_resolve_items()`'s "N instances if the resolved value is a list, else at most one" semantics already match `ApiGroup`'s own inferred repeating-ness — and adds a generic `_extract_api_group()` walker, exactly mirroring `scraper_grouped.py.j2`'s `extract_group()` for container mode's CSS-selector tree. Output is `output.xml` instead of `output.csv`; multiple root groups (and results accumulated across every parameter combination) are combined under the same `<Ergebnis>` wrapper container mode already uses. Also gains `METHOD`/`BODY` support (Issue #55), identical to `scraper_api.py.j2`'s own — response shape (flat/tree) and request method/body are fully orthogonal
- **API mode: embedded JSON source** (Issue #136): both API templates gain, when `EMBEDDED_JSON_SOURCE` is set, a conditional `from bs4 import BeautifulSoup`/`import json` and an `_extract_embedded_json(response)` helper (`BeautifulSoup(response.text, "html.parser").select_one(EMBEDDED_JSON_SOURCE["scriptSelector"])` → `json.loads(tag.string)`) used in `scrape()` in place of `response.json()` at the one call site each has — everything downstream (`_resolve_items`/`_resolve_field`/`_extract_api_group`, transforms, hardening, change detection, output writers) is unchanged, since it already operates on "whatever JSON `data` ended up being" regardless of source. A missing `<script>` tag or unparseable content raises a clear `RuntimeError` naming the configured selector, rather than a raw `AttributeError`/`JSONDecodeError` traceback
- **Multiple start URLs** (Issue #83): `scraper.py.j2`/`playwright_scraper.py.j2` and `scraper_grouped.py.j2`/`playwright_scraper_grouped.py.j2` each gain a `URLS` list constant (from `NavigateStep.Urls`) instead of a single `URL` string. The two flat templates' `main()` loops over it, combining every URL's rows into one `data` list before writing the output file; the two grouped templates' `main()` wraps a single combined `<Ergebnis>` root and appends every URL's own `scrape(url)` children into it — reusing the exact sibling-merging pattern already used for multiple root groups from one URL. `scraper_api.py.j2`/`scraper_api_grouped.py.j2` are untouched — API mode builds its request URL from `URL_TEMPLATE` and never had a `URL`/`URLS` constant to begin with. Fixes a latent bug surfaced by this change: `playwright_navigate_step.py.j2` used to bake the target URL in as a literal (`page.goto("...")`), ignoring `scrape(url)`'s own parameter entirely — it now emits `page.goto(url, ...)`, which is what makes per-URL looping possible for the Browser engine at all (the Static engine's `scrape(url)` already used its parameter correctly)
- **Pagination** (Issue #174): the four non-API templates (`scraper.py.j2`, `playwright_scraper.py.j2`, `scraper_grouped.py.j2`, `playwright_scraper_grouped.py.j2`) restructure `scrape(url)` into a loop instead of a single fetch/extract — page 1 is today's existing logic unchanged, and (when `pagination.enabled`) each further page's URL is either the current page's own `NEXT_LINK_SELECTOR` match's `href` (resolved via `urljoin`/Playwright's `page.url`, both engines alike) or `PAGINATION_URL_TEMPLATE.format(url=url, page=page_number)`. Stops when a page yields no rows/elements, `PAGINATION_MAX_PAGES` is reached, or (next-link kind) the selector no longer matches — when pagination isn't configured, the loop still runs but exits unconditionally after one iteration, byte-for-byte the same single-fetch behavior as before this existed. The two static templates factor the per-page extraction into a new `_extract_page_rows(soup)`/inline element-count check (previously the whole body of `scrape()`); the two Playwright templates keep the **same** browser/page session across paginated pages (`page.goto` for page 2+) instead of relaunching — the full `{{ actions }}` sequence (Navigate/WaitFor/Fill/Click/Scroll, e.g. a login flow) still runs only once, for page 1. The container-mode templates accumulate every paginated page's elements into one shared `<Ergebnis>` root spanning the whole chain from that start URL, so `main()`'s own multi-URL merge loop needs no changes at all. `scraper_api.py.j2`/`scraper_api_grouped.py.j2` are untouched — Api mode has its own `RangeSource(Number)` mechanism and never reads `NavigateStep`/`pagination` at all.

- **Combined mode** (Issue #239): a new, seventh template, `scraper_combined.py.j2` — the only one of the seven not generated by an `ICodeGenerator` implementation (see the Compiler section above for why `PythonCombinedScriptGenerator` renders it directly instead). At runtime, `_run_component(component)` decodes and writes that source to `component.py` inside a **stable** subdirectory next to the combined script's own file — `os.path.join(os.path.dirname(os.path.abspath(__file__)), f"{OUTPUT_FILE_BASE_NAME}_components", component["name"])`, created once via `os.makedirs(..., exist_ok=True)` and reused on every subsequent run — deliberately **not** `tempfile.TemporaryDirectory()`, which was the first design considered: a component enabling `PersistentSession`'s saved login cookies, `ExternalConfig`'s user-editable XML, or the `BaselineCheck` hardening counter all write their own sidecar file relative to their own script's file path (see each feature's own entry above), so those sidecars only actually persist across separate runs of the *combined* script if the component's own `component.py` lives at a stable path run to run — a fresh temp directory every time would silently reset all three to "nothing here yet" on every single execution, without the combined script or its own saved-configuration components ever indicating anything was wrong. `subprocess.run([sys.executable, "component.py"], cwd=component_dir, ...)` passes no explicit `env=`, so the child inherits the combined script's own full process environment — the mechanism (documented in the Companion App section above) that lets both a component's own `Proxy` env-var list and the merged one-time `VerificationValues` `PythonScriptVerifier` injects into the *outer* trial-run subprocess reach every inner per-component subprocess automatically, with no per-component environment plumbing anywhere in this template. A component's own exit code `0`/`78`/`2` (`COMPATIBLE_EXIT_CODES`, mirroring `PythonScriptVerifier.MissingEnvVarExitCode`/`HardeningFailedExitCode` — the same "two independent copies of one constant" duplication this codebase already accepts between C# and every Python template's own `EXIT_MISSING_ENV_VAR`/`EXIT_HARDENING_FAILED`) is treated as "this component produced usable output" (printing a `WARNING:` to stderr for the latter two); any other exit code, a missing `output.json`, or — critically — an *empty* result (`if not data: raise RuntimeError(...)`, since a component whose selector quietly starts matching nothing would otherwise merge in silently as an empty array/object under its own name, exactly the class of failure this whole mechanism exists to catch) aborts the entire combined run, naming which component failed. `main()` merges every component's own already-parsed JSON into one object keyed by component name (`{"componentName": [...], ...}`) and writes it to `OUTPUT_PATH` — a JSON *object* root regardless of whether any individual component's own shape was flat or tree, which `PythonScriptVerifier.VerifyJsonOutput`'s existing tree-shape handling (originally written for container/API-tree mode) already recognizes generically, needing no companion-side changes at all.
- **Blocks mode** (Issue #182): two new templates, `scraper_blocks.py.j2` (Static engine) and `playwright_scraper_blocks.py.j2` (Browser engine) — unlike Combined mode's `scraper_combined.py.j2` above, these render **in-process**, sharing one navigation/browser session across every block rather than subprocessing N separate scripts (see the Compiler section's own "why embed-and-subprocess" bullet for Combined mode — the reasoning is inverted here: Blocks mode's whole premise is one shared page load/session, N extraction+write phases against it, so subprocess isolation would be actively wrong — re-navigating/re-running browser actions per block, risking a non-idempotent action like a login-form submission running more than once). Both templates restructure `main()`'s existing "one shape, one write call" shape into a loop over `BLOCKS`: `scrape(url)` (static) / `scrape(url)`'s inner Playwright `while True` page loop (browser) calls a generalized `_extract_flat_block(block, soup_or_page)` or the tree-walking `extract_group(scope, node, required_field_names, block_name)` per block on every fetched page (mixing shapes freely — a page's own single fetch feeds both a flat block and a group block alike), accumulating results per block name; pagination stops only once *every* block's own extraction yielded nothing new on a page, not per-block. `main()` then writes each block's own output file (CSV/XML/JSON per its own resolved format) and runs its own hardening checks — `_run_hardening_checks(block, result_count, field_values)` unifies what the single-shape templates keep as two separately-duplicated dispatchers (flat vs. tree) into one, via a `field_values(field_name)` callback the caller supplies differently per shape (`row.get(field)` across `data` for flat, `el.iter(field)` across the built `ET.Element` tree for group) — the `noResult`/`baseline`/`blocking` branches need no per-shape duplication at all this way, only `nullRate` actually calls the callback. `_BLOCKING_RESPONSES` (Issue #132's raw-response snapshot) stays a single, page-fetch-scoped list shared across every block's own hardening checks, exactly like it's already scoped to the whole run (not per-field) in the single-shape templates — only *which* blocks have a `"blocking"` check varies, not the captured data itself. `_REQUIRED_FIELDS_DROPPED` (Issue #133) is keyed by block name instead of being one module-level counter, the natural generalization of the single-shape grouped templates' own `_required_fields_dropped_count` to "one counter per block". `BASELINE_PATH`-equivalent sidecars and `SESSION_STATE_PATH` (Issue #175, still shared/outer-level — one browser session for the whole run) are derived the same way as the single-shape templates', just per-block for the former (`block["output_path"] + ".hardening-baseline.json"`) since each block's own baseline is independent. `ExternalConfig` (Issue #178) is deliberately not supported for Blocks mode at all yet (rejected in `Program.cs`, see the Companion App section above) — neither template has any of that feature's sidecar-config machinery.
- **Output Blueprints** (Issue #191): the three flat-shape templates only (`scraper.py.j2`, `playwright_scraper.py.j2`, `scraper_api.py.j2` — container/API-tree output has no flat "row" for a target/source column mapping to apply to) gain a `BLUEPRINT_MAPPING` constant. When non-empty, it takes over building `output_rows`/the CSV fieldnames at write time — renaming, reordering to the blueprint's own order, and dropping any source field not referenced by the mapping — taking precedence over `FIELD_OUTPUT_NAMES` (Issue #178's own field-renaming mechanism) for the same write-time step, since both features rename output columns at the exact same point and a blueprint's mapping is the more specific, explicitly-chosen intent. `data` itself is left completely untouched (only a derived `output_rows` copy is affected) — hardening's `nullRate`/`requiredFields` checks and change detection's own diff keep operating on the original field names regardless of whether a blueprint mapping is active.
- **Output Blueprints: container/API-tree mode flattening** (Issue #192): the three tree-shape templates (`scraper_grouped.py.j2`, `playwright_scraper_grouped.py.j2`, `scraper_api_grouped.py.j2`) gain the same `BLUEPRINT_MAPPING` constant plus a new runtime walker, `_flatten_group_tree_for_blueprint`/`_flatten_api_group_for_blueprint`, that denormalizes the already-built tree into rows instead of `extract_group()`'s/`_extract_api_group()`'s own nested `ET.Element` tree — always returns a list of context dicts, growing only at a *relevant* repeating group's own instance boundary (`_blueprint_subtree_has_mapped_field` short-circuits an irrelevant branch — a repeating group with no mapped field anywhere inside it — so it never needlessly fans out the row count); a higher-level mapped field simply threads through unchanged until a deeper repeating boundary is reached, which is what broadcasts it into every row generated there. `scrape()`/`scrape(url)` now return `(root, blueprint_rows)` instead of just `root`; `main()` writes either the flattened csv/json (mapping active) or the original nested xml/json (not), while hardening/change-detection keep operating on the original, unflattened `root` regardless — neither needs to know a blueprint mapping exists. The Api-tree template's own walker additionally has to resolve "is this node repeating" dynamically (mirroring `_extract_api_group`'s own `_is_repeating_instance` check) and re-derive the "do the mapped fields share one ancestor chain" ambiguity check incrementally as that repeating-ness is discovered — tracked via a module-level `_blueprint_resolved_chain` across the whole run (including separate parameter combinations) — raising a `RuntimeError` on conflict instead of the `400` `OutputBlueprintFlattening` produces for Container-Mode at generate time (see the Compiler section above for why that check can't happen statically there). Deliberately placed unconditionally, right after `GROUPS`/`OUTPUT_PATH` — **not** nested inside the templates' existing `{{ if hardening.enabled }}` block that `REQUIRED_FIELD_NAMES`/`HARDENING` themselves already live in, a real bug caught during development (an early draft put it there by mistake, silently vanishing from any script generated without hardening configured).
- **Output Blueprints: nested/"containered" target schema** (Issue #244): the same three tree-shape templates gain a second constant, `BLUEPRINT_TREE_MAPPING` (empty when the active mapping, if any, is Flat-schema — exactly one of it and `BLUEPRINT_MAPPING` is ever non-empty for a given plan), and a runtime tree-to-tree walker building a real nested output instead of flat rows. A one-time, purely structural index of the source `GROUPS` tree (`_blueprint_index_source_tree`/`_BLUEPRINT_GROUP_BY_NAME`/`_BLUEPRINT_LEAF_BY_NAME`/`_BLUEPRINT_PATH_BY_NAME` — first occurrence wins for a duplicate name, the same "global by name" simplification `NullRateCheck`/`RequiredFieldsCheck`/the flat mapping already established for this tree shape) is built once at import time, independent of any scraped data, giving every named source node its own ordered ancestor-group path. `_build_blueprint_node`/`_build_blueprint_tree` (container templates) walk the *target* tree instead of the source tree: for a target group, `_blueprint_resolve_group_chain` resolves its own row scope from its direct leaves' chains — **trusting**, not re-validating, the generate-time guarantee `ScrapingPlanValidator`'s `ResolveContainerTreeRowScopes` already established (the same asymmetry the Flat mapping's own container-vs-Api-tree walkers already have) — and `_blueprint_walk_suffix` then walks exactly the remaining source-tree path from wherever the recursion already is, fanning out at each repeating step; a leaf with no repeating source ancestor *anywhere* (a "broadcast" field, mirroring the flat mapping's own broadcast fields) is instead resolved once relative to the whole page (`top_scope`), not wherever the current target-group instance happens to be — exactly reproducing the flat walker's own "visited once at its natural shallow position, then threaded into every deeper row" behavior, just via an explicit re-walk from the root instead of falling out of a single shared recursive descent. `scraper_api_grouped.py.j2`'s own version additionally has to resolve "is this ancestor group repeating" dynamically per call (`_blueprint_resolve_leaf_chain`, mirroring `_extract_api_group`'s own `_is_repeating_instance` check) rather than reading a static flag, and **does** validate the per-target-group chain itself (`_blueprint_resolve_group_chain` raises `RuntimeError` on conflict, surfacing as a `422`) since there's no static guarantee available for this shape at all — the same static-vs-runtime split the Flat mapping's own two template families already have, just scoped to one target group's own direct fields at a time now instead of the whole mapping (mirroring `OutputBlueprintFlattening.ResolveContainerTreeRowScopes`'s own per-group scoping on the Compiler side). All three templates' `scrape()`/`scrape(url)` now thread a third `blueprint_tree_elements` value through their existing `(root, blueprint_rows)` return tuple; `main()` writes it (wrapped in the same `<Ergebnis>` convention multi-root/multi-URL output already uses) instead of the original tree only when `BLUEPRINT_TREE_MAPPING` is non-empty — `root` itself, used for hardening/change-detection, is completely unaffected either way, still the full, unmapped source tree.
- Generated code should be idiomatic, commented, and readable for end users

`extension/manifest.json` declares both Chrome/Edge's `side_panel`/`sidePanel` API and the older `sidebar_action`/`sidebarAction` manifest key that Opera (and Firefox) use instead — Opera has no `chrome.sidePanel` API at all, and without `sidebar_action` the toolbar icon did nothing there (see git history, `fix(opera): add sidebar_action ...`). `chrome.sidePanel?.setPanelBehavior(...)` in `service-worker.js` is guarded with optional chaining and is a no-op under Opera; Opera's sidebar opens automatically off the manifest key instead, no JS call needed. Firefox was evaluated as a further target (see closed PR #120) but abandoned — its content-script injection and `"world": "MAIN"` network recorder (API mode) didn't work as expected there, unlike Opera, which is a genuine Chromium fork and needed only the manifest key above.

**Known issue (Chrome/Chromium on Linux):** under tiling Wayland compositors (observed on Hyprland, not fixed by updating the compositor), native `<select>` dropdowns in the side panel can render mispositioned, off-screen — this looks like an upstream Chromium/Ozone-Wayland popup-positioning quirk, not a bug in Scraping Factory. It wasn't reproducible in Opera on the same setup (possibly different Ozone/XWayland defaults; not confirmed), which makes Opera a working alternative for affected users that needs no extra setup beyond loading the same unpacked extension.

## Architecture Decisions

Made during the prototyping phase and actively in use (no longer open questions — changes to them are normal ongoing development, not foundational decisions anymore):

1. **IR schema** — the wire format remains `ScrapingFactory.Compiler.IR.ScrapingConfig` (a fields list, selector as a CSS string, optional attribute, `OutputFormat`; camelCase/string enums, see `CompanionEndpointTests`). Internally, `ScrapingPlanBuilder` translates this into the canonical `ScrapingPlan` (a step sequence of `NavigateStep`/`ExtractStep`), which the code generator and verifier consume — the foundation for future step types (login, waiting, clicks) without breaking the wire format
2. **Extension ↔ companion communication** — a local HTTP server (`http://localhost:5000` by default, configurable — see the Companion App and Browser Extension sections above), no native messaging

A known, ongoing limitation (not an open decision, but a property of the chosen approach):

3. **Selector compatibility** — CSS selectors that don't map 1:1 onto BeautifulSoup/soupsieve (`:contains()`, shadow DOM, dynamic classes). This surfaces during script verification in `/generate` (a selector that returns no data → `422`), and is not validated separately.
4. **`ScrapingEngine.Api` as a third engine value** — conceptually, "engine" (how the page is rendered) doesn't quite fit a plain JSON call, but it's the cheapest way to hook into the existing `LanguageModuleRegistry` mechanism. A deliberate compromise, not a hard requirement — a dedicated axis later would be cleaner, but would require significantly more rework for little additional benefit at the current scale (see Issue #53).
5. **API mode: no dependencies between parameters** — the full cartesian product of all parameter value lists is always tried, exactly like the original manual approach (e.g. "week X only exists for category Y" can't be expressed). A `404` response per combination is therefore treated as expected and skipped, not as an error.
6. **`ApiGroup`'s repeating-ness is inferred, never an explicit flag** (Issue #54) — unlike `GroupNode.Repeating`, which exists because a CSS selector's match count is a transient runtime fact that could vary page to page (chosen explicitly by the user, never inferred from match count), whether resolving a JSON path yields an array or an object/scalar is a structural, stable property of the API's own schema — so `ApiGroup` simply has no `Repeating` property; at runtime, N matches means N instances, anything else means at most one instance.
7. **`ApiNode` uses a structural discriminator, not a tag** (Issue #54) — `ApiGroup` vs. `ApiField` has the same structural asymmetry as `GroupNode` vs. `DataFieldNode` (a branch has `Children`, a leaf doesn't), which is exactly the reason `ApiParameterSource`'s three variants instead needed an explicit `"kind"` tag (no natural structural tell between them) — that reason simply doesn't apply here, so `IR/ApiNodeJsonConverter` sniffs for a `"children"` property, exactly like `ContainerNodeJsonConverter` already does.
8. **API mode's `OutputFormat` follows response shape, not "being API mode" itself** — flat data (one repetition level, `ItemsPath`/`Fields`) still forces `Csv`; tree data (`Groups`, Issue #54) forces `Xml`, since a tree doesn't fit CSV's column model any more than container mode's own tree does. The rule was really always "flat data → CSV, tree data → XML" — API mode just didn't have a tree-shaped response option until Issue #54. `Json` (Issue #86) fits *either* shape, so it isn't part of this rule — it's a caller-chosen override that yields nothing about mode/shape detection, and both forced defaults above (as well as container mode's own `Xml` default) still apply exactly as before whenever `Json` isn't explicitly requested.
9. **A request-body "variable" is just another `ApiParameter`, referenced by name** (Issue #55) — rather than inventing a second, body-specific value-source concept, `ApiBodyVariable.ParameterName` points into the exact same `ApiConfig.Parameters`/`ApiParameterSource` list a `UrlTemplate` placeholder already resolves against. The only genuinely new concept `ApiConfig.Body` introduces is *where else* a parameter can be referenced from — not a new way to *supply* a value.
10. **The request body is a typed tree (`ApiBodyNode`), not a flat string template like `UrlTemplate`** (Issue #55) — a text-splicing approach would force every substituted value to be a JSON string, which is wrong for GraphQL's `variables` object: GraphQL variables are genuinely typed JSON (numbers, booleans, arrays, objects), so a numeric/boolean parameter needs to reach the body as a real JSON value, not a quoted string (see `ApiBodyVariable.CoerceTo`). A typed tree also composes naturally with a tree-shaped editor UI (Phase B4), reusing the same pattern Issue #54's response tree already established — the "overlap, not identity" between #54 and #55 the original issues themselves flagged.
11. **GraphQL gets no dedicated UI/wire concept anywhere** (Issue #55) — a GraphQL request is, structurally, just an ordinary POST body whose top-level JSON happens to have a `query` key (an ordinary fixed-literal leaf) and a `variables` key (an ordinary nested object subtree, marked up with the same generic fixed/variable-value UI as any other nested POST body). Baking in GraphQL-specific handling would duplicate machinery the generic body tree already provides for free; the only place GraphQL is even mentioned is descriptive documentation/UI hints, never a distinct code path.
12. **New popup features are never just appended to `popup.js`** — this is the lesson the module-boundary extraction above exists to encode, not just a description of its current state. `popup.js` is the extension's main file precisely because it's easy to reach for; left unchecked, that's exactly how it grew past 4000 lines in the first place. A new feature's state-mutation/wire-format logic belongs in its own `<feature>.js` (or an existing one it clearly extends, e.g. another hardening check joining `settings-panel-ui.js`, another companion endpoint joining `companion-client.js`/`saved-configs-ui.js`), and its DOM rendering/event wiring in the matching `<feature>-ui.js` — both taking a `bridge` parameter for any `_state` access rather than assuming they live in `popup.js`'s own scope. `popup.js` itself only ever gains the few lines needed to import and call into the new module from `render()`/`wireEvents()`. The same split applies to that feature's tests: pure-function coverage goes in `<feature>.test.js` requiring the module directly; DOM/message-flow integration coverage goes in its own `<feature>.test.js` requiring `./popup` (not into the shared `popup.test.js`, for the same reason `popup.js` itself doesn't keep absorbing new code).

## Feature Scope (as of v1.5.0)

Originally tracked as "v1 scope (MVP)" — the MVP has been reached since v1.0.0; this section is kept up to date with the overall current scope (most recently extended with, among other things, container-based scraping and API mode). Individual items move here from "Planned for Future Releases" once they ship.

- The default engine is still static rendering (`requests` + `BeautifulSoup`, no JS). An optional browser engine (Playwright + Chromium, `Engine: "Browser"`, plain Playwright + stock Chromium — **no commercial stealth-browser/anti-bot services with a license or session model**, e.g. CloakBrowser was evaluated and rejected, see git history) for dynamically rendered pages is fully wired into the extension UI (Issues #41/#42, Phases 5/6): an Engine toggle plus a generic, ordered browser-actions list (`WaitFor`/`Fill`/`Click`/`Scroll`, each with FramePath support for iframe-scoped actions), not a dedicated wizard per action kind. Verified through actual execution just like the static engine (the consistency rule is unchanged)
- Logging in within a single script run is possible (fill out a form → submit → wait → extract, credentials only via environment variables, never in the script) — assembled from the generic browser-actions list above as a Fill+Fill+Click+WaitFor sequence, no dedicated login-specific UI (Issue #43). The popup also lets the user type one-time test values per `Fill` action, sent to the companion only with that `/generate` request (`ScrapingConfig.VerificationValues`, keyed by environment-variable name, filtered server-side against the actually-declared `Fill` actions — see `IR/FillVerificationValues.cs`) and used only for that request's trial-run subprocess (`PythonScriptVerifier`'s `extraEnvironmentVariables`) — never persisted (not even across a popup close/reopen, see `fillTestValues` in `popup.js`), never logged, never written into the generated script — so a login flow can be verified without the credentials already needing to be set as OS environment variables on the machine running the companion app. No persistent session handling across multiple script runs (no saving/reusing cookie/storage state)
- **No CAPTCHA solving/bypassing** — a deliberate boundary, not an open item: CAPTCHAs are a targeted anti-automation measure by the target site; a generic bypass feature would be evasion tooling regardless of intent in any specific case, and would typically require paid third-party solving services (violating the principle above). If a CAPTCHA blocks the flow, the script simply fails honestly (e.g. a `WaitForStep` after the login click doesn't find the expected element → timeout) — there is no special handling
- **Container-based scraping** (groups/containers, Issue #21): fully implemented, including extension UI (mode selection, tree editor, click-based selection scoped to whichever repeating instance is actually clicked, Issue #167). Four field-extraction modes: Text, Attribute, Exists, and OwnText (Issue #169 — an element's direct text only, excluding nested elements like a badge/tag sharing the same container). Every tree node (group or field) can be renamed in place and reordered among its own siblings after creation (Issue #177), without needing to delete and re-add it
- **API-based extraction** (API mode, Issue #53): fully implemented, including extension UI — network recording, click correlation against recorded JSON responses, parameter configuration with a value list/discovery endpoint/range as value sources (including automatic format detection for ISO week/date). GET and POST requests (Issue #55, see below); no dependencies between parameters (see "Architecture Decisions")
- **API mode: nested JSON responses** (Issue #54): fully implemented, including extension UI — a response with more than one repetition level (e.g. `categories[*].subcategories[*].products[*]`) is represented as a full tree editor on the `API_CONFIG` screen instead of a flat record list, output as XML instead of CSV. Multi-level, JSON-scoped click-based search for extending an already-confirmed tree (adding a sibling field at any group's own scope, or an entirely independent second root group) — see the extension section above
- **API mode: POST/GraphQL request bodies** (Issue #55): fully implemented, including extension UI — the recorder captures the outgoing request body alongside the response; a confirmed POST candidate's own captured body becomes an editable draft tree where any value can be marked fixed or variable, the latter bound to a new or already-declared `ApiConfig` parameter (reusing the exact same parameter-source configuration cards a URL variable part already uses). GraphQL needs no dedicated support of its own — its `query`/`variables` shape is just an ordinary nested POST body, handled by the same generic mechanism (see "Architecture Decisions"). Request-body construction has the same "no dependencies between parameters" limitation as URL parameters (see above); discovery-endpoint sources remain GET-only
- **API mode: embedded JSON source** (Issue #136): fully implemented, including extension UI — a second, always-available "Search page's own JSON data" entry point alongside network recording, for sites that render their complete data into the initial page HTML (Next.js `__NEXT_DATA__`, Nuxt `__NUXT__`, a generic `<script type="application/json">` blob) with no separate, capturable network request ever happening. The generated Python script fetches the page via `requests`, extracts the identified `<script>` tag via BeautifulSoup, and `json.loads`s it in place of parsing a live JSON API response — every other API-mode capability (parameterized URLs, flat/tree output shape, transforms, hardening, headers) applies unchanged.
- **Trial-run data preview** (Issue #122): fully implemented — an opt-in checkbox lets the user see a capped sample (up to 50 rows/top-level elements) of what `/generate`'s trial run actually scraped, right in the popup, before downloading/using the script. Flat/API-mode-flat output shows as a table; container/API-mode-tree output shows as a read-only, pretty-printed Xml (or, since Issue #86, Json) text sample (a structured tree view for the latter, mirroring the config-tree editors, is explicitly out of scope for now)
- **Download the full trial-run output** (Issue #161): fully implemented, mode-independent (Fields/Groups/Api alike) and independent of the preview above — a second opt-in checkbox lets the user download the trial run's actual, complete `output.csv`/`.xml`/`.json`, right from the `DONE` screen, without ever needing a local Python/Playwright install to run the generated script themselves. Deliberately still scoped to the *one* trial run `/generate` already performs — no new "run repeatedly from the extension" scheduler; recurring execution stays the user's own cron/Task Scheduler entry, same as Change Detection (Issue #87)
- **Live selector match-count preview** (Issue #85): fully implemented, extension-only (no companion/IR/code-generator changes) — a flat/container field pick shows a live "N elements found" hint the instant the selector is built, and a container-group pick shows the same count as a toast right after insertion; both purely client-side (`document.querySelectorAll(selector).length` in the content script), no `/generate` round-trip needed. Existence/quantity feedback only — a full extracted-values preview remains the separate, existing "Show preview" DOM-highlight feature and Issue #122's trial-run data preview above
- **Per-field data transformations** (Issue #84): fully implemented — an optional, ordered chain of trim/regex-extract/find-replace/to-number steps, configurable in flat mode (`modal-field-name`, which had no per-field configuration UI at all before this), container mode (`modal-field-extended`, hidden for "Exists?" mode), and API mode (a "Transform" button per leaf field on the `API_CONFIG` tree screen, Issue #84 follow-up). Applies identically across every code generator (static/browser × flat/container, API flat/tree). **Live preview** (Issue #143, and its API-mode follow-up Issue #147): fully implemented across all three modes — the modal shows what the chain actually produces against the picked element's own raw value (flat/container) or the field's own captured sample value from candidate-confirm time (API mode), live, purely client-side. **Safe type-conversion transforms** (Issue #205): fully implemented — three more transform kinds ("Convert to integer"/"Convert to boolean"/"Convert to date"), available everywhere the original four already are. Unlike `toNumber`'s best-effort heuristic coercion, all three are strict: a value that isn't already well-formed for the target type is a conversion failure, not an approximation, with a clearly defined, per-transform-configurable fallback (keep the original value, or substitute a configured default) instead of silently guessing. `toDate` parses against a configurable source-format mini-template (reusing the same `"{yyyy}"`/`"{mm}"`/`"{dd}"` placeholder syntax the API mode range-parameter format already uses) and rejects a structurally-matching but non-existent calendar date. Deliberately does not include a "fail the whole row/element" fallback option — that would need the same row/element-dropping machinery the required-fields hardening check (Issue #133) only built at real cost for a check that runs once at the very end, not per-transform
- **Json output format** (Issue #86): fully implemented — a mode-independent "Output as JSON" checkbox lets the user opt into `output.json` instead of the mode's default `output.csv`/`output.xml`, for every mode/shape (flat, container, API flat, API tree). Trial-run data preview (Issue #122 above) supports it too, reusing the Csv table renderer for Json's flat shape and the Xml text-sample renderer for Json's tree shape
- **Multiple start URLs** (Issue #83): fully implemented for flat and container mode — an optional "Additional start URLs" textarea lets the user run the same Fields/Groups extraction config against a static, user-supplied list of pages in one run, combining the results into a single output file (CSV/XML/Json alike). Not applicable to API mode, which already builds its own request URL from `urlTemplate`/parameters and rejects the combination outright rather than silently ignoring it. Composes with classic multi-page pagination (Issue #174, see below) — each start URL paginates onward independently. Deliberately still out of scope: crawling/following links matching an arbitrary pattern (unrelated to "the next page" of the same listing)
- **Change detection + notification** (Issue #87): fully implemented, mode-independent (Fields/Groups/Api alike) — an opt-in toggle lets the generated script compare each run's output against the previous run's (a whole-file text diff via `difflib`, not a granular per-record diff) and notify by email (`smtplib`, opportunistic STARTTLS) or webhook (`urllib.request`) only when something actually changed, both stdlib-only with no new pip dependency. Every credential/target is an environment-variable name the user chooses, never a literal value baked into the script. Single-script, single-machine only, as scoped by the issue itself — no hosted/cloud scheduling and no multi-recipient alerting system; the user is responsible for actually running the script on a recurring basis (their own cron/Task Scheduler entry)
- **Proxy support** (Issue #88): fully implemented, mode-independent (Fields/Groups/Api alike) — an opt-in toggle lets the generated script route its outbound requests through proxies the user already has access to, instead of connecting directly. The extension never sees the proxy addresses themselves, only the name of an environment variable holding a comma-separated list; the generated script reads that list at runtime and, if more than one proxy is present, rotates through them round-robin per request. Wired into every engine's own HTTP layer: `requests`' `proxies` parameter for the static/API engines, Playwright's `proxy` launch option for the browser engine. Pass-through only, as scoped by the issue itself — no proxy acquisition, rotation service, or IP-pool management
- **Script hardening** (Issue #129): the first of five planned checks (see "Planned for Future Releases") sharing one mechanism — an opt-in "no result" check lets the generated script re-validate, on every run (not just the companion's own `/generate` trial run), that it actually scraped at least one row/element, independently configurable to print a warning (script still exits `0`) or fail the run (script exits a dedicated non-zero code, distinguishable from an unhandled crash) so a scheduled re-run weeks later doesn't silently produce nothing without anyone noticing. Mode-independent (Fields/Groups/Api alike).
- **Script hardening: per-field null-rate check** (Issue #130): fully implemented, the second of the five planned checks — catches the narrower case "no result" can't: a row/element count that stays healthy while one specific field's selector quietly starts matching the wrong thing and returns empty every time. Independently configurable per monitored field (any number of fields, each its own threshold and Warning/Error severity), reusing the exact field list already built in the current mode instead of a free-text field-name input. In container/API-tree mode, the rate is computed **globally per field name** across the whole result, not scoped to whichever parent group the field is nested under (a deliberate scoping decision — see the Compiler section above).
- **Script hardening: baseline-drop check** (Issue #131): fully implemented, the third of the five planned checks — catches a gradual volume drop (e.g. a broken "load more"/pagination selector) that neither "no result" nor per-field null-rate would ever trip, by comparing this run's own result count against the last run's, tracked entirely by the generated script itself in a small sidecar file next to its own output (never sent to or known by the companion). The sidecar only ever updates after a run that itself didn't hard-fail, so a bad run's own low count can never become the new baseline for the next comparison. Mode-independent (Fields/Groups/Api alike).
- **Script hardening: blocking-detection check** (Issue #132): fully implemented, the fourth of the five planned checks — catches a site that starts blocking the script (rate-limiting, IP ban, CAPTCHA wall, redirect to a login page) while still responding with a normal-looking HTTP 200, evaluated against the *raw* response (final URL, body length, body text) rather than the already-extracted data. Three signals: a redirect to a different host (always active, no configuration needed), a response shorter than an optional configured byte threshold, and an optional list of case-insensitive block phrases. Mode/engine-independent (Fields/Groups/Api × Static/Browser alike), though each engine's own "response" concept differs — see the Compiler/Python Templates sections above. Detection-and-reporting only, consistent with the "No CAPTCHA solving/bypassing" boundary below — it never attempts to bypass or work around whatever it detects.
- **Script hardening: required-fields check** (Issue #133, tree-shape follow-ups Issue #133/#204): fully implemented, the fifth and last of the originally planned checks — unlike the other four (aggregate checks that only ever *report* on already-final data), this one *filters* the output before it's written: a row missing a non-empty value for any of a configured set of fields is dropped from the output entirely, serving a "safe for database import" use case (e.g. a `NOT NULL` column that would otherwise silently break on import). Filtering happens unconditionally regardless of severity — only whether the run itself is flagged as failed depends on it, so an all-Warning configuration still guarantees the output file never contains an incomplete row. Supported for every mode/shape: flat mode, container mode and API mode's tree shape (both dropping the nearest enclosing repeating group instance, matched globally by field name — the same simplification the per-field null-rate check already established for this exact ambiguity), and API mode's flat response shape.
- **Dark mode** (Issue #140): fully implemented, extension-only (no companion/IR changes) — follows the OS/browser `prefers-color-scheme` by default, with a manual system/light/dark toggle next to the language selector that persists the same way the language preference does (`chrome.storage.local`). See the extension section above for the token/theme-module mechanics
- **Pagination** (Issue #174): fully implemented, mode-independent (Fields/Groups alike, not Api — which already has its own page-parameter mechanism via a Number `RangeSource`) and engine-independent (Static/Browser alike) — an opt-in "Pagination" section lets the generated script follow classic multi-page pagination onward from each start URL (`Url` + every `AdditionalUrls` entry, paginating each independently), either by following a "next page" link's `href` (`NextLinkPagination`, resolved relative to the current page, both engines) or by substituting `{url}`/`{page}` into a page-number URL template (`PageNumberPagination`) — page 1 is always the start URL exactly as given, `{page}` only ever generates page 2 onward. Stops when a page yields nothing, a configurable `MaxPages` safety cap is reached (always active, default 50), or (next-link kind) the selector no longer matches. Distinct from infinite-scroll/"load more" pagination on a single page, already covered separately by the Scroll browser action (Issue #41)
- **Persistent session/cookie handling** (Issue #175): fully implemented, Browser-engine only — an opt-in "Reuse session between runs" toggle inside the browser-actions section lets the generated Playwright script save its cookies/localStorage (`storage_state`) to a sidecar file after every run and, once that file exists from a previous run, skip the configured login-flow browser actions (WaitFor/Fill/Click/Scroll) entirely on the next run, going straight from Navigate to extraction. Avoids repeating a login flow (and any resulting rate-limiting/lockout risk) on every scheduled/recurring run of the same script. If the saved session ever actually expires, there's no automatic fallback to a fresh login — the run simply fails, a deliberate, documented limitation.
- **External XML config file for re-editable script parameters** (Issue #178): fully implemented for the scope described above — an opt-in toggle makes the generated script self-create a small sidecar XML file next to itself (not sent back through `/generate` at all) the first time it actually runs, and re-read it on every run after that, letting a non-technical user tweak the start URL(s), the output filename, a flat field's output name, or a fixed-value-list API parameter's values, by editing that file — without touching the `.py` file or reopening the extension. A missing file is not an error (a fresh one is written); a broken or stale one (bad XML, a missing required attribute, a reference to a field/parameter that no longer exists) fails cleanly with an English message and a dedicated exit code, never a raw traceback. Container-mode's own group/field names and Api-mode's tree shape aren't editable this way yet — deliberately left open, per the issue's own flagged uncertainty about mapping a nested tree onto a flat-ish XML structure.
- **Local saved-configuration history** (Issue #141): fully implemented, mode-independent (Fields/Groups/Api alike) — an opt-in "Save configuration" action persists the current configuration into a small local SQLite database on the companion side (never a companion/IR/wire-format change beyond four new endpoints — the config JSON itself is stored and round-tripped opaquely), and a hostname-scoped "Saved configurations" panel on the popup's idle screen lists/loads/deletes past saves for whichever site is currently open. "Load" restores everything the export/`/generate` request body already captures except the URL itself, which always stays whatever the live browser tab currently shows. Purely local/additive and entirely opt-in, as scoped by the issue itself — no automatic/implicit saving (not a silent history of every `/generate` call), no cross-machine sync, and no export/import of the SQLite file itself (the existing JSON export/no-import-yet mechanism still covers one-off sharing).
- **Persist and browse run outputs** (Issue #202): fully implemented — an opt-in "Save output" action on the `DONE` screen links a trial run's actual, complete output (the same data Issue #161's "Download data" already surfaces) to an already-saved configuration in the companion's local SQLite store, and each saved configuration in the "Saved configurations" panel gains its own expandable list of its past saved outputs (download/delete). Same local/opt-in trust boundary as Issue #141 — no data leaves the user's machine, no automatic/implicit saving of every run. Deliberately does not include evaluating hardening checks against a saved output — that's a separate, not-yet-implemented issue (#207), since hardening today only ever runs live, inside the generated script itself, and a cross-configuration comparison mode for it depends on Output Blueprints (#191, also not yet implemented) existing first. **Create-and-link a new configuration directly from "Save output"** (Issue #209): fully implemented — when the current site has no saved configuration yet, "Save output" creates one inline (collecting a configuration name alongside the output name in the same modal) and links the output to it in one action, instead of only ever redirecting into the separate "Save configuration" modal first. The existing picker for an already-existing configuration is unchanged.
- **Combined mode: merge multiple saved configurations into one script** (Issue #239): fully implemented — a fourth top-level mode lets the user pick 2+ of their own already-saved configurations (Issue #141), possibly targeting entirely different sites/modes/engines, order them into a list, and generate one script that runs every component's own extraction independently and merges all of their outputs into a single combined `output.json`, keyed by each component's own (editable) name. Every component keeps its own engine/browser-actions/proxy/hardening/pagination/persistent-session/external-config exactly as if it had been generated standalone; sidecar-state features specifically are proven to keep working across separate runs of the *combined* script via a stable per-component subdirectory (not a disposable temp directory). Deliberately out of scope for v1: no combined-level (outer) hardening/change-detection/proxy/pagination — component-level only; a smarter "join by shared key" merge (the "generic two-phase join" idea from Issue #181's own discovery process) remains a possible, separate future extension; and the popup has no UI yet for a component's own one-time login `VerificationValues`, though the wire format already supports it.
- **Blocks mode: multiple, independently-shaped output files from one run** (Issue #182): fully implemented — a fifth top-level mode lets the user build several independent extraction blocks (flat or container/group, freely mixed) one at a time against the page currently open, reusing the exact same click-based field/group editors flat/container mode already have, then generate one script that shares one navigation/browser session/proxy/pagination/persistent-session across every block while each block writes its own, independently-formatted output file (CSV/XML/JSON). At least 2 blocks are required, mirroring Combined mode's own minimum. Deliberately out of scope for v1: no UI yet for a block's own `ChangeDetection`/`Hardening`/explicit `OutputFormat` override, though the wire format already supports all three (each block produces its own independent result set, so — unlike `Pagination`, which stays outer-level since it governs the one shared page-fetching loop every block extracts from — these three are genuinely per-block concerns); no per-block trial-run preview table on the `DONE` screen (a "Download" button per block is implemented, reading the per-block sample into a table/text view the way the single-shape preview already does is left as a follow-up); and `ExternalConfig`/API-mode blocks are both rejected outright rather than guessed at, the same "ship the simpler shape first" precedent container mode's own field renaming and Api-mode's tree shape already set for `ExternalConfig` (Issue #178).
- **Output Blueprints: reusable output field-name/order mapping** (Issue #191, extended to container/API-tree mode by Issue #192, and to a nested/tree target schema by Issue #244): fully implemented for flat mode, API mode's flat response shape, container mode, and API mode's tree shape, in either of two target schema kinds. A small, persisted, site-independent "blueprint" — a `schemaKind` of `Flat` (just a name plus an ordered target-field-name list) or `Tree` (a name plus a nested target-schema tree of its own, mirroring the container/API tree editors, with no explicit repeating flag — see Architecture Decision #6's own reasoning applied here too) — lets the user map a scrape's own source fields onto that fixed shape, so recurring exports for the same downstream pipeline stay consistent regardless of which specific configuration produced them. For a Flat schema, a tree-shaped source is *flattened* into denormalized rows instead of being renamed in place — one row per instance of the single repeating group every mapped field's own ancestor chain shares, with any higher-level mapped field (e.g. a category name next to a repeating list of items) copied/broadcast into every row generated beneath it — and mapped fields spanning more than one independent repeating branch are rejected rather than guessed at (no single row layout could include both without either a cross-product or dropping data), at generate-time (`400`) for container mode or a `422` trial-run verification failure for Api-tree mode (Architecture Decision #6). A **Tree** schema resolves this same ambiguity differently, by design: each *target group* resolves its own row scope independently from its own direct mapped fields, so two independent/sibling source repeating groups simply map into two different target branches instead of needing one shared scope — the target tree's own nesting is the disambiguation, the open question #244 was filed to answer. Deliberately still out of scope for both schema kinds: Combined mode and Blocks mode are still rejected outright, neither having a single field/tree config of its own at the outer level; there's no fixed-literal-value target field — every target field must map to a real source field; and the per-scrape mapping picker's source-field `<select>` offers the full current-mode field list at every tree position rather than scoping it to "fields actually reachable from this position" (a first-version simplification — the generate-time/runtime ambiguity check still catches a genuinely wrong pick).
- Python only as a target language
- Backend of the generated script: `requests` + `BeautifulSoup` (static), Playwright (browser), or just `requests` (API mode); output as CSV (flat mode, and API mode's flat response shape), XML (container mode, and API mode's tree response shape, Issue #54), or Json instead of either (Issue #86)

## Consistency Rule

The companion app doesn't just verify at the same rendering stage as the generated script anymore — before delivery, it runs the exact generated script once as a trial (`Backends/Python/PythonScriptVerifier`: write the script to a temporary directory, run it via a `python3`/`python` subprocess, check the exit code and `output.csv`). This rules out any discrepancy between verification and the generated script (encoding, selector compatibility, network errors, runtime errors), and is why a separate Playwright- or AngleSharp-based verification path was rejected: it could only ever have approximated real script behavior.

Before this real execution, `/generate` also runs `IR/ScrapingPlanValidator` as a fast, purely structural pre-check of the `ScrapingPlan` (broken URL, duplicate/empty field names) — this doesn't replace real verification, it just saves the subprocess startup cost for configurations that are always wrong regardless of script behavior. CSS selector syntax/compatibility is deliberately still not checked separately (see point 3 above) — it remains solely the concern of the actual script execution.
