- **Popup module boundaries**: `popup/popup.js` had grown to over 4000 lines by the time Issue #178 shipped — every feature since roughly Issue #83 had simply been appended to it instead of extracted, the one part of the popup that never got the same logic/`-ui` split its own newer features (container mode, API mode, field transforms) already used. It was split into focused modules, each following the pre-existing `<feature>.js` (pure data/logic, no DOM) + `<feature>-ui.js` (DOM rendering + event wiring) convention `container-tree.ts`/`container-tree-ui.js`, `api-config.ts`/`api-config-ui.js`, and `field-transforms.ts`/`field-transforms-ui.js` already established: `toast.ts` (toast notifications + last-reported-error tracking), `bug-report.ts` (log collection, GitHub issue prefill), `scraping-config-builder.ts` (every pure `build*`/`add*`/`remove*`/`update*` wire-format helper — `buildScrapingConfig`, `buildConfigExport`, `buildChangeDetectionConfig`, `buildProxyConfig`, `buildPaginationConfig`, `buildHardeningConfig`, etc.), `dom-tree-ui.js` (the DOM inspector tree), `preview.ts` (the DOM-highlight "Vorschau" feature), `companion-client.ts` (every `fetch` call to the companion's `/health`/`/generate` endpoints, including the resolved `companionUrl` itself via `getResolvedCompanionUrl()`), `download-helpers.ts` (Blob-download plumbing), `saved-configs-ui.js` (Issue #141/#202's `/configs`/`/configs/{id}/outputs` endpoints and the "Saved configurations" panel), and `settings-panel-ui.js` (the Monitoring/Settings sections' render + wiring: change detection, proxy, pagination, all five hardening checks). `popup.js` itself is now the thin orchestrator: `_state`, `setState`/`patchState`/`persistState`, `render()`/`wireEvents()` as dispatchers, `init()`, and the handful of screen-specific bits (flat/container/API mode switching, modal confirm flows) that don't cleanly belong to any single extracted feature. Since none of these modules can import `_state` directly (it stays module-private to `popup.js`), every function that needs to read/mutate state takes a `bridge` object as its first parameter — `{ getState, setState, patchState, stopPreviewIfActive, requestDomTree, showToast, fetchSavedConfigs }`, constructed once at module scope in `popup.js` (not just inside `wireEvents()`, so `popup.js`'s own top-level functions can use it too) — the exact convention `api-config-ui.js`/`container-tree-ui.js` already used for the same reason; a module needing no state access at all (`toast.ts`, `download-helpers.ts`'s `downloadFile`) just takes plain parameters instead. Test coverage was split the same way: each new module with genuine pure-function unit tests got its own `<feature>.test.js` (`scraping-config-builder.test.js`, `dom-tree-ui.test.js`, `bug-report.test.js`), while integration-style tests that exercise the full wired-up popup (`require('./popup')`, simulated `chrome.runtime.onMessage` dispatch, real DOM clicks) were relocated — not rewritten — into their own file per feature (`companion-client.test.js`, `saved-configs-ui.test.js`, `download-helpers.test.js`, `preview.test.js`, `settings-panel-ui.test.js`), shrinking `popup.test.js` from over 9000 lines without changing what any single test actually verifies. See Architecture Decision #12 below for the rule this establishes going forward.
- **Popup module boundaries, flat mode's turn** (follow-up to the above): flat mode was the *original* mode and, unlike container mode (`container-tree.ts`/`container-tree-ui.js`) and API mode (`api-config.ts`/`api-config-ui.js`), had never gotten its own module — its render/wire code was still sitting directly in `popup.js` even after every other feature had been extracted. `popup/flat-mode-ui.js` closes that last gap: the flat fields list (`renderFields`), the "+ Datenfeld" pick flow and `modal-field-name` (`renderFlatFieldModal`/`confirmField`), and that modal's own match-count hint/transform-chain editor (`renderMatchCountHint`/`refreshFlatTransformPreview`), all wired via one `wireFlatModeEvents(bridge)` called once from `popup.js`'s `wireEvents()` — the same `bridge`-parameter convention every other extracted module already uses. `renderMatchCountHint` is intentionally duplicated verbatim in `container-tree-ui.js` (whose own extended-field modal needs the identical hint) rather than shared, consistent with this codebase's then-existing "no cross-module includes for small DOM helpers" convention (obsolete as a constraint since Issue #389: the popup is bundled, so a shared helper is a plain `require()` — existing duplicates stay until the module-split issues, #390, remove them). `container-tree-ui.js` itself gained the matching `renderContainerFieldModal`/`wireContainerModeEvents` pair in the same pass, so `popup.js`'s `render()`/`wireEvents()` now dispatch to `renderFlatFieldModal`/`renderContainerFieldModal` and `wireFlatModeEvents`/`wireContainerModeEvents` symmetrically for both modes instead of inlining container mode's wiring while flat mode's stayed in `popup.js` proper. No new `<feature>.test.js` was added for either — both are still covered by `popup.test.js`'s existing integration tests (`require('./popup')`, real DOM clicks), unchanged by the extraction itself.
- **Inline styles moved to `popup.css`**: `popup.html`'s `<head>` used to carry its entire ~720-line `<style>` block (the Issue #139/#140 design-token system and every rule built on it) directly inline. It's now `popup/popup.css`, loaded via a plain `<link rel="stylesheet" href="popup.css">` — a value-for-value move, not a rewrite, so it carries no behavior change of its own.
- **Popup module boundaries, browser actions' turn**: Issue #41/#42's engine toggle and the generic browser-actions list (WaitFor/Fill/Click/Scroll) were the last feature area still rendered/wired directly in `popup.js`. `popup/browser-actions-ui.js` closes that gap the same way `flat-mode-ui.js` closed flat mode's: `renderBrowserActions`/`buildSelectorRow` (pure render, unchanged), `renderBrowserActionsSection(bridge)` (engine active-state, `#browser-actions-section` visibility, and the Issue #175 persistent-session checkbox's checked-sync, nested inside that section), and `wireBrowserActionsEvents(bridge)` (engine buttons, the four `btn-add-action-*` buttons, and `#browser-actions-list`'s click/change delegation) — called once each from `popup.js`'s `render()`/`wireEvents()`. The two integration-style describe blocks that exercised this in `popup.test.js` moved into their own `browser-actions-ui.test.js`, per Architecture Decision #12's test-split convention.
- **`popup.html` split into runtime-loaded partials**: `#screen-idle` (~493 lines: mode toggle, all three mode-specific sections, engine+browser-actions, output-settings), `#screen-api-config` (~49 lines), and all eight modal `<div>`s (~169 lines, now under one `#modals-mount`) made up ~710 of `popup.html`'s 875 lines — the majority of the file was markup for screens/modals hidden at parse time anyway. That markup now lives in `popup/screens/idle.html`, `screens/api-config.html`, and `screens/modals.html`, fetched into their (now-empty) mount points by a new `loadScreenPartial`/`loadScreenPartials` pair — the first thing `init()` does, before `applyStaticTranslations()`/`wireEvents()`/the first `render()`, all three of which depend on this markup already being in the DOM. Uses `chrome.runtime.getURL` + `fetch`, exactly `i18n.ts`'s own `fetchDictionary` pattern — no `web_accessible_resources` manifest entry needed (the extension's own page fetching its own bundled resource, not a content script/web page reaching in), and (since Issue #389) the partials are copied next to the bundle in `extension/dist/popup/screens/`. Under Jest (`process.env.NODE_ENV === 'test'`, which the esbuild build replaces with a constant — Issue #389) `loadScreenPartial` is a deliberate, **untested-by-design** no-op — the same precedent `i18n.ts`'s own `chrome.runtime.getURL` branch already established, since every existing test already builds its own minimal `document.body.innerHTML` fixture (no test ever loads the real `popup.html`) and actually injecting the real production markup would silently overwrite it; it would also consume fetch-mock call slots (`mockResolvedValueOnce` chains keyed to call order) that plenty of tests already reserve for the real `/health`/`/generate` calls made later in the same startup sequence. `popup.html`: 875 → 167 lines. **Real-browser verification via "Load unpacked" is still required before this ships** — the one part of this change no automated test can exercise, since `loadScreenPartial`'s real fetch path never runs under Jest by construction.
- **Test-flush robustness fix, prompted by the above**: every `flushMicrotasks()` helper across the popup's test files (~31 near-identical copies) used to loop a fixed count of `await Promise.resolve()` calls (10, one at 15) — enough to drain `init()`'s async chain as it stood, but not future-proof against that chain growing by even one more real `await` (which `loadScreenPartials()` did). All ~31 copies now use `await new Promise((resolve) => setTimeout(resolve, 0))` instead, which drains the entire microtask queue unconditionally before the macrotask fires, regardless of how deep any given chain is.
- **Popup module boundaries, the idle screen's turn**: the `STATES.IDLE` render block (~200 lines — URL display, robots.txt check result, mode toggle, `hasConfig`-gated button disabling, preview/API-capture summaries and panels, output-settings filename/additional-urls inputs) plus the mode switch itself (`switchMode`/`MODE_SWITCH_CLEARS`) were the largest remaining chunk of `popup.js`'s `render()`/`wireEvents()` not yet claimed by any feature module. `popup/idle-screen-ui.js` closes that gap the same way `flat-mode-ui.js`/`browser-actions-ui.js` did: `renderIdleScreen(bridge)`/`wireIdleScreenEvents(bridge)`, called once each from `popup.js`. `switchMode` moved with it (`switchMode(bridge, mode)`, previously closing over `popup.js`'s own `_state`/`setState`) since it's exclusively invoked by the mode-toggle buttons this module now wires. No new dedicated test file — same precedent as `flat-mode-ui.js`/`container-tree-ui.js`'s own extraction, this is still covered by `popup.test.js`'s existing integration tests, unchanged by the move. `popup.js`: 1706 → 1460 lines (4044 before this whole module-boundary effort began).
- **Popup module boundaries, `wireEvents()`'s last two chunks**: two more self-contained pieces of `wireEvents()` moved out. First, the "Save configuration"/"Save output" modal open+confirm+cancel buttons and the saved-configs-list's own delegated Load/Delete/Outputs-toggle/download row actions — every function they call into already lived in `saved-configs-ui.js`, so this joined that existing module (`wireSavedConfigsEvents(bridge)`) rather than a new one, per Architecture Decision #12's "or an existing one it clearly extends" rule. Second, the single `chrome.runtime.onMessage` listener handling every message type `content-script.js`/`service-worker.js` send back (selection results, DOM tree data, preview/API-capture results, `API_CANDIDATES`/`EMBEDDED_JSON_CANDIDATES`, ...) — genuinely cross-cutting rather than any one feature's own concern, so it got a new `message-router.ts` (`wireMessageListener(bridge)`) instead of joining an existing module. Neither got a new test file — both are still covered by `popup.test.js`'s existing integration tests. `popup.js`: 1460 → 1204 lines.
- **Popup module boundaries, `init()`'s recovery logic**: `init()`'s `chrome.storage.session` recovery — restoring persisted fields/groups/settings, then replaying whichever pending-selector recovery branch applies (container node insertion, browser-action update, pagination update, generic field modal) — was the largest remaining chunk of `popup.js`. It mirrors `message-router.ts`'s own `ELEMENT_SELECTED` branches closely (the same four outcomes, replayed from storage after a popup reopen instead of from a live message) but stays a separate module, `session-restore.ts`, since it's about session *restore* rather than live message *dispatch*. `applyStoredSessionState(state, stored)` is a pure function (previously inline `_state = {..._state, ...}` reassignments directly in `init()`); `restorePendingSelection(bridge, stored)` replays the pending-selector outcome and returns whether it fully handled the recovery. This logic had zero test coverage before — `session-restore.test.js` adds direct unit coverage for both functions, a gap the previous inline-in-`init()` shape made impractical to close. `popup.js`: 1204 → 1103 lines.
- **Popup module boundaries, the last few pieces**: four more small pieces moved to existing modules, per Architecture Decision #12's "or an existing one it clearly extends" rule — none warranted a new module of their own. The `API_CONFIG` screen's tree-search panel and its three modals (add group, add body parameter, edit a leaf field's transform chain) joined `api-config-ui.js` as `renderApiConfigModals(bridge)`. The Monitoring/Settings collapsible-section header toggles, plus the Settings section's own three toggles (Json output, trial-run data preview, full output-file download), joined `settings-panel-ui.js`'s `wireSettingsPanelEvents(bridge)`. The `SELECTING` screen's DOM-tree-view toggle (checkbox state, wrapper/loading/error/truncated visibility) joined `dom-tree-ui.js` as `renderDomTreeViewState(bridge)`/`wireDomTreeViewEvents(bridge)`. The `COMPANION_ERROR` screen's own render block and its three buttons (retry, use/reset custom URL) joined `companion-client.ts` as `renderCompanionErrorScreen()`/`wireCompanionErrorEvents(bridge)`. `popup.js`: 1103 → 985 lines — under 1000 for the first time since this effort started at 4044.
- Communicates with the companion app via a local HTTP server, `http://localhost:5000` by default — configurable on the companion side (see below) and, independently, overridable per-browser-profile from the extension's own `COMPANION_ERROR` screen if the default address isn't reachable (`extension/shared/companion-config.ts`: `getCompanionUrl`/`setCompanionUrlOverride`, backed by `chrome.storage.local` so a manually entered address survives a browser restart, the same pattern `i18n/i18n.ts` already uses for the language preference)
- **Side panel fills the available height** (Issue #138): `popup/popup.html`'s `<body>`/`.screen` used to have no height layout at all (`width`/`max-width`/`min-width` only, a leftover from when this was a classic dropdown popup that sizes to content), leaving dead whitespace below any screen shorter than the panel. `html, body { height: 100%; }` plus `body`/`.screen` as flex columns (`flex: 1; min-height: 0;` on `.screen`, since only one is ever unhidden at a time, see `render()`) let the active screen stretch to whatever height the side panel actually has. `#screen-idle` (the longest screen) wraps everything except its bottom Export/Generate button row in a new `.screen-idle-scroll` div (`flex: 1; overflow-y: auto;`) so those buttons stay pinned at the bottom of the panel while the field/settings content scrolls independently above them, instead of the whole document scrolling past them. `#screen-api-config`'s own previously hardcoded `max-height: 480px` is gone for the same reason — it now grows via the shared `.screen` rule and scrolls internally within whatever height that ends up being. `body`'s `max-width` was relaxed from `380px` (also a dropdown-popup leftover) to `640px`, since the side panel is user-resizable — the cap now only guards against absurdly long text lines on a genuinely wide panel instead of capping the common case.
- **Visual design refresh: design tokens, icons, interaction consistency** (Issue #139): a purely visual pass over `popup/popup.html`'s CSS — no information-architecture/flow change. A `:root` block of CSS custom properties (`--color-*`, `--radius-*`, `--shadow-*`/`--overlay-*`, `--focus-ring`, `--transition-fast`) replaces ~90 one-off hex/rgba/border-radius literals that had been scattered through the file with no shared source of truth, migrated value-for-value (verified pixel-identical via before/after screenshots) with one deliberate exception: the success-icon's `#22c55e` and the pre-existing `#16a34a` (already used for robots-allowed/toast-info) are two near-identical greens with no reason to differ, so they now share one `--color-success` token. This is also the direct prerequisite for a future dark-mode pass — a `[data-theme="dark"]` block would only need to redefine these tokens, not every rule using them. The two literal Unicode status glyphs (`⚠`/`✓`) are now small hand-drawn inline SVGs (no icon font/CDN, per the "free plugin" principle), sized/colored via the token set. The three independent tree-toggle implementations (`container-tree-ui.js`'s group tree, `api-config-ui.js`'s API tree, `popup.js`'s DOM tree view) — each of which swapped between two different Unicode glyphs (`▸`/`▾`) via `textContent` on every click — now each insert one static chevron SVG per row and toggle a `.collapsed` class instead, with the actual rotation (`transform: rotate(-90deg)`) handled once in shared CSS rather than duplicated per-file click-handler logic; the DOM tree view keeps its "starts collapsed" default (unlike the group/api trees, which start expanded) by applying `.collapsed` at build time. Finally, hover/active/transition treatment is unified: the shared `button{}` base rule now transitions multiple properties via `--transition-fast` (was: `background .1s` only) and every button gets a uniform `:active` press feedback (`translateY(1px)`) — `.mode-btn`/`.btn-toggle` inherit both for free since they're plain `<button>`s; inactive `.mode-btn` tabs and the three tree-row types (`.group-tree-row`/`.api-tree-row`/`.body-tree-row`, previously with zero interactive feedback) gained a hover state; text inputs/textareas/selects share one focus-transition rule. Deliberately out of scope: turning "Remove"/"+ Add"-style text-label buttons into icon+label, which would be a much larger pass and risks breaking existing `.textContent` assertions in `popup.test.js`.
- **Dark mode + visual modernization pass** (Issue #140): builds directly on #139's token groundwork — every color/overlay/shadow token now lives in a light/dark pair instead of one fixed set. `:root` carries the light defaults; `@media (prefers-color-scheme: dark) { :root:not([data-theme]) { ... } }` redefines them automatically when the OS prefers dark and the user hasn't made an explicit choice; an explicit `html[data-theme="light"|"dark"]` override (see `shared/theme.ts` below) always wins over both, and needs no rule of its own for "light" specifically since the media query already stays out of its way when the attribute is present. `color-scheme: light dark` on `:root` (narrowed to a single value by the two explicit-override rules) gives native form controls — checkbox/select-popup chrome, and any `input`/`textarea` with no explicit background of its own, like `#input-additional-urls` — a correct dark rendering for free. **Contrast audit** (called for by the issue): every status color already read from #139's token set, so brightening them for dark backgrounds was enough — no per-rule changes needed for `.robots-txt-allowed`/`.preview-summary.warn`/toast variants/etc. One real bug the audit *did* catch: several "white text on a colored background" rules (`.btn-primary`, `.toast`, picked chips) used `var(--color-surface)` for that text color — correct by coincidence in light mode (surface happens to be white) but flips to near-black in dark mode. A new theme-agnostic `--color-on-accent` token (always a light color regardless of theme, since the accent backgrounds themselves stay readable with light text in both) replaces `--color-surface` at every one of those call sites. **Manual toggle**: a new `extension/shared/theme.ts` mirrors `i18n.ts`'s `getStoredLanguage`/`setLanguage` pattern exactly (`chrome.storage.local`), with one difference — "follow the OS" is a real third state, represented as `null` (not a storable `'system'` string) throughout the module. `#theme-toggle` next to the language selector cycles system → light → dark → system on click (`SFTheme.cycleTheme`), a single compact icon button chosen over a dropdown for lack of panel-width room next to the existing language `<select>`. **Modernization** (requested alongside the issue, not part of its own scope): the radius scale is nudged up again (6/8/10/14, from #139's 4/6/8/10) for a softer feel; `--transition-fast` switches from a plain linear ease to the "standard" `cubic-bezier(0.4, 0, 0.2, 1)` easing curve; a new `--glow-primary` gives `.btn-primary:hover` a soft colored glow instead of a flat color swap; the old flat `--shadow-sm`/`--shadow-md` pair is replaced by a graded `--elevation-1/2/3` scale (layered shadow pairs) for more "floating" depth on the mode-toggle active pill and modal; the `.mode-toggle`/`.mode-btn` segmented controls (mode/engine/notify-method — three markup instances) gain an animated sliding `.mode-toggle-thumb` behind the active button instead of each button just recoloring itself in place, positioned via `popup.js`'s `syncModeToggleThumbs()` (JS, not CSS-only, since it depends on the active button's actual rendered offset/width) — called at the end of every `render()` and on a rAF-throttled `window.resize` listener, since the side panel is user-resizable; `.engine-section`/`.output-settings` get an outlined "card" (border only, no fill, since their own children already use `--color-surface-subtle`) to break up the idle screen's otherwise undifferentiated list of settings — the mode-specific sections are deliberately left unboxed since they're the primary content being edited and already carry their own row-level visual treatment; every scrollable container from #138/#122 gets a slim `::-webkit-scrollbar` (Chromium-only, matching the extension's own supported browser range). Deliberately out of scope, same reasoning as #139: turning text-label buttons into icon+label.
- **esbuild bundling; "Load unpacked" points at `extension/dist/`** (Issue #389): the extension is no longer loaded straight from its source folder. `extension/build.js` (`npm run build`, `npm run build:watch`, plus `--channel release` and `--outdir <dir>` for `install/build-bundle.sh`) bundles four entry points — `popup/popup.js` (side panel), `content/content-script.js` (isolated world, every frame; `shared/logger.ts` is bundled in, so the manifest no longer lists it), `content/api-capture.js` (the `"world": "MAIN"` recorder, `document_start`) and `background/service-worker.js` — as `iife` for Chromium 114+ into `dist/<same relative path>`, source maps beside them, and copies the static files (`manifest.json`, `popup/popup.html`, `popup/popup.css`, `popup/screens/*.html`) to the same relative paths, so `chrome.runtime.getURL('popup/screens/idle.html')` and the manifest paths are unchanged. `dist/` is git-ignored; Jest, `tsc` and the e2e harness treat it as build output (`modulePathIgnorePatterns`, `exclude`). **What the bundler replaced:** every module used to carry dual-environment boilerplate so the same file ran as a classic `<script>` (shared global scope) and under Jest (CommonJS) — an IIFE assigning one `self.SFXxx` global, a `typeof require !== 'undefined' ? require(...) : self.SFXxx` shim per import, a `typeof module`/`self` export footer, a 56-line `<script>` list in `popup.html`, and `classic-script-loading.test.js` guarding the top-level-name-collision bug class that came with it. All of that is gone: a module is now plain CommonJS (`const { x } = require('./y')`, `module.exports = { ... }`), `popup.html` has one `<script src="popup.js">`, and Jest keeps running the sources directly. No behavior change. **The three explicit replacements for what used to be environment sniffing:** `i18n/i18n.ts` `require`s the three dictionaries statically (inlined into the popup bundle, loaded identically in Jest — no fetch, no `chrome.runtime.getURL`); `popup.js`'s `loadScreenPartial` and `content/api-capture.js`'s fetch/XHR patching check `process.env.NODE_ENV === 'test'` (Jest sets it, the build `define`s it to `"production"`, so the code is dead-branch-free in the bundle and `process` never exists at runtime — never reference `process` for anything else). **Release channel** (Issue #352): `shared/build-config.ts` derives `CHANNEL` from `process.env.SF_CHANNEL`, which `build.js` always `define`s (`"development"` by default, `"release"` for `--channel release`); `install/build-bundle.sh` builds the release channel into a temp dir (`npm ci` + `node build.js --channel release --outdir …`, then ships the bundle without `.map` files) instead of `sed`-rewriting a source line, and `build.js` fails the build if a release build did not actually produce the release constant. `shared/companion-url-policy.test.js` builds the real module with each channel to prove it. **Consequences for contributors:** after editing extension code run `npm run build` (or leave `build:watch` running) and reload the extension at `chrome://extensions`; there are no page-level globals any more (`self.SFXxx`, `SFTheme`, a popup's `_state`) — a real-browser check that needs to reach into the popup must go through the DOM, `chrome.storage` or Playwright routes, not `page.evaluate(() => SFFoo…)`; a new module needs no `popup.html` edit, just a `require`. TypeScript conversion stays a separate, file-by-file follow-up.
- **Monitoring / Hardening in plain language** (Issue #399, UX audit finding 4): the Monitoring section is a "set and forget" feature for scripts that run repeatedly and unattended, but nothing said so, the five hardening checks were bare labels, and the Warning/Error toggle was explained only by a hover tooltip in terms of exit codes. **Labels and help only — no change to the wire format or the generated scripts** (the wire severities stay `Warning`/`Error`; only what the buttons say changed). A one-sentence **intro** (`idle.monitoringIntro`: only useful if you run the script again and again, e.g. every night); a **"Checks after every run"** heading whose "?" (`help.hardening.severity`) explains severity in plain words — **"Warn me"** (the run finishes, a message is printed) vs. **"Stop the run"** (marked as failed so a scheduler/monitor notices; exit code 2, an unexpected crash is 1) — which replaces the four hover-only `…SeverityWarning/ErrorTitle` tooltips (removed, as is the `title` attribute; the dynamic null-rate row never had one); a **"?" popover per check** (`help.hardening.noResult|nullRate|baseline|blocking|requiredFields`, one sentence of purpose plus an example) on the check's own toggle/heading; **thresholds as sentences** — "Trigger if there are [20] % fewer rows than in the last run" (static, `.hardening-sentence`) and, in each dynamic null-rate row, "[Preis ▾] is empty in more than [50] % of the rows" (`idle.hardeningNullRateMiddle/After`; the row now wraps), with the existing defaults (20 % / 50 %) unchanged; the blocking check's two rarely needed signals (**min. response length** as "Page shorter than [ ] bytes (optional)" and **block phrases**) sit under an **Advanced** disclosure (`<details data-advanced="hardening-blocking">`, the #396 component, collapsed by default and remembered) with one popover (`help.hardening.blockingAdvanced`: "1000 bytes is about one paragraph", phrases such as "Access Denied"); the blocking toggle reads "Check whether the site blocks the script". **"Recommended checks"**: `popup/hardening-presets.js` (pure, `@ts-check`) `applyRecommendedHardening(hardening, fieldNames)` → `{ hardening, applied, needsFields }` switches on **"empty result" as "Warn me"** and **"required field" for the FIRST field only, as "Warn me"** — the required-fields check *drops rows* from the output, so it is only suggested for the first field (usually the name/ID that makes a row meaningful), never for all of them (that would silently drop rows whose optional fields are legitimately empty); - Content script (`extension/content/content-script.js`): `buildSelector`/`startSelection` accept an optional scope root (`scopeSelector` on the `START_SELECTION` message) — when adding a nested container/data field, click-based selection is restricted to descendants of the parent group, and the resulting selector is valid relative to whichever instance was actually clicked instead of to `document.body`. `startSelection` resolves `scopeSelector` against *every* matching instance (`document.querySelectorAll`, not just the first), and `onClick`/`isInScope` accept a click inside any of them — the selector is then built relative to the specific instance the click landed in (`scopeRootFor`), not a single instance fixed in advance (Issue #167 fix: previously only `document.querySelector`'s implicit first match was ever scoped, so a sub-element absent from that particular instance — e.g. an optional "vegan" badge only some menu items carry — could never be selected at all, even though the resulting selector would already have matched it correctly wherever it does appear; the extraction runtime's own per-instance handling of a non-matching selector was already null-safe, see `extract_group` below). A click outside every instance is still rejected and now also sends `SELECTION_CLICK_OUT_OF_SCOPE`, shown as a brief non-blocking toast hint instead of being silent. A `scopeSelector` miss on the very first lookup now retries for a short window (`retryScopeSelector`, every 180ms up to 1.8s total) before finally sending `SELECTION_UNAVAILABLE`, instead of failing immediately (Issue #137 fix: reported against `penny.de/angebote/`, which server-renders skeleton/placeholder tiles first and swaps them for the real, differently-classed tiles once client-side JS hydrates — a parent container's own selector, confirmed valid the moment it was picked, could transiently stop matching an instant later purely because the page's own rendering caught up in between, permanently blocking every attempt to add a nested container/field inside it. Only ever kicks in on a miss — the common case, where the element is already present, stays perfectly synchronous with zero added delay. Doesn't attempt to solve arbitrary virtual scrolling, where an element is fundamentally never in the DOM until scrolled into view; only closes the gap between "the container was just confirmed" and "the very next click a moment later." A `selectionGeneration` counter, bumped on every `startSelection`/`stopSelection` call, guards a still-pending retry timer from an already-superseded or explicitly cancelled round from re-arming selection or sending a stale `SELECTION_UNAVAILABLE` afterward. **Warning, not error, when the retry itself still finds nothing** (Issue #137 follow-up): confirmed via a real report against `penny.de` that a scope selector can legitimately, repeatedly fail to resolve for reasons entirely outside the extension's control (there: a class only present while the element is actually hovered, removed the instant the user's cursor leaves the page for the side panel to click "+ Datenfeld") — not a plugin malfunction, so this specific case is no longer indistinguishable from a genuine failure. `retryScopeSelector`'s give-up message carries `unavailableKind: 'scopeSelectorNotFound'`, distinct from the *other* `SELECTION_UNAVAILABLE` sender (`service-worker.js`, when `chrome.tabs.sendMessage` itself fails — no content script running at all, e.g. a `chrome://` page or a tab open since before the extension reloaded) — `popup.js` shows the former as a softer, differently-worded warning toast (`toast.scopeSelectorNotFound`, amber `.toast-warn` styling) with no "Report bug" button, so an expected, page-specific situation doesn't get reported as a plugin bug, while the latter (a genuinely unexpected failure) keeps the harder error styling and report option)

- **API mode: nested JSON responses** (Issue #54): the `API_CONFIG` screen's field list is a full tree editor (`renderApiTree`/`buildApiTreeNodeEl` in `popup/api-config-ui.js`, mirroring container mode's own `renderGroupTree`/`buildGroupTreeNodeEl` in `popup/container-tree-ui.js`), not just a flat list — a JSON response with more than one repetition level (e.g. `categories[*].subcategories[*].products[*]`) is represented as nested `ApiGroup` nodes, each scoping its children to whatever its own JSON path resolves to, with `ApiField` as the leaf. A single top-level match still renders as a one-node-deep tree, so the tree UI fully subsumes the original flat shape — the popup only ever builds/sends the tree shape going forward, though the wire format still accepts the legacy flat `ItemsPath`/`Fields` shape too (see the Compiler section below). `content-script.js`'s `deriveApiTreeSkeleton` (generalizing the original single-level `deriveItemsAndValuePath`) splits a clicked value's JSON path at *every* array boundary instead of just the last, and is pre-computed onto each candidate as `treeSkeleton` — `popup.js` runs in a separate execution context and can't call content-script functions directly, the same reason `itemsPath`/`valuePath` were already pre-derived there. - **Pick ids: a handled pick is never replayed** (Issue #429): every element pick (`ELEMENT_SELECTED`) reaches the side panel **twice** — directly from the content script (`chrome.runtime.sendMessage` goes to every extension context) and relayed by the service worker, which also writes it as `pendingSelector`/… to `chrome.storage.session` for a panel that is closed. Unlike `ToNumberTransform`'s heuristic coercion, these are strict, explicit conversions with a clearly defined failure behavior — the design decision the issue itself asked for, resolved as a per-transform `onError` mode rather than the more invasive "fail the whole row" option also floated in the issue (which would have needed the same kind of row/element-dropping machinery `RequiredFieldsCheck`, Issue #133, only built at real cost for a hardening check that runs once at the very end — not worth replicating per-transform for what's fundamentally the same "safe default" need `UseDefault` already covers). `ToDateTransform.SourceFormat` is the same `"{yyyy}"`/`"{mm}"`/`"{dd}"` mini-template `RangeSource.Format` (`Backends/Python/RangeFormat`) already establishes for ISO week/date API parameters — `FieldTransformValidator` delegates straight to `RangeFormat.ValidateFormat(RangeType.Date, ...)` for structural validation, and `PythonFieldTransformLiteral` resolves an unset format via `RangeFormat.Resolve(RangeType.Date, ...)` (`"{yyyy}-{mm}-{dd}"`, already ISO) rather than reimplementing that default. `FieldTransformValidator` additionally rejects `OnError == UseDefault` with no `DefaultValue` set (ambiguous — there's no sensible implicit fallback), the same structural-pre-check role it already plays for a blank/invalid regex pattern. `PythonFieldTransformLiteral` renders `OnError` via `.ToString()` (`"KeepOriginal"`/`"UseDefault"`) — the exact same PascalCase-string convention `HardeningCheck.Severity.ToString()` already uses in `PythonHardeningLiteral`, so both the C#-side literal and every template's own runtime string comparison share one vocabulary instead of a second, transform-specific casing convention.
- **Price/currency-to-number transform, companion side** (Issue #234): `ToCurrencyTransform : FieldTransform` (`"kind": "toCurrency"`, `IR/FieldTransform.cs`) — `Format` (default `ToCurrencyTransform.DefaultFormat`, `"1.234,56"`), plus the same `OnError`/`DefaultValue` contract as Issue #205's strict conversions. Resolves `toNumber`'s documented thousands-vs-decimal ambiguity (a lone `"1.234"` always read as 1.234) by making the separators explicit instead of guessed: `Format` must be one of `ToCurrencyTransform.SupportedFormats` (`1.234,56`, `1,234.56`, `1 234,56`, `1'234.56` — each preset written as its own example amount, its first punctuation mark the thousands separator, its last the decimal separator; the space preset also accepts no-break/narrow no-break spaces, the apostrophe preset a typographic apostrophe), enforced by `FieldTransformValidator`, which also folds it into the shared "`UseDefault` needs a `DefaultValue`" rule. `PythonFieldTransformLiteral` renders `{"kind": "toCurrency", "format", "onError", "defaultValue"}`. - **Combine/split field mapping, companion side** (Issue #206): two more `FieldTransform` derivatives — `CombineFieldsTransform` (`"combineFields"`, `SourceFieldNames: List<string>` ≥2, `Separator`) and `SplitFieldTransform` (`"splitField"`, `SourceFieldName`, `Separator`, `Index`) — the first two kinds whose runtime meaning isn't "transform my own incoming value" but "look up *another* field's own value by name", resolving an idea Issues #191/#192 explicitly deferred rather than designed (strict 1:1 Output Blueprint field mapping has no room for N:1/1:N). `FieldTransformValidator` covers only the structural checks a single transform can see in isolation (Combine needs ≥2 distinct non-blank names, Split needs a non-blank name and non-negative index) — the actual "does the reference make sense" check needs cross-field visibility `FieldTransformValidator` doesn't have, so it lives in a new `ScrapingPlanValidator.ValidateFieldTransformOrdering(transforms, fieldName, precedingSiblingNames, fieldLabel)` instead: rejects a self-reference and any name not already present in `precedingSiblingNames` — the ordered list of names already validated *before* this field in the exact same scope. - **Output Blueprints: import a target schema from a sample** (Issue #193, extended to the Tree schema kind by Issue #253, and to uploading a file from disk by Issue #252): lets the user fill a new blueprint's field list/tree by pasting/uploading a sample instead of typing every field name by hand — a "paste your DB table's column list"/"here's an existing CSV export" shortcut for the exact "typing out every target field name" tedium the issue's own motivation calls out. `extension/popup/output-blueprints.js`'s `parseFieldNamesFromSample(text)` (Flat) is a pure function auto-detecting the sample's own format from its content rather than a separate format picker (per the issue's own "simplest first version" framing): `JSON.parse` is tried first (`findSampleRecord` recursively looks for the actual "record" shape — a plain object whose own values are all scalars — drilling through any wrapper object/array around it, e.g. `{"offerTiles": [{"title": "", ...}]}`, since only the innermost record's own keys are useful field names here; a top-level array of strings is used as the field-name list directly), and only on a parse failure does it fall back to line-based parsing — first trying to recognize a pasted-but-not-strictly-valid JSON object literal one property per line (`extractLeadingKey`, dropping bare structural `{`/`}`/`[`/`]`/`,` lines via `isStructuralOnlyLine`, both prompted by real bug reports against the first version of this parser), and only once that finds nothing either does a comma in the first remaining line decide CSV-header-row vs. one-name-per-line; Deliberately **does not** reuse `findSampleRecord`'s wrapper-drilling here — a Tree import is supposed to reproduce real nesting, so a wrapper key like `"offerTiles"` becomes a genuine group node of its own instead of being collapsed away, which would defeat the entire point of importing a tree rather than a flat list; only when the JSON *root itself* is an array of objects (no wrapper key at all to name a node after) are its first element's own keys used as the top-level nodes directly. Also deliberately **requires valid JSON** — unlike the Flat case, there's no line-based fallback for a broken/non-strict-JSON paste, since recovering nesting from indentation in arbitrarily pasted text would be far more ambiguous than recovering a flat list; a top-level array of strings still becomes flat top-level field nodes, for parity with the Flat importer's own handling of that one shape. `importBlueprintFieldNamesFromSample` dispatches on `schemaKind` to call `buildBlueprintTreeFromSample`/replace `blueprintEditDraft.tree` instead, reporting the success toast's count via `countBlueprintTreeLeaves` (leaf fields, not top-level nodes, so a heavily-nested import doesn't misleadingly report "1 field imported"). `#blueprint-import-section` itself moved out of `#blueprint-flat-schema-section` (Flat-only) to a shared position above both schema sections in `modals.html`, since it now serves either schema kind. **One remaining deliberate first-version scope decision**, carried over unchanged from #193: import only ever **creates** a new blueprint's field list/tree, never merges newly-seen fields into an already-existing one — the issue's own second open question explicitly deferred that decision to "once #191's own Blueprint CRUD UI exists" (it now does, but merge-into-existing still needs its own UI surface: which existing blueprint, dedup-vs-append semantics, whether re-ordering happens — enough scope for its own follow-up issue rather than folding it in here), so the import section is hidden whenever `blueprintEditingId` is set (i.e. editing rather than creating), regardless of schema kind. Since `#blueprint-import-section` is already shared between both schema kinds (Issue #253), the file input is too, with no schema-kind-specific gating of its own. The file input's own value is reset right after reading (`e.target.value = ''`) so picking the exact same file a second time still fires a fresh `change` event. Called from the two places a "fresh site was just detected" actually happens: `companion-client.ts`'s `checkCompanion()` (right after resolving the live tab's URL) and `message-router.ts`'s existing stale-tracked-URL self-correction (Issue #85's own `ELEMENT_SELECTED` page-changed branch — a mid-session site change is treated identically to the initial one). `popup.js`'s `btn-new-scraper` handler additionally resets `scriptFileName`/`outputFileName` back to `''` (previously it didn't) — a small, deliberate behavior fix: without it, `'fixed'` mode's own "only fill when blank" rule would otherwise leave a manually-typed name from the previous scrape permanently pinned in place instead of "New scraper" giving the preference a fresh chance to apply, the same "start over" treatment every other field there already gets.

- **JSDoc type checking, opt-in per file** (Issue #238): no build step is added *for TypeScript* (the esbuild bundling of Issue #389 is separate) — `extension/tsconfig.json` runs TypeScript purely as a checker (`allowJs`, `noEmit`, `checkJs: false` globally) via a new `npm run typecheck` script (`tsc --noEmit`), wired into CI (`.github/workflows/ci.yml`'s `extension` job) right after `npm test`. `checkJs` stays off at the project level deliberately — flipping it on would try to typecheck every `.js` file in the extension at once, and most (every `<feature>-ui.js` DOM module, `popup.js` itself) were never written with JSDoc types in mind, so that would produce a wall of noise rather than catching real bugs. Instead, type checking is opt-in per file via a leading `// @ts-check` pragma — the five pure `<feature>.js` data/logic modules Architecture Decision #12 already keeps DOM-free were the first batch annotated: `scraping-config-builder.ts`, `config-import.ts`, `api-config.ts`, `container-tree.ts`, `field-transforms.ts`. Two new ambient declaration files under `extension/types/` back these annotations: `wire.ts` (the `SFWire` namespace) is a hand-kept mirror of the companion's wire-format IR (`ScrapingConfig`/`ContainerNode`/`ApiConfig`/`FieldTransform`/etc., companion/ScrapingFactory.Compiler/IR/*.cs) — same "both sides must independently reach the same shape" relationship this project already has for `sanitizeFileNameBase`/`FileNameSanitizer` or `RangeFormat`'s client-side mirror, not generated, so it can silently drift if a wire type changes without this file being updated alongside it; `drafts.ts` (the `SFDraft` namespace) describes this popup's own internal, richer "draft" shapes that get converted to/from the wire format (e.g. container-tree.ts's `kind: 'group'|'field'` tree nodes) — kept in one shared ambient namespace, not a local `@typedef` per file, specifically because JSDoc `@typedef`s declared inside a plain script (no import/export, like every file here) are file-scoped to TypeScript's checker and not implicitly global the way a runtime `self.SFXxx` assignment is, so e.g. container-tree.ts's own tree-node shape needs to be referenced from scraping-config-builder.ts's own JSDoc too. A structural union whose variants have no common discriminator-safe property (e.g. walking a `ContainerNode`/`ApiNode`/`ApiBodyNode` tree generically, the same "children present = group" sniff `ContainerNodeJsonConverter` uses companion-side) is read through a scoped `/** @type {any} */` cast at the one call site that needs it, rather than fighting the union everywhere a tree is walked — `buildScrapingConfig`/`buildConfigExport`/`applyConfigToState` themselves (each five-branch builders spanning flat/container/api/combined/blocks) similarly return a plain `object` rather than a precisely-typed wire shape, since no single interface would usefully describe five mutually-exclusive branches without fighting TypeScript's excess-property checks on a returned object literal for little real benefit — every *input* parameter stays precisely typed regardless, which is where a real shape mismatch actually gets caught. To extend this to another popup module: add the pragma, annotate the module's exported functions' `@param`/`@returns` against `SFWire`/`SFDraft` (or a new local `@typedef` if the shape is genuinely local to that one file), and run `npm run typecheck`.
- **TypeScript migration, foundation** (Issue #394, part 1): the extension moves from JavaScript with JSDoc types to TypeScript one file at a time, in the order where types pay off most (the plan and its 21 parts are in #394 and its sub-issues). **Setup.** esbuild bundles `.ts` and `.js` side by side, so a converted module is simply renamed; `module.exports` becomes `export`, `require` becomes `import` inside the converted file, while a still-`.js` consumer keeps its `require` (the interop works in both directions). Jest stays Jest: `extension/jest-transform.js` compiles `.ts` with the esbuild the bundle already uses (no new dependency), `.js` keeps `babel-jest` because that hoists `jest.mock`; tests remain `*.test.js` and `require` the `.ts` sources. `tsconfig.json` includes `**/*.ts` and turns `strict` on globally (a measurement found zero errors across the extension, as the annotated files were already strict-clean); `checkJs` stays off, so a `.js` file is only checked when it carries `// @ts-check`. `typescript.test.js` guards the setup (strict + `.ts` include, a `.ts` module loading through Jest and the bundle, no leftover `module.exports`/`require`/`@ts-check` in a `.ts` file). **A script run by plain Node cannot load a `.ts` file** (`build.js`, `docs-build.js` and what they `require`), so those stay JavaScript unless the wrap-up decides otherwise. **Converted in part 1** (all pure, no DOM, no `chrome`): `choice-guidance`, `advanced-defaults`, `glossary`, `api-link-pagination`, `hardening-presets`, `selector-text-filter`, `env-var`, `transform-presets`, `login-flow`, `docs-links`, `request-header-presets`, `error-messages`, `transform-helpers`, `request-headers`, `dedup-config`;
