> **Code layout (Issue #391):** `Program.cs` is startup and middleware only. The endpoints live in `companion/ScrapingFactory.Companion/Endpoints/` (`ConfigEndpoints`, `BlueprintEndpoints`, `TransformPresetEndpoints`, `GenerateEndpoint` with `.Combined`/`.Blocks`), the trial-run skip rules in `Compiler/Backends/VerificationPolicy.cs`, and `ScrapingPlanValidator` is split into `partial` files by area. Where a note below says "`Program.cs`'s `/generate` handler" or a helper "in `Program.cs`", read it as the matching file there; behavior is unchanged.

- .NET 10 console application
- Starts a local HTTP server for the extension
- `/generate` generates the script, then runs it as a trial via the language module's verifier (`Backends/Python/PythonScriptVerifier`) in a temporary directory and only returns it on success (exit code 0, at least one data row, or — for container mode — one XML element) — on failure, returns `422` with an error message instead of the script
- **Scaling the trial-run timeout for long-running browser actions, and capping it instead of hanging** (Issue #289 follow-up): `PythonScriptVerifier`'s constructor-level default timeout (45s) was never meant to cover a legitimately long-running configuration — a `ScrollStep`/`WaitForStep` (top-level `BrowserActions`, a login flow) or, since Issue #216, a `BrowserDiscoverySource` parameter's own nested `Actions` (a *separate*, sequential Playwright session per such parameter, so N of them are additive, not just "the single worst one") can legitimately need far longer than that to actually finish. `Program.cs`'s new `EstimateExtraVerificationTimeoutMs(ScrapingPlan)` sums `MaxIterations × WaitAfterMs` for every `ScrollStep`/`ScrollAction` and `TimeoutMs` for every `WaitForStep`/`WaitForAction`, across both top-level `BrowserActions` and every `ApiCallStep`'s own parameters' `BrowserDiscoverySource.Actions` — replacing three separate, already-duplicated, narrower inline computations (which only ever looked at top-level `ScrollStep`s, the actual root cause of a real bug: a `BrowserDiscoverySource`-only config's own nested scroll action was invisible to them, since `Actions` never goes through `ScrapingPlanBuilder`'s step translation at all) with one shared helper, used by the single-mode, Combined, and Blocks `/generate` branches alike. The result feeds `VerifyAsync`/`VerifyBlocksAsync`'s existing `extraTimeout` parameter, added on top of the verifier's own base timeout. **A 10-minute cap** (`VerificationTimeoutCap()`) on this *estimate* (not on the actual run) protects the companion from a single absurd config (e.g. `MaxIterations: 1000000`) hanging a `/generate` call indefinitely: when the estimate exceeds the cap, the trial run is skipped entirely — no subprocess is spawned at all — and the already-generated, already-validated script is returned as if verification had succeeded (a synthetic, nothing-populated `ScriptVerificationResult { Success = true }`, or, for Blocks mode, one empty `BlockVerificationResult` per block so the usual `{ script, blocks: [...] }` envelope shape is preserved) rather than failing the request outright — the configuration may well be entirely correct, it just can't be *proven* so within the cap. The skip is surfaced via a response header, `X-ScrapingFactory-Verification-Skipped` (plain English reason text, naming the estimated time and the cap) — a header rather than a body field specifically because it needs to reach the caller regardless of which response-body shape follows (plain script text, or the `{ script, preview, outputFile }`/`{ script, blocks }` JSON envelopes Issues #122/#161/#182 each added) without needing its own per-shape plumbing in each. `companion-client.js`'s `generate()` reads this header unconditionally, right after the existing `res.ok` check and before branching on response-body shape, and — when present — shows it as a warning toast (`showToast(reason, null, 'warn')`, the companion's own English text shown as-is per this project's established "no i18n translation for companion-originated error/warning text" convention, `context: null` since this is expected, by-design safety behavior, not a malfunction worth a "Report bug" prompt).
- **Trial-run timeout scales with API mode's parameter combination count** (Issue #295): the estimate above used to know only browser-action durations, so a perfectly valid API configuration with no browser action at all — e.g. 11 ISO weeks × 22 category slugs = 242 sequential `requests` calls against a real site (observed against `penny.de`) — always hit the bare 45 s verifier default with a generic "exceeded the timeout" error, since API mode sends one real request per cartesian-product combination. The estimate moved out of `Program.cs` into `Backends/VerificationTimeEstimator` (public static, so it is unit-testable; `Program.cs`'s `EstimateExtraVerificationTimeoutMs` is now a one-line delegate) and gained a second term: `(combinationCount - 1) × AssumedMsPerApiRequest` (1000 ms; the `-1` because one request is already covered by the verifier's base timeout). `CountApiCombinations` multiplies every parameter's value count — `StaticListSource.Values.Count`, `RangeFormat.CountValues(RangeSource)` for a range, and 1 for `DiscoverySource`/`BrowserDiscoverySource` (their list size is only known at run time, so they contribute no information rather than a guess; a zero-value parameter makes the product zero, i.e. no extra budget) — with saturating arithmetic, so an absurd product can't overflow. `RangeFormat.CountValues` (`Backends/Python/RangeFormat.cs`) is the C# mirror of the generated script's `_iso_week_range`/`_date_range`/`_number_range` (inclusive on both ends, an inverted range is empty, `"today"` resolves against the companion's clock — for IsoWeek in either position, for Date only as `To`, exactly like the script) and returns `null` for a value it can't parse (the validator rejects those before any estimate is made; the fallback just treats the parameter as 1). It composes with the existing 10-minute `VerificationTimeoutCap()`: ~600 combinations are still verified for real, a larger product skips the trial run via the usual `X-ScrapingFactory-Verification-Skipped` header/warning toast instead of hanging `/generate`. **Why a fixed constant, not a `CompanionBackendOverrides` knob** (the issue's open question): it is an estimate, not a tuning parameter — a slower target loses nothing but the trial run itself, and the verifier's base timeout already has its own `VerifierTimeoutSeconds` override for a slow machine. **Deliberately not counted:** request pauses (#222) and retry waits (#223) — `PythonScriptVerifier` already extends its deadline for every pause/retry the script announces at run time — and cursor-pagination pages per combination (#224), whose count is only known from the responses. Covered by `VerificationTimeEstimatorTests` (the issue's 11 × 22 scenario, range counting incl. year boundary/"today"/unparsable values, saturation), `ApiCombinationTimeoutEndToEndTests` (60 requests of 100 ms against a 3 s base timeout: passes with the estimate, times out without it) and an endpoint test for the skip header.
- **Opt-out of the trial run** (Issue #292): `ScrapingConfig.SkipVerification` (`bool?`, additive — absent/false is today's behavior), mode-independent and read from the **outer** request only (single mode, Combined — where the one verification run belongs to the combined script — and Blocks; a Combined component's own nested value is ignored). `Program.cs`'s `VerificationSkipReason(config, extraMs)` replaces the three direct `CheckVerificationTimeoutCap` calls: with the flag set it returns "Verification was skipped because it is disabled in Settings - …", otherwise the usual timeout-cap check — so the existing skip mechanics (no subprocess, a synthetic success `ScriptVerificationResult`/empty `BlockVerificationResult`s, the `X-ScrapingFactory-Verification-Skipped` header, the envelope shapes) are reused unchanged, and `companion-client.js` already shows the header as a warning toast. A user-chosen skip is checked before the automatic cap so the message says what actually happened. `ScrapingPlanValidator` and the other structural checks (400s) still run first; only the real execution is dropped. A requested preview/output file comes back `null`. The extension side is a plain cross-session preference: `globalSettings.skipVerification` (`shared/global-settings.js`, a "Skip the trial run" checkbox `#toggle-skip-verification` on the Settings screen next to the other three output toggles), threaded through `buildScrapingConfig`/`buildConfigExport` as a new last positional parameter (`skipVerification`, after `respectRobotsDelay`) into all five mode branches and read fresh from `getGlobalSettings()` at the three call sites (`generate()`, "Export configuration", "Save configuration"); deliberately Global-Settings-only, not a per-generate toggle (the issue's open question), like the other output-related preferences. **Bug found on the way:** the header value must be plain ASCII — Kestrel throws on any other character when the header is set, which turned the existing timeout-cap skip (#289/#290, whose text contained an em dash) into a `500` on a real host while the in-memory test server accepted it; both reason texts are ASCII now and `SkipVerificationEndpointTests` asserts it. Covered by `SkipVerificationEndpointTests.cs` (single/Browser/API/Blocks/Combined skip without running anything — every request targets a non-existent host, so a 200 proves no subprocess ran —, envelope with null preview, 400 validation still running, `false` = absent, ASCII header), `skip-verification.test.js`, the Settings/`generate()` tests, and `e2e/examples/issue-292-skip-verification-check.js` (flaky-server: fails with the trial run, reaches DONE with the warning once skipped).
- **Trial-run data preview** (Issue #122): `ScrapingConfig.IncludePreview` (nullable bool, additive/wire-compatible — absent/false is byte-for-byte today's response) lets the caller opt into seeing a capped sample of what the trial run actually scraped, instead of it being discarded once verification's pass/fail check is done. When `true`, a successful `/generate` returns JSON (`{ script, preview }`) instead of the plain script text; `preview` is `Backends/ScriptPreviewData` (`outputFormat`, `totalCount`, `truncated`, plus `columns`/`rows` for Csv or a pretty-printed, capped `xmlSample` for Xml — a structured tree view for Xml, mirroring the container/API config tree UI, is deliberately out of scope for now, see `PLAN-trial-run-data-preview.md`, kept locally/uncommitted like `architekturkonzept.md`). `PythonScriptVerifier.VerifyAsync`'s new `includePreview` parameter builds this from the *same* CSV lines/XML document it already reads for the row/element-count check — no new I/O — capped at 50 rows/top-level elements (`PreviewSampleCap`) regardless of how much the script actually scraped. CSV field-level parsing (needed here, unlike the row-count check, which only counts lines) mirrors Python's `csv.DictWriter` default dialect via a small `ParseCsvLine` helper (quoted fields, `""` escaped quotes) — the row-count check itself is untouched.
- **Download the full trial-run output** (Issue #161): `ScrapingConfig.IncludeOutputFile` (nullable bool, additive/wire-compatible, independent of `IncludePreview` — either, both, or neither may be requested in the same call) lets the caller keep the trial run's *complete*, uncapped output file instead of it being discarded. `IScriptVerifier.VerifyAsync`/`PythonScriptVerifier`'s new `includeOutputFile` parameter reads the raw file text (`File.ReadAllText`, **not** re-derived from `ScriptPreviewData`'s parsed/capped sample) at each of the three success paths (Csv's inline branch, `VerifyXmlOutput`, `VerifyJsonOutput`) and attaches it to `ScriptVerificationResult.OutputFileContent`/`OutputFileName` — reading the raw bytes rather than reconstructing them from already-parsed lines/nodes is what keeps the eventual download byte-identical to what the script actually wrote. `Program.cs`'s `/generate` handler's JSON-envelope condition (previously "`IncludePreview == true`") is now "`IncludePreview == true || IncludeOutputFile == true`", adding an `outputFile: { fileName, content }` key (or `null`) alongside `script`/`preview` — a request with neither flag set still gets byte-for-byte the same plain-text response as before either feature existed.
- **Runtime requirement:** `python3` (or `python`) including `requests` + `beautifulsoup4` must be available on the PATH of the machine running the companion app — not just for the end user who later runs the downloaded script. For the browser engine (`Engine: "Browser"`), `playwright` (`pip install playwright`) plus an installed Chromium (`playwright install chromium`) is additionally required. For the Excel output format (Issue #229), `openpyxl` (`pip install openpyxl`) is additionally required — only when that format is chosen
- **Configuration** (`appsettings.json`'s `Companion` section, standard ASP.NET Core precedence — so also overridable via e.g. `Companion__Port=5050` env var or a CLI arg, with no extra wiring): `Host`/`Port` (default `localhost`/`5000`, read by `CompanionHostOptions.BuildListenUrl` and passed to `builder.WebHost.UseUrls`) let the app bind somewhere other than the default when that port is already taken or the companion runs on a different machine than the extension expects — the extension-side counterpart is `shared/companion-config.js` above. `PythonExecutable`/`VerifierTimeoutSeconds` (both unset/null by default, keeping today's `python3`/`python` auto-probe and 45s timeout) reach `PythonScriptVerifier`'s own already-optional constructor parameters via `CompanionBackendOverrides.Build` and `LanguageModuleRegistry`'s generic `ctorOverrides` (a `Dictionary<string, object?>` matched against a reflectively-discovered backend's constructor parameter names) — useful for a machine with a non-standard Python install path, or one slow enough that the default trial-run timeout needs raising. All four are the same kind of hosting-machine-specific value; `ctorOverrides` is deliberately generic (name-matched, no compile-time reference to `PythonScriptVerifier`) so a future non-Python language module could expose its own optional constructor parameters through the same mechanism without touching the registry again
- **Release bundles, installer and per-user settings file** (Issue #346): every GitHub Release gets one bundle per platform (`win-x64` .zip, `linux-x64`/`osx-arm64`/`osx-x64` .tar.gz) built by `install/build-bundle.sh` and attached by `.github/workflows/release-bundles.yml` (runs when a Release is published, or by hand for a tag). A bundle holds the companion as a **self-contained, single-file, compressed** executable (`dotnet publish -r <rid> --self-contained -p:PublishSingleFile=true -p:EnableCompressionInSingleFile=true`, ~50 MB, deliberately *not* trimmed because `LanguageModuleRegistry` finds the code generators by reflection; the Scriban templates are embedded resources, so nothing else ships next to it), the unpacked `extension/` (runtime files only) and the installer. `install.sh` (Linux/macOS) / `install.ps1` (Windows) copy the bundle into the per-user data directory (`~/.config/ScrapingFactory`, `~/Library/Application Support/ScrapingFactory`, `%APPDATA%\ScrapingFactory` — the same folder .NET's ApplicationData resolves to and the SQLite stores already use) under `app/`, create a **dedicated venv** (`venv/`) with `requests`, `beautifulsoup4`, `openpyxl` (`--browser-engine` adds Playwright + Chromium), write the interpreter into the **per-user settings file** and optionally register autostart (systemd user unit / LaunchAgent / Scheduled Task) before starting the companion and waiting for `/health`. A system Python 3.9+ is still required to create the venv (the trial run executes the real script); the installers fail with an actionable message when it is missing. The extension itself cannot be installed silently (Chrome Stable refuses `--load-extension`), so the installer prints the `Load unpacked` folder; a store listing is a separate step. Re-running updates in place; `uninstall.*` removes the installation but keeps the `*.db` data unless `--purge`/`-Purge`. **Per-user settings file**: `companion.settings.json` in that data directory (path override: env `SCRAPINGFACTORY_COMPANION_SETTINGS`) is loaded as one more configuration source by `CompanionUserSettings.Apply` — precedence appsettings.json < settings file < environment variables < command line (the environment/command-line sources are re-added after it so they still win). The installer only writes `Companion:PythonExecutable` (and `Companion:Port` for `--port`); it is also where later per-installation settings (e.g. a database connection for a MySQL backend) belong, instead of editing the appsettings.json inside the program folder, which an update replaces. Verified on Linux (build → unpack → install into an isolated `HOME`/`XDG_CONFIG_HOME` → `/generate` runs the trial with the venv interpreter, proven by pointing the settings file at a bogus path → uninstall/purge) and by cross-publishing the Windows/macOS bundles; **`install.ps1`, the macOS LaunchAgent and the systemd autostart path are untested** (no PowerShell/macOS/systemd session in the development environment). Covered by `CompanionUserSettingsTests.cs`.
- **Local saved-configuration history** (Issue #141): a small local SQLite database (`Microsoft.Data.Sqlite`, no EF Core — a handful of simple queries don't need it), one table (`SavedConfigStore.cs`: `Id`, `Url`, a `Host` column derived once at save time via `Uri.TryCreate(url, ...).Host` — falling back to the raw string if unparseable — so lookups scope by hostname rather than requiring the exact saved page, `Name`, `SavedAt`, `ConfigJson`). Stored in a per-user app-data directory (`Environment.SpecialFolder.ApplicationData`/XDG-equivalent, resolved by `SavedConfigStore.ResolveDbPath` — overridable via `Companion:SavedConfigsDbPath`/`Companion__SavedConfigsDbPath`, same configuration-precedence pattern as `Host`/`Port`/`PythonExecutable` above, used by the test suite to point at an isolated temp file), never the working directory the companion happens to be launched from. `ConfigJson` is stored and returned **opaquely** — bound as a raw `JsonElement` in `POST /configs` and never deserialized into `ScrapingConfig` — so this endpoint doesn't need to track the wire format's own ongoing evolution, only round-trip whatever JSON object the extension handed it. Registered as `AddSingleton<SavedConfigStore>()` (a type, not a pre-built instance like `LanguageModuleRegistry`) so DI only constructs it — and only then creates the SQLite file — on the first actual `/configs` request; `/health`/`/generate` never touch it. Four endpoints alongside `/health`/`/generate`, same local-HTTP-server pattern (Architecture Decision #2): `POST /configs` (`{ url, name, config }` → `201` `{ id, url, name, savedAt }`), `GET /configs?url=...` (→ `200` with every saved entry for that URL's hostname, newest first, summary-only — no `config` blob), `GET /configs/{id}` (→ `200` with the full record including `config`, or `404`), `DELETE /configs/{id}` (→ `204`/`404`). Purely local/additive — no data ever leaves the user's machine, same trust boundary as the rest of the companion↔extension communication
- **Storage behind interfaces** (Issue #276): the three local stores are no longer injected as concrete classes — `ISavedConfigStore` (`/configs` + saved outputs), `IOutputBlueprintStore` (`/blueprints`) and `ITransformPresetStore` (`/transform-presets`) (`companion/ScrapingFactory.Companion/I*Store.cs`) are what `Program.cs` registers (`AddSingleton<I…, …>`, still lazily constructed on first use) and what every endpoint handler takes; `SavedConfigStore`/`OutputBlueprintStore`/`TransformPresetStore` are simply the current SQLite implementations. A pure refactor — method signatures, wire format and behavior are unchanged. The interfaces list only what the handlers call; everything SQLite-specific (connection string, `PRAGMA foreign_keys = ON`, the idempotent `AddColumnIfMissing` migrations, `ResolveDbPath`, the constructors) deliberately stays inside the implementations, since another backend has its own connection and migration story. The contract notes an implementation must keep are on the interfaces themselves (verbatim `ConfigJson`/`Content`, cascading delete of a configuration's outputs, newest-first lists, null/false for "not found"). Prerequisite for a MySQL backend and per-user authentication (separate issues). Covered by `StoreAbstractionTests.cs` (each endpoint family runs against an in-memory fake registered in DI; the defaults resolve the SQLite classes by interface).
- **MySQL storage backend** (Issue #277): the second implementation behind the #276 interfaces. `Companion:Storage:Provider` = `Sqlite` (default, unchanged: one local file per store) | `MySql`, plus `Companion:Storage:MySql:ConnectionString` (required for MySql) — read through the usual configuration chain, so appsettings.json, the per-user `companion.settings.json` (Issue #346; the installers write it with `--mysql STRING` / `-MySql STRING` / env `SF_MYSQL_CONNECTION_STRING`, file mode 600, `--sqlite` switches back), environment variables and the command line all work. `Storage/StorageOptions.cs` resolves the provider (unknown value → startup error), normalizes the connection string through `MySqlConnectionStringBuilder` (forcing `UseAffectedRows=false`, so `UPDATE` reports *matched* rows — the stores' "false = no such id" contract) and creates the stores; `Program.cs` registers `ISavedConfigStore`/`IOutputBlueprintStore`/`ITransformPresetStore` with factory lambdas over `IConfiguration` (so a test host's configuration overrides are honoured), still lazily created on first use, and calls `StorageOptions.Validate` right after `Build()` (a typo'd provider or a missing connection string stops the companion with a clear message, without connecting). An unreachable/misconfigured database surfaces on first use as a `MySqlException`, which a small middleware turns into `503 { error: "The storage database is not available: …" }` instead of an anonymous 500 (`/health` and `/generate` never touch storage). New optional dependency `MySqlConnector` — a managed NuGet package compiled into the companion, so there is nothing for a SQLite-only user to install and it is never loaded unless MySql is configured. `Storage/MySqlSavedConfigStore.cs`, `MySqlOutputBlueprintStore.cs`, `MySqlTransformPresetStore.cs` implement the same contract (ISavedConfigStore's notes apply) in one shared database with these dialect decisions: `ConfigJson`/`Content`/`*Json` columns are `LONGTEXT` (MySQL's `TEXT` caps at 64 KB), `Host` is `VARCHAR(255)` so it can be indexed (a longer raw-string fallback host is truncated on save and lookup alike), `SavedAt` stays the same fixed-width ISO-8601 text so "newest first" sorts exactly like SQLite, `ON DELETE CASCADE` is a real InnoDB foreign key (no PRAGMA), blueprint/preset lists are ordered by name under the case-insensitive utf8mb4 default collation, and preset name uniqueness is `LOWER(Name) COLLATE utf8mb4_bin` (case-insensitive but accent-sensitive, like SQLite's NOCASE). **Schema/migrations**: tables are created with `CREATE TABLE IF NOT EXISTS` using the original columns and every later column (`SavedConfigs.BlueprintId`, `OutputBlueprints.SchemaKind`/`TreeJson`) is added by `MySqlSchema.EnsureColumn` (an `information_schema` check + `ALTER TABLE`, the MySQL twin of `AddColumnIfMissing`), so a database created by an older build keeps working. Not done: copying existing SQLite data over, per-user separation (needs the authentication issue), PostgreSQL. Tested against a real MySQL 8.4 (`SF_TEST_MYSQL="Server=127.0.0.1;Port=3399;User ID=root;Password=sf"`, e.g. `podman run -d -p 3399:3306 -e MYSQL_ROOT_PASSWORD=sf mysql:8.4`; CI runs a `mysql:8.4` service container; without the variable the MySQL tests are reported as skipped): `StorageContractTests.cs` runs one behavioral contract per store against SQLite *and* MySQL (each MySQL test in its own throwaway database; includes >64 KB configs, cascade delete, newest-first, blueprint join, matched-rows updates, idempotent restart and upgrading an "older" database), `StorageProviderTests.cs` covers provider/connection-string validation, the startup refusal, the 503 path and the three endpoint families end to end on MySQL; the installer path was verified by installing a bundle with `SF_MYSQL_CONNECTION_STRING` and finding the saved configuration in the MySQL table.
- **Store dialects** (Issue #392): the SQLite and MySQL stores used to be the same SQL written twice. Each store is now an abstract base class (`SqlUserStoreBase`, `SqlSavedConfigStoreBase`, `SqlOutputBlueprintStoreBase`, `SqlTransformPresetStoreBase`, all on `SqlStore`) with every query written once against `System.Data.Common`; the concrete SQLite and MySQL classes keep only their DDL, idempotent migrations (`SqliteSchema`/`MySqlSchema.EnsureColumn`) and these hooks, which are everything that really differs: the connection (SQLite's saved-config store also issues `PRAGMA foreign_keys = ON` per connection; InnoDB always enforces its foreign key); the SQL returning the last insert id (`last_insert_rowid()` / `LAST_INSERT_ID()`, read on the same connection right after the INSERT); the email-code upsert (`ON CONFLICT … DO UPDATE` / `ON DUPLICATE KEY UPDATE`); unique-violation detection (`SqliteException` code 19 / `MySqlErrorCode.DuplicateKeyEntry`, and which index the message names, to tell a duplicate email from a duplicate user name); case-insensitive name order and comparison (`COLLATE NOCASE` / the default collation, and `LOWER(…) COLLATE utf8mb4_bin` for preset names, which keeps accents significant like NOCASE); the stored host (MySQL truncates to its indexed `VARCHAR(255)`); and the column types. Differences in what a driver returns (an integer or flag as `long` vs. `bool`) are absorbed by `SqlStore.ToInt64`. A dialect that `UPDATE`s reports *matched* rows (MySQL needs `UseAffectedRows=false`, see `StorageOptions`), which the "false = no such id" contract relies on. A new column or query is now written once in the base class plus one DDL line per backend. Avoided on purpose: a micro-ORM (the duplication was the SQL, not the mapping) and a separate `IDbDialect` object (the same five hooks, one more type). `StorageContractTests`, `AccountTests` and `EmailAccountTests` run the same contract against both backends and are the safety net.
- **Per-user authentication** (Issue #278): optional, **off by default** — a purely local, single-user companion keeps today's "no login" behavior. `Companion:Auth:Enabled` (appsettings.json, the per-user settings file, env `Companion__Auth__Enabled`, or the installers' `--enable-auth`/`-EnableAuth`, `--disable-auth` to undo) switches it on. **Keys and users**: `Auth/ApiKeys.cs` generates a 256-bit random key (`sf_` + base64url), shown exactly once; only its SHA-256 is stored (no salt needed for a random 256-bit secret). `IUserStore` (`SqliteUserStore` → `users.db`, `Companion:UsersDbPath`; `MySqlUserStore` → a `Users` table in the Issue #277 database, so a shared server's users and their data are one thing) holds `Users(Id ≥ 1, Name unique case-insensitive, KeyHash unique, CreatedAt)`. Users are provisioned **out-of-band** by whoever runs the companion — never self-service from the extension — through the same binary: `ScrapingFactory.Companion user add|list|rotate|remove|adopt <name>` (`Auth/UserCommands.cs`, checked in `Program.cs` before the web host starts; it reads the same configuration chain, so an installed companion's settings file or MySQL connection is honored; names `[A-Za-z0-9][A-Za-z0-9._-]{0,63}`). `adopt` hands every row saved while authentication was off (owner 0) to a user via `ClaimUnowned` on the three data stores; `remove` leaves the user's rows in place but unreachable (ids are never reused). **Request handling**: when enabled, a middleware in `Program.cs` (after the 503 handler, so a database outage while checking a key is a 503, not a 500) requires `Authorization: Bearer <key>` on every request except `/health` and CORS `OPTIONS` preflights (which is why the extension can still reach the companion to explain what is missing), answers `401` with `WWW-Authenticate: Bearer` and a message ("requires an access key" vs. "not valid"), and otherwise stores the resolved user as `CurrentUser` (`Auth/CurrentUser.cs`, bound into endpoint handlers as a plain parameter via `BindAsync`; without authentication it is the anonymous owner `0`). `/generate` is protected too. `/health` now returns `{ authRequired }` (still 200) and the new `GET /whoami` returns `{ name, authRequired }` (the extension uses it to validate a key). **Ownership scoping**: every method of `ISavedConfigStore`/`IOutputBlueprintStore`/`ITransformPresetStore` takes the owning user's id as a trailing `long ownerId = 0` (so existing callers and tests mean "no authentication" unchanged), and both implementations add `OwnerId BIGINT NOT NULL DEFAULT 0` to `SavedConfigs`/`OutputBlueprints`/`TransformPresets` through the idempotent column migrations (pre-existing rows are owner 0, still visible without authentication). Saved outputs have no owner column — they are scoped through their configuration with a join (`GetOutput`, `ListOutputsByConfigId`, `DeleteOutput`, `GetMostRecentOutputFor*`, and `SaveOutput`, which inserts only `SELECT … WHERE the configuration belongs to the owner` and throws `KeyNotFoundException` otherwise); "not found" therefore also means "belongs to someone else", and preset names are unique **per owner**. The endpoint handlers pass `user.Id` into every store call; two users cannot read, change or delete each other's rows by id (covered end to end). **Extension**: the key is a device preference (`chrome.storage.local`, `shared/companion-config.js`: `loadAccessKey`/`getAccessKey`/`setAccessKey`, cached for synchronous reads, never logged); `companionFetch` in `popup/companion-client.js` wraps every companion request (health aside) and adds `Authorization: Bearer <key>` — with no key it is byte-for-byte the plain `fetch(url[, init])` — so every `fetch` to the companion in `saved-configs-ui.js`/`output-blueprints-ui.js`/`transform-presets-ui.js`/`companion-client.js` goes through it. `checkCompanion` reads `authRequired` from `/health` and only then calls `/whoami`, showing a warn toast ("requires an access key" / "rejected the access key") when it answers 401; an older companion or an unexpected response is ignored. - **Output Blueprints: `OutputBlueprintStore` and `/blueprints` endpoints** (Issue #191): a small local SQLite database, `OutputBlueprintStore.cs` (own file/db, `output-blueprints.db`, `Companion:OutputBlueprintsDbPath` override — mirrors `SavedConfigStore`'s own configuration-precedence pattern, but no FK/cascade, since a blueprint isn't tied to any saved configuration), one table (`OutputBlueprints`: `Id`, `Name`, `SavedAt`, `FieldNamesJson`). Five endpoints alongside `/health`/`/generate`/`/configs`: `POST /blueprints` (`{ name, fieldNames }` → `201`), `GET /blueprints` (→ `200`, every blueprint, summary + field count), `GET /blueprints/{id}` (→ `200` with the full ordered `fieldNames` list, or `404`), `PUT /blueprints/{id}` (→ `200`/`404`), `DELETE /blueprints/{id}` (→ `204`/`404`). `/generate`'s own outer-request validation rejects `OutputBlueprint` set together with `Combined` or `Blocks` with a `400` — the same "reject outright, don't silently no-op" precedent `AdditionalUrls`-vs-`Api` already established. (`Groups`/`Api.Groups` were rejected the same way originally too — see Issue #192 below for why that's no longer the case.)
- **Output Blueprints: container/API-tree mode support** (Issue #192): extends the mapping above to container mode and Api mode's tree shape by *flattening* the source tree into denormalized rows instead of rejecting the combination outright — see the Compiler section's own `OutputBlueprintFlattening` entry for the row-scope/broadcast mechanics. `Program.cs`'s previous `OutputBlueprint`-vs-`Groups`/`Api.Groups` rejection is gone; `Combined`/`Blocks` still reject it, since neither has a single field/tree config of its own at the outer level to flatten.
- **Output Blueprints: nested/"containered" target schema, store/endpoint side** (Issue #244): `OutputBlueprintStore`'s `OutputBlueprints` table gains two columns, added via an idempotent `ALTER TABLE ... ADD COLUMN` migration (checked via `pragma_table_info`) rather than baked into the original `CREATE TABLE IF NOT EXISTS` — so an `output-blueprints.db` created before this feature keeps working without the user deleting/recreating it: `SchemaKind` (`TEXT NOT NULL DEFAULT 'Flat'` — every pre-existing row defaults to the only schema kind that existed before this issue) and `TreeJson` (`TEXT NULL`, populated only for a Tree-schema blueprint, storing its own `List<OutputBlueprintTreeSchemaNode>`; stays `NULL` for a Flat one, whose `FieldNamesJson` keeps its exact pre-#244 meaning). `SchemaKind` is deliberately a plain string, not the Compiler project's `OutputBlueprintSchemaKind` enum type — but still PascalCase (`"Flat"`/`"Tree"`), matching that enum's own `JsonStringEnumConverter` wire serialization exactly, so the extension never needs to translate between two different casings for what both endpoints/wire types call the same concept. `Save`/`Update` take an additional `schemaKind`/`tree` pair (the existing `fieldNames` parameter simply goes unused for a Tree-schema call, and vice versa); `OutputBlueprintSummary.FieldCount`/`ListAll`/`Get` report the total *leaf* count for a tree, recursively, so the extension's picker shows one consistent "N fields" hint regardless of schema kind. `Program.cs`'s `/blueprints` `POST`/`PUT` share one `ValidateBlueprintRequest` local function: a missing/blank `schemaKind` in the request defaults to `"Flat"` (so a pre-#244 extension build's request, which never sends this field at all, keeps working byte-for-byte); a `"Tree"` request's own `tree` is validated via the new `OutputBlueprintTreeSchemaValidator.Validate` (non-blank node names, recursive, a group needs at least one child) instead of duplicating that structural check inline; an unrecognized `schemaKind` value is rejected with a `400`.
