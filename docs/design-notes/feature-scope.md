# Design notes — Feature scope

What each shipped feature covers and, as importantly, what it deliberately does not (as of v1.20).

> Moved here from `CLAUDE.md` (Issue #379) without changes of substance. This is **reference material, not instructions**: the behavior, edge cases and rationale of individual features, kept for whoever changes that feature. What applies to every change stays in `CLAUDE.md`; the structural map (which file does what) is `docs/ARCHITECTURE.md`. Phrases such as "the Compiler section", "the Python Templates section", "the Companion App section" or "the Browser Extension section" refer to the sibling files [compiler.md](compiler.md), [templates.md](templates.md), [companion.md](companion.md) and [extension.md](extension.md); "Architecture Decision #N" refers to `CLAUDE.md` (the popup module rule is now #13, formerly cited as #12); "Feature Scope" is [feature-scope.md](feature-scope.md). Issue numbers can be looked up with `gh issue view`.

Originally tracked as "v1 scope (MVP)" — the MVP has been reached since v1.0.0; this section is kept up to date with the overall current scope (most recently extended with, among other things, container-based scraping and API mode). Individual items move here from "Planned for Future Releases" once they ship.

- The default engine is still static rendering (`requests` + `BeautifulSoup`, no JS). An optional browser engine (Playwright + Chromium, `Engine: "Browser"`, plain Playwright + stock Chromium — **no commercial stealth-browser/anti-bot services with a license or session model**, e.g. CloakBrowser was evaluated and rejected, see git history) for dynamically rendered pages is fully wired into the extension UI (Issues #41/#42, Phases 5/6): an Engine toggle plus a generic, ordered browser-actions list (`WaitFor`/`Fill`/`Click`/`Scroll`, each with FramePath support for iframe-scoped actions), not a dedicated wizard per action kind. Verified through actual execution just like the static engine (the consistency rule is unchanged). The Scroll action's own default behavior (jump straight to the current bottom every iteration) can optionally be replaced with a fixed per-iteration pixel step (Issue #289) for a site whose sections only lazy-load once actually scrolled through rather than appending new content below the existing bottom. The Click action can target the first, the last or every match of a selector that matches several elements (Issue #267), instead of aborting on Playwright's strict-mode error.
- Logging in within a single script run is possible (fill out a form → submit → wait → extract, credentials only via environment variables, never in the script) — assembled from the generic browser-actions list above as a Fill+Fill+Click+WaitFor sequence, no dedicated login-specific UI (Issue #43). The popup also lets the user type one-time test values per `Fill` action, sent to the companion only with that `/generate` request (`ScrapingConfig.VerificationValues`, keyed by environment-variable name, filtered server-side against the actually-declared `Fill` actions — see `IR/FillVerificationValues.cs`) and used only for that request's trial-run subprocess (`PythonScriptVerifier`'s `extraEnvironmentVariables`) — never persisted (not even across a popup close/reopen, see `fillTestValues` in `popup.js`), never logged, never written into the generated script — so a login flow can be verified without the credentials already needing to be set as OS environment variables on the machine running the companion app. No persistent session handling across multiple script runs (no saving/reusing cookie/storage state)
- **No CAPTCHA solving/bypassing** — a deliberate boundary, not an open item: CAPTCHAs are a targeted anti-automation measure by the target site; a generic bypass feature would be evasion tooling regardless of intent in any specific case, and would typically require paid third-party solving services (violating the principle above). If a CAPTCHA blocks the flow, the script simply fails honestly (e.g. a `WaitForStep` after the login click doesn't find the expected element → timeout) — there is no special handling
- **Container-based scraping** (groups/containers, Issue #21): fully implemented, including extension UI (mode selection, tree editor, click-based selection scoped to whichever repeating instance is actually clicked, Issue #167). Four field-extraction modes: Text, Attribute, Exists, and OwnText (Issue #169 — an element's direct text only, excluding nested elements like a badge/tag sharing the same container). Every tree node (group or field) can be renamed in place and reordered among its own siblings after creation (Issue #177), without needing to delete and re-add it
- **Container mode: download embedded resources** (Issue #213): fully implemented for container mode's Attribute-mode fields — an opt-in "Download this resource" checkbox lets the generated script actually download an embedded resource (e.g. an `<img>`'s `src`) instead of only ever recording its URL, saving it into a sidecar directory next to the output file and writing that resource's own local file path into the output row/element in place of the bare URL. Deterministic, hash-of-the-absolute-URL filenames make repeated runs idempotent (an already-downloaded file is trusted and never re-fetched, so re-scraping the same page doesn't grow the sidecar directory without bound) rather than deriving a name from the URL's own basename, which two entirely different pages' own same-named files could otherwise collide on. A single failed download is logged as a warning and leaves that field empty — never fails the row or the run. Deliberately still out of scope, matching the issue's own open questions: flat mode and API mode (neither has an attribute concept reachable from their UI today — flat mode has no attribute-picking UI at all, API mode has no Mode concept whatsoever); other embedded-media shapes (`<video src>`, `<source srcset>`, CSS background images); any dedicated hardening signal for a high failed-download rate; and Change Detection's interaction with a now-binary-file-referencing output (its existing whole-file text diff already treats a changed local path like any other changed cell, with no special binary-aware handling).
- **Download files linked from scraped pages, and a download safety net** (Issue #214): fully implemented, generalizing Issue #213's mechanism rather than adding a second one — the issue's own motivating case (a listing page linking to downloadable reports/invoices/archives via `<a href="...">`) is served by the exact same "Attribute mode + Download" checkbox, now also reachable from flat mode (previously container-mode only) and backed by an optional safety net: a max file size (entered in MB, converted to bytes) and/or a content-type allowlist (comma-separated), either of which — when violated — is treated exactly like any other failed download (a warning printed, the field left empty, the run continues). Still out of scope, same reasoning Issue #213 already established: API mode (no `Mode`/`Attribute` concept at all) and Blocks mode's own flat draft shape (the wire format doesn't carry `Download` through a block's fields yet, rejected outright rather than silently ignored); the other embedded-media shapes/hardening-signal/Change-Detection open questions Issue #213 itself left open remain open here too.
- **API-based extraction** (API mode, Issue #53): fully implemented, including extension UI — network recording, click correlation against recorded JSON responses, parameter configuration with a value list/discovery endpoint/range/browser-discovery (Issue #216, see below) as value sources (including automatic format detection for ISO week/date). GET and POST requests (Issue #55, see below); a discovery-style source may now depend on an earlier-declared parameter (Issue #217, see below), though most independent-parameters limitations still stand for `RangeSource`/`StaticListSource` as the dependent side (see "Architecture Decisions")
- **API mode: dependent/chained parameter discovery** (Issue #217): fully implemented, including extension UI — a `DiscoverySource`/`BrowserDiscoverySource` parameter's own template may reference an earlier-declared parameter's value via a `{name}` placeholder (e.g. a category-scoped discovery endpoint), resolved once per distinct combination of what it actually depends on instead of once, globally. A strict linear chain (declaration order = dependency order) rather than a full dependency graph — `RangeSource`/`StaticListSource` still can't be the dependent side, since neither has a template field a placeholder could appear in. The extension's own "insert parameter" picker next to both free-text template inputs only ever offers names that are actually legal to reference, enforced server-side regardless.
- **API mode: token/auth bootstrap value** (Issue #220): fully implemented, including extension UI — for APIs that need a short-lived token from a separate login/token request first, an opt-in section on the `API_CONFIG` screen configures that request (method, URL, headers, flat JSON or form-encoded body, JSON path to the token), and the generated script sends it fresh at the start of every run, using the extracted value in a header (e.g. `Bearer {token}`) or URL part — and, on the wire, in discovery templates and body variables too. "Take from recording" adopts a recorded login request in one click, auto-detecting the token's JSON path and rewiring the main request's matching header/query parameter. Credentials are only ever environment-variable names (with one-time test values for `/generate`'s trial run, like the Fill login flow); the token itself never appears in the output or the script's printed URLs. One bootstrap value per configuration, fetched once per run (no mid-run refresh); the token request's body is flat key/value only.
- **API mode: cursor/token-based pagination** (Issue #224): fully implemented, including extension UI — for APIs that only reveal the next page's cursor inside the current response (Relay `pageInfo.endCursor`, `next_page_token`), the generated script fetches page after page for every parameter combination, feeding each response's cursor into the next request as a query parameter or a field of the JSON POST body, until no cursor comes back, an optional has-more flag is false, a cursor repeats, or a configurable page cap (default 50) is reached. Flat and tree response shapes, GET and POST. The extension can detect the cursor/flag/target from the recorded request/response. Not covered: a cursor in the URL *path*, offset/limit pagination (already possible via a Number `RangeSource`) (`Link`-header pagination has its own option, Issue #321).
- **API mode: Link-header pagination** (Issue #321): fully implemented, including extension UI — for REST APIs that announce the next page in the `Link: <url>; rel="next"` response header (GitHub, GitLab, WordPress, ...), the generated script requests that URL page after page for every parameter combination, with the same headers/authentication, until no next link is left, a link repeats, or a configurable page cap (default 50) is reached. A next link to a different host is never followed. GET only, flat and tree response shapes; exclusive with cursor pagination. The extension suggests the option when a recorded response actually carried a `rel="next"` link.
- **API mode: discover parameter values via browser scroll/click + network capture** (Issue #216): fully implemented, including extension UI — a fourth "Browser discovery" value-source option for values only discoverable by actually rendering a page and letting lazy-loading/pagination/search trigger the value-specific requests themselves (e.g. a target site's own category slugs, not exposed by any single discoverable endpoint and not a computable range). Configured with a Discovery URL plus an optional ordered action list (WaitFor/Fill/Click/Scroll, reusing the exact same vocabulary the Browser engine's own login-flow actions already use, including click-based selector picking) — resolved fresh on every script run via a dedicated Playwright session that observes which requests fire and matches them against the main request's own `UrlTemplate`. Playwright becomes a conditional runtime dependency only for a script that actually uses this source on at least one parameter; every other Api-mode script stays `requests`-only.
- **API mode: nested JSON responses** (Issue #54): fully implemented, including extension UI — a response with more than one repetition level (e.g. `categories[*].subcategories[*].products[*]`) is represented as a full tree editor on the `API_CONFIG` screen instead of a flat record list, output as XML instead of CSV. Multi-level, JSON-scoped click-based search for extending an already-confirmed tree (adding a sibling field at any group's own scope, or an entirely independent second root group) — see the extension section above
- **API mode: POST/GraphQL request bodies** (Issue #55): fully implemented, including extension UI — the recorder captures the outgoing request body alongside the response; a confirmed POST candidate's own captured body becomes an editable draft tree where any value can be marked fixed or variable, the latter bound to a new or already-declared `ApiConfig` parameter (reusing the exact same parameter-source configuration cards a URL variable part already uses). GraphQL needs no dedicated support of its own — its `query`/`variables` shape is just an ordinary nested POST body, handled by the same generic mechanism (see "Architecture Decisions"). Request-body construction has the same "no dependencies between parameters" limitation as URL parameters (see above); discovery-endpoint sources remain GET-only
- **API mode: embedded JSON source** (Issue #136): fully implemented, including extension UI — a second, always-available "Search page's own JSON data" entry point alongside network recording, for sites that render their complete data into the initial page HTML (Next.js `__NEXT_DATA__`, Nuxt `__NUXT__`, a generic `<script type="application/json">` blob) with no separate, capturable network request ever happening. The generated Python script fetches the page via `requests`, extracts the identified `<script>` tag via BeautifulSoup, and `json.loads`s it in place of parsing a live JSON API response — every other API-mode capability (parameterized URLs, flat/tree output shape, transforms, hardening, headers) applies unchanged.
- **Trial-run data preview** (Issue #122): fully implemented — an opt-in checkbox lets the user see a capped sample (up to 50 rows/top-level elements) of what `/generate`'s trial run actually scraped, right in the popup, before downloading/using the script. Flat/API-mode-flat output shows as a table; container/API-mode-tree output shows as a read-only, pretty-printed Xml (or, since Issue #86, Json) text sample (a structured tree view for the latter, mirroring the config-tree editors, is explicitly out of scope for now)
- **Skip the trial run** (Issue #292): fully implemented, mode-independent — a "Skip the trial run" preference on the Settings screen makes `/generate` return the script immediately without running it against the live page (structural validation still applies; a warning toast says it wasn't verified, and a data preview/full output file isn't available). Trades the Consistency Rule's safety net for speed, as an explicit opt-in.
- **Download the full trial-run output** (Issue #161): fully implemented, mode-independent (Fields/Groups/Api alike) and independent of the preview above — a second opt-in checkbox lets the user download the trial run's actual, complete `output.csv`/`.xml`/`.json`, right from the `DONE` screen, without ever needing a local Python/Playwright install to run the generated script themselves. Deliberately still scoped to the *one* trial run `/generate` already performs — no new "run repeatedly from the extension" scheduler; recurring execution stays the user's own cron/Task Scheduler entry, same as Change Detection (Issue #87)
- **Live selector match-count preview** (Issue #85): fully implemented, extension-only (no companion/IR/code-generator changes) — a flat/container field pick shows a live "N elements found" hint the instant the selector is built, and a container-group pick shows the same count as a toast right after insertion; both purely client-side (`document.querySelectorAll(selector).length` in the content script), no `/generate` round-trip needed. Existence/quantity feedback only — a full extracted-values preview remains the separate, existing "Show preview" DOM-highlight feature and Issue #122's trial-run data preview above
- **Hover highlight of a single field/container row** (Issue #233): fully implemented, extension-only — hovering a row in the flat fields list or the container tree highlights that row's element(s) on the live page in green (every instance of a repeating container; a nested row once per enclosing instance), with no toggle and alongside the full blue "Vorschau" if that's on. Fields inside an iframe highlight the iframe itself. Not available for API mode, Blocks mode or the transform modals.
- **Per-field data transformations** (Issue #84): fully implemented — an optional, ordered chain of trim/regex-extract/find-replace/to-number steps, configurable in flat mode (`modal-field-name`, which had no per-field configuration UI at all before this), container mode (`modal-field-extended`, hidden for "Exists?" mode), and API mode (a "Transform" button per leaf field on the `API_CONFIG` tree screen, Issue #84 follow-up). Applies identically across every code generator (static/browser × flat/container, API flat/tree). **Live preview** (Issue #143, and its API-mode follow-up Issue #147): fully implemented across all three modes — the modal shows what the chain actually produces against the picked element's own raw value (flat/container) or the field's own captured sample value from candidate-confirm time (API mode), live, purely client-side. **Safe type-conversion transforms** (Issue #205): fully implemented — three more transform kinds ("Convert to integer"/"Convert to boolean"/"Convert to date"), available everywhere the original four already are. Unlike `toNumber`'s best-effort heuristic coercion, all three are strict: a value that isn't already well-formed for the target type is a conversion failure, not an approximation, with a clearly defined, per-transform-configurable fallback (keep the original value, or substitute a configured default) instead of silently guessing. `toDate` parses against a configurable source-format mini-template (reusing the same `"{yyyy}"`/`"{mm}"`/`"{dd}"` placeholder syntax the API mode range-parameter format already uses) and rejects a structurally-matching but non-existent calendar date. Deliberately does not include a "fail the whole row/element" fallback option — that would need the same row/element-dropping machinery the required-fields hardening check (Issue #133) only built at real cost for a check that runs once at the very end, not per-transform. **Combine/split field mapping** (Issue #206): fully implemented — two more transform kinds ("Combine with other field(s)"/"Split from another field") that, unlike every other kind, derive their value from *another already-configured field* rather than their own picked/extracted value, resolving an N:1/1:N need Output Blueprints' own strict 1:1 mapping (Issues #191/#192) explicitly left undesigned. Available in flat, container, and both API-mode shapes; scoped to same-immediate-parent-group siblings (not global-by-name) with a picker that only ever offers already-valid, in-order reference targets rather than a free-text field name. No live client-side preview for either kind, the one deliberate gap in an otherwise "every transform kind gets a preview" feature set — no sibling field's value is ever available at edit time the way the field-being-edited's own raw value already is. **Dedicated creation flow, replacing the transform-kind UI** (Issue #206 follow-up): fully implemented — a standalone "Felder kombinieren"/"Feld aufteilen" button (disabled until enough real fields exist) opens its own modal with no click-based selection at all and a real checkbox list for Combine's source picker (replacing the original native `<select multiple>`), instead of first faking a normal field through the click-based flow the way every other transform kind still requires. An optional "remove original field(s)" checkbox marks the picked sources `HiddenFromOutput` — still computed (so the new field can still read them), just excluded from the written output — rather than deleting them. Still excluded from Blocks mode, same as before this redesign.
- **Price/currency-to-number transform** (Issue #234): fully implemented, in every mode — a "Convert price/currency to number" transform turns a scraped amount such as "Preis: 1.234,56 €", "£51.77" or "CHF 1'234.50" into a plain number ("1234.56"), with the number format picked from four presets (`1.234,56`, `1,234.56`, `1 234,56`, `1'234.56`) instead of guessed, so a thousands-only amount like "€ 1.234" correctly becomes 1234. Same "keep original / use default" error behaviour and live preview as the other strict conversions. Only the numeric amount is produced; the currency symbol/code itself isn't extracted.
- **Reusable transform-chain presets** (Issue #279): fully implemented — a transform chain built on any field can be saved under a name ("Save as preset") into a small local store on the companion and applied to any field of any scrape in one action ("Apply preset …"), in all three modes' transform editors. Applying appends a copy of the steps, which stay freely editable per field afterwards. Two built-in presets ("Clean up price" in the `1.234,56` and `1,234.56` formats — trim + Issue #234's conversion) ship with the extension and work without a companion. Presets are renamed/deleted on the Settings screen; their steps are changed by saving a rebuilt chain under a new name. Combine/split steps can't be part of a preset.
- **Json output format** (Issue #86): fully implemented — a mode-independent "Output as JSON" checkbox lets the user opt into `output.json` instead of the mode's default `output.csv`/`output.xml`, for every mode/shape (flat, container, API flat, API tree). Trial-run data preview (Issue #122 above) supports it too, reusing the Csv table renderer for Json's flat shape and the Xml text-sample renderer for Json's tree shape
- **SQLite / Excel output** (Issue #229): fully implemented — an "Output format" preference (Settings screen) lets the generated script write a SQLite database (table `data`) or an Excel workbook (sheet `Data`) instead of CSV/XML/JSON, for flat mode, API flat, and — flattened into one table (one row per innermost repeating item, higher-level values repeated, a hint says so) — container mode and API tree. Always a fresh file per run; Excel needs `pip install openpyxl` (nothing for SQLite). Not available for Blocks/Combined, with change detection or with deduplication's append mode. Appending to an existing output file for every format is tracked in Issue #342.
- **Multiple start URLs** (Issue #83): fully implemented for flat and container mode — an optional "Additional start URLs" textarea lets the user run the same Fields/Groups extraction config against a static, user-supplied list of pages in one run, combining the results into a single output file (CSV/XML/Json alike). Not applicable to API mode, which already builds its own request URL from `urlTemplate`/parameters and rejects the combination outright rather than silently ignoring it. Composes with classic multi-page pagination (Issue #174, see below) — each start URL paginates onward independently. Partially resolved by Issue #218 (see below): a navigation/listing page's own links can now be discovered automatically via a CSS selector, rather than only ever typed by hand into this textarea — "crawling" in the fuller sense (following links matching a pattern recursively, across more than one hop) is still out of scope
- **Change detection + notification** (Issue #87): fully implemented, mode-independent (Fields/Groups/Api alike) — an opt-in toggle lets the generated script compare each run's output against the previous run's (a whole-file text diff via `difflib`, not a granular per-record diff) and notify by email (`smtplib`, opportunistic STARTTLS) or webhook (`urllib.request`) only when something actually changed, both stdlib-only with no new pip dependency. Every credential/target is an environment-variable name the user chooses, never a literal value baked into the script. Single-script, single-machine only, as scoped by the issue itself — no hosted/cloud scheduling and no multi-recipient alerting system; the user is responsible for actually running the script on a recurring basis (their own cron/Task Scheduler entry)
- **Proxy support** (Issue #88): fully implemented, mode-independent (Fields/Groups/Api alike) — an opt-in toggle lets the generated script route its outbound requests through proxies the user already has access to, instead of connecting directly. The extension never sees the proxy addresses themselves, only the name of an environment variable holding a comma-separated list; the generated script reads that list at runtime and, if more than one proxy is present, rotates through them round-robin per request. Wired into every engine's own HTTP layer: `requests`' `proxies` parameter for the static/API engines, Playwright's `proxy` launch option for the browser engine. Pass-through only, as scoped by the issue itself — no proxy acquisition, rotation service, or IP-pool management
- **Pause between requests** (Issue #222): fully implemented, mode- and engine-independent (Fields/Groups/Api/Blocks × Static/Browser) — an opt-in setting makes the generated script wait between two requests to the target site, either a fixed pause or randomly within a range (e.g. 1–3 s), as protection against rate limits and blocks. Applies before every page of pagination, every start URL, every API parameter combination and every other outbound request (discovery, auth bootstrap, preflight, downloads), but not between reads on an already-loaded page. Measured as a minimum gap between request starts, so processing time counts toward it and the first request isn't delayed. The companion's trial run never counts these pauses against its timeout (up to 10 minutes of pauses in total), so a long, polite scrape can't fail verification just because it makes many requests.
- **Append to the existing output file** (Issue #342): fully implemented, mode- and engine-independent (Fields/Groups/Api/Blocks × Static/Browser; a Combined request's components each carry their own) and available for every output format — CSV rows, JSON entries, XML children under the existing root, JSON-tree merges, SQLite rows and Excel rows are appended to the file the previous runs left instead of replacing it, so a recurring script can accumulate a price history or an archive. Schema drift uses one rule everywhere (keep the file's columns, add new ones, fill gaps with empty values); an unreadable or differently shaped existing file stops the run with exit code 10 without touching it. Deduplication's incremental "Append" output is one case of this mechanism and now also works for trees, SQLite and Excel. Not covered: removing or de-duplicating rows already in the file (use deduplication for that), and appending for Combined's outer output.
- **Check robots.txt Disallow at run time** (Issue #333): fully implemented, mode- and engine-independent (Fields/Groups/Api/Blocks × Static/Browser; a Combined request's components each carry their own) — an opt-in setting makes the generated script check every request it makes (start and further pages, discovered URLs, downloads, API calls) against the target's robots.txt Disallow/Allow rules while it runs, and either skip the disallowed request (default), warn and request it anyway, or stop the run with a dedicated exit code. Matching follows RFC 9309 (the `ScrapingFactory` group else `*`, longest pattern wins, ties go to Allow, `*`/`$` wildcards); a missing robots.txt means no restrictions and an unreadable one only warns. The robots.txt is read once per origin, shared with the Crawl-delay option. Not covered: subresources the Browser engine's page loads itself, the auth-bootstrap request, and browser-discovery sessions.
- **Respect robots.txt Crawl-delay** (Issue #228): fully implemented, mode- and engine-independent (Fields/Groups/Api/Blocks × Static/Browser; a Combined request's components each carry their own) — an opt-in setting makes the generated script read the target's robots.txt once and wait at least its `Crawl-delay` / `Request-rate` between requests, in addition to (the larger gap wins) any configured pause. A site that publishes neither, or no robots.txt at all, is unaffected; an unreadable robots.txt only prints a warning. Only the generic and the `ScrapingFactory` user-agent groups are consulted, the delay is capped at 60 s, and robots.txt is read once per distinct start-URL origin (the largest value applies to all requests, including hosts reached only via pagination/discovered URLs). `Disallow` re-checking at run time has its own option (Issue #333).
- **Retry on transient errors** (Issue #223): fully implemented, mode- and engine-independent — an opt-in setting makes the generated script retry a request that failed with a connection error, a timeout or one of a configurable set of HTTP status codes (429/502/503/504 by default), waiting a fixed or doubling delay between attempts (or exactly what a 429/503's Retry-After asks for, at most 60 s per wait). Other errors (404/401/403, …) still fail immediately, API mode's 404 skip is unchanged, and once every attempt has failed the run stops exactly as before (no "skip and continue" in this first version). Every retry is printed, retries respect the pause between requests (#222), the Browser engine retries navigations only (never a half-run login sequence), and the companion's trial run doesn't count retry waits against its timeout.
- **Deduplication by key field(s), and incremental "only new items" output** (Issue #225): fully implemented, mode-independent (Fields/Groups/Api flat and tree; not Combined's outer level or Blocks) and engine-independent (Static/Browser alike) — an opt-in setting lets the generated script drop a later row/element whose (optionally composite) key already appeared in the same run, for overlapping pagination or an item reachable from several start URLs/categories. A separate opt-in makes it *incremental*: the keys seen so far are remembered in a small sidecar file next to the output (`<output file>.dedup-seen.json`), and only genuinely new rows/elements are written — either as just the delta (the file is replaced every run) or appended to the growing previous file (any output format since Issue #342). The sidecar is bounded by a configurable retention (number of remembered keys, or days since last seen), only updated after a run that didn't fail a hardening check, and safe to delete to start over. For tree output the deduplicated unit is the nearest repeating group instance that owns all key fields. Deliberately out of scope for this first version: dedup together with an Output Blueprint on a tree-shaped source, key fields spread across nesting levels (nothing is deduplicated, with a warning), a free-text/regex key, and any fuzzy/near-duplicate matching.
- **Custom request headers for flat/container/Blocks mode** (Issue #226): fully implemented, engine-independent (Static/Browser alike) — an opt-in "Send custom request headers" setting lets the generated script send extra headers with its requests (a language via `Accept-Language`, a `Referer`, an API key, a lightweight `Cookie` for a page that doesn't need the full Browser-engine login flow), each a fixed value or backed by an environment variable the user names (never a secret literal in the script, with a one-time test value for the trial run like the login flow's). The default identifying `User-Agent` stays unless a header of that name replaces it. Static engine: `requests`' `headers`; Browser engine: Playwright's `extra_http_headers` (sent with every request the page makes, subresources included) and `user_agent`. A missing environment variable stops the run cleanly (exit code 78) instead of continuing without the header. Not available for API mode (its own header editor already exists) or on a Combined request's outer config (each component carries its own). Deliberately out of scope for this first version: per-request or per-domain headers, header values built from other values (`{name}` templates — only the API mode's auth bootstrap has a fresh value to splice in), and a dedicated cookie jar (a plain `Cookie` header is just a header).
- **Text-content selector suffix** (Issue #227): fully implemented, engine- and mode-independent — a selector may end in `:contains("text")` to tell otherwise identical buttons/links apart by their label (case-insensitive, whitespace-collapsed). Picked in the flat/container field modals via a text filter input with live match count. Not available in FramePath segments or the embedded-JSON script selector; no filter input for browser-action selectors.
- **Script hardening** (Issue #129): the first of five planned checks (see "Planned for Future Releases") sharing one mechanism — an opt-in "no result" check lets the generated script re-validate, on every run (not just the companion's own `/generate` trial run), that it actually scraped at least one row/element, independently configurable to print a warning (script still exits `0`) or fail the run (script exits a dedicated non-zero code, distinguishable from an unhandled crash) so a scheduled re-run weeks later doesn't silently produce nothing without anyone noticing. Mode-independent (Fields/Groups/Api alike).
- **Script hardening: per-field null-rate check** (Issue #130): fully implemented, the second of the five planned checks — catches the narrower case "no result" can't: a row/element count that stays healthy while one specific field's selector quietly starts matching the wrong thing and returns empty every time. Independently configurable per monitored field (any number of fields, each its own threshold and Warning/Error severity), reusing the exact field list already built in the current mode instead of a free-text field-name input. In container/API-tree mode, the rate is computed **globally per field name** across the whole result, not scoped to whichever parent group the field is nested under (a deliberate scoping decision — see the Compiler section above).
- **Script hardening: baseline-drop check** (Issue #131): fully implemented, the third of the five planned checks — catches a gradual volume drop (e.g. a broken "load more"/pagination selector) that neither "no result" nor per-field null-rate would ever trip, by comparing this run's own result count against the last run's, tracked entirely by the generated script itself in a small sidecar file next to its own output (never sent to or known by the companion). The sidecar only ever updates after a run that itself didn't hard-fail, so a bad run's own low count can never become the new baseline for the next comparison. Mode-independent (Fields/Groups/Api alike).
- **Script hardening: blocking-detection check** (Issue #132): fully implemented, the fourth of the five planned checks — catches a site that starts blocking the script (rate-limiting, IP ban, CAPTCHA wall, redirect to a login page) while still responding with a normal-looking HTTP 200, evaluated against the *raw* response (final URL, body length, body text) rather than the already-extracted data. Three signals: a redirect to a different host (always active, no configuration needed), a response shorter than an optional configured byte threshold, and an optional list of case-insensitive block phrases. Mode/engine-independent (Fields/Groups/Api × Static/Browser alike), though each engine's own "response" concept differs — see the Compiler/Python Templates sections above. Detection-and-reporting only, consistent with the "No CAPTCHA solving/bypassing" boundary below — it never attempts to bypass or work around whatever it detects.
- **Script hardening: required-fields check** (Issue #133, tree-shape follow-ups Issue #133/#204): fully implemented, the fifth and last of the originally planned checks — unlike the other four (aggregate checks that only ever *report* on already-final data), this one *filters* the output before it's written: a row missing a non-empty value for any of a configured set of fields is dropped from the output entirely, serving a "safe for database import" use case (e.g. a `NOT NULL` column that would otherwise silently break on import). Filtering happens unconditionally regardless of severity — only whether the run itself is flagged as failed depends on it, so an all-Warning configuration still guarantees the output file never contains an incomplete row. Supported for every mode/shape: flat mode, container mode and API mode's tree shape (both dropping the nearest enclosing repeating group instance, matched globally by field name — the same simplification the per-field null-rate check already established for this exact ambiguity), and API mode's flat response shape.
- **Dark mode** (Issue #140): fully implemented, extension-only (no companion/IR changes) — follows the OS/browser `prefers-color-scheme` by default, with a manual system/light/dark toggle next to the language selector that persists the same way the language preference does (`chrome.storage.local`). See the extension section above for the token/theme-module mechanics
- **Pagination** (Issue #174): fully implemented, mode-independent (Fields/Groups alike, not Api — which already has its own page-parameter mechanism via a Number `RangeSource`) and engine-independent (Static/Browser alike) — an opt-in "Pagination" section lets the generated script follow classic multi-page pagination onward from each start URL (`Url` + every `AdditionalUrls` entry, paginating each independently), either by following a "next page" link's `href` (`NextLinkPagination`, resolved relative to the current page, both engines) or by substituting `{url}`/`{page}` into a page-number URL template (`PageNumberPagination`) — page 1 is always the start URL exactly as given, `{page}` only ever generates page 2 onward. Stops when a page yields nothing, a configurable `MaxPages` safety cap is reached (always active, default 50), or (next-link kind) the selector no longer matches. Distinct from infinite-scroll/"load more" pagination on a single page, already covered separately by the Scroll browser action (Issue #41)
- **Discovered additional start URLs** (Issue #218): fully implemented, mode-independent (Fields/Groups alike, not Api/Combined-outer/Blocks) and engine-independent (Static/Browser alike) — an opt-in "Discover additional start URLs automatically" section lets the generated script fetch a navigation/listing page once and harvest every link matching a CSS selector, combining the discovered URLs additively with the statically-typed `Url`/`AdditionalUrls` list, for a target whose set of pages isn't fixed (e.g. a category menu that changes over time) instead of requiring the user to notice the change and manually update a textarea themselves. Deliberately `requests`+BeautifulSoup only for this first version, even on a Browser-engine script — no Playwright fallback for JS-rendered navigation. A failed discovery fetch degrades to a warning, never a hard failure; a `Max. discovered URLs` safety cap (default 100, always active) guards against a misconfigured selector matching an entire sitemap/nav tree.
- **Preflight check** (Issue #219): fully implemented, mode-independent (Fields/Groups alike, not Api/Combined-outer/Blocks) and engine-independent (Static/Browser alike) — an opt-in checkbox lets the generated script send a single cheap `HEAD` request against the primary start URL before the main extraction phase even starts, skipping the full cost of a real scrape (and, for the Browser engine, ever launching a browser session at all) when the target's `ETag`/`Last-Modified` header matches the value recorded from the last successful run, or when the target is currently unreachable — each distinguished by its own dedicated exit code for cron/monitoring purposes. A target that doesn't send either header at all is always treated conservatively as "proceed with a normal run" rather than risk silently never picking up a real change. Single-script, single-machine only, the same scope `ChangeDetection` (Issue #87) already has — the user remains responsible for actually running the script on a recurring basis.
- **Persistent session/cookie handling** (Issue #175): fully implemented, Browser-engine only — an opt-in "Reuse session between runs" toggle inside the browser-actions section lets the generated Playwright script save its cookies/localStorage (`storage_state`) to a sidecar file after every run and, once that file exists from a previous run, skip the configured login-flow browser actions (WaitFor/Fill/Click/Scroll) entirely on the next run, going straight from Navigate to extraction. Avoids repeating a login flow (and any resulting rate-limiting/lockout risk) on every scheduled/recurring run of the same script. If the saved session ever actually expires, there's no automatic fallback to a fresh login — the run simply fails, a deliberate, documented limitation.
- **External XML config file for re-editable script parameters** (Issue #178): fully implemented for the scope described above — an opt-in toggle makes the generated script self-create a small sidecar XML file next to itself (not sent back through `/generate` at all) the first time it actually runs, and re-read it on every run after that, letting a non-technical user tweak the start URL(s), the output filename, a flat field's output name, or a fixed-value-list API parameter's values, by editing that file — without touching the `.py` file or reopening the extension. A missing file is not an error (a fresh one is written); a broken or stale one (bad XML, a missing required attribute, a reference to a field/parameter that no longer exists) fails cleanly with an English message and a dedicated exit code, never a raw traceback. Container-mode's own group/field names and Api-mode's tree shape aren't editable this way yet — deliberately left open, per the issue's own flagged uncertainty about mapping a nested tree onto a flat-ish XML structure.
- **Local saved-configuration history** (Issue #141): fully implemented, mode-independent (Fields/Groups/Api alike) — an opt-in "Save configuration" action persists the current configuration into a small local SQLite database on the companion side (never a companion/IR/wire-format change beyond four new endpoints — the config JSON itself is stored and round-tripped opaquely), and a hostname-scoped "Saved configurations" panel on the popup's idle screen lists/loads/deletes past saves for whichever site is currently open. "Load" restores everything the export/`/generate` request body already captures except the URL itself, which always stays whatever the live browser tab currently shows. Purely local/additive and entirely opt-in, as scoped by the issue itself — no automatic/implicit saving (not a silent history of every `/generate` call), no cross-machine sync, and no export/import of the SQLite file itself (the existing JSON export/no-import-yet mechanism still covers one-off sharing).
- **Persist and browse run outputs** (Issue #202): fully implemented — an opt-in "Save output" action on the `DONE` screen links a trial run's actual, complete output (the same data Issue #161's "Download data" already surfaces) to an already-saved configuration in the companion's local SQLite store, and each saved configuration in the "Saved configurations" panel gains its own expandable list of its past saved outputs (download/delete). Same local/opt-in trust boundary as Issue #141 — no data leaves the user's machine, no automatic/implicit saving of every run. Deliberately does not include evaluating hardening checks against a saved output — that's a separate, not-yet-implemented issue (#207), since hardening today only ever runs live, inside the generated script itself, and a cross-configuration comparison mode for it depends on Output Blueprints (#191, also not yet implemented) existing first. **Create-and-link a new configuration directly from "Save output"** (Issue #209): fully implemented — when the current site has no saved configuration yet, "Save output" creates one inline (collecting a configuration name alongside the output name in the same modal) and links the output to it in one action, instead of only ever redirecting into the separate "Save configuration" modal first. The existing picker for an already-existing configuration is unchanged.
- **Replay script hardening checks against saved outputs** (Issue #207): fully implemented — a "Test hardening" action on any saved output replays whichever hardening checks are currently configured live in the popup against that one output's already-materialized data (CSV/JSON/XML), entirely companion/extension-side and without ever touching the generated `.py` script or its own runtime hardening mechanism. Covers four of the five check kinds (`NoResultCheck`/`NullRateCheck`/`RequiredFieldsCheck`/`BaselineCheck`); `BlockingCheck` is permanently out of scope for replay specifically, since it needs the raw HTTP response, which a saved output never carries. A `BaselineCheck`'s "previous" comparison point is either the same saved configuration's own next-older output, or (when this configuration has an Output Blueprint set) the most recent output across *any* configuration sharing that Blueprint — the second, cross-configuration mode Output Blueprints (#191) existing was originally the prerequisite for. Purely an on-demand analysis/tuning aid, per the issue's own scoping — no autonomous new runtime behavior, no change to a scheduled/cron run of an already-downloaded script.
- **Combined mode: merge multiple saved configurations into one script** (Issue #239): fully implemented — a fourth top-level mode lets the user pick 2+ of their own already-saved configurations (Issue #141), possibly targeting entirely different sites/modes/engines, order them into a list, and generate one script that runs every component's own extraction independently and merges all of their outputs into a single combined `output.json`, keyed by each component's own (editable) name. Every component keeps its own engine/browser-actions/proxy/hardening/pagination/persistent-session/external-config exactly as if it had been generated standalone; sidecar-state features specifically are proven to keep working across separate runs of the *combined* script via a stable per-component subdirectory (not a disposable temp directory). Deliberately out of scope for v1: no combined-level (outer) hardening/change-detection/proxy/pagination — component-level only; a smarter "join by shared key" merge (the "generic two-phase join" idea from Issue #181's own discovery process) remains a possible, separate future extension; and the popup has no UI yet for a component's own one-time login `VerificationValues`, though the wire format already supports it.
- **Blocks mode: multiple, independently-shaped output files from one run** (Issue #182): fully implemented — a fifth top-level mode lets the user build several independent extraction blocks (flat or container/group, freely mixed) one at a time against the page currently open, reusing the exact same click-based field/group editors flat/container mode already have, then generate one script that shares one navigation/browser session/proxy/pagination/persistent-session across every block while each block writes its own, independently-formatted output file (CSV/XML/JSON). At least 2 blocks are required, mirroring Combined mode's own minimum. Deliberately out of scope for v1: no UI yet for a block's own `ChangeDetection`/`Hardening`/explicit `OutputFormat` override, though the wire format already supports all three (each block produces its own independent result set, so — unlike `Pagination`, which stays outer-level since it governs the one shared page-fetching loop every block extracts from — these three are genuinely per-block concerns); no per-block trial-run preview table on the `DONE` screen (a "Download" button per block is implemented, reading the per-block sample into a table/text view the way the single-shape preview already does is left as a follow-up); and `ExternalConfig`/API-mode blocks are both rejected outright rather than guessed at, the same "ship the simpler shape first" precedent container mode's own field renaming and Api-mode's tree shape already set for `ExternalConfig` (Issue #178).
- **Output Blueprints: reusable output field-name/order mapping** (Issue #191, extended to container/API-tree mode by Issue #192, to a nested/tree target schema by Issue #244, to importing a sample for either schema kind by Issues #193/#253, and to uploading that sample as a file by Issue #252): fully implemented for flat mode, API mode's flat response shape, container mode, and API mode's tree shape, in either of two target schema kinds. A small, persisted, site-independent "blueprint" — a `schemaKind` of `Flat` (just a name plus an ordered target-field-name list) or `Tree` (a name plus a nested target-schema tree of its own, mirroring the container/API tree editors, with no explicit repeating flag — see Architecture Decision #6's own reasoning applied here too) — lets the user map a scrape's own source fields onto that fixed shape, so recurring exports for the same downstream pipeline stay consistent regardless of which specific configuration produced them. For a Flat schema, a tree-shaped source is *flattened* into denormalized rows instead of being renamed in place — one row per instance of the single repeating group every mapped field's own ancestor chain shares, with any higher-level mapped field (e.g. a category name next to a repeating list of items) copied/broadcast into every row generated beneath it — and mapped fields spanning more than one independent repeating branch are rejected rather than guessed at (no single row layout could include both without either a cross-product or dropping data), at generate-time (`400`) for container mode or a `422` trial-run verification failure for Api-tree mode (Architecture Decision #6). A **Tree** schema resolves this same ambiguity differently, by design: each *target group* resolves its own row scope independently from its own direct mapped fields, so two independent/sibling source repeating groups simply map into two different target branches instead of needing one shared scope — the target tree's own nesting is the disambiguation, the open question #244 was filed to answer. Either schema kind's own target shape can additionally be **imported from a pasted or uploaded sample** (Issue #193 for Flat, extended to Tree by Issue #253, and to picking the sample as a file from disk — rather than only pasting it — by Issue #252) instead of built by hand, when creating a new blueprint — a JSON object/array (a wrapper object/array around the real data is drilled through for Flat, but preserved as real nesting for Tree, since collapsing it there would defeat the point of a tree import), plus, Flat only, a CSV header row or a plain newline/comma-separated list, format auto-detected from the content either way; a file picked from disk (`.csv`/`.json`/`.txt`) is simply read into the same textarea the paste flow already uses, so it goes through the exact same auto-detection/parsing rather than a second code path; editing an already-existing blueprint of either schema kind still only supports the original manual tree/list editing. Deliberately still out of scope for both schema kinds: Combined mode and Blocks mode are still rejected outright, neither having a single field/tree config of its own at the outer level; there's no fixed-literal-value target field — every target field must map to a real source field; the per-scrape mapping picker's source-field `<select>` offers the full current-mode field list at every tree position rather than scoping it to "fields actually reachable from this position" (a first-version simplification — the generate-time/runtime ambiguity check still catches a genuinely wrong pick); importing a sample can only ever create a new blueprint's field list/tree, never merge newly-seen fields into an already-existing one (deferred, per Issue #193's own second open question, to a possible future follow-up); and a Tree-schema sample import requires valid JSON, with no line-based recovery fallback for a broken paste the way the Flat case has (Issue #253's own deliberate first-version restriction).
