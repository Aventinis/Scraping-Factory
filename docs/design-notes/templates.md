# Design notes — Python templates

`language-modules/python/templates/`: the Scriban templates and fragments behind the generated scripts.

> Moved here from `CLAUDE.md` (Issue #379) without changes of substance. This is **reference material, not instructions**: the behavior, edge cases and rationale of individual features, kept for whoever changes that feature. What applies to every change stays in `CLAUDE.md`; the structural map (which file does what) is `docs/ARCHITECTURE.md`. Phrases such as "the Compiler section", "the Python Templates section", "the Companion App section" or "the Browser Extension section" refer to the sibling files [compiler.md](compiler.md), [templates.md](templates.md), [companion.md](companion.md) and [extension.md](extension.md); "Architecture Decision #N" refers to `CLAUDE.md` (the popup module rule is now #13, formerly cited as #12); "Feature Scope" is [feature-scope.md](feature-scope.md). Issue numbers can be looked up with `gh issue view`.

- **Shared template fragments, via a compile-time `#@include`** (Issue #326): Scriban has no cross-template includes, which used to force every shared runtime helper into a hand-maintained copy per template (the transform helpers alone existed eight times, and the copies had started to drift). The compiler now does the include itself: `Backends/EmbeddedScribanTemplate.Load` expands, as plain text substitution *before* Scriban parses anything, every line consisting of `#@include <name>` (any indentation) into the embedded fragment `language-modules/python/templates/fragments/<name>.py.j2`, re-indented to the directive's indentation — recursively (a fragment may include others; cycles and unknown names fail with a message naming the include chain), and a trailing line break of the fragment is not duplicated, so extracting a block verbatim into a fragment and including it back reproduces the original text exactly. Fragments are ordinary Scriban text rendered with the *including template's own context*, so they can still say `{{ if retry.enabled }}` or `{{ dedup.key_fields_literal }}`; that is why every template reads its keys at the top level of the context (see `scraper.py.j2` above). The directive is a `#` line, so a template read as Python is still a valid comment; `EmbeddedResource`s for `fragments/*.py.j2` are declared by wildcard in `ScrapingFactory.Compiler.csproj`. **Where the fragments are split:** by what is genuinely shared. Engine-independent helpers exist once (`transforms`, `retry`, `request_delay`, `change_detection_*`, `pagination_constants`, `discovered_urls_constants`, `hardening_baseline`, `proxy_pool`, `xml_to_dict`, `tree_without_hidden_fields`, `dedup_*`); engine-specific ones exist once per engine (`preflight_static`/`preflight_playwright`, `discovered_urls_static`/`_playwright`, `download_static`/`_playwright`, `proxy_requests`/`proxy_playwright`, `playwright_locators`, `require_env_playwright`, `session_constants`); shape-specific ones once per shape (`hardening_flat`/`hardening_tree`/`blocks_hardening`, `external_config_flat`/`_grouped`/`_api`, `dedup_flat`/`dedup_tree`, `main_flat`/`main_grouped`/`main_blocks`); and the two API templates share `api_prelude`/`api_common`/`api_fetch`, leaving `scraper_api.py.j2`/`scraper_api_grouped.py.j2` with only the genuinely flat-vs-tree parts. **Consequence for the rest of this section:** wherever an entry below says a helper is "hand-duplicated" per template, that describes the state before this issue — the code now lives once in the fragment named after it, and a fix there reaches every template that includes it. Differences that were accidental were unified (one wording of the "no data" message, one `ERROR: required environment variable ...` form, `urlsplit` imported the same way in every engine, the Browser-engine Blocks proxy helper now identical to the others); differences that are real (a per-block hardening dispatcher, the Browser engine's `page.context.request` download, ...) stayed as separate fragments. `TemplateIncludeTests` covers the expansion rules (indentation, nesting, cycles, unknown fragments), that every embedded template still parses, that no fragment is orphaned, and that no generated script contains a literal directive.
- **The remaining shell structure, shared (Issue #395)**: after #326 the top-level templates still carried the same blocks as the fragments' neighbors (jscpd on `language-modules`: 17.5 % duplicated lines, 1,204 lines; now 7.2 %, 452 lines). Because the include is plain text substitution, extracting a block verbatim and including it back is byte-identical by construction, and the golden-file snapshots prove it; so the rule was: share a block only when it is *textually identical* in every template that includes it, and leave a difference alone when removing it would change a rendered comment or an import's position. New fragments: the Browser-engine shell of `playwright_scraper`/`_grouped`/`_blocks` (`playwright_browser_start` — launch, session, navigation and login actions —, `playwright_paginate`, `playwright_browser_end`) and the import/constant blocks of the flat and container Browser shells (`playwright_imports_head`/`_tail`, `playwright_constants_prelude`); the Static counterparts for the flat, container and Blocks shells (`static_imports_and_constants`, `static_fetch_request`, `static_paginate`); the flat field constants of the two flat shells, split around the one differing rendered comment (`flat_field_selectors`, `flat_field_download_constants`); the container output of `main_grouped`, shared with the API tree template (`main_grouped_output`, `main_grouped_post_checks`, `main_grouped_save_state`) and the row-writing block and `main()` head of the flat one (`main_write_rows`, `main_head`); the API templates' imports, `scrape()` head and per-combination request (`api_imports_base`, `api_imports_features`, `api_scrape_head`, `api_combo_request`); the `blueprint_source_index` of the three container shells; and, inside the fragments themselves, the hardening dispatcher branches (`hardening_check_no_result`, `hardening_checks_tail`), the external-config writer/loader (`external_config_error_and_defaults`, `external_config_write_and_load`), the preflight state and evaluation (`preflight_state`, `preflight_evaluate`) and the discovered-URL parsing (`discovered_urls_parse`). **Deliberately left separate**: import blocks whose order differs between shapes (the `xml.etree` import sits at a different place in the flat and the container shell), the places where the Static and Browser engines word a rendered comment differently, the per-block loops of the Blocks shells (they differ in `page` vs `soup` and in the hardening flag), and the download/pagination-constants fragments, whose differing lines outnumber the shared ones. A fragment that opens a conditional the including template closes (e.g. `main_grouped_output` ends in `{{~ else ~}}`) is intentional: it keeps the extraction a pure move.
- Scriban templates (the `.j2` file extension is a historical artifact — the syntax is Scriban, not Jinja2)
- `scraper.py.j2`: a monolith for the static engine (`PythonCodeGenerator`) — a declarative dict approach (SELECTORS/ATTRIBUTES), no step-by-step composition needed
- `playwright_scraper.py.j2` + `playwright_navigate_step.py.j2` + `playwright_wait_step.py.j2` + `playwright_fill_step.py.j2` + `playwright_click_step.py.j2`: for the browser engine (`PythonPlaywrightCodeGenerator`) — Navigate/WaitFor/Fill/Click steps are each rendered as their own fragment per step type and inserted into the shell in order, because (unlike Extract) each corresponds to one concrete action at a fixed point in the flow. `FillStep` values are never written into the script as a literal — they're always read at runtime via the shared `_require_env(name)` helper (`import os` is only added when a `FillStep` is actually present). A missing (not just empty) credential env var no longer surfaces as a raw, unhandled `KeyError` traceback — `_require_env` prints a clean English error naming the missing variable and exits via the same `EXIT_MISSING_ENV_VAR` (78) sentinel Proxy uses below, instead of the default `1` from an uncaught exception (Issue #88 follow-up, prompted by exactly this confusing traceback surfacing through `/generate`'s error response). Unlike Proxy, this is still a hard stop — a login flow genuinely can't continue without its credential — but `PythonScriptVerifier` surfaces the clean stderr message as the error instead of the generic "script did not produce output.csv" it would otherwise fall back to
- `scraper_grouped.py.j2` (static) + `playwright_scraper_grouped.py.j2` (browser): for container mode. The group tree is not reproduced as Scriban recursion (Scriban has no cross-template recursion) — instead, `Backends/Python/PythonGroupTreeLiteral` builds it as a nested Python dict/list literal (`GROUPS = [...]`) and inserts it into the template verbatim; a generic `extract_group()` function in the template walks the tree at runtime — identical between the two templates except for the two DOM-access calls (`select`/`select_one` vs. `query_selector_all`/`query_selector`). Output is `output.xml` (`xml.etree.ElementTree`; multiple root groups are combined under an `<Ergebnis>` wrapper)
- **XML output: control characters are stripped** (Issue #291, bug fix): XML 1.0 only allows tab/LF/CR and characters from U+0020 on (minus the surrogate range and U+FFFE/U+FFFF); a control character such as BEL (U+0007) is illegal even as a character reference, yet Python's `xml.etree.ElementTree` serializes it raw — so a scraped value containing one (first seen in a live `penny.de` JSON API response, API tree shape) produced an `output.xml` no conforming parser accepts, and the companion's trial run failed on every attempt with `XmlException: … hexadecimal value 0x07, is an invalid character`. The new fragment `fragments/xml_sanitize.py.j2` (`_ILLEGAL_XML_CHARS_RE`, `_strip_illegal_xml_chars(root)`, walking every element's `text`/`tail`) is called right before `ET.indent(tree)` at every place a tree is written as XML — `main_grouped` (static + Browser container mode, both the normal and the Output-Blueprint-tree branch), `scraper_api_grouped` (both branches) and `main_blocks` (a group block) — instead of at each of the ~30 `el.text = …` assignments, so no assignment site (transforms, downloads, derived fields, flattened blueprint leaves) can be missed and the helper lives once. Stripping, not escaping: there is no legal XML spelling for these characters. JSON output is deliberately untouched (`json.dump` already escapes them as `\uXXXX`, and nothing is lost), as is CSV/SQLite/Excel; the in-memory tree used by hardening/dedup is unaffected apart from the same characters being gone. Covered by `XmlControlCharacterTests.cs`, which runs the real script and parses the real output (container static, container Browser — the character set through script so Chromium's HTML parser can't interfere —, API tree, a Blocks group block; plus guards that JSON keeps the `\u0007` escape and that tabs/umlauts/emoji are untouched); without the fix the four XML cases fail with exactly the reported exception.
- **Container mode: download embedded resources, runtime** (Issue #213): both grouped templates gain, when `download_enabled`, a `DOWNLOADS_DIR = OUTPUT_PATH + ".downloads"` sidecar-directory constant (same "append a suffix to the full `OUTPUT_PATH` string, extension included" convention `BASELINE_PATH` already establishes) and their own `_download_resource` helper, called from `extract_group()`'s Attribute-mode branch right after `_apply_transforms` runs (so a transform fixing up e.g. a protocol-relative `//host/x.jpg` URL is already in effect by the time it's resolved/downloaded) whenever `node.get("download")` and the value is non-empty. The local filename is a SHA-1 hash of the already-resolved-to-*absolute* URL (never the URL's own basename) with the URL's own extension preserved where present — hashing, not reusing the basename, is what keeps two different pages' own differently-sourced-but-same-named files (e.g. two unrelated `thumb.jpg`s) from silently colliding, and is also what makes downloads idempotent across repeated runs of the same script: a file that already exists on disk is trusted as-is and never re-fetched, so scraping the same page again doesn't grow `DOWNLOADS_DIR` without bound (the issue's own "needs to be deterministic enough that a repeated run doesn't blow up storage indefinitely" open question). A failed download (network error, non-2xx status, ...) is never fatal to the row/run — caught, printed as a `WARNING:` to stderr, and the field is simply left empty, the same "skip it, don't crash" treatment API mode's own `404 = skip this combination` convention already established for a conceptually similar failure. The two engines' own helpers differ in exactly one respect, both named `_download_resource` but with different signatures: the static engine's takes an explicit `base_url` (threaded as a new third parameter through `extract_group(scope, node, base_url)`, sourced from `response.url` — the actual, post-redirect URL — at `scrape()`'s own root call site) and fetches via a plain `requests.get(...)` (reusing `_proxies_for_requests()` when Proxy is enabled, exactly like every other `requests` call in this template already does); the Browser engine's instead takes the already-in-scope `page` parameter (`extract_group()` already threads `page` through every call, unlike the static engine) and resolves both the base URL (`page.url`) and the fetch itself via `page.context.request.get(...)` — Playwright's own `APIRequestContext`, which correctly shares cookies/auth with the browser session that already navigated there, unlike a bare new `requests` import would (this engine doesn't have one at all otherwise). `download_enabled` gates each template's own extra conditional imports (`os`/`sys`/`hashlib`, plus `urljoin`/`urllib.parse` — reusing whichever import style, `from ... import urljoin` vs. `import urllib.parse`, that template's own pagination code already established). Covered by real end-to-end tests for both engines (`DownloadResourceEndToEndTests`, `PlaywrightDownloadResourceEndToEndTests`) running the generated script as an actual subprocess against a real local HTTP server — a black-box "did `/generate` succeed" check can't tell "wrote the URL" apart from "wrote a local path", the same reasoning every other `*EndToEndTests` class in this project is built on.
- **Download safety net, and flat mode's own `_download_resource`** (Issue #214): both grouped templates' `_download_resource` gains two optional parameters, `max_size`/`allowed_types` (`None`/`[]` = no restriction, today's exact Issue #213 behavior) — the static engine's version switches to a streamed `requests.get(..., stream=True)` so an oversized response is aborted mid-transfer (`response.iter_content(chunk_size=65536)`, checked against `max_size` on every chunk) rather than always buffering the whole thing first, and checks `response.headers.get("Content-Type")`/`"Content-Length"` before/during the stream; the Playwright engine's version has no equivalent incremental-read API on `page.context.request.get(...)`, so it can only check `response.headers.get("content-type")` before, and the already-fully-buffered `response.body()`'s own length after — a documented, engine-specific limitation, the same kind `_BLOCKING_RESPONSES`' own per-engine "response" concept already has. **The two flat templates (`scraper.py.j2`, `playwright_scraper.py.j2`) gain their own `DOWNLOADS_DIR`/`_download_resource`** — near-identical to the grouped templates' versions but taking plain arguments (`url, base_url, max_size, allowed_types` for the static engine; `page, url, max_size, allowed_types` for Playwright) instead of a `node` dict, since flat mode has no tree node to read config from. Three new always-present dicts, `DOWNLOAD`/`MAX_DOWNLOAD_SIZE`/`ALLOWED_CONTENT_TYPES` (mirroring `TRANSFORMS`'s own "always present, keyed by field name" convention), gate a call inserted into `_extract_page_rows` right after `_apply_transforms` (`if attr and DOWNLOAD.get(name) and value: value = _download_resource(...)`) — `attr` being truthy is what stands in for flat mode's missing `Mode == Attribute` check. The static engine's `_extract_page_rows` gained a `base_url` parameter (`response.url`, the actual post-redirect URL, from `scrape()`'s own call site) for this; the Playwright engine's didn't need one, since `_download_resource(page, ...)` already resolves `page.url` itself exactly like the grouped template's own Playwright version does. Covered by new end-to-end tests mirroring the container-mode ones (`FlatModeDownloadEndToEndTests`, `PlaywrightFlatModeDownloadEndToEndTests`, plus two new cases each in `DownloadResourceEndToEndTests`/`PlaywrightDownloadResourceEndToEndTests` for the safety net itself).
- `scraper_api.py.j2` (API mode, `PythonApiCodeGenerator`): no BeautifulSoup needed for an ordinary live API call (just `requests` + `itertools.product`, conditionally imported alongside `json`/`bs4` only when `EmbeddedJsonSource` is set — see Issue #136 below), plus a minimal JSON-path DSL (dot notation for object keys, `[*]`/`[n]` for arrays) for per-record field extraction. Discovery sources resolve their values via an extra request; range sources (ISO week/number/date) are parsed/rendered against the `Format` mini-template (`_parse_range_value`/`_render_range_value`, mirroring `RangeFormat` on the companion side). A `404` response for a single parameter combination is skipped instead of aborting the run. Auth headers configured via `EnvironmentVariableName` are, like `FillStep`, never written as a literal — they're read via `os.environ[...]`. Output is `output.csv`, with parameter values as extra columns. `METHOD`/`BODY` (Issue #55) control whether `scrape()` sends a `requests.post(..., json=body)` with a rendered request body (`_render_body`/`_coerce_body_value`) instead of a plain `requests.get(...)` — see the Compiler section above
- `scraper_api_grouped.py.j2` (API mode, nested responses, Issue #54): the tree-shaped counterpart to `scraper_api.py.j2`, picked instead of it whenever `ApiConfig.Groups` is set. Reuses `scraper_api.py.j2`'s existing `_resolve_items()`/`_resolve_field()` JSON-path helpers unchanged — `_resolve_items()`'s "N instances if the resolved value is a list, else at most one" semantics already match `ApiGroup`'s own inferred repeating-ness — and adds a generic `_extract_api_group()` walker, exactly mirroring `scraper_grouped.py.j2`'s `extract_group()` for container mode's CSS-selector tree. Output is `output.xml` instead of `output.csv`; multiple root groups (and results accumulated across every parameter combination) are combined under the same `<Ergebnis>` wrapper container mode already uses. Also gains `METHOD`/`BODY` support (Issue #55), identical to `scraper_api.py.j2`'s own — response shape (flat/tree) and request method/body are fully orthogonal
- **API mode: embedded JSON source** (Issue #136): both API templates gain, when `EMBEDDED_JSON_SOURCE` is set, a conditional `from bs4 import BeautifulSoup`/`import json` and an `_extract_embedded_json(response)` helper (`BeautifulSoup(response.text, "html.parser").select_one(EMBEDDED_JSON_SOURCE["scriptSelector"])` → `json.loads(tag.string)`) used in `scrape()` in place of `response.json()` at the one call site each has — everything downstream (`_resolve_items`/`_resolve_field`/`_extract_api_group`, transforms, hardening, change detection, output writers) is unchanged, since it already operates on "whatever JSON `data` ended up being" regardless of source. A missing `<script>` tag or unparseable content raises a clear `RuntimeError` naming the configured selector, rather than a raw `AttributeError`/`JSONDecodeError` traceback
- **API mode: discover parameter values via browser scroll/click + network capture** (Issue #216): both API templates gain, when `needs_browser_discovery`, a conditional `from playwright.sync_api import sync_playwright` plus a handful of new runtime helpers (hand-duplicated across the two templates, same "no cross-template includes" convention as every other Hardening/Proxy helper): `_resolve_frame_locator`/`_resolve_locator` ported verbatim from the Playwright shell templates; `_run_scroll_action(page, action)`, a *data-driven* port of `playwright_scroll_step.py.j2`'s own fragment — rendered there as literal code for the one, fixed-at-generate-time login action sequence, here reading its own settings off a runtime `action` dict instead, since this action list is only known at generate time as data (`PythonApiConfigLiteral.RenderBrowserActions`), not as a sequence to bake into source; `_run_browser_action(page, action)`, a generic WaitFor/Fill/Click/Scroll dispatcher over one such dict; `_parse_url_parts`/`_match_url_against_template(candidate_url, template, target_name)`, a runtime port of `findUrlTemplateMatches` (`popup/api-config.js`) matching one captured request URL against `URL_TEMPLATE` itself (origin + path-segment-count must match exactly, every literal path segment/query value must match exactly, every *other* `{name}` placeholder is free to differ, `target_name`'s own placeholder is the one value harvested); and `_resolve_browser_discovery(source, headers, target_name)`, which opens a throwaway Playwright session, sets `headers` via `page.set_extra_http_headers` (reusing the main request's own resolved `HEADERS`, the same "discovery reuses the main request's auth" precedent `DiscoverySource`'s own `requests.get` call already established), navigates to `source["discoveryUrl"]`, runs every configured action, and harvests every distinct matching value out of whatever requests fired along the way. Hooked into the existing `_resolve_parameter_values(source, headers, parameter_name)` dispatch as a new `"browserDiscovery"` kind — its signature gained the `parameter_name` argument specifically for this (every other kind ignores it). `EXIT_MISSING_ENV_VAR`/`_require_env` (previously defined only inside the Proxy-only block, for Proxy's own missing-var case) are hoisted out into their own `needs_require_env_helper`-gated block so a `FillAction` inside a discovery source's own action list can use them independently of whether Proxy itself is enabled.
- **Configurable scroll step distance** (Issue #289): `playwright_scroll_step.py.j2` (the login-flow's generate-time-baked fragment) and `_run_scroll_action` in both API templates (Issue #216's runtime dispatcher) both gain a `ScrollStepPx`-conditional branch — null/unset renders byte-for-byte the original `window.scrollTo(0, document.body.scrollHeight)`/`el.scrollTop = el.scrollHeight` jump-to-bottom code; when set, the same scroll call instead becomes `window.scrollBy(0, N)`/`el.scrollTop += N`. The stop condition gains a second signal in that case — `_scroll_at_bottom` (`window.scrollY + window.innerHeight >= document.body.scrollHeight - 1`, or the container-relative equivalent) — combined with the existing "height stopped growing" check via `and`, since a short step can legitimately report the same height for several rounds before genuinely reaching the bottom, which the original "height unchanged" signal alone would've stopped on too early. Kept out of the unconditional code path entirely (rather than always-computed-but-ignored) so a config that never sets `ScrollStepPx` produces exactly the same generated script as before this existed.
- **Click target: first/last/all matches, runtime** (Issue #267): `playwright_click_step.py.j2` renders `<locator>.first.click()` / `.last.click()` for First/Last (so the generated click line changes from `.click()` to `.first.click()` for every existing Click step — behavior only differs where it used to crash), and for All an inline block: `targets.first.wait_for()` (so zero matches still fails with Playwright's usual timeout instead of silently clicking nothing), then `for i in range(targets.count()): targets.nth(i).click(); page.wait_for_timeout(waitAfterMs)` — the match count is snapshotted once, so a click that removes elements from the page can make a later `nth` time out. The data-driven dispatcher `_run_browser_action` in `api_common.py.j2` (browser-discovery action lists) does the same from the `target`/`waitAfterMs` keys. No helper function was added, so scripts without a Click step are byte-identical. Covered by `ClickTargetTests.cs` (real Playwright runs against three identical toggles: first/last/all/no match) and `e2e/examples/issue-267-click-target-check.js` (fixture `test-pages/click-targets`).
- **API mode: dependent/chained parameter discovery** (Issue #217): both `scraper_api.py.j2`/`scraper_api_grouped.py.j2` replace their independent "resolve every parameter, then `itertools.product` the full cartesian product" model with an incremental combo builder, `_resolve_parameter_combos(headers)` — for each parameter in `PARAMETERS`' own declared order, resolves it once per *distinct* combination of whichever earlier-declared values its own `DiscoverySource.UrlTemplate`/`BrowserDiscoverySource.DiscoveryUrl` actually references (`_URL_TEMPLATE_PLACEHOLDER_PATTERN`, relocated out of the `needs_browser_discovery`-gated block to always-defined, since it's now needed regardless of whether any parameter uses browser discovery specifically), via a `cache` keyed on just those referenced values — a parameter with no such reference (every pre-existing config) still maps to one shared (empty) cache key regardless of how many combos exist at that point, so it's still resolved exactly once, byte-identical behavior/performance to before this existed. `_substitute_known_parameters(template, combo)` does the actual `{name}` → already-resolved-and-URL-encoded-value replacement, leaving an unrecognized placeholder untouched; `_resolve_parameter_values`/`_resolve_browser_discovery` both gained a `combo` parameter threading this through to the one call site each has (`requests.get(url_template, ...)` / `page.goto(discovery_url)`). `itertools.product` is no longer used anywhere in either template (the `import itertools` stays, for `_proxy_cycle` elsewhere) — confirmed via two new real end-to-end tests (`ChainedParameterDiscoveryEndToEndTests.cs`, one per template family) asserting on the *specific* per-category rows a chained discovery produces, not just a total count, since a regression back to "resolve once, globally" would either fail the whole run outright (an unsubstituted literal `{category}` segment resolving to zero values in the test fixture) or silently produce the wrong rows — a coincidentally-matching total wouldn't prove the per-combination filtering actually happened.
- **API mode: token/auth bootstrap value** (Issue #220): both `scraper_api.py.j2`/`scraper_api_grouped.py.j2` gain, when `has_bootstrap`, a `BOOTSTRAP` literal, `EXIT_BOOTSTRAP_FAILED = 6`, and `_run_bootstrap()` — called first thing in `scrape()`, once per script execution (a token expiring mid-run isn't refreshed, the issue's own accepted first-version scope). It sends the bootstrap request (`requests.post(..., json=...)` or `data=...` for `Form`, or a plain GET; same default User-Agent and proxy handling as every other request), reading every env-var-backed header/body field via `_require_env` (exit 78 with a clean message when missing), then extracts `ValuePath` via the existing `_resolve_field` JSON-path DSL. A network error, a non-2xx status, a non-JSON response, or no scalar value at the path all exit via `_bootstrap_error` with a clean `ERROR: bootstrap request to <url> failed: ...` line and `EXIT_BOOTSTRAP_FAILED` — deliberately not in `PythonScriptVerifier`'s "compatible with success" allowlist, since nothing downstream can work without the token. The value lands in module-level `_BOOTSTRAP_VALUES` and is merged *alongside* (never into) each parameter combo: into `URL_TEMPLATE.format(...)`, `_render_body(...)`, and the `combo` passed to `_resolve_parameter_values` (so a discovery template can reference it); `_build_headers(bootstrap_values)` substitutes a `"template"` header via the existing `_URL_TEMPLATE_PLACEHOLDER_PATTERN`. Since `combo` itself never carries it, it can't become an output column; `_redact_bootstrap()` masks it (raw and URL-encoded) in the "Skipped (404 Not Found)" line and in Blocking-hardening's captured URLs, the only places a URL is ever printed. With no bootstrap configured, every touched line is gated so the rendered script stays byte-for-byte what it was (signatures included). Covered by real end-to-end tests (`ApiBootstrapEndToEndTests.cs`) against a LocalTestServer whose data endpoints 401 without the exact issued token: JSON and form-encoded credentials, header-template and URL-placeholder usage, the tree template with a token-protected discovery request and redacted 404 line, and the exit-6/exit-78 failure paths.
- **API mode: cursor/token-based pagination** (Issue #224): both `scraper_api.py.j2`/`scraper_api_grouped.py.j2` move their per-request code (the delay/retry/POST-vs-GET block, 404 skip, `_require_ok`, blocking snapshot, JSON parse) out of `scrape()` into `_fetch_page_data(url, body, headers)` (returns the parsed JSON, or `None` for a 404), and `scrape()` now iterates `_fetch_pages(url, body, headers)` per parameter combination — a one-shot generator when cursor pagination is off (functionally identical to before), a page loop when on. With `CURSOR_PAGINATION` set the loop applies the previous page's cursor (`_apply_cursor`: `_with_query_param` replaces/appends one query parameter leaving every other byte of the URL untouched; `_set_body_path` sets a dot path in a deep copy of the rendered body), and `_next_cursor` resolves `nextCursorPath` via `_resolve_field` (missing/null/empty/object/array = last page; a falsy `hasNextPagePath` value — `false`/`0`/`"false"` — ends the chain even though a cursor is present). The chain also stops on a repeated cursor (printed as a warning — an API handing back the same cursor forever would otherwise loop endlessly) and at `maxPages` (printed). A 404 on page 1 keeps the existing "combination doesn't exist" skip; on a later page it just ends that chain. Every parameter combination runs its own independent chain; retry/delay/proxy/bootstrap/hardening apply per page, since they live in `_fetch_page_data`. Covered by real end-to-end tests (`ApiCursorPaginationEndToEndTests.cs`: query + body targets, per-combination chains, `MaxPages`, repeated cursor, `hasNextPage`, tree shape, late 404).

Two clearly distinct failure modes, per the issue's own robustness requirement: a **missing** file is not an error at all — `_load_external_config()` calls `_write_default_external_config()` (built from whatever's already baked into the script: `URLS`, the output filename, and — flat mode only — every configured field's original name) and proceeds using the script's own existing defaults for that run, mirroring the self-bootstrapping precedent the baseline hardening check's own sidecar (`BASELINE_PATH`, Issue #131) already established, deliberately under a **separate** file/naming convention (next to the *script*, not the *output*) per the issue's own fourth open question. A file that **exists but is broken** — invalid XML, a `<Field>`/`<Parameter>` missing its required attribute, an empty required value, or a reference to a field/parameter name that no longer exists (e.g. the scraper was regenerated with different fields since the file was last edited) — is a hard failure via `_external_config_error()`: one clean `ERROR: The external config file '<path>' ...` line naming exactly what's wrong, then `sys.exit(EXIT_EXTERNAL_CONFIG_INVALID)` (`3` — `2` and `78` were already taken by Hardening/Proxy) instead of a raw `xml.etree.ElementTree.ParseError`/`KeyError` traceback. This exit code is deliberately **not** added to `PythonScriptVerifier`'s "compatible with success" allowlist (unlike `EXIT_HARDENING_FAILED`/`EXIT_MISSING_ENV_VAR`) — it doesn't need to be: `/generate`'s trial run always starts from an empty temp directory, so it can only ever take the missing-file/self-bootstrap path, never the broken-file path, regardless of whether this feature is enabled. **Which values are actually read back depends on mode/shape** (see the Compiler section above for the scope reasoning): every template applies `<OutputFileName>`/`<Urls>` (Fields/Groups shapes only) the same way — a present, non-blank element fully replaces `OUTPUT_PATH`/`URLS`, an absent one leaves the baked default untouched (partial override, never a wholesale replacement); the two flat templates (`scraper.py.j2`/`playwright_scraper.py.j2`) additionally parse `<Fields><Field original="...">newName</Field></Fields>` into a `FIELD_OUTPUT_NAMES` dict (`{}` when the feature is off or nothing was renamed — a guaranteed no-op) applied only at the very end, to a *separate* `output_rows` copy built right before the file is written (`{FIELD_OUTPUT_NAMES.get(k, k): v for k, v in row.items()}` for every row) — `data` itself stays keyed by the original field names throughout, since hardening's `nullRate`/`requiredFields` checks and change detection's own field-name-agnostic whole-file diff both still need to see (or in the diff's case, simply don't care about) the real names, not a possibly-renamed view of them; the two API templates (`scraper_api.py.j2`/`scraper_api_grouped.py.j2`) instead parse `<ApiParameters><Parameter name="...">​<Value>...</Value>​...</Parameter></ApiParameters>` and mutate the matching `PARAMETERS` entry's `source["values"]` list in place — `_resolve_parameter_values`'s existing `kind == "staticList"` branch already just reads `source["values"]`, so no other runtime code needs to change at all. Every template's final "Done — N rows/elements written to X" message was switched from a baked-in filename literal to reading the (possibly now-overridden) `OUTPUT_PATH` variable at print time, so it stays accurate regardless of whether this feature ends up changing it.
- **Combined mode** (Issue #239): a new, seventh template, `scraper_combined.py.j2` — the only one of the seven not generated by an `ICodeGenerator` implementation (see the Compiler section above for why `PythonCombinedScriptGenerator` renders it directly instead). Its own `COMPONENTS` constant is a list of `{"name": ..., "source_b64": ...}` dicts — each component's *entire*, already-independently-generated script (whichever of the other six templates actually produced it, Static/Browser/API alike) embedded as a base64 string rather than a raw triple-quoted one, so nothing about a component's own generated content (a user-entered block phrase, a regex pattern, a static list value) needs re-escaping to safely nest one already-generated Python file inside another. At runtime, `_run_component(component)` decodes and writes that source to `component.py` inside a **stable** subdirectory next to the combined script's own file — `os.path.join(os.path.dirname(os.path.abspath(__file__)), f"{OUTPUT_FILE_BASE_NAME}_components", component["name"])`, created once via `os.makedirs(..., exist_ok=True)` and reused on every subsequent run — deliberately **not** `tempfile.TemporaryDirectory()`, which was the first design considered: a component enabling `PersistentSession`'s saved login cookies, `ExternalConfig`'s user-editable XML, or the `BaselineCheck` hardening counter all write their own sidecar file relative to their own script's file path (see each feature's own entry above), so those sidecars only actually persist across separate runs of the *combined* script if the component's own `component.py` lives at a stable path run to run — a fresh temp directory every time would silently reset all three to "nothing here yet" on every single execution, without the combined script or its own saved-configuration components ever indicating anything was wrong. `subprocess.run([sys.executable, "component.py"], cwd=component_dir, ...)` passes no explicit `env=`, so the child inherits the combined script's own full process environment — the mechanism (documented in the Companion App section above) that lets both a component's own `Proxy` env-var list and the merged one-time `VerificationValues` `PythonScriptVerifier` injects into the *outer* trial-run subprocess reach every inner per-component subprocess automatically, with no per-component environment plumbing anywhere in this template. A component's own exit code `0`/`78`/`2` (`COMPATIBLE_EXIT_CODES`, mirroring `PythonScriptVerifier.MissingEnvVarExitCode`/`HardeningFailedExitCode` — the same "two independent copies of one constant" duplication this codebase already accepts between C# and every Python template's own `EXIT_MISSING_ENV_VAR`/`EXIT_HARDENING_FAILED`) is treated as "this component produced usable output" (printing a `WARNING:` to stderr for the latter two); any other exit code, a missing `output.json`, or — critically — an *empty* result (`if not data: raise RuntimeError(...)`, since a component whose selector quietly starts matching nothing would otherwise merge in silently as an empty array/object under its own name, exactly the class of failure this whole mechanism exists to catch) aborts the entire combined run, naming which component failed. `main()` merges every component's own already-parsed JSON into one object keyed by component name (`{"componentName": [...], ...}`) and writes it to `OUTPUT_PATH` — a JSON *object* root regardless of whether any individual component's own shape was flat or tree, which `PythonScriptVerifier.VerifyJsonOutput`'s existing tree-shape handling (originally written for container/API-tree mode) already recognizes generically, needing no companion-side changes at all.
- **Blocks mode** (Issue #182): two new templates, `scraper_blocks.py.j2` (Static engine) and `playwright_scraper_blocks.py.j2` (Browser engine) — unlike Combined mode's `scraper_combined.py.j2` above, these render **in-process**, sharing one navigation/browser session across every block rather than subprocessing N separate scripts (see the Compiler section's own "why embed-and-subprocess" bullet for Combined mode — the reasoning is inverted here: Blocks mode's whole premise is one shared page load/session, N extraction+write phases against it, so subprocess isolation would be actively wrong — re-navigating/re-running browser actions per block, risking a non-idempotent action like a login-form submission running more than once). Both templates restructure `main()`'s existing "one shape, one write call" shape into a loop over `BLOCKS`: `scrape(url)` (static) / `scrape(url)`'s inner Playwright `while True` page loop (browser) calls a generalized `_extract_flat_block(block, soup_or_page)` or the tree-walking `extract_group(scope, node, required_field_names, block_name)` per block on every fetched page (mixing shapes freely — a page's own single fetch feeds both a flat block and a group block alike), accumulating results per block name; pagination stops only once *every* block's own extraction yielded nothing new on a page, not per-block. `main()` then writes each block's own output file (CSV/XML/JSON per its own resolved format) and runs its own hardening checks — `_run_hardening_checks(block, result_count, field_values)` unifies what the single-shape templates keep as two separately-duplicated dispatchers (flat vs. tree) into one, via a `field_values(field_name)` callback the caller supplies differently per shape (`row.get(field)` across `data` for flat, `el.iter(field)` across the built `ET.Element` tree for group) — the `noResult`/`baseline`/`blocking` branches need no per-shape duplication at all this way, only `nullRate` actually calls the callback. `_BLOCKING_RESPONSES` (Issue #132's raw-response snapshot) stays a single, page-fetch-scoped list shared across every block's own hardening checks, exactly like it's already scoped to the whole run (not per-field) in the single-shape templates — only *which* blocks have a `"blocking"` check varies, not the captured data itself. `_REQUIRED_FIELDS_DROPPED` (Issue #133) is keyed by block name instead of being one module-level counter, the natural generalization of the single-shape grouped templates' own `_required_fields_dropped_count` to "one counter per block". `BASELINE_PATH`-equivalent sidecars and `SESSION_STATE_PATH` (Issue #175, still shared/outer-level — one browser session for the whole run) are derived the same way as the single-shape templates', just per-block for the former (`block["output_path"] + ".hardening-baseline.json"`) since each block's own baseline is independent. `ExternalConfig` (Issue #178) is deliberately not supported for Blocks mode at all yet (rejected in `Program.cs`, see the Companion App section above) — neither template has any of that feature's sidecar-config machinery.
- **Output Blueprints** (Issue #191): the three flat-shape templates only (`scraper.py.j2`, `playwright_scraper.py.j2`, `scraper_api.py.j2` — container/API-tree output has no flat "row" for a target/source column mapping to apply to) gain a `BLUEPRINT_MAPPING` constant. When non-empty, it takes over building `output_rows`/the CSV fieldnames at write time — renaming, reordering to the blueprint's own order, and dropping any source field not referenced by the mapping — taking precedence over `FIELD_OUTPUT_NAMES` (Issue #178's own field-renaming mechanism) for the same write-time step, since both features rename output columns at the exact same point and a blueprint's mapping is the more specific, explicitly-chosen intent. `data` itself is left completely untouched (only a derived `output_rows` copy is affected) — hardening's `nullRate`/`requiredFields` checks and change detection's own diff keep operating on the original field names regardless of whether a blueprint mapping is active.
- **Output Blueprints: container/API-tree mode flattening** (Issue #192): the three tree-shape templates (`scraper_grouped.py.j2`, `playwright_scraper_grouped.py.j2`, `scraper_api_grouped.py.j2`) gain the same `BLUEPRINT_MAPPING` constant plus a new runtime walker, `_flatten_group_tree_for_blueprint`/`_flatten_api_group_for_blueprint`, that denormalizes the already-built tree into rows instead of `extract_group()`'s/`_extract_api_group()`'s own nested `ET.Element` tree — always returns a list of context dicts, growing only at a *relevant* repeating group's own instance boundary (`_blueprint_subtree_has_mapped_field` short-circuits an irrelevant branch — a repeating group with no mapped field anywhere inside it — so it never needlessly fans out the row count); a higher-level mapped field simply threads through unchanged until a deeper repeating boundary is reached, which is what broadcasts it into every row generated there. `scrape()`/`scrape(url)` now return `(root, blueprint_rows)` instead of just `root`; `main()` writes either the flattened csv/json (mapping active) or the original nested xml/json (not), while hardening/change-detection keep operating on the original, unflattened `root` regardless — neither needs to know a blueprint mapping exists. The Api-tree template's own walker additionally has to resolve "is this node repeating" dynamically (mirroring `_extract_api_group`'s own `_is_repeating_instance` check) and re-derive the "do the mapped fields share one ancestor chain" ambiguity check incrementally as that repeating-ness is discovered — tracked via a module-level `_blueprint_resolved_chain` across the whole run (including separate parameter combinations) — raising a `RuntimeError` on conflict instead of the `400` `OutputBlueprintFlattening` produces for Container-Mode at generate time (see the Compiler section above for why that check can't happen statically there). Deliberately placed unconditionally, right after `GROUPS`/`OUTPUT_PATH` — **not** nested inside the templates' existing `{{ if hardening.enabled }}` block that `REQUIRED_FIELD_NAMES`/`HARDENING` themselves already live in, a real bug caught during development (an early draft put it there by mistake, silently vanishing from any script generated without hardening configured).
- **Output Blueprints: nested/"containered" target schema** (Issue #244): the same three tree-shape templates gain a second constant, `BLUEPRINT_TREE_MAPPING` (empty when the active mapping, if any, is Flat-schema — exactly one of it and `BLUEPRINT_MAPPING` is ever non-empty for a given plan), and a runtime tree-to-tree walker building a real nested output instead of flat rows. A one-time, purely structural index of the source `GROUPS` tree (`_blueprint_index_source_tree`/`_BLUEPRINT_GROUP_BY_NAME`/`_BLUEPRINT_LEAF_BY_NAME`/`_BLUEPRINT_PATH_BY_NAME` — first occurrence wins for a duplicate name, the same "global by name" simplification `NullRateCheck`/`RequiredFieldsCheck`/the flat mapping already established for this tree shape) is built once at import time, independent of any scraped data, giving every named source node its own ordered ancestor-group path. `_build_blueprint_node`/`_build_blueprint_tree` (container templates) walk the *target* tree instead of the source tree: for a target group, `_blueprint_resolve_group_chain` resolves its own row scope from its direct leaves' chains — **trusting**, not re-validating, the generate-time guarantee `ScrapingPlanValidator`'s `ResolveContainerTreeRowScopes` already established (the same asymmetry the Flat mapping's own container-vs-Api-tree walkers already have) — and `_blueprint_walk_suffix` then walks exactly the remaining source-tree path from wherever the recursion already is, fanning out at each repeating step; a leaf with no repeating source ancestor *anywhere* (a "broadcast" field, mirroring the flat mapping's own broadcast fields) is instead resolved once relative to the whole page (`top_scope`), not wherever the current target-group instance happens to be — exactly reproducing the flat walker's own "visited once at its natural shallow position, then threaded into every deeper row" behavior, just via an explicit re-walk from the root instead of falling out of a single shared recursive descent. `scraper_api_grouped.py.j2`'s own version additionally has to resolve "is this ancestor group repeating" dynamically per call (`_blueprint_resolve_leaf_chain`, mirroring `_extract_api_group`'s own `_is_repeating_instance` check) rather than reading a static flag, and **does** validate the per-target-group chain itself (`_blueprint_resolve_group_chain` raises `RuntimeError` on conflict, surfacing as a `422`) since there's no static guarantee available for this shape at all — the same static-vs-runtime split the Flat mapping's own two template families already have, just scoped to one target group's own direct fields at a time now instead of the whole mapping (mirroring `OutputBlueprintFlattening.ResolveContainerTreeRowScopes`'s own per-group scoping on the Compiler side). All three templates' `scrape()`/`scrape(url)` now thread a third `blueprint_tree_elements` value through their existing `(root, blueprint_rows)` return tuple; `main()` writes it (wrapped in the same `<Ergebnis>` convention multi-root/multi-URL output already uses) instead of the original tree only when `BLUEPRINT_TREE_MAPPING` is non-empty — `root` itself, used for hardening/change-detection, is completely unaffected either way, still the full, unmapped source tree.
